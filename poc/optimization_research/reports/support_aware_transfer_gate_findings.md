# 공분산 전이의 지원 범위 게이트: 실패를 포함한 탐색 결과

## 질문과 판정

과거 모델의 오차 공분산은 같은 작업 조건을 공유하는 8개 encoder 모델에서 성능 예측을 개선했지만, 새로운 입력 조건의 처리량 예측에는 역효과가 있었다. 모델당 GPU 1개·CPU 2코어 기준 측정 8개만 허용한 상태에서, **정렬된 과거 작업의 지원 범위와 측정한 앵커만 이용해** 공분산·부드러운 커널·직접 Ridge 보정 중 하나를 선택하면 역효과를 피할 수 있는지 검사했다.

결론은 제한적이다. 과거 모델 2개 이상에서 **동일한 작업 좌표**가 있는 경우에만 공분산을 쓰고 그 외에는 직접 Ridge로 돌아가는 단순 규칙은 새 조건과 원격 모델의 요청/초 오차를 낮췄다. 그러나 일부 지연 오차를 높였고, 같은 호스트의 Qwen에서도 주 캠페인 성능을 떨어뜨렸다. 측정한 8개 앵커만으로 방법을 내부 선택하는 규칙은 외부의 처리량 역전이를 막지 못했다. **두 규칙 모두 공동 성능 개선이나 학술적 노벨티를 입증하지 못했다.** 학습 분포의 지원 범위 밖에서 전이가 어려워진다는 문제는 [covariate shift 연구](https://jmlr.csail.mit.edu/papers/v8/sugiyama07a.html)와 [support mismatch 연구](https://proceedings.mlr.press/v202/segovia-martin23a.html)에서도 다룬다. 이 정확한 좌표 게이트를 신규 원리로 주장할 수 없다.

## 정보 경계와 동일 예산

- 모델 단위 바깥 분할의 donor는 나머지 주 캠페인 모델뿐이다. donor 앵커 잔차는 다시 donor 모델 하나씩 제외한 안쪽 모델 단위 교차 검증으로 생성했다.
- `workload_task`, batch, 최대 길이, 동시성, repeats가 모두 같은 donor 모델이 **2개 이상** 있을 때만 경험적 공분산을 허용했다. 키와 donor 수는 정적 입력·학습 자료로만 결정한다. 원격 GPU/호스트를 보고 별도의 임계값을 조정하지 않았다.
- `support_only`: 정확히 지원되는 작업에는 경험적 공분산, 나머지에는 직접 Ridge를 적용했다. `support_loo`: 측정한 8개 앵커 각각을 하나씩 가리고 잔차 MAE가 가장 낮은 공분산·커널·Ridge를 지연과 요청/초에 각각 선택했다. 정확한 donor 지원이 없으면 공분산은 선택할 수 없다. 동률은 Ridge, 커널, 공분산 순서로 해결했다.
- 모든 방법은 같은 K8 공간 선택 프로브를 사용하고 같은 비앵커 7개 자원 후보를 각 작업에서 점수화했다. 주 캠페인·새 조건은 모델당 평균 **6.96 GPU-wall초**, 원격은 **11.34초**다. 새 조건에는 별도 측정을 추가하지 않았다. 원격의 `always_cov`는 정렬 donor가 없어 커널 fallback과 완전히 같은 예측이다.
- 선택 단계에는 새 조건의 성능 결과, 원격에서 선택되지 않은 작업, 주 캠페인의 선택되지 않은 앵커, 다른 자원 후보의 측정값이 들어가지 않는다. SLO는 수집기가 만든 값이라 아래 성공 수는 실제 서비스 보장으로 해석하지 않는다.

## 고정 평가 결과

숫자는 모델별 절대 로그오차(MALE)의 평균이다. 괄호의 성공은 생성 SLO에서 실제 가능한 작업에 대해 올바른 자원을 선택한 작업 수다.

| 평가 집합 | 방법 | 지연 MALE | 요청/초 MALE | SLO 성공 | 위반 |
| --- | --- | ---: | ---: | ---: | ---: |
| 주 캠페인 9개 모델, 575작업 | 항상 공분산 또는 fallback | **0.238** | **0.127** | 338/357 | 18 |
|  | 항상 커널 | 0.249 | 0.141 | 330/357 | 22 |
|  | 직접 Ridge | 0.262 | 0.145 | 328/357 | 19 |
|  | 지원 범위만 사용 | 0.242 | 0.130 | 338/357 | 18 |
|  | 지원 범위 + 앵커 LOO | 0.239 | 0.129 | 335/357 | 21 |
| Novel matrix, 9개 모델·18작업 | 항상 공분산 또는 fallback | 0.320 | 0.361 | 12/13 | 1 |
|  | 항상 커널 | 0.344 | 0.344 | 12/13 | 1 |
|  | 직접 Ridge / 지원 범위만 사용 | **0.312** | **0.333** | 12/13 | 1 |

|  | 항상 커널 | **0.329** | 0.306 | 29/33 | 2 |

주 캠페인에서는 encoder 8개×64작업, 즉 **512작업**만 동일 좌표의 donor 2개 이상을 가진다. 해당 작업의 `support_only` 예측은 공분산과 완전히 같다. Qwen 63작업은 지원 범위 밖이며 Ridge fallback 때문에 전체 오차가 오히려 높아졌다. 새 조건 62작업과 원격 24작업은 정확한 donor 지원이 하나도 없어 `support_only`가 전부 직접 Ridge가 된다.

앵커 LOO 규칙은 직관과 달리 원격 두 모델의 요청/초에서 모두 커널을 선택했다. 앵커 8개의 오차를 잘 예측하는 방법이 **나머지 GPU·CPU 형상의 반응**까지 잘 예측한다는 보장은 없고, 새 입력 조건에서는 앵커 자체를 추가로 관측하지 않았기 때문이다. 따라서 현재 SQLite의 앵커만으로 신뢰성 있는 방법 선택을 학습했다고 주장할 수 없다.

## 연구 판단과 재현

이 분석은 이미 관찰한 외부 악화 현상을 계기로 고안한 **사후 탐색**이다. 외부 라벨로 게이트 임계값을 고르거나 평가를 반복하며 규칙을 조정하지 않았지만, 독립적인 사전 확정 검증으로 볼 수 없다. 정렬 여부에 따른 fallback 자체도 기존 원리여서 신규 연구 방법 후보로 채택하지 않는다. 다음 가설은 공분산 전이의 신뢰도를 앵커 잔차만이 아니라 **자원 형상 반응의 별도 관측**으로 검사해야 한다는 것이며, 그 관측에는 추가 측정 비용이 든다. 비용을 같게 맞춘 새 비교 없이는 이 가설의 이점을 주장할 수 없다.

- 코드: `scripts/support_aware_transfer_gate.py`
- 정보 경계·baseline 일치 테스트: `tests/test_support_aware_transfer_gate.py`
- 고정 입력·코드 해시, 모델별 결과, 작업별 게이트 결정: `artifacts/support_aware_transfer_gate_v1/`

5개 전용 테스트가 통과했고, 결과 JSON의 스크립트 및 참조 입력 파일 SHA-256이 현재 파일과 일치한다.
