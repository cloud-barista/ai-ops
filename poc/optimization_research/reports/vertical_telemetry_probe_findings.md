# GPU 1개 실행 계측으로 CPU affinity 반응 예측: 기각한 가설

## 질문과 분할

현재 AI 응용을 GPU 1개·CPU affinity 2코어에서 실행한 뒤, 그 실행의 GPU·CPU 계측이 같은 작업의 affinity 4/8/16코어 성능을 더 정확하게 예측하는지 검사했다. 후보 방법은 기존 정적 입력과 GPU1/core2 실측 지연·처리량에 `gpu_utilization_percent_mean/max`, `gpu_memory_used_mib_max`, `cpu_percent_mean` 네 계측을 더하는 것이다. 같은 100-tree ExtraTrees 회귀기를 두 방법에 사용했다. **두 방법 모두 같은 GPU1/core2 실행 한 번을 관측**한다. 계측값을 따로 수집하는 시간은 SQLite에서 식별할 수 없으며, GPU 측정 예산은 같다고 볼 수 있다.

학습에는 `khu-hf-local-exhaustive`의 GPU1/core4/8/16 결과만 썼다. 평가 모델 ID를 통째로 제외한 9개 분할과, BERT 4종 및 BERT 4종+DistilBERT를 함께 제외한 2개 분할을 수행했다. 타깃 core4/8/16의 실측 성능·계측은 예측 전에 가렸다. 같은 호스트의 주 캠페인 및 새로운 입력 조건인 novel-matrix·space-filling 캠페인을 평가했다. *코어 수는 VM CPU 할당량이 아니라 프로세스 CPU affinity 한도*이며, 타깃은 GPU1 실행이다. GPU2 또는 실제 VM의 수직 변경 효과를 말하지 않는다.

기록된 실행 순서에서는 각 작업의 GPU1/core2 기준 실행이 모든 core4/8/16 대상 실행보다 먼저 끝났다. 주 캠페인 1,725건, novel 54건, space 132건에서 확인했다. 이는 기준 계측의 시간적 가용성만 확인하며, 순서에 따른 호스트 상태 변화를 통제했다는 뜻은 아니다.

## 결과

오차는 타깃 모델별 평균 절대 로그오차(MALE)를 다시 평균했다. 낮을수록 좋다. 9개 모델별 제외 평균은 다음과 같다.

| 조건 | 기준선 지연 / 요청·초 | 계측 추가 지연 / 요청·초 |
| --- | ---: | ---: |
| 주 캠페인, 575작업 × 3형상 | 0.21745 / **0.08513** | **0.21718** / 0.08521 |
| Novel, 18작업 × 3형상 | **0.27982 / 0.12270** | 0.28927 / 0.12845 |
| Space, 44작업 × 3형상 | **0.19999** / 0.07873 | 0.20321 / **0.07856** |

주 캠페인의 지연 차이는 로그오차 **0.00027**에 불과하다. 두 새 입력 조건에서 지연은 모두 악화하고, Novel의 처리량도 악화했다. 모델별 오차 방향은 섞인다. 이 실험은 계측 추가가 일반적으로 CPU affinity 반응을 더 잘 예측한다는 근거가 되지 않는다.

공동 제외에서는 다른 양상이 있다. BERT 4종의 주 지연은 `0.2990→0.2894`, Novel `0.3561→0.3361`, Space `0.2866→0.2799`로 개선되지만 Novel 처리량은 `0.0934→0.0993`으로 악화한다. DistilBERT까지 함께 제외하면 주 지연 `0.3458→0.2739`, Novel `0.4078→0.3071`, Space `0.3441→0.2474`로 크게 개선된다. 이 분할에서 donor가 4종만 남아 정적 기준선이 특히 어려운 소형 BERT 모델에서 무너진다. 계측이 외삽을 도울 가능성은 남지만, 일부 새 조건의 처리량과 최종 형상 판단이 같이 개선되지는 않았다. 분할·특징을 여러 번 탐색한 뒤의 결과이므로 확증적 통계로 취급하지 않는다.

## CPU affinity 선택에 도움이 되는가

실제 사용자 SLO가 없어, 각 외부 분할의 **학습 donor** GPU1/core4/8/16 결과에서 지연·처리량 분위수 5개씩을 만들어 작업마다 25개의 서로 상관된 가상 목표를 평가했다. 현재 core2가 목표를 못 맞출 때만, 예측상 두 목표를 만족하는 가장 작은 core4/8/16을 선택했다. 여기서 *성공*은 선택한 형상이 실측 두 목표를 모두 충족한 횟수이고, *오승인*은 선택했지만 충족하지 못한 횟수다.

| 분할·조건 | 실제 구제 가능한 질의 | 기준선 성공 / 오승인 | 계측 추가 성공 / 오승인 |
| --- | ---: | ---: | ---: |
| 모델별 제외·주 | 110 | **8 / 15** | 5 / **11** |
| 모델별 제외·Novel | 24 | 0 / 0 | 0 / 0 |
| 모델별 제외·Space | 2 | 0 / 0 | 0 / 0 |
| BERT 4종 공동 제외·주 | 32 | 0 / 11 | 0 / **6** |
| BERT+DistilBERT 공동 제외·주 | 35 | 1 / 12 | 1 / **6** |

계측 모델의 오승인이 적은 경우는 **승인을 더 적게 한 결과**다. 모델별 제외 주 캠페인에서 승인 자체가 23→16으로 줄었고 성공도 8→5로 감소했다. BERT+DistilBERT에서는 승인 13→7, 성공 1→1이다. 유용한 형상 선택이 늘었다고 말할 수 없다. Novel·Space는 두 방법 모두 성공 선택이 없다. 추가 코어가 늘 좋은 것도 아니다. 주 캠페인의 GPU1 측정에서 core2 대비 4/8/16의 지연 로그비 중앙값은 각각 `+0.234/+0.349/+0.382`로 오히려 악화하고, 처리량 로그비는 `−0.032/−0.021/−0.007`이다. 실행 순서와 호스트 상태의 교란이 있으므로 이를 코어 증가의 인과 효과로 단정하지 않는다.

## 신규성 경계와 결론

온라인 계측을 자원 형상 변경의 입력으로 쓰는 원리 자체에는 선행 연구가 있다. [FIRM](https://www.usenix.org/system/files/osdi20-qiu.pdf)은 실행 중 계측과 학습 모델로 세밀한 자원 조정을 수행한다. [IBM의 ML 서비스 수직 오토스케일링 연구](https://research.ibm.com/publications/proactive-container-auto-scaling-for-cloud-native-machine-learning-services)는 자원 사용 단계 예측으로 CPU 할당을 조정한다. [ARISE](https://research.ibm.com/publications/arise-ai-right-sizing-engine-for-ai-workload-configurations)는 AI 작업 이력과 성능 예측으로 자원 구성을 추천한다. 따라서 이 실험의 특징 추가를 경희대 고유 알고리즘으로 주장할 수 없다.

**이 가설은 현재 방법 후보에서 제외한다.** 특히 실제 VM CPU 변경, 사용자 요청 지연, 운영 중 scale action에 대한 효과를 보여주지 않는다. BERT 계열 공동 제외의 지연 개선은 후속 연구 질문으로 기록하되, 처리량과 독립된 새 모델·호스트, 실제 사용자 SLO 판단에서도 함께 재현되어야 한다. 현재 SQLite만 사용 가능한 상황에서는 이 조건을 충족하지 못한다.
