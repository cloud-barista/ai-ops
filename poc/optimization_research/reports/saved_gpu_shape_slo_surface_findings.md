# 저장된 GPU 형상 모델의 연속 SLO 민감도면: 후향 진단

2026-09-29. [점수 전 규약](saved_gpu_shape_slo_surface_protocol.md)에 따라, 저장된 같은 호스트 GPU 형상 예측에 수집기 생성 SLO의 지연 상한·요청/초 하한을 각각 0.75–1.25배로 바꿨다. **로그 배수 평면의 정확한 면적**에서 저장 Extra Trees의 주 시험 잘못 승인 비율은 전체 면적의 **1.835%**, 저장 모델·장치 훈련 중앙값 기준은 **7.252%**였다. 이는 합성 목표의 면적 비율이며 실제 사용자 요청의 실패확률이나 새 모델의 독립 시험 성적이 아니다. 저장 정책이나 승인 문턱을 바꾸지 않았다.

## 원본·결정 규칙

[기존 저장 모델 선택 감사](saved_gpu_shape_decision_audit_findings.md)의 측정 Parquet, 저장 예측 Parquet, 분할 manifest, 저장 모델 파일의 네 SHA-256을 다시 확인했다. 모델 파일은 로드하지 않고 해시만 검사했다. `(host, execution_id)` 일대일 결합과 기존 `test` 90작업군, 별도 `novel-matrix` 10군, `space-filling` 33군의 **GPU 1/2개 × CPU affinity 2/4/8/16코어** 완전한 여덟 후보를 [코드](../scripts/audit_saved_gpu_shape_slo_surface.py)가 검증한다. GPU 2개는 한 호스트의 복제 프로세스 두 개이며 VM 두 개가 아니다. 지연은 배치 p95이고, 실측·예측 처리량은 `examples_per_second / batch_size`로 요청/초 단위를 맞췄다.

각 후보의 실측·예측 지연과 요청/초가 목표를 통과하는 모든 경계를 두 축에 넣었다. 이 경계 사이에서는 어느 후보의 통과 여부도 변하지 않으므로, 직사각형 중심에서 선택 결과를 계산하고 `Δlog(지연 배수)×Δlog(요청/초 배수)`로 정확히 가중했다. 한 작업의 여러 목표 구간을 독립 표본으로 세지 않았고 캠페인 안에서는 **고유 작업군을 동일 가중**으로 평균했다. 선택은 GPU 복제본 수를 먼저, 이어 CPU affinity 코어 수를 최소화한다. 실제 가격이나 VM 비용은 없다.

비교 방법은 저장 Extra Trees 전체 8후보, 저장된 `model_id × device` 훈련 중앙값 전체 8후보, 그리고 중앙값 예측에서 **(GPU 1개, CPU affinity 2코어) 한 후보만 통과하면 승인**하는 고정 후보 정책이다. 실측 oracle는 실제 가능 영역과 최소 형상의 정답을 정하는 데만 썼다. 저장 중앙값 예측은 이 133작업군 각각에서 여덟 후보 사이에 지연·처리량 값이 동일했다. 그래서 전체 중앙값 정책은 고정 후보 정책과 **모든 작업군·목표 면적에서 결과가 정확히 같았다**. 두 행은 독립적인 성능 비교군이 아니다.

## 주 시험 90작업의 면적

전체 목표 면적의 실측 가능 영역은 **61.266%**, 그중 일부 후보 1–7개만 가능한 영역은 전체의 **25.747%**였다. 모든 8후보가 불가능한 영역은 38.734%, 전부 가능한 영역은 35.519%다. 원래 한 점의 부분가능 고유 작업군은 23/90으로 사전 지원량 기준 20개를 넘었다. 다음 값의 단위는 **90작업을 동일 가중한 전체 로그 목표 면적 대비 백분율**이다.

| 방법 | 승인 | 실제 성공 | 잘못 승인 | 실제 가능하지만 보류 | 정확한 최소 형상 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 저장 Extra Trees | 59.915% | 58.080% | **1.835%** | 2.597% | 55.504% |
| 훈련 중앙값 전체 8후보 | 46.761% | 39.509% | 7.252% | 14.505% | 39.509% |
| 훈련 중앙값 고정 GPU1·CPU2 | 46.761% | 39.509% | 7.252% | 14.505% | 39.509% |

실제 일부 후보만 가능한 **25.747% 영역**을 따로 보면 저장 모델의 성공/잘못 승인/보류 면적은 전체 기준 **22.561/0.589/2.597%p**였고, 중앙값은 **6.045/7.252/12.450%p**였다. 이 세 값은 각각 25.747%p로 합쳐진다. 저장 모델의 전체 잘못 승인 1.835%p 중 0.589%p는 다른 실측 가능 후보가 있었는데 잘못된 후보를 고른 경우이며, 나머지 1.246%p는 여덟 후보가 모두 실측 불가능한 목표에서 선택한 경우다. `실제 가능하지만 보류`와 `실제 가능하지만 잘못 승인`은 분리해서 저장했다.

## 별도 입력 캠페인과 해석

`novel-matrix` 10작업군의 원 목표 부분가능 작업은 **2개**뿐이라 사전 지원량 기준 10개에 못 미쳤다. 모델 간 우열을 논하지 않고 행별 면적 (`../artifacts/saved_gpu_shape_slo_surface_v1/per_workload_surface.csv`)에 참고로 남겼다. `space-filling` 33작업군은 부분가능 11개로 그 기준을 넘었다. 여기서 저장 모델의 전체 면적 성공/잘못 승인/가능하지만 보류는 **73.867/3.491/2.412%**, 훈련 중앙값은 **50.399/6.524/19.663%**다. 그러나 이 캠페인도 이미 이전 연구에서 선택 결과를 확인했고 새 모델·호스트가 아니다. 내부 모델별 그룹은 대개 4개뿐이어서 모델별 확정적 순위를 주장하지 않는다.

이 분석은 [이전 9점 감사](saved_gpu_shape_decision_audit_findings.md)의 원 목표+9개 민감도 결정 **2,660행을 새 선택 함수로 전부 재생**해 일치시켰다. 이전 행 CSV·코드·원본의 SHA도 확인했다. [합성 회귀 시험](../tests/test_audit_saved_gpu_shape_slo_surface.py) 4개는 경계에 걸친 등호, 닫힌 식으로 계산한 로그 면적, 실제 가능하지만 잘못 승인/보류한 영역의 구분, 문자열 `"False"`의 불리언 오인을 검사했다. 기존 감사 시험 5개도 통과했다. 규약 SHA-256 `da46551644ae79ccb86213c04eaadca7e384dcb574bfb4e8c0c8688807166b1e`, 코드 SHA-256 `a13bb87ef8ea18c986b85c01ad5170359c4d6aaf533573f83b55d36b3e4498f8`, [전체 결과](../artifacts/saved_gpu_shape_slo_surface_v1/metrics.json)에는 행별 CSV SHA와 재생 건수를 기록했다.

연구 디렉터리에서 다음 명령으로 결과를 다시 만든다.

```bash
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 /usr/bin/python scripts/audit_saved_gpu_shape_slo_surface.py
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 /usr/bin/python -m unittest discover -s tests -p 'test_audit_saved_gpu_shape*.py' -v
```

결과는 같은 호스트의 한 번씩 측정한 정적 배치 성능과 수집기 생성 목표에 한정한다. 목표 배수의 로그 균등 면적은 실제 사용자 SLO 분포가 아니다. 기존 시험·별도 캠페인은 이미 노출됐으므로 이 면적 차이를 새 모델 채택 근거, 최소 안전 VM 형상, `DEPLOY` 또는 `SCALE_OUT/IN` 효과로 해석하지 않는다.
