# 저장 GPU 형상 판단 경로의 다음 계산 최적화 감사

2026-09-29. **다음 구현 후보는 한 호출 안에서 동일한 후보 격자 객체의 검증 결과와 정규 키를 재사용하는 것**이다. 저장 모델의 예측값이나 판단 정책을 바꾸는 제안이 아니다. 현재 `microbatch_v2`는 요청마다 검증을 한 번만 하지만, 하나의 8후보 격자에 25개 SLO를 붙인 경우에는 같은 후보 8개의 필드·일관성·형상 검사를 25번 수행하고 같은 격자를 25번 JSON 직렬화한다. 이 두 작업은 요청별 SLO 검사와 분리할 수 있다.

## 현재 구현과 관측

- [`assess_gpu_shape_microbatch_v2.py`](../scripts/assess_gpu_shape_microbatch_v2.py)는 먼저 모든 요청에 `_request_errors`를 호출한 뒤, 유효한 요청마다 `_grid_key(candidates)`를 만든다. `key_by_candidates_id`는 그 뒤 원본 예측 결과를 요청에 다시 연결할 때만 사용한다. [`assess_gpu_shape.py`](../scripts/assess_gpu_shape.py)의 `_request_errors`는 상위 요청의 필드·SLO뿐 아니라 8개 후보의 필드, 숫자, 공통 작업 조건과 8형상 완전성을 모두 검사한다. `_assess_gpu_shape`는 사전 검증 결과를 받아 재검증하지 않는다.
- 고정된 [`slo_reuse_v1` manifest](../artifacts/slo_reuse_v1/manifest.json)의 45개 작업 조건 × 25개 생성 SLO = **1,125개 요청**에서 후보 리스트 객체의 `id`는 **45개**, 정규 후보 격자도 **45개**였다. `make_requests`는 한 작업 조건의 25개 요청에 같은 후보 리스트 객체를 넣는다.
- 저장 모델과 원본을 로드하고 한 번 예열한 뒤, 현행 코드에 대해 **cProfile 한 호출만** 실행했다. `_request_errors` 1,125회 누적 **0.175초**, `_grid_key` 1,125회 누적 **0.051초**, `_predict_grids` 1회 안의 실제 모델 예측 6회 누적 **0.263초**, `_assess_gpu_shape` 1,125회 누적 **0.049초**였다. 계측된 전체는 0.544초다. 누적 시간은 프로파일러 오버헤드를 포함하므로 이 차이를 예상 속도 향상으로 취급하지 않는다. 단일 비계측 예열 뒤 3회는 `303.027/455.393/373.451 ms`로 편차가 컸다. 비교 실행은 순서를 교차하는 쌍 측정이 필요하다.
- [이전 v2 결과](cross_workload_microbatch_v2_findings.md)의 중앙 303.448 ms는 *당시* 평가기 코드 해시 `13a3dee8534feb79cc152d12517110fba0d401d6e789f97b16dd51a9ed187d39`에서 측정됐다. 위의 짧은 프로파일은 평가기 해시 `e27a70aef4b14fe827eac5c9a1d08b8ed688bc6de84de34582f5a94d45ccddd6`에서 수집했다. **현재 재실행 기준**의 평가기는 `e904a76d9e7940630e8a53f3f0e5d952bb98760fa74697bd7c42bfadb6a1e30e`, 예측기는 `46c85961fb4d9388c99bc073522f8cf9c839065a1f4fe67a1b92aa33f3123075`이다. 예측기의 모델별 지원 키에 `device`가 추가됐고, 저장 ExtraTrees를 직접 읽어 지원 범위 검사를 우회하는 경로도 차단됐다. v3 방법·입력 모집단·7쌍 측정·채택 게이트는 바꾸지 않았다. 앞의 두 시간 수치를 이 버전의 기준 시간으로 사용하지 않는다. [처음 점수의 결과](../artifacts/gpu_shape_microbatch_v3/results_before_device_support_key.json)와 [당시 규약](../artifacts/gpu_shape_microbatch_v3/protocol_before_device_support_key.md)은 별도 보존했다. v2 구현은 `20e73cdcf39dbe7252399a3bff8eda9387ff592d046ea6483df15b13710e996d`, 저장 모델은 `7a934da440ea0c7473e4e59eb5fa0c8c57f347389272bd303cb0051ef918b161`, 원본 Parquet은 `b7bba7963e8a309b6a8502a1d98eefb150476b1381ec016beeb68cbf63fae906`, manifest는 `dcea7d8dc21ab6928da990d0fd3a4cfb6883fe1d01a831462c214d059d8ba679`이다.

## 한 가지 변경 가설

새 연구용 `v3` 함수는 현재 v2·공용 평가기 코드를 그대로 둔 채, 한 함수 호출 안에서만 유효한 후보 리스트 객체를 준비한다. 요청의 **상위 필드와 두 SLO 수치**는 매번 검사한다. 같은 후보 리스트 객체가 앞서 완전히 유효하다고 확인된 경우에만 후보 8개의 검사를 건너뛰고, 이미 만든 정규 격자 키를 쓴다. 처음 보는 객체는 기존 `_request_errors`로 전체를 확인하고, 오류가 없을 때만 객체 참조와 키를 기억한다. 서로 다른 객체지만 내용이 같은 격자는 현재 `_grid_key` 결과로 모델 예측만 합쳐 재사용한다. 잘못된 후보는 캐시하지 않아 현재의 오류 순서와 요청별 `reasons` 리스트 독립성을 유지한다.

캐시는 호출 밖으로 나가지 않는다. 기존 v2의 명시 계약처럼 호출 도중 요청·모델을 수정하지 않아야 한다. 이 계약이 없다면 객체 동일성만으로 과거 검증을 재사용할 수 없다. `_predict_grids`의 배치 크기는 **8로 고정**하고, 현재의 합친 예측 실패 시 격자별 재시도와 결과 복사 규칙을 유지한다. 이 변경은 모델 추론보다 요청 검증·키 생성의 CPU 비용을 겨냥한다. 25번 반복되는 유효 격자가 없는 입력에서는 이득이 작거나 오히려 느릴 수 있다.

## 구현 전 고정할 비교 규약

1. **기준선과 입력:** 위 해시의 현행 `assess_gpu_shape_microbatch_v2(..., max_grids=8)`을 기준선으로 삼는다. 같은 검증된 모델·원본, 같은 45×25 manifest와 주 CUDA 캠페인의 575개 서로 다른 8후보 격자를 사용한다. 저장 모델·데이터·공용 평가기·기준선 파일은 변경하지 않는다. 평가 중 해시가 달라지면 기준선부터 다시 고정한다.
2. **의미 동등성:** 1,125개 반복 SLO와 575개 단일 격자 요청의 최종 정규 JSON을 기준선과 전부 비교한다. 같은 후보 리스트의 서로 다른 SLO, 내용은 같지만 별도 객체인 격자, 격자 순서 변경, 잘못된 상위 필드(`price_usd_per_hour_max` 포함), 0/무한대 SLO, 후보 7개·형상 중복·필드 오류·작업 혼합·미지원 revision, 미검증 bundle, 합친 예측 호출만 실패하는 모형을 포함한다. 응답 하나의 `reasons`를 수정해도 다른 응답이 변하지 않아야 한다. 모델 예측 호출 수와 원본 예측값도 같아야 한다. 하나라도 다르면 변경을 버린다.
3. **시간과 메모리:** 모델·입력 적재 및 첫 완전 호출은 타이머 밖에 둔다. BLAS/OMP/MKL 각 한 worker, `max_grids=8`, 동일한 요청 순서로 기준선·제안 경로를 7쌍 실행하며 쌍 안의 실행 순서는 고정 난수로 교차한다. 함수 전체 wall time과 process CPU time을 모두 기록한다. 45×25에서 쌍별 중앙 wall time 기준 **1.20배 이상** 빠르고, 575개 단일 격자에서는 **10% 초과 악화가 없을 때**만 기본 연구 경로로 남긴다. 같은 값의 복사된 후보 리스트 25개를 사용한 별도 스트레스 입력에서도 10% 초과 악화가 없어야 한다. 별도 프로세스의 peak RSS는 기준선보다 **20 MiB 초과 증가하지 않아야** 한다. 결과와 코드·모델·입력 해시를 보존한다.

이 시험의 시간은 한 호스트의 저장 모델을 사용하는 **오프라인 CPU 판단 함수** 시간이다. 반복 SLO는 원본 측정에서 만든 가상 목표이고, 이 최적화로 새 AI 모델의 예측 정확도, 실제 VM 형상, 배포·Scale-out/in 효과나 학술적 방법 신규성이 생기지는 않는다. 통과한다면 경희대의 배포·제어 판단 **계산 경로** 개선으로만 기록한다.
