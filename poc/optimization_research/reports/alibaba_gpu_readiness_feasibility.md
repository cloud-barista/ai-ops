# Alibaba GPU v2026 준비 지연 자료의 배포 판단 적합성

점검일: 2026-09-28. **판정: 이 공개 자료만으로 경희대 `DEPLOY`·`UPDATE`의 요청 시점 준비 위험 모델을 학습하거나 검증하지 않는다.** `ready_status`, `schedule_delay_sec`, `ready_delay_sec`는 존재하지만, 두 공개 표 모두 이미 GPU 서버에서 관측됐거나 실행 구간으로 집계된 pod를 담는다. 미배치 요청을 포함한 제출 모집단, 제출·준비 시각, 고정 판정 기한이 없다. 준비 상태의 의미를 "요청 후 N분 내 준비 성공"으로 검증할 수 없고, 대체 배치·업데이트 행동의 결과도 없다. 좁게는 *관측된 실행 구간의 사후 지연 분포*를 연구할 수 있지만 운영용 배포 판단의 정답은 아니다. [공식 스키마](https://github.com/alibaba/clusterdata/blob/master/cluster-trace-gpu-v2026/docs/schema.md), [다운로드 목록](https://github.com/alibaba/clusterdata/blob/master/cluster-trace-gpu-v2026/docs/data_download.md).

## 조사 방법과 표본 범위

공식 OSS의 ZIP 두 개에 `HEAD`와 HTTP `Range`만 보냈다. ZIP 중앙 디렉터리와 선택한 비압축 Parquet의 footer·필요한 열 조각을 읽었다. ZIP 전체나 Parquet 전체를 저장하지 않았고 모델을 학습하지 않았다. 요약 ZIP은 1,188,295,031바이트, 시간별 pod ZIP은 351,803,513,445바이트였다. 조사 중 받은 바이트는 약 **33.4 MB**다. 객체 ETag는 각각 `19C10452429092949CC044ED5FE3FCEB-284`, `092823B8D7C37992AF1BB732C8865E58-400`이었다.

- `asi_opensource_job_execution_summary/part-000.parquet`: 전체 **40,522,321행·346 row group** 중 위치가 떨어진 row group **0, 100, 300**을 읽었다. 표본 **352,244행**은 시간 무작위 표본이 아니다. 이 파일에는 상대 `day/hour`가 없다.
- `asi_opensource_pod_hourly/day=0/hour=00`과 `hour=01`: 각 파일의 row group **0, 8, 16**을 읽었다. 각각 **171,708행**, **208,715행**으로, 두 시간 전체 1,179,029행·1,212,189행의 일부다. 두 시간만으로 185일 전체의 비율을 추정하지 않는다.

아래 숫자는 이 고정 표본의 **행 수**다. 동일 pod가 여러 실행 구간 또는 여러 시간에 반복될 수 있다.

| 표본과 GPU 요청 조건 | 행 | `ready_status=True` | `False` | 결측 | `ready_delay_sec >= 0` |
| --- | ---: | ---: | ---: | ---: | ---: |
| 실행 요약, `online_inference` | 44,021 | 22,472 | 20,643 | 906 | 18,469 |
| 실행 요약, 그중 `genai` | 4,694 | 3,173 | 1,438 | 83 | 2,370 |
| 시간별 pod, day 0 hour 00의 `online_inference` | 8,493 | 7,909 | 570 | 14 | 4,020 |
| 시간별 pod, day 0 hour 00의 그중 `genai` | 1,880 | 1,741 | 137 | 2 | 1,298 |
| 시간별 pod, day 0 hour 01의 `online_inference` | 10,495 | 9,676 | 804 | 15 | 5,040 |

요약 표본은 전부 `gpu_request > 0`이고, 시간별 표본에는 GPU 요청 0인 행도 있다. 위 시간별 코호트에는 `gpu_request > 0` 필터를 적용했다. 요약 표본의 온라인 추론에서 `schedule_status=False`는 **26/44,021행**뿐이고, `schedule_delay_sec >= 0`은 **43,089행**이다. 실행 구간으로 선택된 뒤에는 미배치 위험을 대표하지 못한다. 공식 정의에서도 요약 표는 **GPU를 요청한 실행 구간**, 시간별 표는 **GPU 서버에서 그 시간에 관측된 pod**다.

## 라벨의 관측·선택 문제

요약 표본 온라인 추론의 관측된 준비 상태 중 True 비율은 **52.1%**이고, day 0 hour 00 시간별 표본은 **93.3%**다. 이 차이를 모델 개선 가능성이나 전체 자료의 모집단 비율로 해석하지 않는다. 시간별 표는 오래 서버에 머문 pod를 여러 번 세며, 실행 요약과 표본 추출 단위가 다르다. 요약 표본 온라인 추론에서 준비 상태 True인 실행 구간의 중앙 지속 시간은 **2.39시간**, False는 **0.77시간**이었다. 시간별 행으로 준비 성공률을 계산하면 오래 지속된 성공 pod가 더 큰 가중치를 받는다.

`ready_delay_sec`의 **음수**는 유효한 시간 지연으로 계산할 수 없다. 요약 표본 온라인 추론에서는 `ready_status=True` 22,472행 중 **4,003행**에서도 음수다. `ready_status=False` 20,643행은 모두 음수였고, 906행은 준비 상태와 두 지연 모두 결측이었다. 준비 여부가 True라는 사실만으로 완료 시각이 알려진 것은 아니다. `ready_delay_sec >= 0`인 행만 회귀에 넣으면 준비 시각이 기록된 집단으로 다시 선택된다. `schedule_delay_sec`는 스케줄링 지연이고 `ready_delay_sec`는 스케줄링부터 준비까지의 지연이다. 제출부터 준비까지의 지연을 만들려면 두 성분 모두 유효해야 하지만, `ready_status=True`에서도 그 조건이 자주 성립하지 않는다.

`ready_status`는 공식 문서상 *소스 메타데이터에 따라 준비 상태가 되었는지*를 뜻한다. 공개 표에는 상태 평가 시각, 준비 기한, 관측 종료 시각과 검열 사유가 없다. 따라서 False를 "N분 내 준비 실패"로, 결측이나 음수 지연을 0초로 해석하지 않는다. `UPDATE` 시도 식별자나 업데이트 명령도 없어 재배포와 최초 배포를 분리할 수 없다.

## 독립 사례·시점 누출 점검

요약 표본 352,244행에 고유 `pod_id`는 **350,669개**다. 반복되는 `pod_id`는 1,405개이며, 이 중 **123개**는 반복 행 간 `ready_status`가 다르다. 파일에는 각 실행 구간의 시작 시각이 없으므로 같은 pod의 어느 실행 구간이 특정 시간별 행과 대응하는지 안정적으로 정할 수 없다. `workload_id`는 요약 표본 온라인 추론에서 **5,962/44,021행**에만 있다. 동일 응용 분할도 결측의 영향을 크게 받는다.

선택한 두 시간별 표본의 같은 `pod_id` 중 **21,433개**가 겹쳤다. 그중 GPU 요청 온라인 추론은 **1,493개**이며 `ready_status`, `schedule_delay_sec`, `ready_delay_sec`가 **모두 1,493쌍에서 정확히 같았다**. `genai` 온라인 추론 **331쌍**도 세 라벨이 모두 같았다. 시간별 행을 무작위로 학습·시험 분리하면 동일 사건의 라벨이 양쪽에 들어갈 수 있다. 따라서 좁은 사후 연구를 하더라도 pod·workload 수준 중복 제거와 시간 분리가 필요하다. 요약 표에는 자체 `day/hour`가 없어 단독 시간 분리도 불가능하다.

## 요청 시점에 쓸 수 있는 열

제출 시점 특성으로 가장 명확한 공개 값은 `gpu_request`, `priority_class`다. `job_type_public`, `model_type_public`, `is_genai_request`는 실제 연동 입력에 이 분류가 제출 전에 있음을 확인한 경우에만 쓸 수 있다. `cpu_request_cores`와 `gpu_mem_request`는 시간별 pod 표에 있지만 실행 요약에는 없으며, 두 표를 연결하면 GPU 서버에서 관측된 pod만 남는다. `workload_id`는 결측이 많고 원본 요청에 보장되는지 확인이 필요하다.

`server_id`, `gpu_spec_public`, `cluster_id`, `server_gpu_count`, `server_cpu_capacity_cores`는 이 표에서 관측된 배치·호스트에 결부된 정보다. **배치 전** 준비 지연을 예측할 때 그대로 넣으면 배치 후에 알게 되는 사실이 누출될 수 있다. `state_public`, 사용량, `duration_hours`, `schedule_status`, 세 준비·지연 라벨은 결과 또는 후행 관측이다. 익명 `pod_id`와 `server_id`는 그룹·결합 키로만 쓰고 예측 변수로 쓰지 않는다. 후보 서버별 위험을 비교하려면 요청 시점에 실제로 제공된 후보 상태와 각 후보에 대한 결과 자료가 별도로 필요하다.

## 개발 결정

이 자료를 KHU `DEPLOY`·`UPDATE` 승인 점수 또는 준비 시간 보장 모델로 채택하지 않는다. 현시점의 실용적 산출물은 **입력/출력 계약과 검증 조건**이다: 모든 제출 요청의 시각과 요청 형상, 그 시점의 후보 자원 상태, 실제 선택·명령, 스케줄·준비 시각, 명시적 판정 기한과 관측 종료, 준비 실패 사유, 업데이트 시도 식별자, 사용자 지연·처리량 결과가 연결돼야 한다. 이 기록이 생기면 제출 요청을 단위로 시간순 보류 집합을 만들고, 정해진 기한 내 준비 확률을 단순 유형별·요청량별 기준선과 비교한 후에만 배포 판단 메커니즘을 평가한다. 현재 공개 표의 지연 분석은 그때의 후보 특성 설계 참고자료 수준으로 둔다.
