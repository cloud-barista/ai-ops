# Alibaba GPU v2026 시간순 활용 진단

점검일: 2026-09-28. **판정:** 이 16시간 표본의 온라인 GenAI GPU 메모리 평균은 한 시간 뒤에도 대부분 동일하여, GPU 메모리 부족 위험 또는 스케일링 판단 모델의 학습 정답으로 채택하지 않는다. 더 좁은 단일 GPU 층에서는 GPU SM 사용률에 시간 변동이 있으나, 압박 상태의 사례와 독립 날짜가 부족하다. 이번 단계에서는 모델을 학습하거나 검증·시험 점수를 열지 않았다.

## 출처와 표본

[Alibaba 공식 공개 스키마](https://github.com/alibaba/clusterdata/blob/master/cluster-trace-gpu-v2026/docs/schema.md)에 따르면 `pod_hourly` 한 행은 GPU 서버에서 관측한 pod 한 개의 한 시간 기록이다. `pod_id`·`workload_id`는 이 공개판 안에서 안정적인 익명 ID이고, `workload_id`는 원래 메타데이터가 없으면 null이다. `gpu_request`는 GPU 개수 상당량, `used_gpu_hours`는 이 시간에 귀속된 GPU-hour, `avg_gpu_mem_gib`는 평균 GPU 메모리 GiB다. `gpu_mem_request`는 출처가 보고한 요청량이지만 **공식 스키마에 단위가 없다**. `avg_gpu_sm_util`도 출처가 보고한 평균 GPU SM 사용률이다.

[공식 다운로드 목록](https://github.com/alibaba/clusterdata/blob/master/cluster-trace-gpu-v2026/docs/data_download.md)의 ZIP 객체 크기 351,803,513,445 B와 ETag `092823B8D7C37992AF1BB732C8865E58-400`을 확인했다. ZIP 중앙 디렉터리의 4,440개 시간별 Parquet 중 **day 0의 00–07시, day 1의 00–03시, day 5의 00–03시**, 총 16시간을 사전에 선택했다. 선택한 원본 멤버는 990,345,080 B·18,277,894행이다. HTTP `206` 범위 요청 52건, 총 990,858,534 B만 읽었고 원본 ZIP을 저장하지 않았다. 각 멤버의 ZIP CRC32와 개별 SHA-256을 확인했다. `job_type_public=online_inference`, `model_type_public=genai`, `gpu_request>0` 조건을 적용한 **222,093행**을 7,838,557 B Parquet (`../data/external/alibaba_gpu_2026_temporal/online_genai_gpu_16h.parquet`)로 보존했다. 파일 SHA-256은 `04aa37e8c21cbb97beab42f76e5e47afe1b399652d6bee52f0af55ec0577443f`이며 멤버별 해시·행수·필드는 [SOURCE.json](../data/external/alibaba_gpu_2026_temporal/SOURCE.json)에 있다. 이 16시간은 185일 전체의 대표 표본이 아니다.

`gpu_mem_request / 2^30`의 표본 중앙값은 95.625이고 `avg_gpu_mem_gib` 중앙값은 94.177이다. 양수 요청·유효 사용량 220,834행의 `사용량 / (요청량 / 2^30)` 중앙값은 0.981이며 64행만 1을 넘는다. 이는 요청값이 바이트 단위일 가능성을 보여 주는 **표본상 추론**이다. 공식 단위와 요청·평균 사용량의 집계 범위를 확인하기 전에는 이 비율을 OOM 또는 부족 위험 정답으로 쓰지 않는다. 평균값은 짧은 피크와 실패를 보여 주지 않는다. 최대 사용량 1,559.9 GiB는 다중 GPU pod가 포함된 값이므로 임의의 1GPU 상한으로 배제하지 않았다.

같은 pod의 **인접 시간** 유효 메모리 관측 쌍은 day 0/1/5 순으로 94,086 / 40,854 / 41,982개다. `workload_id`가 있고 해당 시간의 모든 선택 pod에서 메모리 값이 유효한 workload 쌍은 25,019 / 10,559 / 10,410개다. 이는 행이나 쌍의 수이고 독립 날짜 수는 개발 1일·검증 1일·시험 1일뿐이다. 시간별 pod 요청 형상이 고정된 같은 pod 기록이 반복되므로 쌍을 독립 실험 단위로 세면 안 된다.

day 0과 day 1에 모두 등장한 pod/workload는 11,970/3,149개, day 0과 day 5에는 10,952/2,881개, day 1과 day 5에는 11,698/3,077개다. day 5에서 앞 두 구간에 한 번도 없던 ID는 pod 3,189개·workload 675개다. 따라서 날짜 순 분할은 **기존 응용의 미래 시점** 평가에는 맞지만 **새 응용 일반화**를 증명하지 않는다. ID는 결합과 군집화에만 사용하고 모델 특징에는 넣지 않는 것이 적절하다.

## 메모리 목표 판단

개발 구간의 유효 동일 pod 인접 시간 94,086쌍 중 `avg_gpu_mem_gib`가 수치상 정확히 같은 쌍이 **87,533개(93.0%)**였다. `workload_id`별 선택 pod의 평균 메모리 합계는 25,019쌍 중 **23,760개(95.0%)**에서 동일했다. workload 합계가 현재값 대비 10%를 넘게 바뀐 쌍은 **89개(0.36%)**였다. 동일 workload의 pod 개수가 달라진 쌍은 36개다. 이 결과는 개발 날짜의 정답 분포 진단이며 검증·시험 예측 점수는 아니다.

따라서 현재 표본으로 `t`시 평균 메모리에서 `t+1`시 평균 메모리를 맞히는 모델은 변화 없는 값을 반복하는 기준선보다 연구적·운영적 가치를 보이기 어렵다. `gpu_mem_request`를 임시 바이트로 환산해도 평균 사용량이 요청량을 넘은 행은 64/220,834개뿐이고 이는 OOM 정답이 아니다. 실제 사용자 지연·처리량 SLO, 피크 VRAM, OOM 기록, 자원 형상 변경 후 결과도 없다. **GPU 메모리 부족 위험 분류·최소 메모리 권고·Scale-out/in 효과 학습은 이 자료에서 보류한다.** 장기 변화나 다른 날짜에는 다른 분포가 있을 수 있으므로 이 판정은 선택한 16시간과 한 시간 예측 목표에 한정한다.

## 단일 GPU 사용률과 GPU-hour 대안

`gpu_request<1`인 2,284행은 SM 값이 전부 결측이다. `gpu_request=1`인 행은 195,868개다. 이 층의 SM 값은 36,592개가 결측이고 5개만 100을 넘는다. 전체 SM 100 초과 1,551개 중 나머지 1,546개는 주로 2·4·8·16 GPU 요청이다. 요청이 1GPU이고 서버도 1GPU인 더 엄격한 층은 **14,334행·고유 pod 1,115개·고유 workload 316개**다. 이 층의 SM 결측은 9개, 음수 또는 100 초과는 0개다. 개발/검증/시험 행은 7,099/3,630/3,605개이고, 인접 시간 유효 SM 쌍은 6,178/2,697/2,663개다. 개발 6,178쌍 중 동일 SM은 2,423개, 절대 10%포인트 초과 변화는 192개다. 값이 변하더라도 개발 구간의 SM 중앙값은 0.603, 90백분위는 17.97이다. 50 초과 행은 56개·고유 pod 25개뿐이고 검증 날짜에는 6행·한 시간에만 나타났다. 압박 여부 분류를 검증하기에는 양성이 매우 적다.

[공식 스키마](https://github.com/alibaba/clusterdata/blob/master/cluster-trace-gpu-v2026/docs/schema.md)는 `used_gpu_hours`를 그 시간 pod에 귀속된 GPU-hour로 정의한다. `gpu_request=1` 행 195,868개 중 189,489개, 서버까지 1GPU인 행 14,334개 중 14,129개가 정확히 1.0이다. 개발 단일 서버 GPU 층의 유효 SM 인접 쌍 6,178개 중 GPU-hour가 바뀌지 않은 쌍은 6,141개다. GPU-hour는 부하 강도보다 **GPU를 사용한 시간과 GPU 수**에 가까워, 이 조건에서 평균 처리량 또는 GPU 압박을 대신할 목표가 아니다. 부분 시간 관측은 시작·종료, 누락 등 다른 원인이 섞일 수 있다. 모든 선택 행의 `state_public`은 `Unknown`이므로 GPU-hour 감소를 스케일인·실패 결과로 읽을 수 없다.

## 점수를 열기 전 제안하는 한정 프로토콜

GPU SM 원시값의 한 시간 앞 **계측 예측**만 탐색한다면, `gpu_request=1`과 `server_gpu_count=1`, 현재 시각에 확인된 유효 `avg_gpu_sm_util ∈ [0,100]`를 적용한다. 완전히 종료된 시간 `t`의 요청 형상·GPU 유형·현재 및 과거 SM만 특징으로 쓰고, 다음 시간에 같은 pod가 관측될 때의 SM을 조건부 정답으로 둔다. 다음 시간의 pod 소멸은 별도 지속 여부 정답으로 기록하고, 소멸한 pod의 SM을 0으로 위조하지 않는다. 정답 시간 `t+1`의 사용량이나 `ready_status`, pod/workload ID 자체를 특징으로 넣지 않는다. `state_public`은 사용할 수 없다.

현재 16시간 파일의 day 0은 개발, day 1은 검증 후보, day 5는 시험 후보로 유지한다. 세 구간에서는 표본 품질과 연결 수만 진단했으며 예측 점수로 방법을 선택하지 않았다. 기준선은 현재 SM 지속, 직전 두 시간 평균, 개발 구간 GPU 유형별 과거 중앙값으로 미리 고정한다. 평가는 MAE와 95백분위 절대오차를 행 기준과 날짜별 평균 기준으로 보고하고, SM 사용률 구간별 오차·훈련에 없던 pod의 별도 결과를 낸다. 그러나 검증·시험 날짜가 각 하루라서 모델 선택이나 일반화 주장에는 부족하다. 실제 학습 실험 전에는 원본 185일에서 **여러 완전한 날짜**를 시간순으로 추가 취득하고, 분할과 기준선을 먼저 동결해야 한다. 검증 목표는 계측 예측이며 SLO 위반이나 스케일링 행동의 효과가 아니다.
