# 경희대 담당 연구: 기존 SQLite와 공개 AI·GPU 추적 자료의 활용 결정

2026-09-29 기준의 연구·오프라인 검증 상태다. 플랫폼 실행 기능은 이 문서의 대상이 아니다.

## 데이터 선택

기존 [SQLite 진단](../data/audit_v1/data_audit.md)은 한 호스트의 정적 CPU/GPU 배치 측정에는 적합하지만 실제 사용자 요청의 변화, VM 스케일 명령과 그 후의 서비스 결과를 담지 않는다. 따라서 응용 요청·부하 시계열에는 공개 [Alibaba GenTD26](../data/external/gentd26/SOURCE.md)을 별도 데이터로 사용했다. 요청 실행시간 26,823건과 약 23시간의 QPS·대기열·GPU 모니터링이 있으며 원본 압축과 SHA256을 고정했다. 요청 파일과 모니터링 파일의 익명 시각 범위가 서로 달라 두 파일을 요청 단위로 연결하지 않는다.

[2026-09-28 로컬 SQLite 재점검](local_signal_refresh_2026_09_28.md)에서 KHU 원본 7개 DB의 물리 측정 9,591행과 마지막 실행 시각이 이전 감사와 같음을 확인했다. 파생 `SCALE_OUT/IN` 라벨은 정적 복제 수 측정쌍이고, `UPDATE` 12,000행씩은 합성 시나리오 DB에만 있다. 새 실행 명령·전후 사용자 결과는 없다.

더 긴 시간대의 LLM 응용 부하는 [Alibaba MaaS 2026](../data/external/alibaba_maas_2026/SOURCE.md)의 작은 공개 사례로 별도 검토했다. 일주일·시간별 계측 7,401행 중 세 응용에서 응용별 정규화 QPS를 얻었다. QPS와 GPU 배정이 동시에 있는 응용은 두 개다. 이 사례의 QPS는 절대 요청/초가 아니고 스케일 명령도 없다. 로컬 SQLite·GenTD26·MaaS는 모델과 시각축이 달라 원시 행을 합쳐 학습하지 않는다.

독립 요청 검증 후보인 [BurstGPT v2.0](burstgpt_data_audit.md)도 전량 확인했다. 534만 건 중 완료시간 0초가 317만 건(59.4%)이고 시기·호출 유형별 차이가 커서 전체 요청의 지연 검증에 사용할 수 없다. [사전 평가 규약](burstgpt_external_validation_protocol.md)을 품질 검사 이후 수정 적용하고, 양수 완료시간 부분집합만 [탐색적으로 분석](burstgpt_observed_duration_findings.md)했다. [ETH SwissAI 기록 1,632만 건](swissai_trace_full_audit.md)은 전량 정렬·감사했지만, [사전 규약](swissai_external_validation_protocol.md)의 첫 30일에는 학습 요청이 70건뿐이고 한 시험 블록의 유효 라벨 비율이 `94.1%`라 원래 독립 검증이 중단됐다. 성능 점수를 보기 전에 요청 발생 건수만으로 첫 학습 가능 시작일을 고른 [후속 탐색 규약](swissai_exploratory_followup_protocol.md)을 따로 고정하고, [모델·단순 기준선을 같은 요청에 평가](swissai_exploratory_findings.md)했다. 공개 원시 행을 기존 SQLite의 정적 벤치마크와 합쳐 학습하지 않는다.

추가 독립 계측 자료로 [Microsoft Philly DNN 학습 클러스터의 GPU 1분 추적](../data/external/msr_philly_2017/SOURCE.md)을 사용했다. 공개 원본 GPU 4,475만 행을 감사하고, 고정 기계 해시 표본 21기계·170만 행에서 [사전 동결한 30분 고사용률 위험 평가](philly_gpu_risk_findings.md)를 진행했다. 이후 기존 결과를 보고 선택한 통합 모델을 [겹치지 않는 새 기계 47대의 별도 표본](../data/external/msr_philly_2017_holdout/SOURCE.md)에 고정 적용했다. 이 47대는 기계별 사전기간 교정의 개발 자료로 재분류하고, [다른 해시 구간 42대](../data/external/msr_philly_2017_calibration_holdout/SOURCE.md)를 새 독립 표본으로 수집했다. 세 표본 모두 원시 GPU 행을 로컬 SQLite·MaaS와 합쳐 학습하지 않는다. 실제 사용자 SLO와 VM 변경 결과가 없으므로 위험 확률의 정확도만 평가한다.

이어 앞선 두 새 기계 집합의 점수를 본 뒤 전날 기계별 보정식을 설계하고, 수집 전에 규약을 동결한 [네 번째 해시 구간 58기계](../data/external/msr_philly_2017_day_ahead_holdout/SOURCE.md)를 추가했다. 그중 시험 적격 41기계·685,940개 판단에서 [기계별 하루 보정](philly_day_ahead_calibration_holdout_findings.md)의 Brier는 원래 모델 `0.086988→0.082766`으로 낮아져 사전 탐색 게이트를 통과했다. [피드백 지연 가정](philly_feedback_delay_sensitivity.md)을 늘린 분석도 했지만 같은 이미 채점한 자료의 사후 진단이다. 두 결과 모두 관측 GPU 위험 확률에 한정한다.

[Google 2019 Borg trace](https://github.com/google/cluster-data/blob/master/ClusterData2019.md)는 CPU/메모리 작업 추적에 유용하지만 사용자 AI 요청시간과 GPU SLO 라벨을 제공하지 않는다. 공식 소개는 압축 약 2.4 TiB의 BigQuery 접근을 설명하고, 연결된 [v3 형식 문서](https://drive.google.com/file/d/10r6cnJ5cJ89fPWCgj7j4LtLBqYN9RiI9/view)는 공개 GCS JSON 객체 접근도 설명한다. [Google 2011 자료](google_2011_resource_feasibility.md)는 압축 약 41 GB 중 떨어진 세 시점의 사건·사용량 조각 6개를 공식 해시와 대조해 진단했고, 이후 동시 피크 시험용 `00450` 두 파일을 추가했다. 원래 세 조각의 엄격한 1시간 연속 관측 task는 조각별 124/95/248개이고 AI 응용·GPU·사용자 SLO 라벨이 없다. [30분 관측 CPU·RAM 최대값의 별도 시간순 학습](google_2011_observed_resource_findings.md)에서는 CPU 손실이 줄었지만 90분위 피복률 기준이 실패했다. [새 시간 조각의 동시 피크 상한 시험](google_2011_joint_envelope_findings.md)도 사전 채택 기준에 실패했다. 관측 CPU·RAM은 기존 배정 아래의 값이라 최소 안전 형상의 정답이 아니다.

같은 Google 2011 사건 자료에서는 [배정 뒤 첫 기록 사건의 별도 감사](google_2011_early_exit_feasibility.md)로 `EVICT/FAIL` 정답의 존재를 확인했다. 재시도를 task별 첫 적격 시도로 줄인 30분 개발 조각의 양성은 학습 4,845건·검증 4,316건이지만, 검증 양성이 소수 job에 몰리고 업데이트 뒤 후속 종료 71건은 첫 사건 정답과 별도로 처리해야 한다. 범용 Borg task의 첫 사건은 AI 응용 VM 배포·스케일 조치의 결과가 아니므로 현재 자료로 직접 행동 모델을 학습하지 않는다. 이 과제의 시험 후보 사건 조각 `00400`은 열지 않았다.

[Alibaba GPU v2026 공개 추적](alibaba_gpu_2026_feasibility.md)도 ZIP 내 두 인접 시간의 일부 Parquet 열만 범위 요청으로 점검했다. AI 작업 범주·GPU/CPU 요청과 사용량은 연결되지만, 절대 RAM 요청·사용량, 모델명, 사용자 SLO와 대체 형상의 결과가 없다. 이어서 [16시간의 서로 다른 세 날짜에서 온라인 GenAI GPU pod 222,093행을 시간순 진단](alibaba_gpu_temporal_feasibility.md)했다. 첫 개발 날짜의 다음 시간 pod 평균 GPU 메모리 관측쌍 94,086개 중 93.0%가 정확히 동일했고, 단일 GPU 사용률의 고부하 사례도 드물었다. 이 표본으로 GPU 메모리 부족·스케일 위험 모델을 학습하지 않는다. 전체 185일의 다른 날짜까지 같은 분포라는 주장은 아니다.

같은 자료의 [`ready_status`·준비 지연 감사](alibaba_gpu_readiness_feasibility.md)는 제출 요청 전체와 판정 기한이 없어 요청 시점의 배포 성공 라벨을 만들 수 없음을 확인했다. 온라인 GPU 실행 요약 표본에서는 준비 상태가 True인데도 준비 지연이 음수인 행이 4,003건이었다. 시간별 pod 표는 같은 사건의 라벨을 여러 시간에 반복하므로 `DEPLOY/UPDATE` 승인 모델의 정답으로 사용하지 않는다.

## 연구 모델과 배포 판단의 입력 경계

기존 Go shadow 클라이언트 (`/home/researcher/ai-mcmp/deployment_agent/go/service-control-api/internal/api/shadow_policy_api.go`)는 후보 형상의 CPU·RAM·GPU 용량을 실제 가용량으로 복사하고, 추천 점수를 시간당 가격으로 바꿔 정책 서비스에 보냈다. 현재 정책 특성 (`/path/to/aiops/khu_policy_agent/contracts.py`)은 이 수치들을 서로 다른 입력으로 사용하므로 대리값을 그대로 보내면 shadow 비교도 의미가 달라진다. 2026-09-28 수정 후에는 Flow에 관측 가용량·건강 상태·검증된 시간당 가격과 출처가 없으면 `ABSTAIN`과 `policy_input_missing_provenance`를 기록하고 정책 서버를 호출하지 않는다. 현재 모든 Flow 생성 경로가 이 원본 필드를 보존하지 않아 shadow 정책 서버 호출은 중단됐다. 기존 규칙 기반 판단과 `DeploymentPlan`은 유지한다. Resource Ops Prometheus adapter (`/home/researcher/ai-mcmp/resource_ops/internal/resource/prometheus/adapter.go`)는 기본 2분보다 오래되거나 조회 시각보다 미래인 표본을 제외하고 실제 표본 시각을 전달하도록 보강했다. 그러나 focused Resource Ops 입력 (`/home/researcher/ai-mcmp/deployment_agent/go/service-control-api/internal/api/focused_planning_api.go`)의 관측 가용량은 현재 Flow 변환에서 보존되지 않고 가격 필드도 없다. 이후 연동 시 원본 시각·출처·단위를 보존하는 별도 계약, 학습 라벨의 지원 범위 확인, 실제 조치 결과 검증이 필요하다.

[측정 없는 정적 추천의 donor 보정 문턱](cold_start_selective_safety_findings.md)은 대상 모델을 제외한 자료에서만 양의 여유값 또는 전부 보류를 선택했다. 기존 9개 모델·한 호스트·합성 SLO를 다시 사용한 탐색 평가에서 8모델이 전부 보류됐고, 나머지 한 모델은 365건 승인·365건 성공이었다. 하지만 고정 0.05 문턱은 그 모델에서 492건 승인·492건 성공이었고, 보정법의 승인 중 91.8%는 모든 후보가 실측상 성공하는 쉬운 목표였다. 성공 승인 유지 기준에 실패해 채택하지 않는다.

[한 응용의 여러 입력 조건을 공통 형상 하나로 처리하는 연구](workload_envelope_recommendation_proposal.md)는 모델 학습 전에 [자료 적격성만 감사](workload_envelope_gate_findings.md)했다. 원본 생성 SLO에서 형상 8개 중 일부만 90% 조건을 만족하는 비자명 묶음은 **18개 중 3개**로 사전 요구 4개에 못 미쳤다. 높은 수요 묶음 9개는 가능한 형상이 하나도 없었다. donor 실측으로 만든 합성 목표에서는 450개 중 75개가 비자명이었지만 동일한 9모델을 반복 사용한 가상 목표다. 사전 규약대로 이 방법의 학습·점수화는 중단했다.

기존 SQLite의 완전한 8개 후보 배치 측정으로 [SLO 경계 기반 경량→강한 2단계 추론](cascade_inference_findings.md)을 별도 시험했다. 모델 전체 제외 9분할·14,375개 상관 합성 질의에서 항상 강한 모델 대비 오승인은 `1,307→1,383`, 정확 최소 형상 선택은 `3,775→3,736`으로 악화했다. 공정한 단일 worker 강한 모델의 8후보 warm p95 채점시간 `45.90ms`는 2단계 `46.71ms`보다 짧았다. 이 방법은 채택하지 않는다. 같은 적합 강한 모델의 worker를 2개에서 1개로 줄이면 이 환경의 평균 채점시간은 `53.62→34.12ms`였고 예측 최대 차이는 `2.7e-15`였다. 이와 별도로 [저장된 연구용 성능 예측 경로](performance_predict_workers_findings.md)에도 단일 worker 채점을 적용했다. 저장 모델을 유지한 채 4,856개 후보의 예측값이 같았고, 한 후보의 예열된 모델 채점 평균은 `57.20→39.95ms`였다. 이어 [8후보 일괄 채점](performance_batch_predict_findings.md)으로 후보별 모델 호출을 8회에서 1회로 줄였다. 한 작업군의 warm 오프라인 함수 호출에서 출력이 정확히 같고 p95가 `175.55→23.00ms`였으며 사전 2배 기준을 통과했다. 각 시간 비교는 별도 실행의 동일 입력·동일 환경 내에서만 해석한다. 이 수치들은 로컬 CPU 추론이며 실제 플랫폼 지연이나 사용자 SLO 검증이 아니다.

공개 요청 자료의 1시간 피드백 지연 **가정**에서, 초기 학습에도 결과 가용 시각을 적용해 미가용 198건을 제외했다. 기본 학습기+전역 보정은 시험 6,244건의 90% 분위수 pinball 손실 `2.911초`, coverage `90.1%`였다. 시험 시작 전에 가용한 검증 결과만으로 선택한 모델 ID별 잔차 보정은 `2.770초`와 `90.4%`였다. 다만 `IMG_2_IMG`의 coverage는 `83.4%`에 그친다. [세부 평가](gentd26_subgroup_findings.md)는 후향 탐색이며 독립 서비스 검증이 아니다.

[같은 GenTD26 요청의 최종 `FAILED` 상태 위험 탐색](gentd26_request_failure_validation_findings.md)은 확정 상태 학습 13,208건·실패 231건, 검증 7,263건·실패 92건을 사용했다. 사전 정의한 모델×작업종류 빈도 기준선 대비 로지스틱의 검증 날짜 동일 가중 Brier가 **0.006053→0.005100**으로 낮아 사전 탐색 게이트를 통과했다. 그러나 검증 실패 **54/92건**이 학습에서 전량 실패한 모델 ID 세 개에 속했고, 이를 제외한 사후 분석에서는 후보 Brier가 기준선보다 높았다. 사후 추가한 전역률 1 pseudo-count 수축 모델별 빈도도 후보보다 낮은 Brier를 보였다. [같은 서비스의 후행 기간 6,319건·실패 75건](gentd26_request_failure_temporal_findings.md)에서 이 단순 빈도 기준선은 저장된 로지스틱보다 날짜 동일 Brier가 **0.007122→0.006255**로 낮았다. 세 모델을 제외한 6,300건·실패 56건에서도 **0.006983→0.006270**으로 낮았으나, 전체 AP는 로지스틱이 더 높았다(`0.3947` 대 `0.3706`). 기준선은 검증 결과를 보고 정했고 시험의 실패 분포도 이미 일부 열람됐으므로 **새 방법의 고유 이득·독립 일반화·운영 판단 적용은 확인되지 않아 미채택**이다. 최종 실패 상태의 확정 시각·실패 원인·VM 조치 결과는 이 자료에 없다.

공개 모니터링 자료는 다음 5분 대기열 발생의 시간순 시험 580분에서 QPS 모델 Brier `0.0949`를 보였다. 최근 대기열 상태 기준은 `0.2331`이었다. 그러나 실제 발생률 `9.8%`에 비해 평균 예측 위험은 `20.9%`였고, 표본 개수만으로도 상당한 성능이 나와 수집 편향 가능성이 있다. 이 점수는 **스케일 전후의 사용자 지연 개선을 뜻하지 않는다**.

[최근 결과로 위험 확률을 보정한 실험](gentd26_queue_calibration_findings.md)에서는 전체 시험 Brier가 `0.0949→0.0871`로 내려갔다. 하지만 대기열이 실제 발생한 14–20시에는 `0.1366→0.1389`로 악화했고, 평균 정밀도도 `0.292→0.244`로 낮아졌다. 전체 이득은 뒤쪽 대기열 무발생 구간에 집중되어 동적 보정은 채택하지 않는다.

[요청 예측의 비중복 2일 시험 구간 5개](gentd26_walkforward_findings.md)를 합치면 모델 ID별 잔차 보정은 전역 보정보다 p90 pinball 손실이 `2.775→2.637초`로 낮았지만, 전체 포괄률도 `90.0→88.9%`로 낮아졌다. `IMG_2_IMG` 포괄률은 `85.2%`다. 기존 시험 결과를 본 뒤 방법을 설계한 같은 자료의 후향 검증이므로 독립 일반화 증거가 아니다. 이 정책은 p90 상한으로 채택하지 않는다.

[검증 커버리지를 제약한 보정](gentd26_coverage_guard_findings.md)은 같은 5개 구간 합산에서 검증 목표 92%를 적용했을 때 손실 `2.693초`, 전체 포괄률 `92.2%`, `IMG_2_IMG` `90.8%`, `M0003` `90.1%`를 보였다. 그러나 12월 1일 시작 구간의 전체 포괄률은 `86.5%`이고 목표·지원 문턱 자체도 기존 시험 진단 후 정한 탐색 가설이다. 합산 수치만으로 기간별 상한을 보장할 수 없어 운영 정책 채택은 보류한다.

[검증을 시간순으로 다시 나눠 보류 여부를 정한 실험](gentd26_selective_guard_findings.md)에서도 90% 상한을 안정적으로 확보하지 못했다. 최근 검증 포괄률을 확인하는 규칙은 전체 13,415건 중 2,841건만 수락했는데, 12월 7일 수락 요청의 포괄률은 `85.4%`였다. `IMG_2_IMG`는 1,103건 중 8건만 수락했고 `M0003`은 전부 보류했다. 이 보류 규칙도 운영 판단으로 채택하지 않는다.

[BurstGPT 양수 라벨 요청 103만 건의 별도 시간순 시험](burstgpt_observed_duration_findings.md)에서는 모델별 최근 잔차가 전역 보정보다 7개 블록 모두에서 pinball 손실을 낮췄고, 검증 여유값 적용 후 관측 부분집합 포괄률은 `94.1%`였다. 하지만 시험 블록의 양수 라벨 비율은 `18.8–82.9%`였으므로 전체 요청 기준 독립 재현성 증거가 아니다. 이는 LLM 요청 지연 절차의 연구 가설만 뒷받침하며 VM 증감의 효용을 평가하지 않는다.

[SwissAI 후속 탐색](swissai_exploratory_findings.md)은 원래 독립 검증의 자료 품질 실패를 그대로 둔 채, 요청 건수로 고른 뒤 기간의 양수 종료시간 1,385만 건에 수행했다. 모델별 잔차 보정은 전역 보정보다 p90 pinball 손실이 `4.490→4.743초`로 높았고 24개 블록 중 12개에서만 이겼다. 점수를 보기 전에 고정한 직접 최근 완료시간 p90 기준선의 손실은 `4.152초`로 더 낮았다. 다만 직접 기준선의 전체 포괄률은 `81.7%`, 검증 여유값 방법도 24개 블록 중 8개에서 90% 미만이었다. 따라서 기존 절차의 독립 일반화나 운영용 p90 상한은 입증되지 않았다.

[MaaS 상대 QPS 실험](maas_trace_findings.md)에서는 결정 시점 이후의 관측값을 학습·선택에 쓰지 않고, 1시간 예측의 전체 MAE가 현재값 지속 `0.0458`에서 최근 수준으로 전날 패턴을 보정한 방법 `0.0335`로 낮아졌다. [4개 비중복 시험일의 응용별 감사](maas_robustness_findings.md)에서도 보정법은 전체 `0.0391`, 현재값 지속은 `0.0619`였지만 App2에서는 보정법이 더 나빴다. 6·12시간의 **요청이 있는 시간**에는 전날 같은 시간 기준보다 나빴고, 공개 사례는 세 응용·일주일뿐이다. Ridge 회귀도 단순 기준보다 나빴다. 부하 예측의 탐색 자료로만 사용한다.

공개 [Alibaba MaaS 인스턴스 5분 GPU 계측](maas_instance_risk_findings.md)은 21개 Parquet·1억 4,091만 행을 모두 감사하고 고정 ID 표본 146만 행을 시간순 평가했다. 과거·미래 계측이 유효하게 연결되는 비율은 학습 47.1%, 검증 46.6%, 시험 52.3%였다. 시험 217,672개 판단의 30분 GPU 고사용률 위험에서, 검증으로 고른 최근 3창 임계값 조건부 기준선 Brier는 `0.006128`, 학습 로지스틱은 `0.059147`이었다. 원래 [사전 성공 기준](maas_instance_risk_protocol.md)의 네 성능 조건은 모두 실패했다. 현재 정상 상태의 신규 초과 1,899건에 대해서도 기준선이 더 정확했다. 원자료에 GPU 메모리 사용률 100% 초과 행 0.038%가 있고 공개 설명으로 원인을 확인하지 못했다. 범위 밖 제외 규칙을 적용했지만 규약의 별도 중단 문장과 해석이 충돌할 수 있어 점수는 탐색 결과로만 보고한다. 이 결과는 기존 운영 상태에서의 **위험 입력** 평가이고 실제 `SCALE_OUT/IN` 행동 효과 검증은 아니다.

이 실패 뒤 별도로 고정한 [MaaS 상태별·결측 인식 후속 탐색](maas_state_followup_findings.md)은 완전 창·현재 정상 53,513건에서 기존 선택 기준선 대비 Brier `0.020702→0.019403`(상대 6.28%)으로 사전 **탐색** 기준을 충족했다. 그러나 같은 확대 학습 자료의 새 단일 모델 Brier `0.019285`가 상태별 모델보다 낮았다. 점수를 본 뒤 추가한 현재 정상 전용 단순 Beta 기준선은 `0.020339`로 상태별 모델의 이득이 4.60%여서 5%에 못 미친다. 과거 부분결측·현재 정상층은 관측 위험률 44.83%로 완전 창 3.55%와 크게 달랐고 정답 관측률·ID 구성도 달랐다. 같은 주 시험일을 재사용했고 실제 스케일 명령 정답도 없으므로 이 결과는 상태·계측 품질이 **위험 입력 후보**임을 보여 주는 탐색으로만 남긴다.

[SwissAI 활성 모델의 다음 10분 요청량 탐색](swissai_demand_findings.md)은 두 모델의 학습 12,426개, 검증 3,039개, 시험 3,428개 판단을 시간순 평가했다. 완료 뒤 1시간이 지나 사용 가능한 피드백을 추가한 분위수 모델의 두 모델 균등 평균 시험 pinball 손실은 `1,614.081건`으로, 도착량만 쓴 모델 `1,594.655건`보다 1.22% 높았다. 검증에서 선택한 직전 10분 요청 수 지속 기준선은 `779.609건`이었다. 완료 피드백 방법은 네 개 완전 시험 주 모두에서 졌고 모델별 p90 포괄률도 90%보다 낮았다. 이 결과도 수요 예측의 탐색이며 실제 VM 수·스케일 명령 효과를 입증하지 않는다. 확인된 큰 수요 규모 변화에 대응하려는 [상대 수요 후속 규약](swissai_scale_adaptive_protocol.md)은 2025-08-16 이후 보류 기간의 결과를 열기 전에 별도로 고정했다. 그러나 두 모델 중 하나가 새 기간에 적격 판단 134개·양수 18개뿐이라 [사전 품질 게이트에서 중단](swissai_scale_adaptive_gate_failure.md)했다. 상대 수요 방법의 보류 시험 점수는 계산하지 않았다.

[SwissAI 요청의 기록상 `ERROR` 위험 실험](swissai_error_risk_findings.md)은 완료 후 1시간이 지난 과거 상태만 입력에 넣고, 모델별 최근 오류·도착량과 지원범위 게이트를 고정한 뒤 736,928건을 시험했다. HGB Brier는 검증 선택 최근 전역 오류율의 `0.228107`보다 낮은 `0.137778`이었지만, 다섯 7일 블록 중 세 블록에서만 이겨 사전 네 블록 기준에 미달했다. 평균 위험은 관측 오류율보다 **9.58%p 낮았고**, 99.82%의 요청이 학습에 없던 모델 ID였다. 지원범위 게이트를 붙인 혼합 점수는 `0.146081`로 게이트 없는 학습기보다 악화했다. 따라서 두 방법 모두 판단 모듈에 채택하지 않는다. `ERROR`의 원인과 실제 스케일 조치의 결과는 이 로그에서 알 수 없다.

[Microsoft Philly GPU 위험 평가](philly_gpu_risk_findings.md)는 2017년 DNN 학습 클러스터 GPU 추적에서 80% 미만인 현재 상태의 30분 고사용률 사건을 예측했다. 사전 동결 규약에 따른 완전 관측 시험 217,750건에서 검증 선택 단순 기준선 Brier `0.067942`보다 학습 모델 `0.054683`이 19.52% 낮았고, 고정 시험 반구간 모두에서 이겼다. 하지만 같은 입력의 단일 모델 Brier `0.054578`이 상태별 모델보다 낮았고, 부분결측 시험 건수는 0이라 관측 품질 성분은 검증하지 못했다. 따라서 **학습한 위험 신호의 제한적 유용성**은 확인했지만 상태별·결측 인식이라는 방법 자체의 고유 이득은 입증되지 않았다. 실제 `SCALE_OUT/IN` 명령의 효용도 이 자료로 평가할 수 없다.

이 기존 결과를 보고 선택한 통합 모델을 [Philly의 서로 겹치지 않는 기계에서 후속 확인](philly_machine_holdout_findings.md)했다. 새 기계 47대 중 주 시험층이 있는 37대·741,597건에서 Brier는 고정 Beta 기준선 `0.089879`보다 학습 모델 `0.077783`이 **13.46% 낮았다**. 두 반구간, 기계 단위 재표집 구간, AP와 일별 상위 5% 경보 recall이 모두 사전 기준을 충족했다. 37대 중 5대에서는 악화됐고 부분결측층은 이번에도 0건이다. 이는 같은 클러스터·같은 2017년 12월의 다른 기계로 위험 확률이 전이된 결과이며 사업자·시기·응용 서비스로의 일반화나 VM 조치 효과는 아니다. 현재 SQLite의 `max_rss_kib`는 장수명 프로세스 누적 고수위이므로 독립적인 응용 RAM 요구량 정답으로 학습하지 않는다.

[Philly 동결 모델의 연구용 위험 신호 API](philly_gpu_risk_signal_api.md)는 같은 GPU 슬롯의 완전한 과거 5분 창 세 개와 시점·출처 선언을 검사한 뒤, 저장된 통합 모델과 Beta 기준선의 다음 30분 고사용률 확률만 반환한다. 모델·원본·코드 해시가 다르면 예측 전에 중단한다. 저장된 holdout 후보·예측 한 행과 두 확률이 정확히 일치했으며 새 시험 점수는 계산하지 않았다. 분별 계측과 선언된 수신 시각의 진위는 호출자가 보장해야 하고, 결과는 VM 형상이나 스케일 행동 승인이 아니다.

위 확률을 경보 판단으로 바꾸는 [연속 확인 상태 규칙의 별도 탐색](philly_alert_state_machine_exploratory_no_go.md)은 실패했다. 개발 16기계에서 정답을 보지 않고 기준선과 비슷한 경보량을 내도록 정한 임계값을 이미 공개된 다른 37기계에 적용하면, 단발 위험 경보보다 발행 건수가 **19.13% 많고** 실제 고사용률 시작 사건 탐지율은 **57.92%→44.92%**로 낮았다. 위험 확률의 검증 성공을 연속 확인 정책의 성공으로 넘겨 해석하지 않는다.

이 47대의 12월 결과를 개발 자료로 삼아, 각 기계의 12월 이전 완결 사건으로 확률을 교정하고 앞선 기간의 이득이 재현된 기계에만 적용하는 [시간 검증 게이트](philly_machine_calibration_findings.md)를 만들었다. 개발 자료의 기계 동일 가중 Brier는 기존 통합 모델 `0.069491`에서 `0.068578`로 줄었지만 행 Brier와 AP는 악화했다. 값을 열기 전에 규약을 고정한 새 해시 구간의 주 시험층 33기계·599,752건에서는 행 Brier가 `0.109416→0.109163`(0.23% 감소)에 그쳤고, 기계 재표집 95% 구간은 0을 포함했으며 후반 달력 구간은 악화했다. [사후 점수 분해](philly_machine_calibration_posthoc_diagnosis.md)에서는 교정 적용 9기계의 후반기 사건률 하락과 기계 간 경보 순위 악화를 확인했다. 사전 채택 기준인 행 Brier 5% 개선을 포함한 공동 게이트가 실패했으므로 **기계별 교정은 채택하지 않는다**. 기존 통합 위험 모델도 여전히 실제 스케일 조치의 효과를 예측하는 모델은 아니다.

[SwissAI 유휴 모델의 10분 내 재도착 위험](swissai_idle_return_findings.md)은 경희대 `SCALE_IN` 보류 판단에 쓸 별도 신호로 학습했다. 5분 유휴 상태의 고정 시험 845건에서 로지스틱 Brier `0.214223`은 검증 선택 모델별 경험적 재도착률 `0.222405`보다 **3.68% 낮았지만**, 사전 채택 하한 5%를 넘지 못했다. 네 완전 주 중 세 주에서 이겼으나 충분한 시험 표본이 있는 모델별 균등 평균은 기준선보다 나빴다. 전체 845건 중 322건은 정답 창에 전역 요청이 없어 수집 공백 여부도 알 수 없다. 따라서 학습기를 운영 판단에 추가하지 않고 단순 기준선을 연구용 참조로 남긴다. 이 결과는 실제 VM 축소·복구 효과를 측정한 것이 아니다.

[같은 SwissAI 서비스의 후행 점수 동결 탐색](swissai_idle_return_post_findings.md)에서는 기존 로지스틱을 완료된 모델별 재요청 결과에 고정 수축한 혼합식의 Brier가 `0.223085`로 경험적 기준선 `0.225165`와 로지스틱 `0.226553`보다 낮았다. 그러나 1,266건/양성 443건에서 상대 개선은 각각 **0.92%·1.53%**였고 지원 충분 5개 블록 중 두 기준선을 모두 이긴 블록은 **0개**였다. 사전 채택 기준을 통과하지 않아 혼합기를 추가하지 않는다. 정답 창의 서비스 전체 요청도 없는 464건은 기록 공백 여부를 확인할 수 없다. 실제 VM `SCALE_IN` 효과 정답은 여전히 없다.

[Philly 기계 전체 유휴 뒤 2시간 내 GPU 재활성화 연구](philly_idle_rebound_validation_no_go.md)는 개발군 30분 유휴 표본을 학습 6,345건·검증 4,839건으로 구성했다. 로지스틱의 최선 검증 Brier **0.050831**이 학습 전체 재활성화율을 수축한 Beta 기준선 **0.046015**보다 **10.47% 높아** 검증에서 중단했다. 후행 날짜의 적격성만 집계하고 예측 성능은 계산하지 않았으며, 미사용 기계군의 이 새 라벨은 열지 않았다. 이는 축소 명령 효과가 아닌 관측 사용률 신호 실험이다.

[지연 정답을 반영한 Philly 후속 탐색](philly_idle_rebound_adaptive_v3_validation_no_go.md)은 입력만으로 선택한 2시간 간격 앵커 1,240건에서 만기된 정답만 이용했다. 지원량 문턱을 통과한 검증 4,839건에서 제안 확률의 Brier **0.045143**은 고정 Beta **0.046015**보다 1.895% 낮았으나 사전 5% 기준에 못 미쳤고, 기계별 단순 적응 기준선 **0.045054**보다 높았다. 기계 동일 가중·두 반구간·재표집·저위험층 조건도 실패해 채택하지 않았다. 후행 12월 행별 정답과 다른 기계의 이 목표 정답은 열지 않았다.

## 추가 검증: 정적 축소 용량과 파이프라인 적재 지연

기존 SQLite의 [GPU 2개→1개 정적 형상 판단](static_scale_in_findings.md)은 주 캠페인의 575개 물리 측정쌍을 모델 전체 제외로 평가했다. 현재 GPU 2개가 생성 목표를 충족한 357개 중 GPU 1개도 충족한 작업은 249개, 실패한 작업은 108개였다. donor 교차검증으로 여유를 고른 단순 비율 규칙은 안전 승인 232개·잘못 승인 14개, 정적 특징 학습기는 **240개·8개**였다. 현재 GPU 계측을 더하면 239개·8개로 결정 이득이 없었다. Qwen에서 정적 학습의 승인 38개 중 5개가 잘못됐고, 추가 입력 캠페인에서 단순 규칙보다 악화된 사례가 있어 자동 축소 판단으로 채택하지 않는다. **GPU 1개 실행은 575쌍 모두 GPU 2개보다 앞서 측정됐으므로** 시간순 Scale-in 재연이나 인과적 전환 효과가 아니다.

공개 [GenTD26 파이프라인 적재 지연](gentd26_update_latency_findings.md)은 사전 5분 계측·이력으로 마지막 2,924개 기록의 p90을 예측했다. 상태 추가 회귀의 pinball 손실 `2,607.17ms`는 검증 선택 경험적 기준선 `2,820.29ms`보다 7.56% 낮았지만, 이력 전용 회귀 `2,634.82ms` 대비 이득은 1.05%라 [사전 2% 기준](gentd26_update_latency_protocol.md)을 충족하지 못했다. 원본에 업데이트 명령 시각이 없어 `t−5분` 특징의 `t`는 미래 기록 시각을 조건으로 삼는다. 따라서 이 시험은 온라인 UPDATE 판단기가 호출될 시점을 검증하지 못하며, 학습기를 채택하지 않는다.

[GenTD26 파이프라인 응답시간의 별도 적격성 감사](gentd26_pipeline_inference_support_no_go.md)는 고정 시점 다음 30분 p90 라벨을 검토했다. 한 날짜 22.8시간·34,421행에서 시간순 후반 시험의 적격 컨테이너 창은 최소 10개 미래 표본 기준 **7개**뿐이고, 10분 창은 **0개**다. 순수 추론시간 파일과 같은 키로 결합한 6,111쌍 중 6,084쌍은 파이프라인 값이 더 작아 두 지표를 빼서 적재 오버헤드 정답을 만들 수도 없다. 이 자료로 새 모델 학습은 열지 않는다.

## 추가 검증: 요청 출력량과 공개 자원 추적

[BurstGPT 출력 토큰 요구량 실험](burstgpt_output_tokens_findings.md)은 입력 토큰이 양수인 495만 요청을 시간순으로 나누고, 요청 시점의 모델·호출 유형·입력 토큰만으로 출력 토큰 p90을 학습했다. 검증 603,725건의 일별 동일 가중 pinball 손실에서 고정 HGB 모델이 여섯 후보 중 가장 낮아 [시험 전에 선택을 고정](burstgpt_output_tokens_selection_frozen.md)했다. 하지만 시험 836,144건에서 포괄률은 **69.61%**로 명목 90%보다 낮았다. 최근 7일의 호출 유형·입력 길이별 경험적 p90은 사후 비교에서 손실이 낮았으나 포괄률 **86.08%**로 역시 상한 채택 기준에 못 미쳤다. 뒤쪽 GPT-4 API 출력 길이가 크게 변한 것이 주요 원인이다. 출력 토큰 수는 GPU 메모리·노드 수·스케일 효과의 라벨이 아니므로 요구사항 분석의 불안정한 연구 신호로만 남긴다.

[SwissAI의 별도 출력 토큰 학습](swissai_output_tokens_validation_no_go.md)은 요청에 제출된 생성 파라미터와 완료 후 1시간이 지나 가용한 모델별 출력 이력을 사용했다. 학습 후보 HGB는 247,802건으로 적합했고, 검증 212,296건에서 7일 블록 동일 가중 p90 pinball 손실이 최근 모델별 경험적 p90 `344.514`보다 높은 `383.798`이었다. 모델별 피복률도 두 곳에서 사전 하한 85% 아래여서 **미채택**했고 시험 점수는 열지 않았다. 이 자료는 `DEFAULT`·출력 관측 요청에 조건부이며 원본 전체 요청의 출력 미관측 비율이 22.9%다. 다른 서비스의 학습 결과를 합쳐 GPU·VM 요구 형상이나 실제 스케일 효과로 바꾸지 않는다.

이 사후 규칙을 바꾸지 않고 [같은 서비스의 앞선 기간 `_1/_2`에서 재평가](burstgpt_12_output_tokens_findings.md)했다. `_1` day 0–59의 1,389,856건으로 고정 학습하고 `_2` day 61–120의 3,784,215건을 시험했다. 최근 코호트×입력 길이 구간 p90은 최근 코호트 p90보다 동일 일 가중 pinball 손실이 **31.319→28.877토큰(7.80% 감소)**이어서 사전 상대 손실 기준을 통과했다. 그러나 전체 포괄률은 **82.90%**, GPT-4 API 코호트는 **73.54%**로 사전 안전 상한 기준에 실패했다. 미래 기간 `_3`의 사후 분석에서 고른 규칙을 과거 기간에 적용한 **역방향 동일 서비스 재현**이므로 독립 서비스 또는 전향 배포 검증으로 해석하지 않는다. 이 규칙도 실제 인프라 형상 판단에는 채택하지 않는다.

[BurstGPT `Conversation log`의 미래 1시간 입력 토큰량 검증](burstgpt_input_demand_validation_no_go.md)은 상대일 225–264의 모델별 934시간만 적합하고 265–284의 모델별 480시간만 채점했다. 학습 분위수 HGB의 집단 동일 가중 pinball 손실은 검증 선택 전날 같은 시간 기준선 **6,901.853→6,180.628**로 낮았으나, ChatGPT/GPT-4 피복률 **84.17%/81.46%**가 사전 85% 조건에 미달했다. 학습기는 **미채택**, 상대일 285–334의 시간별 시험 채점은 **중단**했다. 로그 무기록은 실제 무부하와 구분할 수 없고, 토큰량은 GPU·VM 필요 형상의 정답이 아니다.

이 실패 이후 사전 고정한 [30일 적합·10일 보정 후속](burstgpt_input_demand_v2_validation_no_go.md)은 각 집단 694시간 적합·239시간 보정으로 검증 동일 가중 pinball 손실을 **6,152.008**로 낮췄다. 하지만 GPT-4 피복률이 **398/480시간(82.92%)**으로 85% 문턱에 10시간 부족했다. ChatGPT는 418/480시간(87.08%)이었다. 이 후속도 **미채택**이며 시험 50일의 시간별 목표는 열지 않았다. v1 검증을 이미 보고 설계했으므로 이 검증은 탐색 결과다.

[같은 대화 로그의 미래 1시간 출력 토큰 합계 후향 탐색](burstgpt_output_demand_validation_no_go.md)은 입력 합계 및 요청별 출력 길이와 별도 라벨을 학습했다. 집단 동일 가중 검증 pinball은 전날 같은 시간 기준선 **1,485.291→학습기 1,284.764**로 낮고 20일 중 16일 우세했으나, ChatGPT/GPT-4 피복률 **82.08%/82.50%**가 [점수 전 85% 기준](burstgpt_output_demand_protocol.md)에 미달해 **미채택**이다. 상대일 285–334의 시간별 시험 출력 합계는 열지 않았다. 이 과제는 같은 원본의 출력 분포를 이미 본 뒤 설계한 탐색이고, 출력 토큰 합계는 GPU·VM 수나 조치 효과의 정답이 아니다.

다른 서비스의 [Azure 코딩 요청 7일 자료](azure_code_output_tokens_findings.md)에서는 입력 길이 조건부 분위수 원리를 **새로 학습**해 3일·9,476,819건을 시간순 평가했다. 최근 길이 구간 p90은 모든 시험일 포괄률이 90% 이상이었고 최근 전체 p90보다 손실이 낮았지만, 같은 길이 구간의 정적 p90보다 동일 일 가중 손실이 **11.594884→11.595461토큰**으로 아주 조금 높았다. 사전 성공 기준은 실패했으며 최근 이력 갱신의 추가 이득을 주장하지 않는다. 이는 BurstGPT 학습 모델의 무보정 외부 전이 시험이 아니다. Azure에는 모델 ID·하드웨어·사용자 SLO·행동 결과가 없다.

[Google 2011 범용 작업의 CPU·RAM 실험](google_2011_observed_resource_findings.md)은 `00050/00200/00400` 조각을 학습·검증·시험으로 고정하고 기존 배정 아래 30분 관측 최대값만 예측했다. 시험 6,447개 task·49개 job에서 CPU HGB의 job 균등 손실은 검증 선택 비학습 기준선 `0.03254→0.01952`로 감소했지만 job 균등 피복률 **0.8379**가 사전 0.85 기준에 미달했다. RAM은 검증에서 원래 요청값을 선택했고 HGB 피복률은 **0.6563**이었다. 사전 학습 모델 개선 게이트는 실패했다. 생존·관측 가능한 작업만 포함되고 한 job이 시험 task의 59.8%를 차지한다. 따라서 이 결과를 AI-App의 최소 안전 CPU·RAM 형상으로 해석하지 않는다.

[Google 2011의 새 `00450` 시간 조각](google_2011_joint_envelope_findings.md)에서는 같은 CPU HGB와 RAM 원 요청을 job 동일 가중 **CPU·RAM 동시 피복 90%**에 맞춰 보정했다. 4,921 task·57 job의 동시 피복은 학습 모델 94.25%·원 요청 보정 기준선 94.02%였고, 평균 `log1p(CPU 상한)+log1p(RAM 상한)`은 17.3% 작았다. 이는 실제 비용 절감률이 아니다. CPU q90 pinball은 `0.03217→0.03271`로 악화해 사전 채택 기준을 통과하지 못했다. 두 조각 모두 일반 Borg 작업의 기존 배정 아래 관측값이며, AI-App 자원 요구량·배포 판단의 정답이 아니다.

[같은 Google 사건 조각의 배정 지연 라벨 감사](google_2011_placement_delay_feasibility.md)에서는 제출 뒤 10분 내 미배정 task가 학습·검증·시험 조각에서 `1,339/235/393개`였지만 독립 job은 각각 **7/2/3개**에 불과했다. 5초·30초 문턱도 시험 조각의 미배정 사건이 일부 job에 집중됐다. 신규 배정 지연 예측 모델은 학습하지 않는다. 이 사건은 AI-App VM 생성·삭제나 배포 후 SLO 결과가 아니다.

[GenTD26 서빙 컨테이너의 30분 관측 GPU 메모리 피크](gentd26_gpu_memory_peak_findings.md)는 이전 60분 계측만 사용하고 보류 컨테이너 28개·3,032건을 시험했다. 시험 전에 고른 메모리 이력 모델의 p90 pinball 손실은 `0.669 GiB`로, 검증 선택 기준선 `0.785 GiB`보다 **14.7% 낮아 사전 연구 게이트를 통과**했다. 그러나 검증에서 선택되지 않은 4시간 피크 기준선은 `0.688 GiB`였고, 모델과의 컨테이너 재표집 차이는 불확실했다. 현재 피크보다 2GiB 이상 높은 미래 관측 195건의 포괄률은 **55.4%**였다. 약 23시간의 한 서비스 자료이고 GPU 용량·OOM·형상 변경 결과가 없어 요구 GPU 메모리나 `SCALE_OUT/IN` 승인에 적용하지 않는다.

[Google 2011 사건·사용량 조각 진단](google_2011_resource_feasibility.md)은 엄격한 1시간 연속 관측 에피소드가 세 시점에 124/95/248개뿐이고, 해당 job 수도 11/9/11개임을 보였다. Google의 범용 task 사용량은 기존 요청·생존 조건의 영향을 받으므로 최소 안전 CPU/RAM의 정답으로 쓰지 않는다. [Alibaba GPU v2026 시간순 표본](alibaba_gpu_temporal_feasibility.md)도 현재 선택한 날짜에서 메모리 변화와 GPU 압박 사례가 부족해 모델 학습을 중단했다. 최소 형상·배포 효과 학습에는 응용·형상·사용자 결과가 연결된 별도 자료를 요구한다.

## 이어서 필요한 자료와 검증

추가 [H100/vLLM 시작 실험의 단계별 준비시간 학습](h100_readiness_eta_findings.md)은 Qwen3 모델 크기 하나씩을 통째로 제외해 200회 시작 기록을 평가했다. 학습기는 첫 단계별 p90 기준선보다 낮은 손실을 냈지만, 점수 뒤 별도로 비교한 모델 크기 직선·잔차 p90 기준선에는 뒤졌다. 4B의 준비시간 피복률도 낮아 기본 판단기에 채택하지 않는다. 이 자료에는 실패한 배포·VM 생성·단계 로그의 수신 시각·후속 사용자 SLO가 없어 실제 스케일 효과를 제공하지 않는다.

실제 판단 메커니즘을 평가하려면 응용·버전 ID, 요청 생성·완료 시각, 사용자 SLO, 동시 부하, 배포된 VM/GPU/CPU/메모리 형상, 배포·업데이트·스케일 명령과 완료 시각, 전후 사용자 지연·오류율·비용을 하나의 시각축으로 연결해야 한다. 기존 플랫폼 식별자와 시각 규칙을 반영해 [연구 데이터 계약 초안](scale_effect_data_contract_v1.md)에 필수 사건·기관별 제공 범위·누출 방지 검사를 적고, [버전형 JSONL 사건 검증기](scale_action_events_v0_1_0.md)로 연결 누락·역순 시각·모호한 재시도를 거부하도록 했다. 이 검증기의 적격 플래그는 출처가 선언한 기록의 구조적 연결일 뿐이며, 비교군·동시 부하 정보가 없는 현재 버전은 인과적 효과 학습을 허용하지 않는다. 같은 응용을 여러 날짜와 자원 형상에서 관측하고, 정책이 개입한 구간과 비교 구간을 확보해야 효과를 구분할 수 있다. 이 자료가 생길 때까지 외부 추적의 위험 점수와 로컬 정적 벤치마크를 실제 `DEPLOY/UPDATE/SCALE_OUT/SCALE_IN` 자동 승인기로 연결하지 않는다.

[공개 스케일 조치 자료 감사](public_scale_action_dataset_audit.md)에서는 Google 작업 추적과 소형 Kubernetes 자료에 명령·사용자 결과 연결이 없음을 확인했다. Airflow 실험의 자원 예약 이벤트와 후속 작업 기록은 같은 실험 DB에 있지만, [사전 선택한 단일 실험의 수집 가능성 점검](airflow_action_feasibility.md)에서 원본 4.18GB의 전송 시간과 현재 약 11GB 디스크 여유를 확인했다. 작은 공식 요약 CSV 22개에는 사건 시각·자원 ID가 없고, 원본 DB 압축 앞 8MiB에도 선택 실험의 사건 행이 없다. 실제 사건 수·매칭률은 미측정이다. 이 조치는 기존 Celery worker의 예약 변경이며 AI-App VM 생성·삭제가 아니다. 따라서 공개 자료로 사실적 부하·처리량 예측 방법을 시험하더라도 AI-App 스케일 정책의 효과를 대신 검증할 수 없다.

추가 [소형 공개 자료 감사](public_subgigabyte_action_outcome_audit.md)에서는 1.3MB PAX Cassandra ZIP의 온라인 노드 수 변화 58회와 같은 실험의 YCSB 기록이 시각상 연결됨을 확인했다. 후속 [사전 관측 적격성 게이트](pax_transition_gate_findings.md)에서는 이전·새 노드 수 표본 사이 간격이 **58건 모두 120초 상한을 초과**해 전후 효과 비교를 중단했다. 실제 명령 시각도 없다. 이 자료는 데이터 결합·관측 지연 진단에는 쓸 수 있지만 조치 효과나 AI GPU VM 정책의 학습·검증 근거는 아니다. [약 948MB OpenStack Monasca 원본의 1MiB 접두부 감사](ucc2021_action_outcome_join_feasibility.md)는 같은 실행의 서버 시작 시각과 요청별 지연을 확인했다. 하지만 공개 내보내기에서 조치 명령 ID·발행 시각은 확인되지 않았고 전체 원본은 수집하지 않았으므로 조치·요청 행의 실제 결합은 여전히 미검증이다.

[PAX의 관측 공백을 제외한 후속 적격성 감사](pax_transition_gap_bracket_v2_findings.md)에서도 58건 중 전후 관측·클라이언트 안정성을 만족한 변화는 6건(증가 1, 감소 5)으로 사전 최소 10건·양방향 각 3건 기준을 충족하지 못했다. **v2 게이트를 판단할 때** YCSB 처리량·응답시간 값은 읽지 않았다. 이후 별도 점검에서 결과 열을 열람했으므로 같은 PAX 원본의 향후 시험을 블라인드라고 주장하지 않는다.

[추가 공개 AI 추론·오토스케일 자료 감사](public_ai_autoscaling_dataset_followup.md)에서 HAS-GPU의 18개 실행·요청 61,021건과 관측 GPU quota 변화를 찾았다. [원본 시계·권리·표본 게이트](has_gpu_training_gate.md)는 요청 기록만 사용하는 단기 지연 p95의 후향 탐색을 허용하지만, GPU 집계 열의 의미와 GPU-요청 시계 동기화가 불명확해 첫 학습 입력에서는 GPU 열을 제외한다. 발행 조치·Ready 시각이 없어 실제 Scale-out/in 효과 학습도 불가능하다. [IOG의 온라인 LLM 추론 벤치마크](iog_llm_inference_benchmark_feasibility.md)는 동일 RTX 4090에서 GPU 수를 비교할 3개 모델·15개 부하 묶음을 제공한다. KHU SQLite와 모델·GPU가 겹치지 않고 배치/온라인 지표가 달라 기존 저장 모델의 외부 정확도 시험은 아니다. [다음 연구 우선순위](next_research_priority_2026_09_28.md)는 이 자료들을 별도 과제로만 다룬다.

IOG의 [GPU 2→4 상대 반응 후향 학습](iog_gpu24_response_findings.md)은 모델 전체 제외에서 요청 처리율 평균 절대 로그오차가 Ridge `0.0520`, 현재 GPU2 측정값 유지 `0.0617`이었다. 그러나 TTFT p95는 Ridge `1.1548`, 유지 `0.6610`으로 세 모델 모두 악화했다. 처리율의 작은 이득과 지연의 역효과가 공존해 형상 추천 학습기로 채택하지 않는다. 이는 같은 날의 세 DeepSeek-R1-Distill 모델에서 수행한 탐색이며 KHU 형상의 독립 검증이나 VM 스케일 조치 평가는 아니다.

HAS-GPU의 [요청 기록만 이용한 30초 미래 지연 p95 평가](has_gpu_request_p95_30s_findings.md)는 18실행에서 과거·미래 각 100요청 이상인 비중첩 창 121개를 선정하고 BERT·ResNet·ConvNeXt·MobileNet을 각각 통째로 제외했다. 계열 동일 가중 평균 절대 로그오차는 최근 p95 유지 `0.395`, 고정 Ridge `0.738`이었고 20% 초과 과소예측률도 `8.9%→24.6%`로 악화했다. 원본 요청 시계만 사용해 GPU 상태와의 정렬 가정을 피했지만, 이 학습기 역시 채택하지 않는다. 원본은 한 실험 환경의 완료 요청만 담고 실제 스케일 명령·Ready·대체 조치 결과가 없다.

담당 항목을 다시 나누어 [요구사항 분석의 새 정답](sqlite_requirement_analysis_new_task_feasibility.md)과 [실제 배포·스케일 조치의 정답](scale_decision_feasibility.md)을 원본 SQLite에서 검사했다. 7개 DB의 9,591회 실행에는 등록 요청에서 필요 VM 형상으로 이어지는 정답이나 실제 조치·완료·사용자 결과가 없었다. 따라서 두 지도학습 목표는 열지 않는다. 대신 동일 작업의 SLO만 바뀌는 오프라인 평가에서는 8개 형상 예측을 재사용할 수 있어, 후자의 보고서에 정확한 출력 동등성과 계산 시간의 사전 검증 규약을 고정했다.

저장된 Extra Trees를 이용한 [오프라인 8후보 형상 평가기](gpu_shape_assessment_v1.md)는 모델·원본 해시와 학습 scikit-learn 버전을 확인하고, 지원 범위 안의 후보만 일괄 예측한다. 예시의 시연용 배치 지연 `≤3ms`·요청 `≥600건/초` 기준에서는 GPU 복제본 2개·CPU affinity 2코어가 선택됐다. 결과는 한 호스트의 이미 알려진 모델에 대한 보정되지 않은 벤치마크 예측이다. VM 노드 수나 실제 배포·스케일 행동을 출력하지 않는다. [연구 결과와 Go 명세 사이의 경계](research_to_deployment_spec_boundary.md)를 따로 기록했다.

2026-09-29에는 평가기 최상위 입력의 가격 같은 미지원 제약을 조용히 무시하고 형상을 선택하던 경로를 수정했다. 이제 허용 필드 세 개 외의 필드와 필수 필드 누락은 채점 전에 `ABSTAIN`한다. 단건·다건·마이크로배치·연구 증거 경로의 정상 출력 동등성도 확인했다. 별도 [저장 모델 선택 사후 감사](saved_gpu_shape_decision_audit_findings.md)에서는 원 생성 SLO의 시험 90작업 중 54건을 선택해 54건 모두 관측 성공했지만, 동일 실측에 요청/초 목표를 1.25배 적용한 합성 질의에서는 잘못 승인한 4건이 있었다. 따라서 원 목표의 관측 오승인 0건은 사용자 SLO 안전성이나 목표 변경 시의 안전성을 뜻하지 않는다.

소수 측정 연구의 [지연·처리량 공동 잔차 전이](cross_metric_anchor_transfer_findings.md)도 모델·BERT 계열 전체 제외로 재학습·평가했다. 대상당 같은 기준 측정 8회, 외부 조건 0회에서 공유 encoder 8모델의 미측정 셀 지연 MALE는 독립 지표 전이 `0.238524→0.226669`로 낮아졌지만 요청/초 MALE는 `0.120705→0.126337`로 높아졌다. 원 생성 SLO 성공 선택은 `298→295건`, 오승인은 `13→14건`이었다. 새 입력 조건 두 캠페인에서도 처리량이 kernel·Ridge 기준선에 못 미쳤다. 사후 탐색의 고정 채택 게이트에 실패해 이 공동 전이를 **미채택**한다. 다출력 공분산 자체의 신규성이나 실제 VM 스케일 효과를 주장하지 않는다.

[버전형 연구 증거 JSON](gpu_shape_evidence_v0.1.0_findings.md)은 이 8후보 결과와 원 요청의 일치, 후보별 상태·보류 이유·단위, 생성 시각과 해시 출처를 검증·보존한다. 예시에서 명시한 목표 출처는 `research_demo`이며 실제 사용자 SLO로 표시하지 않는다. [Go 계약 대조](research_evidence_contract_feasibility.md)에 따라 GPU 복제본·CPU affinity를 VM 노드·할당량으로 치환하거나 연구 상태를 배포·스케일 행동으로 전달하지 않는다.

[v0.2 증거의 엄격 재실행 검증](gpu_shape_evidence_v0.2.0_findings.md)은 원 요청과 고정 모델·자료를 다시 대조한다. 한 GPU 후보의 예측값을 변조해 자체 일관성을 맞춘 증거는 구조 검사만으로 통과하지만 재실행에서는 거절됐다. 원 요청·고정 아티팩트가 수신자에게 있어야 하고, 호출자가 선언한 목표 출처의 진위는 이 방법만으로 확인되지 않는다.

[원스텝 증거 생성 경로](gpu_shape_evidence_direct_generation.md)는 저장 모델과 원본 추출 파일의 해시를 확인한 프로세스에서 곧바로 8후보 평가와 증거 직렬화를 수행한다. 기존 별도 결과 JSON의 검증 표시를 외부 입력으로 받지 않으며, 예시 증거와 전체 JSON·ID가 같았다. 모델 해시 오류에서는 새 결과 파일이 생성되지 않는다. 이는 증거 생성 경로의 일관성 개선이며 추정의 정확도나 배포 권한을 늘리지 않는다.

[요구 신호 API](requirement_signal_api_feasibility.md)는 반환 하드웨어 프로필의 공유 참조와 Python의 `bool==int` 동등성 때문에 지원하지 않는 CPU/GPU 입력이 통과할 수 있던 오류를 수정했다. 현재는 결과를 호출자가 바꾸어도 다음 요청의 지원 범위가 변하지 않고, 프로필 필드의 JSON 타입이 정확히 맞지 않으면 두 연구 신호를 보류한다.

동일 작업의 SLO만 바뀔 때 [후보별 예측 재사용 실험](slo_reuse_findings.md)은 사전 선정 45작업군·1,125개 합성 질의에서 **전체 출력 불일치 0건**, 25질의 묶음 중앙 시간 **556.08→31.08ms(17.89배)**를 기록했다. 첫 질의 p95 증가는 3.36%로 사전 허용 20% 이내였다. 이는 반복 SLO 평가의 로컬 CPU 계산 비용이며, 실제 SLO 재질의 빈도·배포 시간·Scale-out/in 효과를 측정한 결과가 아니다.

[서로 다른 작업 조건 묶음의 v2 계산 최적화](cross_workload_microbatch_v2_findings.md)는 요청별 유효성 검사와 후보 격자 키를 한 번만 계산했다. 고정 45격자·1,125개 합성 질의의 중앙 전체 처리 시간은 v1 `505.251→303.448ms`였고, 주 캠페인 575격자·4,600후보의 최종 JSON은 기존 단건 평가기와 전부 같았다. 저장된 성능 모델과 실제 조치 판단은 바꾸지 않았다.

[정적 평가기 보정 재점검](static_assessor_calibration_gap.md)에서는 기존 GPU 정책의 그룹 단위 conformal 검증과 중복되는 부분을 확인했다. 현재 저장 모델의 train 396작업군에는 그 정책의 보정 99작업군이 이미 포함돼 있어, 기존 보정 상수를 현재 평가기에 옮기면 누수가 생긴다. 기존 시험의 점예측도 54건 선택·위반 0건이라 같은 자료에서 새 보정의 위험 감소를 확인할 수 없다. 새 보정 학습은 열지 않았다. 대신 [반복 SLO 계산을 호출 범위 API로 분리](slo_reuse_many_findings.md)했다. 새 API는 단건 평가와 5,625쌍 전체 출력이 같았고, 25질의 묶음 중앙 함수 시간은 **487.01→24.19ms(20.13배)**였다. 이는 앞선 실험용 캐시 측정과 분리한 직접 호출 결과다.

[요구 신호 지원 조건의 사후 감사](requirement_signal_gate_impact.md)는 기존 SQLite의 모델 전체 제외 예측을 사용했다. GPU 예약 피크는 주 캠페인 575회 중 답변이 **512→384회**로 줄고, 남은 모델의 평균 90% 상한 포괄률도 **95.12→93.75%**로 내려갔다. 새 입력·공간표본 조건에서는 GPU 피크 답변이 **0/18·0/44회**였다. 로컬 적재시간은 주 캠페인 남은 384회에서 평균 절대 로그오차가 **0.246→0.229**로 낮아졌다. 이는 저장된 최종 모델의 새 앱 검증이 아닌 fold 예측의 지원 범위 분석이다. 사전 등록 파라미터 메타데이터도 이 자료에 없어 운영 판단기로 승격하지 않는다.

[MLPerf Inference v5.0 공개 결과 감사](external_inference_benchmark_feasibility.md)에서는 공식 26.4MiB 요약과 같은 실행의 Server 로그에서 처리량·p95가 존재함을 확인했다. 그러나 KHU 자료와 정확히 같은 모델 ID·GPU 제품의 교집합은 각각 0개이고, 지연·처리량의 의미도 다르다. GPU 수만 달라지는 엄격한 동일 스택 비교도 3묶음·7결과에 그쳐 현재 저장 모델의 외부 검증이나 VM scale 효과 학습에는 사용하지 않는다.

[연구 증거 JSON 계약 감사](research_evidence_contract_feasibility.md)는 배치 벤치마크 형상 추정과 Go의 실제 VM·배포 명세를 별도 객체로 유지하도록 했다. [요구 신호 모델 감사](requirement_signal_api_feasibility.md)는 조건부 관측 GPU 예약 피크와 로컬 캐시 적재시간을 독립 연구 신호로 출력할 수 있음을 확인했다. 조건부 VRAM 모델은 현재 형상 평가기에 알려진 9개 학습 모델을 거부한다. 전역 VRAM 상한 모델은 같은 모델에 숫자를 낼 수 있어도 저장 모델의 학습 내 단일 GPU1·CPU2 관측 피크 추정이므로 8후보 메모리 적합성으로 결합하지 않는다.

[새 SQLite 정답의 CPU 작업량 학습](replica_cpu_work_findings_v1.md)에서는 GPU1 완료 뒤 GPU2의 두 자식 프로세스가 같은 AI 작업을 수행한 2,300짝을 감사했다. encoder 8모델 전체 제외 2,048짝에서 HGB의 모델 균등 평균 절대 로그오차는 `0.04558`, Ridge 대조군은 `0.05627`이었다. 그러나 한 모델에서 HGB가 Ridge보다 `2.13배` 나빠 사전 게이트를 실패했고 연구용 예측기로 미채택했다. 원본은 한 호스트의 정적 프로파일링 CPU초로, 실제 VM 최소 코어·조치 준비·사용자 SLO를 제공하지 않는다. Google 2019 자료의 일반 Borg 부하 예측 시험은 로컬 복제 작업량보다 담당 항목에 덜 직접적이므로 별도 과제로 평가한다.

[CPU 작업량의 별도 로컬 캠페인 시험](replica_cpu_work_external_campaign_findings_v1.md)은 기존 donor 모델을 수정하지 않고 `live` encoder 반복 550짝과 `diverse-cpu-matrix` encoder 40짝에 적용했다. 평균 오차는 HGB가 Ridge보다 낮았지만, `diverse`의 작은 BERT에서 HGB/Ridge 오차가 `1.32배`로 고정 안정성 게이트를 다시 어겼다. 같은 호스트·모델의 이전 캠페인이므로 새 모델 검증으로 승격하지 않고 미채택을 유지한다.

[Google 2019 cell-b 독립 셀 시험](google_2019_cell_b_adaptive_findings_v1.md)은 공식 JSON 사건 4개를 모두 검증하고, 특수 시각을 뺀 8,926개 완전 5분 bin에서 cell-a 학습기의 온라인 보정을 평가했다. 8,626개 시험 bin의 MAE는 최근 1시간 평균 `48.63`, 보정 학습기 `47.84`로 개선률 1.61%가 사전 2% 게이트에 못 미쳤다. 전날 같은 5분의 MAE `39.90`이 더 낮았다. 이것은 다른 Borg 셀의 일반 JOB 제출량 검증일 뿐 AI-App 사용자 요청·실제 스케일 명령 결과와 연결되지 않는다.

[cell-a 특수 시각 감사](google_2019_cell_a_sentinel_impact.md)는 기존 동결 추출이 `time=0` 추적 전 JOB을 제외하지 않았음을 밝혔다. 그 때문에 정상시각 SUBMIT이 있는 두 ID를 train bin 1227·1528에서 각각 한 번 놓쳤고, 첫 완전 bin과 시간 분할 경계도 수정이 필요하다. 기존 cell-a·cell-b 모델 점수는 과거 동결 규칙의 결과로 보존하고, 수정 시계열로 학습한 결과처럼 해석하지 않는다.

[정상시각 cell-a 재추출](google_2019_cell_a_sentinel_impact.md)은 원본 10개를 다시 검증·스트리밍해 bin `3–8928`의 시계열을 별도 산출물로 만들었다. 이를 이미 노출된 cell-b와 함께 개발 자료로 쓰고, 계절 잔차 보정의 창 2개·셀 균등 MAE 학습 계수 `0.85`를 [cell-g 원본 열람 전 동결](google_2019_cell_g_seasonal_protocol_v1.md)했다. [독립 cell-g 시험](google_2019_cell_g_seasonal_findings_v1.md)에서는 MAE가 전날 같은 시각 `76.38`보다 보정식 `103.06 JOB/5분`으로 커졌고, 최근 1시간 평균 `63.42`가 가장 낮았다. 사전 오차·고부하 게이트가 실패해 미채택한다. 이 실패는 한 달의 다른 Borg 셀에 대한 이전성 한계이며 AI-App 조치 효과 검증은 아니다.

이미 노출된 [cell-a·b·g의 초기 3일 선택 개발 분석](google_2019_burnin_gate_development_v1.md)은 a·g에서 최근 1시간 평균, b에서 계절식을 골랐지만, g의 고부하 603건은 경보 0건이었다. 이를 반영해 [cell-e 원본 열람 전 동결한 선택 규약](google_2019_cell_e_selector_protocol_v1.md)에 절대 고부하 재현율 20% 하한을 넣었다. [독립 cell-e 평가](google_2019_cell_e_selector_findings_v1.md)에서는 초기 564개 bin에서 최근 1시간 평균을 골랐고 이후 8,062개 bin의 MAE `50.68`은 계절식 `75.09`보다 낮았다. 하지만 고부하 재현율은 `18/301=5.98%`여서 게이트를 실패했다. 선택기는 최근 1시간 평균과 같은 예측을 냈으므로 추가 정확도도 없었다. 이 결과 역시 일반 Borg JOB 제출의 보조 신호로만 읽고 AI-App Scale-out/in 정책으로 채택하지 않는다.

[SwissAI Qwen 입력 접두 재사용 연구](swissai_qwen_full_prefix_support_no_go.md)는 공식 버킷 원본 3,994,435행을 검증하고 중복 ID·완전 블록 없음 등을 제외한 3,127,766행을 시간순으로 정리했다. 미래 60분에 같은 **전체** 접두가 나타나는지 학습하기 전 고정한 지원량 기준에서, 검증 양성은 30,800건 중 **2,204건**으로 1만 건 하한에 못 미쳤다. 따라서 접두 재사용 모델과 캐시 입장 정책의 검증·시험 점수는 만들지 않았다. 이 자료의 접두 블록은 실제 GPU KV 메모리·TTFT나 VM 배포·스케일 결과가 아니며, 학습형 접두 캐시 자체는 선행 연구가 있다. 같은 원본의 다른 접두 목표는 실패를 본 뒤 설계하는 사후 탐색으로만 다룬다.

[접두 깊이 1·2·4·8·16·32블록의 사후 지원량 감사](swissai_qwen_prefix_depth_support_exploratory.md)에서는 잠금 시험을 열지 않고 같은 검증 30,800행만 검사했다. 깊이 1의 재사용 음성은 35건, 가장 균형에 가까운 깊이 16도 양성/음성이 26,809/2,632건이고 양·음성 각각 100건인 날짜는 2일뿐이었다. 따라서 짧은 접두의 이진 재사용을 새 학습 과제로 즉시 승격하지 않는다.
