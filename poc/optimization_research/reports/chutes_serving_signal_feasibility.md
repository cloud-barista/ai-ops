# Chutes 공개 서빙 추적 자료: 인스턴스별 첫 토큰 지연 신호의 적격성

2026-09-29. 결론은 **첫 토큰 지연(TTFT) 위험 예측 자료로 추가 감사 진행**, **실제 Scale-out/in 조치의 감독학습 정답으로는 부적격**이다. 이 문서는 원자료의 일부를 확인한 *학습 전* 타당성 검사다.

## 출처와 확인한 범위

[Harvard MadSys 공개 허브](https://data.freeinference.org/)와 [공식 데이터 카드](https://huggingface.co/datasets/harvardMadsys/chutes_metadata)는 Chutes의 6,122,413,756개 요청, 9,174개 모델을 설명한다. 카드상 요청 추적은 시간순 45개 Parquet 샤드, 약 94GB다. `chute_models`는 4,558개 메타데이터 행이며 모델명과 *지원 가능한* GPU 목록을 제공한다. 데이터 카드는 CC BY 4.0이다. [저자 저장소](https://github.com/HarvardMadSys/chutes_workload)는 `instance_id`를 서빙 인스턴스로, 시각을 원래 날짜에서 정규화한 상대 시각으로 설명한다. `user_id`는 분기마다 다시 익명화되므로 이번 분석에 사용하지 않았다.

전체 추적은 받지 않았다. 고정 revision `85722e694bf7bb8a5a5ccdf70424fa5998372467`에서 모델 메타데이터(199,541 bytes)와 **2개 row group만**, 필요한 10열로 추출했다. 하나는 중간 구간의 샤드 22/row group 68, 다른 하나는 후반 구간의 샤드 44/row group 65다. 각각 1,001,472행이고 표본 파일은 14.3/15.7MB다. 원본 파일 크기·해시, 추출한 표본 해시와 재생성 명령은 자료 설명 (`../data/external/chutes_metadata/README.md`)에 있고, 정량 감사는 [`audit.json`](../artifacts/chutes_metadata_sample_v1/audit.json)에 있다. 두 시간 조각은 임의 추출이 아니며 전체 결측률 또는 운영 분포를 추정하지 않는다.

| 검사 | 중간 구간 | 후반 구간 |
| --- | ---: | ---: |
| 상대 시각 범위 | 1970-06-26 08:39~10:10 | 1970-12-27 22:13~28 00:36 |
| 요청 / 관측 모델 / 요청을 처리한 인스턴스 ID | 1,001,472 / 131 / 772 | 1,001,472 / 137 / 258 |
| 스트리밍 요청 / 유효 TTFT | 388,384 / 378,326 | 567,658 / 522,581 |
| `ct` 기록 / 양수 | 0 / 0 | 939,081 / 828,907 |
| 완전한 5분 구간에서 유효 TTFT ≥100인 모델·구간 | 530 | 535 |
| 위 구간 중 관측 인스턴스 ≥2 | 530 | 246 |
| 30분 입력 이력 확보 뒤 유효 TTFT ≥100인 모델·구간 | 357 | 427 |
| 위 구간 중 관측 인스턴스 ≥2 | 357 | 192 |

유효 TTFT는 `chat_stream`/`completion_stream`이고, TTFT와 완료 시각이 있으며 `0 < TTFT ≤ 완료−시작+1ms`인 요청으로 한정했다. 후반 표본에는 TTFT가 완료 소요시간보다 1ms 넘게 긴 요청이 **9,088건** 있어 제외했다. 두 표본에서 스트리밍 요청 중 유효 TTFT가 빠진 수는 10,058/45,077건이다. 추적에는 실패 상태·원인이 없으므로 누락을 정상 응답이나 실패 중 하나로 해석하지 않는다. 후반 표본의 `ct`는 토큰 수가 있는 행에서 모두 `0≤ct≤it`였다. 5분 지원량은 같은 약 1.5시간/2.4시간 내 다수 모델을 합산한 **모델·구간 수**라 독립된 1,065개 기간이나 장기 일반화 증거가 아니다.

## 경희대 담당 항목에서 새로 가능한 학습 목표

**후보: 인스턴스·캐시 관측을 이용한 모델별 다음 5분의 TTFT 90백분위 예측.** 매 5분 결정 시각 `t`에 동일 모델의 `[t,t+5분)` 유효 스트리밍 요청 TTFT의 경험적 p90을 정답으로 둔다. 단일 구간에 유효 요청이 100건 이상일 때만 평가한다. 과거 `[t−30분,t)`에 시작하고 **`t`까지 완료된** 요청만 특징에 쓰면, 당시 알 수 없던 TTFT·출력 토큰·캐시 결과가 입력에 들어가지 않는다. 과거 도착 수·입력 토큰·TTFT, 인스턴스별 요청 분포와 활성 인스턴스 수를 사용한다. 캐시 입력 `ct`는 공개 카드에 따라 마지막 약 10주로만 제한하고, 실제 측정 결측 여부를 시간순 전체에서 다시 확인한다. 원본의 익명 시각을 실제 요일·날짜로 해석하거나 현재 가격·지원 GPU 목록을 과거 자원 상태로 넣지 않는다.

이 목표는 저장소의 [SwissAI 다음 10분 도착량 예측](swissai_scale_adaptive_protocol.md)이나 [GenTD26 요청 실행시간 예측](gentd26_request_latency_findings.md)과 결과 변수가 다르다. 특히 Chutes는 **요청별 TTFT와 처리 인스턴스 ID를 같은 행에서** 제공한다. 최근 5분 p90 지속, 최근 30분 경험 p90, 도착량·토큰만 쓰는 모델, 여기에 과거 인스턴스 분산·캐시 비율을 추가한 모델을 동일한 미래 기간에 비교할 수 있다. 표본에서 30분 이력 뒤에도 후보 정답 구간은 357/427개이고 그중 여러 인스턴스가 보이는 구간은 357/192개다. 이는 후속 자료 추출을 시도할 근거일 뿐, 모델의 성능 향상이나 새 방법의 학술적 독창성에 대한 증거는 아니다.

다음 단계에서는 캐시가 기록된 **연속된** 후반 구간을 분리 추출해 품질·빈 구간·모델별 지원량을 검사한다. 점수를 보기 전에 학습/검증/시험의 시간 경계, 최소 지원량과 모델 균등 점수, 앞의 세 기준선 및 실패 문턱을 고정해야 한다. 중간·후반의 떨어진 두 표본을 이어 붙여 시계열로 학습하거나 이 표본의 점수를 독립 시험 점수로 제출해서는 안 된다.

## 스케일·형상 정답 여부

`instance_id`는 **요청이 도착한 서빙 인스턴스**만 나타낸다. 유휴 상태의 전체 인스턴스 목록, VM/GPU 형상·수량, 생성·삭제 명령, Ready 시각, 가격, 조치의 이유나 비교 조치가 없다. 관측 인스턴스 수는 실제 배포 replica 수의 하한에 가까운 *관측량*이며 최적 노드 수가 아니다. `completed_at`은 요청 완료이지 VM 준비 완료가 아니다. `ttft`는 이미 시행된 라우팅·용량 정책 아래의 결과이므로 특정 `SCALE_OUT/IN`의 반사실 효과를 식별하지 못한다. `supported_gpus`는 지원 가능한 선택지이고 요청별 실제 GPU를 알려주지 않는다. 따라서 **배포 형상 추천의 실제 GPU 라벨**이나 `DEPLOY/UPDATE/SCALE_OUT/SCALE_IN/KEEP`의 감독학습 라벨로 사용하지 않는다. 활용 범위는 요구사항 분석과 배포·스케일 판단에 제공할 *지연 위험 입력 신호*까지다.

재현: `python scripts/audit_chutes_sample.py`(기존 검증 표본 감사), `python scripts/audit_chutes_sample.py --fetch`(고정 revision에서 정확히 두 row group 재추출). 두 명령 모두 모델을 학습하지 않는다.
