# 다음 연구 후보: 유휴 AI 모델의 요청 재도착 위험

2026-09-28 현재 **자료 적격성만 확인한 실행 계획**이다. 이 과제의 학습기나 시험 점수는 아직 만들지 않았다. 경희대의 `SCALE_IN` 판단에 앞서, 모델에 요청이 5분간 없을 때 **이후 10분 안에 요청이 다시 오는 확률**을 추정한다. 이는 수요 신호이며, 실제 VM 축소의 비용·준비 지연·사용자 SLO 개선을 뜻하지 않는다.

## 자료와 라벨

- [SwissAI 공식 데이터셋](https://huggingface.co/datasets/eth-easl/swissai-serving-trace)의 고정 revision `c3dd66602b564ce189f7db81115620413e646cd5`에서 만든 시각순 Parquet (`../data/external/swissai_serving_trace/requests_sorted.parquet`)을 쓴다. 로컬 SHA256은 `d5c2bf4cc038f936a9713f8fc7c0430703ddd1c03ed0518fb65aaf68e160997b`로 [전량 감사](swissai_trace_full_audit.md)와 일치한다. 원본은 16,329,237요청·214개 모델 문자열이다. 이름이 `\N`인 미상 모델은 제외하고, 산출물에는 모델 원문 대신 해시 별칭을 쓴다. [출처·재배포 경계](../data/external/swissai_serving_trace/SOURCE.md)를 따른다.
- 모델별 요청을 `created_utc_us` 순으로 놓고, 요청 시각 `s`에서 `t=s+5분`까지 다음 요청이 오지 않았으면 **유휴 간격당 판단 1회**를 만든다. 정답은 첫 후속 요청이 `[t,t+10분)`에 도착하면 1, 아니면 0이다. 그 모델의 마지막 기록 뒤 유휴도 추적의 전체 관측 끝까지 정답 창이 들어오면 음성 에피소드로 포함한다. 같은 모델의 여러 간격은 서로 의존하므로 모델·주 단위로 결과를 묶는다. 분할 끝을 가로지르는 정답 창은 버린다.
- 결정 시각 직전 10분에 서비스 전체의 도착 요청이 있어야 한다. **이번 사건 기반 판단에서는 마지막 대상 모델 요청이 정확히 5분 전이므로 이 조건은 항상 참이며, 추가 품질 보호가 되지 않는다.** 서비스 전체에서 이미 **관측된** 6시간 이상 공백이 끝난 뒤 120분은 보류한다. 공백의 끝을 미래에 보고 그 전 판단을 소급 삭제하지 않는다. 이 조건은 기존 [요청량 규약](swissai_demand_protocol.md)의 가용성 규칙과 [구현](../scripts/evaluate_swissai_demand.py)을 따른다. 수집기 생존 신호가 없어, 조건을 통과해도 긴 무요청이 실제 무부하인지 기록 누락인지 완전히 구분할 수 없다.

## 읽기 전용 표본 진단과 분할 제안

`created_utc_us`와 `model` 두 열만 읽어 위 규칙으로 **라벨 건수만** 재계수했다. 아래 수치는 성능 점수가 아니다. 마지막 요청 뒤의 관측 가능한 유휴 에피소드를 포함하고 `\N`을 제외한다.

| 유휴 기준 | 학습 2025-01-16~06-16 | 검증 06-16~07-16 | 시험 07-16~08-16 | 후행 08-16~10-16 |
| --- | ---: | ---: | ---: | ---: |
| **5분** | **2,237 / 양성 846** | **780 / 양성 335** | **845 / 양성 276** | **1,266 / 양성 443** |
| 15분 | 422 / 98 | 181 / 38 | 248 / 38 | 360 / 66 |
| 30분 | 307 / 28 | 120 / 22 | 178 / 17 | 239 / 29 |

따라서 첫 실험은 **5분 유휴**로 제한한다. 15·30분 결과는 라벨 지지 수만 남기고 학습 성능을 주장하지 않는다. 5분 시험의 네 완전한 7일 블록은 각각 판단/양성 `123/32`, `239/84`, `217/60`, `157/42`이고 마지막 3일은 `109/58`이다. 시험에서 100개 이상 에피소드와 양·음성 각각 10개 이상인 모델은 4개다. 그러나 학습 ≥20개와 검증 ≥10개를 모두 충족한 모델을 시험에서 보면 512개/양성 190개로, 그 대부분이 두 모델에 집중된다. 따라서 전체·기존 모델·처음 나타난 모델을 따로 보고, 모델별 평균과 주별 점수를 함께 제시한다.

시험 845개 중 322개는 정답 창 10분 동안 **서비스 전체의 요청도 0건**이다. 수집기 생존 신호가 없으므로 그 음성이 실제 무요청인지 기록 공백인지 불확실하다. 미래의 전역 요청이 하나 이상 있는 523개/양성 276개를 별도 민감도 분석에 쓰되, 이는 **사후에 정답과 연결된 사건을 조건으로 고른 집단**이다. 모든 양성이 이 집단에 남아 사건률이 `276/845`에서 `276/523`으로 바뀌므로 온라인 판단 가능 표본, 주 점수 또는 결측 음성의 보정치로 쓰지 않는다. 같은 집단 안에서 방법끼리만 비교하고, 전체와 결론이 갈리면 수집 품질을 해결하기 전에는 사용을 보류한다.

이 날짜는 이전 [SwissAI 요청량 연구](swissai_demand_findings.md)에 사용됐다. 이번 재도착 라벨은 그 연구의 ‘활성 모델 다음 10분 요청 수 p90’과 다르지만, 같은 공개 서비스·기간을 이미 탐색했다. 유휴 기준도 위 표의 라벨 지지 수를 본 뒤 선택했다. 이후 점수는 **후향적 탐색 결과**이며 새로운 독립 서비스 검증이라고 부르지 않는다. 후행 기간은 모델 교체로 주별 지지 수가 고르지 않아 보조 시간순 진단으로만 남긴다.

## 학습·비교·중단 기준

1. 입력은 `t` 이전의 해당 모델·전체 서비스 도착 건수(30·120분), 해당 모델의 과거 완료된 요청 간격, UTC 시간대, 과거 적격 유휴 에피소드의 결과만 허용한다. 과거 결과는 해당 `t_j+10분 < t`가 확인됐을 때만 쓴다. 미래 도착, 완료 상태·시간, 출력 토큰, 미래의 모델 생존 여부는 입력에서 제외한다. 모델 선택과 계수 적합은 학습·검증에서만 하고 시험 예측 전에 고정한다.
2. 강한 기준선은 (a) 정답 창이 이미 끝난 과거 유휴 에피소드로 구한 모델별 `P(다음 도착<15분 | 이미 5분 유휴)`를 학습 전역 사전 확률로 수축한 경험적 위험, (b) 분당 과거 요청률 `λ`의 Poisson 예측 `1−exp(−10λ)`이다. 학습 로지스틱과 작은 부스팅 모델은 같은 특징·표본에서 검증 Brier로 하나를 고른다. 모델 ID가 처음 나타나면 경험적 위험은 전역 사전 확률로 돌아가고 이 경우를 별도 보고한다.
3. 원본·축약 파일 해시, 정렬, 시각 단위, 겹치는 에피소드와 정답 창 경계를 먼저 검사한다. 주 시험의 적격성 게이트는 학습 ≥1,000건/양성 ≥100건, 검증·시험 각각 ≥500건/양성·음성 각 ≥100건, 시험의 완전 7일 블록 ≥4개(블록마다 ≥100건·양성 ≥20건)다. 위 읽기 전용 계수에서는 통과한다. 구현 계수가 다르거나 품질 게이트가 실패하면 점수 계산 전 원인을 조사한다.
4. 1차 지표는 시험 Brier 점수다. 로그손실·캘리브레이션·모델별 Brier와 주별 차이를 함께 기록하고, 불확실성은 요청 행이 아닌 **모델·주 블록**을 단위로 본다. 탐색적 채택 기준은 두 단순 기준선 각각보다 Brier가 상대 5% 이상 낮고, 네 완전한 시험 주 중 최소 3주에서 둘 다보다 낮은 것이다. 실패하면 단순 기준선을 남기고 이 자료에 맞춘 재조정을 새 독립 검증처럼 제시하지 않는다.

## 현재 SQLite와 연결 범위

기존 [SQLite 감사](untapped_signal_audit.md)의 `SCALE_OUT/IN`은 실제 명령 전후가 아닌 정적 복제 측정의 재표현이라 이 재도착 라벨과 합칠 수 없다. RAM 요구 학습 대안으로 보이는 `max_rss_kib`도 **개별 응용 실행의 독립 피크가 아니다**. 원본 수집기 (`/path/to/aiops/khu_policy_agent/live_collector.py:1892`)는 장수명 프로세스의 `resource.getrusage(RUSAGE_SELF).ru_maxrss`를 기록한다. 고정 SQLite 추출 (`../data/audit_v1/measurements.parquet`)(SHA256 `b7bba7963e8a309b6a8502a1d98eefb150476b1381ec016beeb68cbf63fae906`)의 local-exhaustive 단일 replica 성공 2,556개를 실행 순으로 보면 감소 0회·동일 2,465회·증가 90회다. 앞선 실행의 고수위가 뒤 실행에 남으므로 이를 모델별 최소 VM RAM 정답으로 학습하지 않는다. CUDA 예약 피크는 수집기가 매 작업 전 `reset_peak_memory_stats()`를 호출하므로 이 RSS 문제를 그대로 적용하지 않는다.

실제 `SCALE_IN` 결정을 검증하려면 응용별 replica/VM 수, 축소 명령·완료 시각, 복귀 요청의 지연·실패, 재기동 비용과 비교 기간이 필요하다. 필요한 사건은 [연구 데이터 계약](scale_effect_data_contract_v1.md)에 정리돼 있다.
