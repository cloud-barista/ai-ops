# 정적 GPU 후보 묶음 예측의 최대 격자 수 8→64 비교 규약

2026-09-29. [v4 결과](decision_inference_microbatch_v4_findings.md)와 복사 입력의 프로파일을 확인한 뒤 정했다. v4의 기존 `max_grids=8`은 서로 다른 45개 후보 격자를 **6번** 예측한다. 이 시험은 같은 검증·선택 코드를 쓰면서 한 번에 최대 64개 격자를 예측하도록 하는 **추론 배치 크기 실험**이다. 과거 결과를 보고 설계한 탐색적 계산 최적화다.

## 고정 대상과 비교

- 저장된 SHA-256 고정 ExtraTrees 모델, 추출 Parquet, 분할 manifest와 원래 v4 평가 코드를 사용한다. 모델 적합·특징·요청·SLO 또는 결과 스키마는 바꾸지 않는다.
- 입력: [기존 v4 벤치마크](../scripts/benchmark_gpu_shape_microbatch_v4.py)의 (1) 45개 후보 격자 ×25개 합성 SLO, 같은 객체 공유, (2) 같은 격자·SLO를 별도 객체로 복사, (3) 서로 다른 575개 후보 격자. 같은 순서의 요청에 v4를 `max_grids=8`과 `64`로 호출한다.
- 3개 입력 모두에서 **정규 JSON 전체**, 상태·선택·보류 이유, 호출 결과 수가 같아야 한다. `_predict_once` 호출 수를 기록한다. 합친 큰 예측 호출이 실패할 때 v4의 기존 격자별 재시도 경로가 남아 있어야 한다.
- 모델·Parquet 적재와 첫 완전 호출은 타이머 밖이다. 각 입력에서 고정 시드로 요청 블록과 두 함수 실행 순서를 바꾼 **7쌍**의 wall/CPU 시간을 잰다. 각 쌍의 `8/64` wall 비율 중앙값을 주 속도비로 한다. BLAS/OMP/MKL은 각 한 worker로 제한한다. 입력 생성·출력 정규화는 타이머 밖이다.
- 별도 프로세스에서 peak RSS를 기록한다. 모든 입력에서 `64`의 peak RSS가 `8`보다 20 MiB 넘게 높아지면 실패다.

## 채택 기준

세 입력 모두 JSON 전체가 같고, 복사된 1,125질의에서 쌍별 중앙 속도비 **≥1.10**, 공유 입력과 575고유 격자에서 속도비 **≥0.90**, 모든 입력 peak RSS 증가 **≤20 MiB**이면 이 고정 저장 모델의 오프라인 다중 질의 경로에서 `max_grids=64`를 사용한다. 하나라도 실패하면 `8`을 유지한다. 단일 질의·다른 예측 모델·온라인 서비스 지연에는 이 시험의 최적 배치 크기를 외삽하지 않는다.
