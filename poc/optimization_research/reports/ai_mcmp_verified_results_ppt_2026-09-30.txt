AI-MCMP 경희대학교 연구: 개선이 확인된 알고리즘과 결과
PPT 작성용 상세 원고 | 성과 검증 2026-09-30, 개선 계획 보강 2026-10-02

문서의 범위
이 원고는 저장된 코드와 평가 결과 중 비교 기준보다 성능 또는 계산 효율의 개선이 확인된 네 가지 연구 결과만 다룬다. 서로 다른 데이터셋의 개선율을 합산하지 않는다. “우리 방법”은 경희대 연구에서 구성·구현·검증한 방법을 뜻한다. Extra Trees, 로지스틱 회귀, HGB, 로그오즈 보정 자체를 학술적으로 최초 제안했다고 주장하지 않는다.

핵심 요약
1. 정적 인프라 형상 추천: AI 모델·입력·부하·자원 형상에서 배치 지연과 처리량을 예측한 뒤, 두 목표를 동시에 충족할 것으로 예측되는 최소 GPU/CPU 형상을 선택한다. 로컬 시험 90작업 중 54작업을 추천했고 54개 모두 기록된 1회 실측에서 생성 목표를 만족했다. 단순 중앙값 기준선은 42개 추천 중 36개가 만족했다.
2. GPU 고사용률 위험: 최근 GPU 사용률로 30분 내 고사용률 확률을 예측하고, 전날 완료된 결과로 기계 및 GPU 슬롯별 오차를 보정한다. 새로운 37기계에서는 기본 확률 모델의 Brier가 단순 기준선보다 13.46% 낮았고, 별도의 새로운 51기계에서는 슬롯 보정을 더해 강한 기계별 보정 기준선보다 Brier가 추가로 2.63% 낮았다.
3. 짧은 미래 입력 수요: 직전 1시간의 입력 토큰량으로 규모를 정규화한 다음 5분 상대 수요의 90분위를 학습한다. Azure Coding 공개 표본의 후향 시간순 3일 평가에서 가장 강한 단순 기준선보다 pinball 손실이 43.6% 낮았다. 이 개선은 Coding 서비스에 한정된다.
4. 판단 추론 최적화: 동일 형상의 여러 SLO 질의에는 원시 모델 예측을 재사용하고, 서로 다른 형상 격자는 큰 묶음으로 한 번에 예측한다. 동일 형상 25질의의 함수 시간은 487.01→24.19ms(20.13배), 고유 575격자의 64→256 묶음 변경은 747.305→528.949ms(짝별 중앙 1.518배)였다. 결과 JSON은 기존 경로와 같았다.


1. 정적 GPU·CPU 인프라 형상 추천

1-1. 연구 질문과 담당 항목
“응용 모델과 입력 조건이 주어졌을 때 어떤 GPU 복제 수와 CPU affinity 코어 수가 배치 지연·처리량 목표를 만족하는가?”를 다뤘다. 경희대 담당 항목 중 구조화된 응용 요구 신호의 해석과 인프라 형상 추천에 해당한다. 실제 CSP·리전·VM 상품명이나 새 VM 생성은 다루지 않는다.

1-2. 데이터와 정답
- 기존 SQLite 7개에서 총 9,591실행을 진단했고, 이 중 9,445실행을 일반적인 학습 후보로 분류했다. 첫 성능 모델의 주 자료는 local-exhaustive 캠페인의 4,856실행·575개 workload 그룹·9개 모델이다.
- 입력에는 모델 ID/revision, CPU 또는 CUDA 장치, batch 크기, 최대 입력 길이, 동시 요청 수, CPU 스레드·affinity 코어 수, GPU replica 수, 반복 횟수를 사용했다. 실행 이후의 지연·처리량·모니터링 결과를 입력에 섞지 않았다.
- 지도학습 정답은 배치 호출 p95 지연(ms)과 처리 샘플 수/초(examples/sec)다. 요청 처리량으로 판정할 때는 반드시 examples/sec를 batch 크기로 나눈다.
- GPU replica가 2개인 기록의 지연 정답은 더 느린 replica의 배치 p95, 처리량 정답은 두 replica의 합계다. 온라인 사용자 요청의 종단간 지연·처리량과 구분한다.
- 주 GPU 형상 격자는 동일 호스트의 GPU 프로세스 replica 1/2개 × CPU affinity 2/4/8/16코어 = 8후보다. GPU 2개 형상이 VM 2대의 Scale-out이라는 의미는 아니다.

1-3. 비교 방법과 우리 방법
- 기준선: 학습 분할에서 모델 ID×장치별 성능의 로그 중앙값을 예측한다.
- 학습기 후보: Random Forest와 Extra Trees를 같은 검증 분할에서 비교했고, Extra Trees 200개·min_samples_leaf=2·seed=42를 선택했다. 두 양의 정답을 로그값으로 학습하고 예측 뒤 지수 변환했다. 후보 수가 다른 workload 그룹에는 그룹별 같은 총 가중치를 줬다.
- 데이터 분할: 같은 workload의 CPU/GPU·자원 후보 전체를 한 그룹으로 묶어 모델별 train 396그룹, validation 89그룹, test 90그룹으로 나눴다. 같은 작업의 형상 대안이 학습과 시험 양쪽에 섞이지 않게 했다. 학습된 모델/revision·호스트·장치·수치 범위를 벗어나면 예측을 보류(ABSTAIN)한다. 이후 모델·장치별 세부 입력 지원 범위도 추가했다.
- 경희대의 형상 선택 규칙: 후보마다 예측 배치 p95 ≤ 목표 지연, 예측 요청/초 ≥ 목표 요청/초인지 동시에 검사한다. 통과 후보 중 GPU replica 수를 먼저, CPU affinity 코어 수를 다음으로 비교해 가장 작은 후보를 반환한다. 모든 후보가 실패하거나 입력이 미지원이면 보류한다. 연구 평가기의 출력 상태는 RESEARCH_ESTIMATE 또는 ABSTAIN이다.
- 핵심 연구 구성은 “두 성능 지표의 학습 → 응용 조건별 8후보 평가 → 두 목표의 공동 판정 → 최소 형상 선택 및 보류”다. Extra Trees 자체가 새로운 모델 구조라는 주장은 하지 않는다.

1-4. 평가 결과
주 test 760행의 배치 p95 중앙 절대백분율오차는 기준선 73.71% → 학습 모델 16.99%였다. 샘플/초는 66.01% → 10.41%였다. 이 행 단위 예측 결과와 아래 90작업 단위 형상 선택 결과는 다른 지표다.

원래 수집기 생성 목표, GPU test 90작업:
                         학습 모델     모델·장치 중앙값 기준선
추천/승인 작업            54             42
그중 1회 실측 성공        54             36
그중 1회 실측 실패         0              6
실측상 가능한 작업       55             55
실측 최소 형상과 일치     50             36

따라서 동일한 생성 목표에서는 실측 성공 추천이 기준선보다 18작업 많았고, 관측 오승인은 6→0건이었다. 별도 입력 캠페인의 저장 예측 감사에서도 novel-matrix 9/9, space-filling 25/25 추천이 해당 목표를 만족했다. 다만 이후 입력 지원 범위를 더 좁혔으므로 이 별도 캠페인의 역사적 승인 수를 현재 평가기가 그대로 반환한다고 말하지 않는다.

1-5. 수치 해석과 PPT 문장
- 90작업 중 35작업은 실측상 8후보 중 가능 형상이 없고, 32작업은 8후보 전부 가능했다. 일부만 가능한 23작업에서 모델은 22개를 올바르게 선택하고 1개를 보류했다. 따라서 전체 54/54만 보여 주지 말고 문제 난도도 함께 표시한다.
- 원 목표는 실제 사용자가 정한 SLO가 아니라 수집기가 만든 목표다. 요청/초 목표를 1.25배로 강화해 같은 측정을 다시 채점하면 50작업 승인 중 4작업이 실제 목표를 위반했다. 원 목표의 관측 오승인 0건을 운영 안전률 0%로 해석하지 않는다.
- 발표 권장 문장: “동일 호스트·기존 모델의 정적 8형상 연구에서, 배치 성능 예측을 공동 SLO 판정에 연결해 단순 기준선보다 실측 성공 추천을 36개에서 54개로 늘렸다.”


2. GPU 고사용률 위험 확률과 전날 기계·슬롯 보정

2-1. 연구 질문과 담당 항목
“최근 GPU 계측으로 다음 30분의 고사용률 가능성을 예측하고, 기계·GPU 슬롯마다 달라지는 확률 오차를 전날 피드백으로 줄일 수 있는가?”를 다뤘다. 경희대 배포·스케일링 판단에 필요한 운영 위험 신호의 연구다. 이 확률만으로 SCALE_OUT/SCALE_IN 조치를 결정한 실험은 아니다.

2-2. 데이터와 사건 정의
- Microsoft Research Philly DNN 훈련 클러스터의 GPU 사용률 추적을 사용했다. 원본 GPU 행 44,750,640개를 전체 검산하고, 기계 ID가 겹치지 않는 집합을 학습·개발·후속 시험에 사용했다.
- 판단 시점 전에 완료된 5분 GPU 사용률 창 세 개와 현재 상태·추세 등을 입력한다. 정답은 판단 뒤 30분의 여섯 5분 창 중 어느 하나에서 해당 GPU 슬롯의 평균 사용률이 80% 이상인지 여부다.
- 기본 모델의 주 결과는 현재 사용률 80% 미만이고 과거 창이 완전한 판단에 한정한다. 실제 AI-App 요청 지연이나 SLO 위반 라벨은 아니다.
- Brier 점수는 예측 확률 p와 실제 이진 사건 y에 대한 평균 (p−y)^2이며 낮을수록 좋다. Average precision은 위험 순위 품질을 보조로 보여 준다.

2-3. 기본 위험 확률 모델과 우리 방법의 첫 단계
- 기준선은 현재 고사용률 상태와 최근 초과 여부를 묶은 Beta 확률표다.
- 세 과거 창의 사용률, 평균·최대, 최근 추세와 현재 상태에서 30분 고사용률 확률 p0를 만드는 로지스틱 회귀를 학습했다. 이전 시험에서 상태별 분리나 관측 품질 특징의 독립적인 이득은 확인되지 않아, 후속 보정의 기반으로는 통합 모델을 고정했다.
- 기존 기계 21대에서 만든 모델을 새로운 기계 집합에 그대로 적용해 기계 ID 이동의 효과를 확인했다. 이 단계의 우리 기여는 미래 결과 누출을 막는 창 구성, 완전 관측층 구분, 강한 단순 기준선과의 고정 비교, 새 기계 시험이다. 로지스틱 회귀 자체의 신규성은 주장하지 않는다.

새 기계 37대·741,597판단의 결과:
                         Beta 기준선      통합 로지스틱
Brier(낮을수록 좋음)      0.089879         0.077783   상대 13.46% 감소
Average precision        0.457322         0.707340
동일 경보량 상위 5% recall 0.253886         0.296129

37대 중 32대에서 Brier가 낮았고, 기계 단위 2,000회 재표집의 Brier 차(모델−기준선) 95% 백분위 구간은 [-0.017790, -0.007629]였다. 같은 클러스터의 새로운 기계에 대한 결과이며 새 클러스터·AI 추론 서비스 검증은 아니다.

2-4. 전날 기계·GPU 슬롯 잔차 보정: 가장 구체적인 우리 연구 메커니즘
기본 p0가 기계마다 체계적으로 높거나 낮은 확률을 내는 문제를 전날 완료된 정답으로 보정한다. 먼저 기계별 벌점 로그오즈 절편 δ_m을 구하고, 그 뒤 같은 기계 안의 슬롯별 남은 오차 g_{m,s}를 수축해 더한다.

  z = logit(clip(p0, 1e-9, 1-1e-9))
  δ_m : Σ전날[y_i − sigmoid(z_i + δ_m)] − 20·δ_m = 0,
        δ_m은 [-0.5, +0.5]로 제한
  p_machine = sigmoid(z + δ_m)
  g_{m,s} = clip( Σ슬롯[y_i − p_machine_i]
                  / (Σ슬롯[p_machine_i(1−p_machine_i)] + 20), -0.5, +0.5 )
  p_final = sigmoid(z + δ_m + g_{m,s})

계산에는 바로 전날의 기계×GPU 슬롯×시간당 첫 적격 판단 한 건을 쓰고, 30분 정답 창과 결과 전달이 당일 00:00 UTC 전에 끝난 기록만 쓴다. 새 기계나 슬롯에 전날 적격 피드백이 없으면 해당 보정값을 0으로 둔다. 공개 원본에는 실제 피드백 전달 시각이 없어, 시험에서는 정답 창이 끝나는 즉시 전달된다고 가정했다. 플랫폼 중립 계산 모듈 calibrate_day()는 확률과 보정량을 반환하며 VM ID·Manifest·배포 행동은 만들지 않는다.

중간 결과: 전날 기계별 보정은 또 다른 새로운 41기계·685,940판단에서 기존 p0 Brier 0.086988 → 0.082766(상대 4.85% 감소)로 개선됐다. 이 시험에는 후속 슬롯 보정 시험과 다른 기계 집합을 썼다.

최종 슬롯 추가 결과: 새로운 51기계·812,729판단에서 “벌점이 있는 정확한 기계별 절편”을 강한 기준선으로 두고 비교했다.
                         기계별 보정 기준선    기계+슬롯 잔차 보정
Brier(낮을수록 좋음)       0.085786             0.083532   상대 2.63% 추가 감소
기계 동일가중 Brier       0.081152             0.078693
Average precision         0.870159             0.873825

51대 중 44대에서 Brier가 낮았고, 기계 단위 2,000회 재표집의 Brier 차(우리 보정−기준선) 95% 구간은 [-0.003105, -0.001443]이었다. 이 시험의 원래 p0는 0.092431이지만, 슬롯 보정 고유의 기여를 말할 때는 0.085786과 비교해야 한다. 서로 다른 37대·41대·51대 시험의 개선율을 더하지 않는다.

2-5. PPT 문장
“기본 GPU 위험 확률을 전날 기계·슬롯별 피드백으로 보정한 결과, 처음 보는 51기계에서 강한 기계별 보정 기준선 대비 확률오차 Brier를 2.63% 낮췄다.”


3. 다음 5분 입력 토큰 수요 상한 예측

3-1. 연구 질문과 담당 항목
“현재까지 접수된 AI 요청의 입력 토큰량으로 다음 5분의 입력 토큰 예산을 예측할 수 있는가?”를 다뤘다. 경희대의 배포·스케일링 판단에 공급할 수요 입력 신호 후보다. 필요한 GPU 수나 실제 Scale-out 조치 효과를 직접 예측하지 않는다.

3-2. 자료와 시간순 분할
- Azure LLM Coding 공개 요청 표본의 TIMESTAMP와 ContextTokens만 사용했다. 16,803,695요청을 UTC 5분 구간 2,016개로 집계했다. 공개 자료는 전체 생산 요청이 아니라 일부 표본이다.
- 학습은 2024-05-10~12 중 초기 1시간을 제외한 852구간, 개발 검증은 05-13의 288구간, 후향 시간순 평가는 05-14~16의 864구간(날짜별 288)이다. 평가 구간의 미래 값을 특징으로 쓰지 않고, 이미 완료된 이전 구간의 값을 순차 피드백으로 사용했다.
- 이 평가 기간의 일별 집계 일부는 다른 실험에서 이미 열람됐으므로 완전한 블라인드 독립 시험이라고 부르지 않는다.

3-3. 우리 문제 설정과 학습 방법
  y_t = 다음 5분에 기록된 입력 토큰 총량
  m_t = 직전 완료 12구간(1시간)의 y 평균
  r_t = y_t / m_t
  y_hat_t = m_t × max(0, q_hat_0.9(r_t | 과거 특징))

m_t가 1,000토큰 미만이면 비율이 불안정해 보류한다. 특징은 직전 1·2·3·12구간의 정규화 수요, 전날 같은 5분 구간의 상대 수요, 지난 1시간의 최대·90분위, 최근 30분과 그 전 30분의 평균 비율, UTC 시각의 sin/cos, 주말 여부다. 표준 HistGradientBoostingRegressor의 0.9 분위수 손실을 사용했다. 학습 중 각 구간 가중치에 m_t/학습평균(m)을 사용해 “상대 수요” 모델이 “절대 입력 토큰” pinball 손실을 줄이도록 맞췄다. 이는 pinball(y_t, m_t·q_hat)=m_t·pinball(r_t, q_hat)의 관계를 이용한 설계다. HGB 자체의 신규성은 주장하지 않는다.

강한 기준선 네 개는 학습 비율의 가중 전역 90분위, 직전 완료 1시간의 경험적 90분위, 전날 같은 시각 비율, 전날 비율+학습 잔차 90분위다. 평가 지표는 절대 5분 입력 토큰 예산의 0.9 pinball 손실과 경험적 피복률이다. pinball 손실은 목표보다 낮게 예측한 경우에 더 큰 벌점을 주며 작을수록 좋다.

3-4. 결과
Coding의 05-14~16 세 날짜 동일 가중 평균:
  우리 상대 수요 q90 HGB       pinball 418,627
  가장 강한 단순 기준선         pinball 742,048
  상대 손실 감소               43.6%

세 날짜 각각의 우리 방법 피복률은 93.75%, 92.01%, 93.75%였고 사전에 정한 85~95% 범위에 있었다. 세 날짜 모두 그날 최선 기준선보다 pinball이 낮았다. 이 결과는 Coding 표본의 짧은 미래 입력 토큰 상한 예측 개선이다.

적용 경계: 같은 모델을 Conversation 서비스에 그대로 옮긴 후속 평가에서는 최근 1시간 기준선보다 손실이 높았다(348,600 대 335,196). 그래서 범서비스 일반화 성과나 현재 판단기 채택으로 표현하지 않는다. 입력 토큰 예산을 GPU 용량·VM 수로 직접 환산한 실험도 없다.

3-5. PPT 문장
“Azure Coding 공개 표본의 시간순 3일 평가에서, 직전 1시간 규모로 정규화한 90분위 수요 모델은 최선의 단순 예측보다 5분 입력 토큰 예산 손실을 43.6% 줄였다. 서비스 간 전이는 별도 문제로 남는다.”


4. 형상 판단의 추론 비용 최적화

4-1. 문제
응용·8개 후보 형상은 같지만 지연/처리량 목표만 여러 번 바뀌면, 모델은 같은 후보 성능을 반복 예측하게 된다. 서로 다른 작업을 각각 평가할 때도 Extra Trees 예측 호출을 너무 작은 묶음으로 나누면 호출 비용이 커진다. 이는 배포·제어용 판단 로직의 오프라인 계산 비용 문제다.

4-2. 우리 구현 방법
- 동일 형상의 여러 SLO: assess_gpu_shape_many()는 한 호출 안에서 순서까지 같은 8후보의 원시 예측을 재사용한다. 각 요청의 SLO 값은 매번 별도로 검증하고 다시 판정하므로 목표가 달라져도 출력 의미가 유지된다. 캐시는 호출이 끝나면 폐기하며 입력·모델이 바뀐 다음 호출에는 이전 예측을 재사용하지 않는다.
- 여러 서로 다른 형상 격자: 검증을 통과한 여러 8후보 격자를 모아 Extra Trees에 최대 256격자씩 예측 요청한다. 후보·결과 순서를 보존하고 큰 묶음 호출이 실패하면 원래 격자별 예측으로 재시도한다. 최종 연구 경로는 v6, max_grids=256이다.
- 복사된 후보 리스트도 내용·순서·자료형이 안전하게 같을 때에만 검증을 재사용한다. 입력이 잘못됐거나 지원 범위 밖이면 기존 보류 이유를 유지한다. 알고리즘은 학습된 모델·추천 규칙·예측값을 변경하지 않는다.

4-3. 검증 결과
A. 동일 8후보의 25개 합성 SLO 질의, 원래 9모델에서 선택한 45작업 격자:
  매번 단건 평가 함수 시간 중앙값: 487.01ms
  동일 격자 묶음 API 함수 시간 중앙값: 24.19ms
  속도 개선: 20.13배, 예측 호출 25→1회
  전체 응답 5,625쌍의 JSON 불일치: 0건

B. 서로 다른 575격자의 예측 묶음:
  8→64격자: 같은 실행에서 짝지은 시간비 중앙 3.753배, 호출 72→9회
  64→256격자: 별도 실행에서 짝지은 시간비 중앙 1.518배, 호출 9→3회
  64→256의 실제 벽시계 중앙값: 747.305→528.949ms
  출력 JSON: 기존 경로와 정확히 동일; peak RSS 증가도 사전 20MiB 한도 이내

두 속도비는 서로 다른 시점의 별도 벤치마크에서 나왔으므로 곱해 “전체 5.7배”라고 주장하지 않는다. 25질의 묶음과 서로 다른 575격자 묶음도 서로 다른 입력·API 실험이다. 측정에는 모델 적재, 네트워크 왕복, 실제 배포, 온라인 요청 p95가 포함되지 않았다.

4-4. PPT 문장
“같은 후보 성능 예측을 재사용하고 여러 후보 격자를 묶어 호출해, 연구용 형상 평가기의 출력을 유지하면서 오프라인 판단 함수의 계산 시간을 줄였다.”

9. 데이터셋과 모델을 선택한 이유: PPT용 상세 설명

9-0. 먼저 구분할 것: 세 종류의 데이터, 세 종류의 학습, 한 종류의 계산 최적화
이번 네 성과는 하나의 데이터셋·하나의 통합 모델에서 나온 것이 아니다. 각 데이터가 실제로 관측하는 현상과 정답이 다르기 때문에 과제를 분리했다.

연구 A. 로컬 SQLite 벤치마크 → 입력·자원 형상별 배치 성능 회귀 → 정적 GPU/CPU 형상 선택.
연구 B. Philly GPU 시간 추적 → 다음 30분 GPU 고사용률 이진 위험 → 확률 보정.
연구 C. Azure Coding 요청 표본 → 다음 5분 입력 토큰 총량의 90분위 → 수요 예산 신호.
연구 D. 연구 A의 저장 모델·입력 재사용 → 같은 출력으로 판단 함수 계산량 절감. D에서 새 예측 모델을 학습하지 않았다.

이 분리는 데이터의 관측 가능성에 맞춘 것이다. SQLite에는 후보 형상과 실측 배치 성능이 있어 A의 정답을 만들 수 있지만, 장기 GPU 운영 시간열·실제 배포 명령·전후 사용자 SLO가 부족하다. Philly에는 장기 GPU 사용률 시간열이 있어 B의 위험 사건을 정의할 수 있지만 앱별 성능·VM 조치 효과는 없다. Azure에는 요청 시각·입력 토큰이 있어 C의 단기 도착 수요를 만들 수 있지만 GPU 수나 VM 증감의 정답은 없다. 그러므로 B·C의 숫자를 A의 형상 추천 성공률로 합치거나, 네 결과를 실제 자동 배포 정책의 성능으로 설명하지 않는다.

데이터·학습기 빠른 대조
- A: 경희대 기존 SQLite 7개를 진단; 주 학습은 local-exhaustive 4,856실행. 지도 정답은 배치 p95 지연과 examples/sec. 선택 학습기는 Extra Trees 회귀 200개 나무. 형상 선택기는 학습된 예측 두 개와 명시적 공동 목표 규칙.
- B: Microsoft Research Philly DNN 클러스터 GPU 1분 추적. 지도 정답은 다음 30분에 5분 평균 사용률 ≥80%인 창의 존재. 선택 기본 학습기는 통합 L2 로지스틱 회귀. 전날 완료 정답으로 기계·GPU 슬롯별 로그오즈 오차를 보정.
- C: Azure LLM Coding 공개 요청 표본 16,803,695행. 지도 정답은 다음 5분의 표본 입력 ContextTokens 총합. 학습기는 0.9 분위수 HistGradientBoostingRegressor 한 개.
- D: A의 같은 저장 Extra Trees와 8후보 격자. 성능 라벨을 새로 학습하지 않고 동일 예측을 재사용하거나 여러 격자를 한 번에 계산하는 구현 실험.

9-1. A: 로컬 SQLite를 왜 골랐고, 실제로 무엇을 학습했는가

① 원천과 주 자료의 관계
- 기존 수집 결과는 SQLite 7개, 전체 9,591실행이다. 실행 ID 중복은 없었다. 성공·완료·유효한 배치 성능 정답을 만족하는 일반 학습 후보는 9,445실행이다. 제외 146건은 중단 136건과 실패 10건이며, 실패를 임의로 “해당 형상 불가능” 정답으로 바꾸지 않았다.
- 첫 성능 예측과 형상 추천 평가에는 7개를 섞지 않고, 같은 호스트에서 자원 후보를 폭넓게 측정한 khu-hf-local-exhaustive 4,856실행·575 workload 그룹을 주 자료로 사용했다. 그중 CUDA 4,600건, CPU 256건이다. 호스트는 icns이고 기록의 dataset 필드는 operations이다.
- SQLite 감사에서 확인한 캠페인별 규모와 이번 문서에서의 역할은 다음과 같다. “학습 후보”는 정제 기준을 통과했다는 뜻이며, 실제 첫 성능 모델의 학습행 수와 동일하지 않다.

  캠페인                          전체 / 학습 후보     이번 네 성과에서의 역할
  khu-hf-cpu-scaling-local          240 / 240          초기 자료 진단; 주 성능 모델 학습 제외
  khu-hf-diverse-cpu-matrix         210 / 192          CPU 다양성 진단; 주 학습 제외
  khu-hf-live                     2,640 / 2,640        반복 측정 진단; 10 workload 집중
  khu-hf-local-exhaustive         4,856 / 4,856        첫 성능 모델과 정적 형상 선택의 주 자료
  khu-hf-local-novel-matrix         176 / 176          학습 외 입력 조건의 별도 저장 예측 점검
  khu-hf-local-space-filling        384 / 384          학습 외 입력 조건의 별도 저장 예측 점검

- 이 캠페인에 포함된 AI 모델 ID 9개는 google/bert_uncased_L-2_H-128_A-2, google/bert_uncased_L-4_H-256_A-4, google/electra-small-discriminator, albert/albert-base-v2, google/bert_uncased_L-4_H-512_A-8, distilbert/distilbert-base-uncased, google-bert/bert-base-uncased, FacebookAI/roberta-base, Qwen/Qwen2.5-0.5B-Instruct다. 앞의 여덟 모델은 각각 544실행, Qwen은 504실행이다. 이들은 성능을 측정한 “응용 모델”이고, 우리가 학습한 성능 예측기 Extra Trees와 서로 다른 개념이다. 발표 때 이 구분을 먼저 설명하면 “어떤 모델을 썼나”라는 질문의 혼동을 줄일 수 있다.
- 사용한 입력 열은 model_id, model_revision, device, batch_size, max_length, request_concurrency, cpu_threads, cpu_core_limit, replica_count, repeats다. 실행 뒤에만 알 수 있는 지연·처리량 또는 노드 telemetry를 예측 입력으로 쓰지 않았다. 출력 정답은 batch latency_p95_ms와 examples_per_second 두 값이다.

② 왜 local-exhaustive가 첫 연구에 알맞았나
- 목표가 “같은 앱 입력에 대해 GPU replica 수와 CPU affinity 코어 수를 바꾸면 배치 성능이 어떻게 달라지는가”였기 때문이다. GPU 1/2 replica × CPU affinity 2/4/8/16코어의 8후보를 같은 환경에서 비교할 수 있어, 후속 형상 선택 평가에서 관측된 후보별 성능과 예측 선택을 대응시킬 수 있다.
- 다른 SQLite도 양이 많아 보일 수 있지만, live의 2,640행은 독립 workload가 10그룹에 집중됐다. 반복 측정 2,640개를 서로 다른 2,640개 응용 조건으로 세면 평가가 과장된다. remote-216에는 다른 호스트에서 모은 1,085행이 있지만, 첫 문제의 같은 호스트 비교와 섞으면 하드웨어·측정 환경 차이까지 학습해야 한다. novel-matrix 176행, space-filling 384행은 별도 입력 조건 점검에 활용할 수 있지만 주 학습집합 자체를 키우는 용도로 사용하지 않았다.
- CPU는 주 자료의 256건뿐이어서 GPU와 같은 수준으로 검증됐다고 설명하지 않는다. 아래 전체 test 오차에는 CPU가 섞여 있지만, 형상 선택의 주 수치는 GPU 90작업에 대한 것이다. 7개 DB의 전체 9,591건을 모두 Extra Trees에 적합한 것처럼 말하면 안 된다.

③ 왜 Extra Trees였나: 설계 적합성 + 실제 검증 점수
- 이 문제에는 앱 종류·입력 길이·동시성·CPU 코어·replica 사이의 비선형 상호작용이 있다. 표형 자료에서 그 관계를 학습하기 위한 고정 후보로 Random Forest와 Extra Trees를 두고, “모델 ID×장치별 로그 중앙값”을 단순 기준선으로 삼았다. 범주형 열은 one-hot 입력으로, 양의 지연·처리량은 로그 변환한 정답으로 학습했다. 로그 정답은 큰 절대값 몇 건보다 비율 차이에 관심이 있는 평가와 연결된다.
- 둘 다 나무 200개, 최소 잎 표본 2, seed 42로 비교했다. 같은 검증셋의 두 정답에 대한 workload 그룹 동일가중 평균 절대 로그오차를 다시 평균낸 선택 점수는 중앙값 기준선 0.978937, Random Forest 0.192705, Extra Trees 0.192454였다. 가장 낮은 검증 점수라 Extra Trees를 고정했고, 그 뒤 test를 보고 교체하지 않았다.
- Extra Trees와 Random Forest의 선택 점수 차이는 약 0.000252에 불과하다. 따라서 “Extra Trees가 일반적으로 월등하다”는 결론은 없다. 이 연구에서 선택했다는 근거는 동일한 제한 후보·분할·지표에서 소폭 낮았다는 사실이다. 저장 모델 설정은 ExtraTreesRegressor 200 trees, min_samples_leaf=2, max_features=1.0, random_state=42, n_jobs=2다.
- 같은 workload의 8후보와 반복을 train/test 양쪽에 흩뜨리지 않기 위해 그룹 단위로 나눴다: train 396그룹/3,348행, validation 89그룹/748행, test 90그룹/760행. 후보·반복 수가 많은 workload가 학습을 지배하지 않도록 그룹당 총 가중치를 같게 했다. 저장된 모델·장치·수치 지원 범위를 벗어나는 입력에는 ABSTAIN한다.

④ 학습된 성능 모델을 추천 규칙에 연결한 이유
- 모델이 지연 하나만 낮추거나 처리량 하나만 높여도 앱 목표를 만족했다고 할 수 없다. 후보마다 예측 배치 p95 ≤ 생성 목표, 예측 examples/sec ÷ batch_size ≥ 목표 요청/초를 동시에 검사한다. 통과한 후보 중 GPU replica 수, CPU affinity 코어 수 순으로 최소 형상을 고른다.
- 이것은 새 신경망 구조가 아니라 “구조화 응용 조건 → 후보별 두 성능 예측 → 공동 목표 판정 → 최소 자원 선택 또는 보류”라는 경희대의 연구 절차다. SQLite의 batch 지연은 사용자 종단간 요청 지연이 아니고, 2 GPU replica는 VM 2대 생성 이력이 아니다. RAM 최소 요구량이나 실제 GPU 종류·CSP·리전 추천 정답도 이 자료에는 없다.
- 성과 설명은 같은 호스트·같은 AI 모델 종류·기록된 GPU 후보 격자의 정적 선택으로 제한한다. 원 생성 목표의 54/54 성공은 한 번씩 기록된 배치 측정과의 비교이며, 요청률 목표 1.25배의 사후 강화에서는 50승인 중 4건이 위반됐다.

발표자 설명 예시:
“우리는 기존 SQLite 7개를 먼저 진단했습니다. 반복 회차를 독립 작업으로 과장하지 않기 위해, 575개 작업 조건에서 자원 형상이 넓게 측정된 local-exhaustive를 학습에 골랐습니다. BERT·RoBERTa·Qwen 등 9개 앱 모델의 배치 성능을 Extra Trees로 예측했고, Extra Trees는 Random Forest와 중앙값 기준선 중 검증 점수가 가장 낮아서 선택했습니다. 그런 다음 지연과 요청 처리량 목표를 모두 만족할 것으로 예측되는 최소 GPU/CPU 형상을 반환하도록 연결했습니다.”

9-2. B: Philly GPU 추적을 왜 추가했고, 로지스틱 회귀를 왜 썼는가

① 원천과 정답
- SQLite 수집 기간은 2026-09-10~11로 짧고 자원 후보별 배치 실험에 집중돼 있다. “향후 30분에 GPU가 고사용률에 도달하는가”, “기계별 운영 확률이 어긋나는가”를 안정적으로 평가할 장기 GPU 시간열이 부족하다. 이 때문에 Microsoft Research Philly DNN 훈련 클러스터의 공개 GPU 사용률 추적을 별도의 운영 위험 과제에 사용했다.
- Philly 원본은 GPU 1분 계측 44,750,640행·552기계다. 처음 연구에 사용한 기계 해시 표본은 21기계·1,704,704행이다. 1분 값을 GPU 슬롯별 5분 평균 창으로 구성하고, 결정 전 완료된 세 창만 특징으로 쓴다. 정답은 뒤따르는 30분의 여섯 5분 창 중 해당 슬롯 사용률 평균 ≥80%가 한 번이라도 생기는지다. 원래 분값·슬롯 폭·결측을 감사했고 미래 관측이 불완전한 판단을 임의로 음성 처리하지 않았다.
- 시간 경계는 학습 2017-10-04~11-15, 검증 11-16~11-30, 시험 12-01~12-15 UTC다. 주 평가층은 과거 세 창이 완전하고 현재 사용률이 80% 미만인 판단이다. 사건 80%는 GPU 사용률 위험의 연구상 임계값이며, 특정 AI-App의 지연 SLO 임계값이 아니다.

② 왜 확률 모델이고, 어떤 비교를 했나
- 스케일 판단의 입력 신호에는 단순 0/1보다 “지금 얼마나 위험한가”라는 보정된 확률이 유용하다. 이산적인 상태·최근 초과 여부별 경험 사건율에 Beta(1,1) 평활을 적용한 확률표를 단순 기준선으로 두고, 최근 사용률 수준·변동과 추세를 수치 입력으로 쓰는 L2 로지스틱 회귀를 비교했다. 확률 오차는 Brier 평균제곱오차로 평가했다.
- 실제 로지스틱 입력은 과거 세 창의 사용률, 그 평균·최대, 현재−오래된 창의 변화, 현재 고사용률 여부, 최근 고사용률 여부와 관측 품질 표시다. 과거 결측 대체 중앙값과 표준화 모수는 학습 분할에서만 적합했다. L2 규제 강도 C는 0.1/1/10 중 검증 Brier로 정했고 현재 정상층의 통합 모델은 C=10이었다.
- 첫 21기계 시간순 시험에서 상태별 분리 로지스틱은 Beta보다 좋았지만 통합 로지스틱의 Brier 0.054578이 상태별 모델 0.054683보다 조금 더 낮았다. 결측 품질 입력의 독립 이득도 확인되지 않았다. 그러므로 후속 새 기계 검증과 전날 보정의 p0로는 더 단순한 통합 로지스틱을 고정했다. “상태별 분리가 새 기여로 성공했다”는 주장은 하지 않는다.
- 고정된 p0를 학습에 없던 새 기계 37대에 적용했을 때 Beta 0.089879 대비 Brier 0.077783이었다. 이 비교는 같은 클러스터의 새 기계 일반화이며, 다른 CSP·GPU 세대·AI 추론 서비스로의 전이가 아니다.

③ 왜 전날 기계·슬롯 피드백을 넣었나
- 기본 확률 p0의 평균적 순위가 좋아도 어떤 기계 또는 한 기계의 특정 슬롯에서 확률이 지속적으로 높거나 낮게 치우칠 수 있다. 기계별 절편만 보정한 방법을 강한 비교기로 둔 다음, 그 절편으로 설명되지 않는 슬롯 잔차가 남는지 별도의 새 기계 집합에서 검사했다.
- 당일 판단에 당일 미래 정답을 넣으면 시점 누출이 생긴다. 보정은 전날의 적격 판단과 정답 창이 끝난 결과만 사용하고, 기계×슬롯×시간당 첫 판단 한 건으로 피드백의 과밀 중복을 줄인다. 기계 절편에는 벌점 20을 주고 슬롯 잔차의 분모에는 20을 더한다. 두 보정량 모두 ±0.5로 제한해 표본이 적을 때의 과도한 변경을 막는다. 전날 적격 기록이 없으면 기본 p0를 유지한다.
- 보정 자체는 익숙한 로그오즈 절편·잔차 원리다. 연구 기여는 기계 보정 뒤 슬롯 잔차를 순서대로 구성하고, 하루 경계·결과 완료 시각·무피드백 기본값을 명시하며, 강한 기계별 보정과 짝지어 평가한 데 있다. 51개 새로운 기계의 별도 시험에서 기계 보정만 한 Brier 0.085786을 기계+슬롯 보정 0.083532으로 낮췄다.
- 원본에는 “계측·정답이 운영 시스템에 실제로 도착한 시각”이 없어, 완료되면 바로 사용 가능하다고 가정한다. 실제 운영 지연이 있다면 전날 피드백의 유효 범위가 줄 수 있다.

발표자 설명 예시:
“로컬 벤치마크는 형상별 성능에는 맞지만 장기 운영 위험을 학습하기에는 짧았습니다. 그래서 1분 간격 GPU 추적이 있는 Philly에서 다음 30분의 80% 이상 사용률을 사건으로 정의했습니다. 최근 이용률로 확률을 내는 통합 로지스틱이 단순 확률표보다 새 기계에서 더 정확했고, 전날 피드백으로 기계별 오차를 먼저 맞춘 뒤 슬롯별 잔차를 보정하자 강한 기계 보정 기준선보다 Brier가 2.63% 더 낮았습니다.”

9-3. C: Azure Coding을 왜 골랐고, 90분위 HGB를 왜 썼는가

① 자료의 역할
- 형상 추천과 운영 위험만으로는 “앞으로 유입될 앱 요청이 얼마나 큰가”를 판단하기 어렵다. 기존 SQLite에는 장기간 이어진 실제 사용자 요청의 시각별 입력 토큰 열이 없고, Philly에는 앱 요청·토큰이 없다. Azure LLM 공개 Coding 표본은 요청마다 UTC TIMESTAMP와 입력 ContextTokens가 있어 다음 5분 수요 문제를 분리해 정의할 수 있다.
- 원본 Coding CSV에서 유효한 양수 ContextTokens와 TIMESTAMP만 읽어 2024-05-10~16의 16,803,695요청을 5분 구간 2,016개로 집계했다. GeneratedTokens는 이 실험의 정답이나 특징으로 사용하지 않았다. 공개 파일은 생산 트래픽 일부만 담은 표본이므로 y는 “표본에 기록된 다음 5분 입력 토큰 합계”다. 전체 서비스 처리량, 실제 GPU 용량, VM 대수는 정답이 아니다.
- 학습은 첫 1시간을 제외한 05-10~12의 852구간, 개발 검증은 05-13의 288구간, 후향 시간순 평가는 05-14~16의 864구간이다. 미래 구간 값은 입력에서 제외한다. 직전 5분 계측이 예측 시각까지 전달됐다는 가정이 필요하며, 실제 전달 지연은 공개 원본에서 알 수 없다. 평가 날짜 일부의 일별 통계를 앞선 연구에서 본 적이 있으므로 블라인드 독립 시험으로 소개하지 않는다.

② 예측 대상과 모델 선택 이유
- 평균 수요를 맞히면 갑작스러운 입력 증가를 지나치게 낮게 잡을 수 있다. 연구에서 필요한 것은 다음 5분 입력 토큰 “예산” 후보이므로 90분위와 그에 대응하는 pinball 손실을 사전에 고정했다. 과소예측에 더 큰 벌점을 주는 지표이지만, 90분위가 실제 GPU 비용·SLO 손실의 최적 비율이라고 검증한 것은 아니다.
- 절대 수요 y_t는 서비스의 전체 규모와 시간대 변화에 크게 좌우된다. 직전 완료 12개 5분 구간의 평균 m_t로 나눈 상대 수요 r_t=y_t/m_t를 학습하고, 예측 후 m_t를 곱해 절대 토큰으로 복원했다. m_t<1,000이면 작은 분모에 따른 불안정을 피하려고 보류한다.
- 입력은 직전 1·2·3·12구간의 상대량, 전날 같은 5분 구간, 지난 1시간 최대/90분위, 최근 30분 대비 직전 30분 비율, UTC 시각 sin/cos, 주말 표시다. 이 조합은 최근 급증·반복 시간대·주말 차이를 모델에 보여 준다. HistGradientBoostingRegressor는 표형 입력의 비선형 관계를 학습하고 quantile=0.9 손실을 직접 최적화할 수 있어서 고정 후보로 택했다. 지난날 특징의 초기 결측도 처리할 수 있다.
- 정확한 고정 설정은 loss='quantile', quantile=0.9, max_iter=150, learning_rate=0.05, max_leaf_nodes=7, min_samples_leaf=20, l2_regularization=1, early_stopping=False, random_state=42다. 훈련 가중치 m_t/mean_train(m)은 상대 수요 예측의 손실을 절대 입력 토큰 pinball 손실과 일치시키려는 선택이다.
- 이 HGB는 여러 ML 학습기에서 검증 점수로 승자를 뽑은 결과가 아니다. 사전에 정한 HGB 한 개를 학습했고, 전역 비율 90분위·직전 1시간 경험적 90분위·전날 같은 시각·전날 같은 시각+훈련 잔차 90분위의 네 단순 기준선과 비교했다. 따라서 “모든 예측 모델 가운데 최적”이라는 표현은 피한다.

③ 선택이 통과한 범위와 실패한 범위
- Coding 후향 평가 3일의 일별 동일가중 평균 절대 토큰 pinball은 418,627로, 최선 단순 기준선 742,048보다 43.6% 낮았다. 세 날짜 피복률 93.75/92.01/93.75%가 사전 허용 범위 85~95% 안에 있었다. 그러나 날짜는 3개뿐이고 인접 5분 구간은 독립 표본이 아니다.
- 같은 모델을 Conversation 서비스에 옮겼을 때 pinball 348,600으로 직전 1시간 기준선 335,196보다 나빴다. 이 결과는 왜 Coding을 주 성과의 적용 범위로 적어야 하는지를 보여 준다. 절대 규모를 제거하는 것만으로 서비스별 도착 패턴 차이를 없앨 수는 없었다.
- 모델의 결과는 “요청 입력 수요 신호”다. 얼마의 GPU 메모리·연산량·노드가 필요한지 또는 SCALE_OUT 명령을 언제 내야 효과적인지는 이 실험으로 학습하거나 검증하지 않았다.

발표자 설명 예시:
“요청 수요를 보려면 요청 시각과 입력량이 필요해 Azure Coding 표본을 썼습니다. 다음 5분의 평균이 아니라 90분위 예산을 예측했고, 직전 1시간 규모로 정규화해 급증 비율을 HGB로 학습했습니다. Coding의 후향 3일에서는 강한 단순 기준선보다 손실이 43.6% 낮았지만, Conversation 전이는 실패했으므로 Coding 범위에서만 성과로 말합니다.”

9-4. D: 추론 최적화에는 어떤 데이터·모델을 썼고 왜 별도 연구 결과인가

① 새 학습 데이터나 새 예측기는 없음
- 이 연구에는 A에서 이미 검증·고정한 Extra Trees 모델 파일과 8후보 GPU 형상 격자를 그대로 썼다. 모델을 다시 적합하거나 성능 정답을 다시 만들지 않았다. 그래서 계산 속도 차이는 모델 성능 개선이 아니라 같은 모델을 호출하는 방법의 차이로 해석할 수 있다.
- 입력 1은 9개 AI 모델에서 5작업씩 선택한 45개 고유 격자 각각에 25개 합성 SLO를 붙인 1,125개 질의다. 동일 격자의 예측은 같고 SLO 비교만 달라진다는 상황을 시험하기 위해 이렇게 구성했다. 다섯 번 반복해 5,625개 응답 쌍을 비교했다. 25라는 수는 실제 플랫폼에서 관측된 평균 질의 빈도가 아니라 계산 실험의 부하 조건이다.
- 입력 2는 서로 다른 575개 workload 격자다. 중복이 없어 캐시보다 여러 격자의 한 번에 예측 호출이 효과적인지 평가한다. 이것도 온라인 서비스 요청 trace가 아니라 저장된 로컬 후보 격자를 재사용한 오프라인 벤치마크다.

② 방법 선택의 이유
- 같은 격자에서는 원시 배치 지연·처리량 예측이 SLO 값과 독립이다. 따라서 하나의 호출 내부에서 원시 예측만 재사용하고, 각 SLO의 유효성 검사와 공동 목표 판정은 다시 실행하면 결과 의미를 바꾸지 않고 반복 모델 계산을 제거할 수 있다. 호출 간 영구 캐시를 두지 않아 새 모델·입력에 오래된 예측을 잘못 붙일 위험을 피했다.
- 서로 다른 격자에서는 예측기를 8후보씩 수백 번 부르는 비용이 있다. 후보의 전체 순서와 매핑을 유지한 채 최대 256격자를 묶어 예측하도록 변경했다. 큰 호출 실패 시 기존 격자별 방식으로 되돌아간다. 256은 미리 정한 64→256 출력 일치·시간·메모리 채택 게이트를 통과한 현재 연구 경로의 설정값이지, 가능한 모든 하드웨어에서 전역 최적 크기라는 뜻이 아니다.
- 결과를 “형상 추천 알고리즘 자체의 개선”과 구분하려고, 완전 정규화 JSON 동등성을 채택 조건에 넣었다. 동일 격자 25질의는 487.01→24.19ms, 575개 고유 격자의 64→256 추가 변경은 747.305→528.949ms였다. 후자의 1.518배는 개별 쌍 시간비의 중앙값이므로 표시된 두 시간 중앙값의 몫과 같을 필요가 없다.
- 모델 적재·네트워크·실제 VM 실행·사용자 지연은 측정하지 않았다. 따라서 여기서 말하는 속도는 저장 모델이 준비된 상태에서의 오프라인 판단 함수 시간이다.

발표자 설명 예시:
“네 번째 결과는 다른 AI 모델을 학습한 성과가 아닙니다. 같은 Extra Trees 예측을 여러 SLO에 재사용하고 서로 다른 격자를 묶어 계산해, 반환 JSON을 유지하면서 연구용 판단 함수의 시간을 줄인 엔지니어링·추론 최적화 성과입니다.”

9-5. 모델 선정 근거의 증거 수준을 한 장으로 설명하기

- Extra Trees: Random Forest·중앙값과 같은 검증 분할의 사전 정의 점수로 선택했다. RF와 차이가 아주 작다. 시험셋은 선택 뒤 평가했다.
- Philly 통합 로지스틱: 원래 상태별 모델의 독립 이득 실패를 확인한 뒤 후속 새 기계 시험의 고정 기반으로 채택했다. 새 기계에서 Beta 기준선 대비 개선을 검증했다. 새 기계 결과를 원래 상태별 모델 선택의 사전 증거로 거꾸로 제시하지 않는다.
- Azure Coding 90분위 HGB: 문제·특징·하이퍼파라미터·채택 게이트를 점수 전에 고정한 단일 ML 후보였다. 네 비학습 기준선보다 Coding에서 좋았지만 다른 ML 학습기들과의 우열은 검증하지 않았다.
- 기계/슬롯 보정: p0 위에 얹은 전날 피드백 규칙이다. 강한 “기계별 벌점 절편”과 비교해야 슬롯 잔차의 추가 기여를 말할 수 있다.
- 256격자 묶음: 새 학습기 선택이 아니라 출력 동등성·시간·메모리 게이트를 통과한 구현 선택이다.

9-7. 모델을 직접 만들었나: 발표 질의응답용 답변

짧은 답변: **새 LLM이나 새 딥러닝 구조를 처음부터 만든 것은 아니다.** 기존 AI 응용 모델을 대상으로 실행한 성능 기록을 모아, 경희대 연구 코드에서 표형 데이터 예측 모델을 직접 학습했다. 학습된 모델 파일은 저장한 뒤 추천 시점에 불러와 추론한다. 모델 구조를 구현한 주체와 학습 데이터·절차를 구성한 주체, 추론 때 파일을 불러오는 동작을 구분해서 설명한다.

① 성능 측정 대상이 된 응용 모델
BERT 계열, ALBERT, ELECTRA, DistilBERT, RoBERTa, Qwen 등 9개는 기존 모델 ID로 식별되는 앱 모델이다. 이 연구에서 이들의 가중치를 다시 학습하거나 미세조정하지 않았다. SQLite에 쌓인 실행 결과에서 모델 ID/revision을 입력 범주로 사용했다. 그래서 우리 추천기가 질문을 이해하거나 텍스트를 생성하는 LLM은 아니다.

② 경희대가 데이터로 학습한 로컬 성능 예측기
Extra Trees는 scikit-learn 구현을 사용해 연구 데이터로 적합했다. 범주형 model_id/model_revision/device를 one-hot 변환하고, batch_size/max_length/request_concurrency/cpu_threads/cpu_core_limit/replica_count/repeats를 수치 입력으로 넣는다. 나무 200개의 ExtraTreesRegressor가 로그 변환된 두 출력(batch p95 지연, examples/sec)을 함께 예측하고, 지수 변환으로 원 단위를 복원한다. 저장된 joblib 파일을 형상 판단 API가 검증한 뒤 불러온다. 즉 **알고리즘 구현은 라이브러리 것을 사용했지만 트리 분기 구조는 우리 SQLite 학습 분할로 새로 적합한 로컬 모델**이다. Extra Trees라는 알고리즘 자체를 새로 발명한 것은 아니다.

③ 공개 운영 추적으로 별도 적합한 두 모델
- Philly 통합 로지스틱: 경희대 코드에서 Philly 시계열 학습 분할로 적합한 기존 LogisticRegression 구현이다. 입력 전처리·특징·규제 강도를 구성하고 확률을 학습했다. 이어지는 기계/슬롯 보정 규칙은 경희대가 정한 별도 추론 단계다.
- Azure Coding 수요 모델: 경희대 코드에서 해당 trace의 학습 구간으로 적합한 HistGradientBoostingRegressor다. 0.9 분위수 목표를 학습하며, 이 학습기 구조도 표준 scikit-learn 구현이다.
- 두 모델 모두 학습이 끝난 후 모델 파일로 저장해 평가·추론 때 로드한다. 원래 데이터셋에 저장된 예측모델을 가져다 쓴 것이 아니다.

④ 직접 만든 연구 요소는 무엇인가
우리의 독자적 기여를 모델 아키텍처 발명으로 주장하지 않는다. 연구 질문에 맞는 정답·시점·분할·지원범위와 강한 기준선을 설계하고, 데이터로 학습한 예측을 공동 목표 형상 선택이나 전날 기계/슬롯 확률 보정에 연결한 절차, 그리고 실제 적용 범위를 제한해 검증한 결과가 연구 내용이다. 동일 예측을 캐시·묶음 처리한 추론 최적화에서는 학습 모델을 새로 만들지 않았다.

발표 한 문장:
“새 LLM을 만든 것은 아닙니다. 기존 앱 모델의 배치 측정 데이터를 이용해 경희대 연구 코드에서 Extra Trees 성능 예측기를 직접 학습했고, 학습 완료 후 저장 모델을 불러와 인프라 형상 후보를 평가합니다. 예측기 알고리즘은 검증된 표준 라이브러리를 썼고, 연구 기여는 데이터 기반 예측과 추천·보정 판단 절차를 구성하고 검증한 데 있습니다.”

9-6. PPT 도표에 바로 붙일 수 있는 짧은 주석

- 데이터셋 지도: “SQLite=같은 호스트의 정적 후보 성능 / Philly=GPU 운영 위험 / Azure Coding=요청 입력 수요. 세 정답은 서로 다름.”
- AI 모델과 예측 모델: “BERT·RoBERTa·Qwen 등 9개는 성능이 측정된 응용 모델; Extra Trees는 그 성능을 예측하는 학습기.”

- 위험 결과: “새 Philly 기계 집합. Brier 13.46%는 기본 확률 대 Beta; 추가 2.63%는 다른 새 기계 집합에서 기계+슬롯 대 강한 기계 보정.”

10. 문제점·해결 방법·다음 개선 계획

10-1. 이번에 해결한 문제와 확인된 결과

문제 1: 응용 조건만 보고 CPU/GPU 형상의 지연·처리량을 미리 알기 어려웠다.
해결: SQLite 측정 자료에서 모델·revision·입력 길이·batch·동시성·CPU/GPU 형상으로 배치 p95와 처리량을 함께 학습했다. 예측 후보마다 두 목표를 동시에 확인하고, 만족하는 최소 형상을 고르며 지원 범위 밖이면 보류한다.
확인 결과: 주 test에서 배치 p95 중앙 APE 73.71%→16.99%, 처리량 APE 66.01%→10.41%였다. 생성 SLO를 사용한 GPU 90작업에서는 단순 기준선의 성공 추천 36건보다 54건이었고, 추천 54건은 각 1회 실측에서 목표를 만족했다.
남은 문제: 한 호스트·기존 모델·좁은 후보 형상이고 목표도 실제 사용자가 준 SLO가 아니다. 생성 목표를 1.25배 강화하면 추천 50건 중 4건이 위반했다. 다른 하드웨어와 실제 서비스 안전성이 해결됐다고 할 수 없다.

문제 2: 평균 사용률이나 현재 상태만으로는 다음 시점의 GPU 고사용률 가능성을 충분히 표현하기 어렵고, 기계·슬롯마다 예측 편향이 다를 수 있었다.
해결: Philly GPU 추적의 최근 사용률로 30분 내 80% 초과 위험 확률을 학습하고, 전날 완료된 정답으로 기계별 확률 절편을 보정한 뒤 슬롯별 잔차를 추가 보정했다. 시계열 누출 방지를 위해 판단 전에 완료된 자료만 썼다.
확인 결과: 처음 보는 37기계에서 통합 로지스틱 Brier가 Beta 기준선보다 13.46% 낮았다. 별도 51기계 시험에서는 슬롯 보정이 강한 기계별 보정보다 Brier를 2.63% 더 낮췄다.
남은 문제: 이는 GPU 계측 위험 확률이지 AI-App 사용자 SLO나 실제 SCALE_OUT/IN 효과가 아니다. 공개 데이터의 정답 전달 시각이 없어 결과가 완료되자마자 쓸 수 있다고 가정했다.

문제 3: 다가오는 입력 요청량을 자원 판단에 넣을 단기 수요 신호가 없었다.
해결: Azure Coding 표본을 5분 단위로 집계하고 직전 1시간 규모로 나눈 상대 입력 수요의 90분위를 HistGradientBoosting으로 학습했다. 모델·강한 단순 기준선을 시간순으로 비교했다.
확인 결과: Coding 후향 3일 평가에서 절대 토큰 pinball 손실이 최선 기준선보다 43.6% 낮았고, 세 날짜 피복률은 85~95% 범위에 들었다.
남은 문제: Conversation 서비스로 옮긴 결과는 최근 1시간 기준선보다 나빴다. 표본 토큰 수요가 GPU 수요나 VM 수량으로 변환되는지도 검증하지 않았다.

문제 4: 같은 후보의 SLO만 달라져도 성능 모델 예측을 반복해 판단 함수 계산이 중복됐다.
해결: 동일 후보의 원시 성능 예측을 한 요청 묶음 안에서 재사용하고, 다른 후보 격자는 큰 묶음으로 예측했다. 후보 순서·입력 검증·결과 형식을 보존했다.
확인 결과: 동일 후보 25개 SLO 질의는 중앙 함수 시간이 487.01→24.19ms였고 출력 JSON 5,625쌍이 같았다. 575개 다른 격자의 묶음 크기 64→256에서는 별도 실행의 짝별 시간비 중앙값이 1.518배였다.
남은 문제: 오프라인 함수 시간만 측정했다. 모델 로드, API 왕복, 실제 배포와 사용자 응답 시간은 포함되지 않았다.

문제 5: SQLite 실행 기록이 여러 파일에 있어 행 수를 독립 응용 수처럼 세거나 반복 자료·실패 행을 잘못 정답화할 위험이 있었다.
해결: 7개 원본 DB를 진단해 9,591실행·9,445 유효 학습 후보·671 작업 조건 그룹을 확인했다. 실패와 중단은 성공 성능 데이터와 구분하고, 분할은 행이 아니라 workload 그룹으로 했다. 추천 입력의 지원 범위도 검사하고 미지원이면 ABSTAIN하도록 했다.
확인 결과: 학습·검증·시험에 같은 workload의 자원 후보가 섞이지 않게 평가 기반을 만들었다.
남은 문제: 이 자료는 자연어 요청, 실제 사용자 요구 SLO, 최소 RAM/노드/GPU 정답, 클라우드 가격이나 시간에 따른 실제 스케일 전환을 담지 않는다. 데이터 진단은 중요 기반이지만 새 요구분석 성능을 증명한 것은 아니다.

10-2. 아직 해결하지 못한 핵심 문제

- 자연어 앱 요청을 CPU·메모리·GPU 종류와 수·노드 수·배치 조건이 있는 구조화 요구로 바꾸는 지도 데이터가 없다. 기존 SQLite의 선택 형상은 연구자가 실험에 넣은 값이지 “최소로 필요한 자원”의 정답이 아니다.
- 정적 추천 시험의 SLO는 수집기가 만든 값이고, 관측은 한 호스트의 배치 처리량·배치 p95다. 실제 사용자 요청 p95·요청 처리량·허용 비용으로 검증하지 않았다.
- 기존 데이터에서 replica 1/2는 같은 호스트 프로세스 수다. VM 1/2대의 배포 완료나 서로 다른 CSP VM 형상으로 해석할 수 없다. RAM·GPU 종류·리전·가격·노드 수의 충분한 비교 정답도 없다.
- 실제 경희대 판단→실행 측 명령 접수→VM/앱 READY 또는 FAILED→트래픽 전환→후속 사용자 요청 결과가 하나의 action ID로 연결된 자료가 없다. 따라서 학습된 SCALE_OUT/IN 효과 정책과 인과적 SLO 개선은 아직 검증되지 않았다.
- Azure 수요 모델의 서비스 간 전이와 Philly 위험 모델의 새 클러스터 전이는 검증되지 않았다. 공개 추적 자료는 해당 도메인의 부하·위험 연구에는 쓸 수 있어도 AI-App의 실행 결과 정답을 대신하지 못한다.
- 기존 SQLite의 test·별도 캠페인은 여러 후속 탐색에 이미 노출됐다. 같은 행으로 새 규칙을 반복 선택하면 그 점수를 독립 확인 결과라고 부를 수 없다.

10-3. 다음 개선은 데이터와 인터페이스부터 진행

1순위 — 실제 의사결정 사건을 연결해 수집한다.
- 응용 등록: app_id/app_version/profile_id, 사용자가 요구한 작업과 SLO, 입력 크기·모델 revision, 요구의 출처·유효 시각을 저장한다. 자연어 원문이 민감하면 원문 대신 승인된 구조화 요약과 사람 검토 라벨을 남긴다.
- ETRI 후보 자원: resource_id, CSP/리전, CPU·RAM·GPU 종류와 총량/가용량, 가격·통화·가격 유효 시각, 계측 원본과 observed_at/available_at을 저장한다.
- 경희대 판단: decision_id, 당시 사용 가능했던 입력 시각, 정책 버전, DEPLOY/UPDATE/SCALE_OUT/SCALE_IN/KEEP/ABSTAIN, 추상 자원 형상, 후보 점수·보류 이유를 남긴다.
- 실행과 결과: 실행 측이 발급한 action_id를 decision_id에 연결하고 요청·접수 시각, READY/FAILED, 준비 replica 수, 트래픽 전환, 사용자 요청별 성공·종단 지연·요청량·비용을 기록한다. 관측 시각과 판단기가 실제 사용할 수 있게 된 시각을 따로 저장한다. “명령 요청”을 “VM 생성 성공”으로, replica 수 변화 관측을 “명령 발행”으로 대체하지 않는다.
- 하나의 사건 데이터 계약으로 식별자와 시간을 검증한 다음에 학습을 시작한다. 현재 scale_action_events v0.2.0은 좁은 SCALE_OUT 수집 형식을 정의한 계약이며, 예시 JSONL은 합성이다. 실측 행동 효과 결과는 아직 아니다.

2순위 — 새 독립 벤치마크를 확보해 정적 추천을 다시 평가한다.
- 다른 호스트와 새 모델·모델 계열, CPU·GPU 형상, 반복 실행을 포함한다. 학습에 참여한 그룹과 확인 시험은 app/model/host/time 단위로 분리한다.
- 실제 요청 SLO와 가격이 준비되면 지연·처리량·비용을 함께 평가하고, GPU/CPU/RAM/GPU 메모리 부족·실패 경계를 직접 관측한다.
- 기존 90개 시험 작업군은 이미 사용됐으므로 새로운 보정 안전성 확인에 다시 쓰지 않는다. 새 보정이 필요하면 독립 보정 그룹과 미사용 확인 그룹을 먼저 확보하고, 성공 승인·잘못 승인·가능했지만 보류·자원 초과를 함께 보고한다.
- 앱이 학습 지원 범위 밖일 때는 과감히 ABSTAIN하고 추가 프로파일 측정 또는 ETRI 후보 확인을 요청하는 선택을 평가한다. 단, 보류 비율만 줄이려다 잘못된 승인을 늘리지 않도록 한다.

3순위 — 요구사항 분석은 우선 명시적 형식과 사람 검토로 시작한다.
- 앱 요청을 바로 큰 언어 모델로 자동 자원 수량화하기보다 먼저 작업 종류, 입력 크기, 지연·처리량 SLO, 모델 크기·형식 등 필드를 정의한다.
- 구조화 결과와 사람이 승인한 요구사항을 쌍으로 쌓고, 각 필드의 출처·확신·누락을 보존한다. 충분한 앱 종류가 모인 뒤에만 분류/추출 모델을 학습하고, 새 app/model 전체 제외 평가를 한다.
- 현재 SQLite의 batch p95·GPU 예약 피크·적재시간을 최소 VM 사양 정답으로 재명명하지 않는다. 기존 requirement signal 증거는 관측 예약 VRAM과 캐시 모델 적재시간을 보여 주는 제한된 신호다.

4순위 — Scale-out/in은 간단한 판단 인터페이스와 정책부터 실측한다.
- 데이터 수집 전에는 DEPLOY/UPDATE/SCALE_OUT/SCALE_IN/KEEP/ABSTAIN 반환 형식과 간단 정책·재생 시뮬레이션을 연구용으로 고정한다. 예측 신호만으로 VM을 자동 조작하지 않는다.
- 실제 action/READY/전환/요청 결과가 쌓이면 최근 부하·대기열·SLO 위반 위험을 써서 간단한 임계값 기준선부터 만든다. Scale-in 진동과 준비 지연을 고려해 cooldown·히스테리시스, 최소 유지시간, 보류 조건을 둔다.
- 시간순 재생과 shadow 평가에서 기존 정책 대비 SLO 위반, 불필요한 증설·축소, 비용, READY 지연을 함께 비교한다. 결과가 괜찮을 때 제한된 canary/통제 실험으로 넓혀 행동 전후의 관측 효과를 평가한다.
- 실제 실행 정책과 인과 효과는 실행 계측과 적절한 비교군이 확보되기 전에는 완료 성과로 주장하지 않는다.

5순위 — 수요·위험·추론 모듈의 적용 범위를 넓힌다.
- Azure Coding 모델은 새 기간·새 Coding 표본으로 재시험하고, Conversation 실패 원인을 보고 서비스별 모델과 통합 모델을 같은 시간순 기준선에 비교한다. 미사용 서비스 holdout이 확보되기 전에는 일반 서비스 모델로 부르지 않는다.
- Philly는 실제 결과 available_at 지연에 대한 민감도를 평가하고, 다른 클러스터·GPU 세대로 확장한다. 고사용률 확률 개선을 VM scale 효과라고 바꾸어 해석하지 않는다.
- 추론 최적화는 실제 서비스 프로세스에서 후보 수·요청 동시성·모델 크기별 CPU/RSS·왕복시간을 측정한다. 현재의 함수 내부 속도 개선과 온라인 응답 개선을 구분한다.

10-4. 발표와 연구보고서에서 사용할 결론

“현재까지는 기존 실행 데이터를 이용해 정적 GPU/CPU 형상 성능 예측과 최소 후보 선택, 공개 GPU 추적의 고사용률 위험 보정, 한 서비스의 단기 입력 수요 예측, 연구 판단 함수의 중복 계산 제거를 확인했다. 다음 핵심 과제는 실제 앱 요구·인프라 후보·배포 명령·준비 완료·후속 사용자 지표를 하나의 시간 순서 사건으로 수집하는 것이다. 그 데이터로 새 호스트·앱에서 독립 검증한 뒤에야 자연어 요구 분석과 Scale-out/in 정책의 효과를 주장할 수 있다.”

11-2. 현재 데이터로 이미 부족하다고 확인된 항목

- **응용 요구 분석:** 기존 SQLite에 사용자 자연어 요청, 앱 설명, 사람이 확인한 CPU/RAM/GPU 요구, 실제 사용자 지연·처리량 SLO가 없다. 모델 ID와 실험 프로필은 요청 의미의 대체 라벨이 아니다.
- **최소 자원 추정:** SQLite의 CPU core limit과 GPU replica 수는 실험에서 선택한 프로세스 형상이다. VM의 CPU/RAM 한도, GPU 종류·메모리, 노드 수를 바꿔 얻은 최소 성공 경계가 없다. GPU 실행 성공이 있었다고 해서 그 형상이 최소 요구량이라는 뜻도 아니다.
- **실제 인프라 추천:** 후보 당시의 CPU·RAM·GPU 총량/가용량, CSP·리전, 가격·가격 유효 시각, 노드 라벨·배치 제약의 출처가 충분히 결합돼 있지 않다. 배치 측정으로 실제 VM 상품이나 최저 비용을 학습할 수 없다.
- **배포·스케일 조치:** 판단 기록만으로는 실행 측이 명령을 실제 접수했는지, VM/응용이 언제 READY 또는 FAILED였는지, 트래픽이 언제 새 replica로 이동했는지, 이후 사용자 요청이 좋아졌는지 알 수 없다. 현재 수집 구조의 decision_id·deployment_id만으로 실제 action_id와 결과를 복원할 수 없다.
- **시점 정합성:** 관측이 발생한 시각 observed_at과 판단기가 실제 사용할 수 있게 된 available_at이 구분되지 않으면 지연 도착 지표를 미래 누출 없이 평가할 수 없다. 모니터링 누락과 실제 0도 따로 표시해야 한다.

11-3. 연구별로 새로 필요한 최소 요구사항

A. 자연어·구조화 응용 요구 분석을 학습하려면
1. app_id, app_version, model_id/revision, 모델 크기와 각 메타데이터의 출처·수집 시각.
2. 요청에서 확인한 작업 종류, 입력 데이터 크기/토큰 범위, 예상 동시성·요청량, 요구 p95/처리량 SLO, 비용 한도.
3. 자연어 또는 비민감 요약과 사람이 검토·승인한 구조화 필드의 짝. 필드별 근거와 불확실성·결측 표기.
4. 새 앱·새 모델을 통째로 제외한 시험 사례. 같은 앱 템플릿의 유사 요청이 train/test에 나뉘지 않게 한다.

B. 추상 인프라 형상·후보 추천을 학습·검증하려면
1. 실제로 평가한 후보별 CPU 코어, RAM, GPU 종류·수·메모리, 노드 수, 이미지, 노드 라벨·배치 제약.
2. 후보 시점의 총량·가용량·건강 상태, resource_id, CSP·리전, 가격·통화·가격 기준과 유효 기간. 각 값의 출처·단위·observed_at·available_at.
3. 같은 앱·요구 조건을 여러 형상에서 반복 실행한 준비 성공/실패·OOM·준비시간, 요청별 종단간 지연·처리량·오류율 및 비용.
4. “형상이 존재한다/사용 가능하다”와 “이 앱 요구를 만족한다”를 구분하는 라벨. ETRI가 정하는 실제 CSP·리전·VM은 실행 결과로 기록하고, 경희대의 추상 형상 추천 정답과 섞지 않는다.

C. DEPLOY·UPDATE·SCALE_OUT·SCALE_IN 판단 효과를 평가하려면
1. decision_id, correlation_id, app/profile/deployment 버전, policy_version, 판단 시각과 판단에 사용된 가장 늦은 available_at.
2. 실행 측이 확인한 고유 action_id, 명령 종류·접수 결과·재시도·실패 사유, 요청·접수·완료 시각. KEEP와 ABSTAIN도 남긴다.
3. 명령 전·후 실제 replica/VM 수, 앱 READY/FAILED 시각, 서비스 건강 상태, 트래픽 라우팅 전환 시각과 라우팅 버전.
4. action_id와 실제 처리 배포를 연결한 사용자 요청 결과: 요청 시작·완료·수집 가능 시각, 성공 여부, 종단간 지연, 요청 종류/입력 크기. 전후 비교 창과 목표 SLO를 시험 전에 고정한다.
5. 같은 시간대 부하·요청 복잡도·동시 업데이트와 자원 상태. 가능하면 비개입 비교 구간이나 사전 정의한 canary/통제 실험군을 기록한다. 비교군이 없으면 인과 효과 대신 관측 연관성만 보고한다.

공통 품질 조건
- 모든 시각에 시간대와 원본 출처를 기록하고 observed_at/available_at을 분리한다.
- 수치마다 단위·측정 주기·분모를 저장한다. GPU 사용률/메모리는 산출 기준을, 가격은 통화·시간 기준을 함께 기록한다.
- 값 0, 미관측, 수집 실패를 구분하고 수집기 생존 신호도 저장한다.
- 반복 실행은 그대로 보존하되 독립 사례처럼 세지 않는다. 앱/모델/호스트 단위 제외와 시간순 holdout을 마련하고, 최종 시험 자료는 모델·정책을 고르는 데 재사용하지 않는다.
- 성공·실패뿐 아니라 실행 불가, 사용자 취소, 보류, action 재시도도 이유와 함께 기록한다. 명령 요청을 실제 적용이나 성공 라벨로 대체하지 않는다.

11-4. 당장 우선할 일

1. 이노그리드·ETRI와 공통 이벤트 식별자와 시각 필드부터 합의한다. 현재 PoC의 decision/deployment 기록에 실행 측 action_id, READY/FAILED, 실제 replica 수·트래픽 전환, 후속 사용자 결과를 연결한다.
2. 앱 등록 입력·SLO와 자원 후보의 단위·출처·가용 시각을 정한다. 운영 데이터를 받을 때까지 자연어→최소 자원 지도학습을 완료 성과로 주장하지 않는다.
3. 다른 호스트·새 앱·다양한 CPU/RAM/GPU 후보를 반복 측정하고 사용자 SLO로 평가할 미사용 holdout을 만든다. 기존 SQLite 시험·별도 캠페인은 새 독립 시험으로 다시 쓰지 않는다.
4. 실제 action 결과가 쌓이기 전까지는 판단 인터페이스와 간단 정책·오프라인 재생·shadow 평가를 연구한다. 실제 행동 효과는 READY와 사용자 결과가 연결된 뒤 제한된 실험으로 확인한다.

한 문장으로 정리하면, 현재 데이터는 “특정 벤치마크 조건의 성능·GPU 위험·요청 토큰 수요”를 연구하기에는 쓸 수 있지만, “사용자 요구에 맞는 최소 VM을 알아내고 실제 스케일 명령이 SLO를 개선했는가”를 학습·검증하기에는 정보가 부족하다. 필요한 핵심은 요청부터 인프라 후보, 판단, 실제 action, 준비 완료, 후속 사용자 결과까지 이어지는 앱 단위 시간순 기록이다.
