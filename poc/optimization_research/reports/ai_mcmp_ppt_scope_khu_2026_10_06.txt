0. 발표에서 먼저 말할 범위
======================================================================

이번 발표의 주제는 “AI 응용의 요구·자원 조건을 해석해 형상과 운영 판단에 필요한 연구 신호를 만들고, 이를 INNO·ETRI 실행 구조에 연결하는 방법”이다.

경희대가 담당하는 연구 범위:
- 응용 조건을 이용한 추상 인프라 형상 추천
- GPU 위험·수요·계측 신호 예측
- 배포·스케일 판단에 사용할 보정 및 추론 최적화
- 연구 결과를 단위·근거·보류 상태와 함께 전달하는 메커니즘

현재 발표에서 운영 완성으로 말하면 안 되는 항목:
- 실제 VM 생성·삭제 성공
- 실제 사용자 SLO 개선
- 학습된 SCALE_OUT/SCALE_IN 정책의 인과 효과
- 자연어 요청에서 최소 CPU·RAM·GPU·노드 수를 자동으로 정답화
- 경희대 연구 모듈과 INNO·ETRI가 실제 운영 API로 통합된 상태

권장 결론 문장:
“현재까지는 정적 형상 추천, 운영 위험·수요 신호, 계측 예측, 판단 함수 계산 효율을 저장 자료로 검증했다. 다음 단계는 이 연구 결과를 실제 앱 요구·자원 후보·배포 action·READY·사용자 결과와 연결해 운영 판단 효과를 검증하는 것이다.”

1-2. 정적 GPU/CPU 형상 추천

발표 메시지
“앱 조건에서 배치 성능을 예측하고, 지연과 요청률 목표를 동시에 만족하는 최소 후보만 승인한다.”

데이터
- SQLite 7개: 총 9,591 실행, 유효 후보 9,445 실행, 671 workload 그룹.
- 주 학습: khu-hf-local-exhaustive 4,856 실행, 575 그룹, 9개 응용 모델.
- 원본: /path/to/aiops/runs/khu-hf-local-exhaustive/executions.sqlite3
- 정제 스냅샷: /home/researcher/ai-mcmp/research/data/audit_v1/measurements.parquet
- 실행 기간: 2026-09-10~11.

입력·정답
- 입력: model_id/revision, device, batch_size, max_length, request_concurrency, CPU threads/affinity, replica_count, repeats.
- 정답: batch invocation p95 latency(ms), examples/sec.
- 요청률 판정: examples/sec ÷ batch_size.
- 후보: GPU process replica 1/2 × CPU affinity 2/4/8/16 = 8개.
- 2 replica 지연은 느린 replica p95, 처리량은 합계다.

방법
- 범주형 3개를 one-hot하고 수치 특징을 함께 Extra Trees에 입력.
- ExtraTreesRegressor 200 trees, min_samples_leaf=2, max_features=1.0, seed=42, n_jobs=2.
- 지연·처리량을 로그 변환해 학습하고 예측 뒤 지수 복원.
- 같은 workload의 후보를 그룹 단위로 train/validation/test 분리.
- 후보별 예측 p95≤목표 지연, 예측 요청률≥목표 요청률을 동시에 검사.
- 통과 후보 중 replica 수와 affinity 코어 수가 가장 작은 후보 선택. 지원 범위 밖이면 ABSTAIN.

결과
- Test 760행: p95 중앙 APE 73.714%→16.992%.
- Test 760행: examples/sec 중앙 APE 66.008%→10.412%.
- GPU 90작업: 기준선 승인42/성공36/오승인6.
- 우리 모델: 승인54/성공54/오승인0/최소 형상 일치50.
- 실측상 가능한 작업은55개. 35개는 8후보 모두 불가, 32개는 모두 가능, 23개는 일부 가능.

해석 한계
- 생성기가 만든 목표와 동일 호스트의 정적 배치 측정에 대한 결과다.
- process replica 1/2는 VM 1/2대가 아니다.
- CPU affinity는 VM vCPU 수가 아니다.
- 실제 RAM, GPU 종류, CSP/리전, 가격, 사용자 E2E SLO는 검증하지 않았다.

1-3. GPU 위험 확률과 기계·슬롯 피드백 보정

발표 메시지
“최근 GPU 사용률로 다음 30분의 고사용률 위험을 계산하고, 전날 완료된 결과로 기계·슬롯 편향을 보정한다.”

데이터·정답
- Microsoft Research Philly GPU 1분 계측, 원본 44,750,640행·552기계.
- 과거 5분 평균 창 3개와 현재 상태·추세를 입력.
- 정답: 뒤 30분의 6개 5분 창 중 하나라도 평균 사용률 80% 이상이면 사건.
- 주 결과: 새 기계 37대·741,597 판단.
- 슬롯 결과: 별도 새 기계 51대·812,729 판단.

방법
- 통합 L2 LogisticRegression으로 기본 위험확률 p0 생성.
- 학습/검증에서 결측 대체·표준화를 적합하고, C=10을 선택.
- 전날 기계별 로그오즈 절편 δ를 먼저 보정.
- 같은 기계 안에서 슬롯 잔차 g를 추가.
- 보정량은 벌점20, ±0.5로 제한.
- 판단 당일의 미래 정답은 사용하지 않고 전날 완료·전달된 피드백만 사용.

결과
- 새37기계: Beta 기준선 Brier 0.089879→통합 로지스틱 0.077783, 상대 13.46% 감소.
- AP: 0.457322→0.707340.
- 별도 새51기계: 정확 기계별 보정 Brier 0.085786→기계+슬롯 보정 0.083532, 추가 2.63% 감소.
- 51기계 중44기계에서 개선.

해석 한계
- GPU 사용률 사건 확률이며 AI-App 사용자 SLO가 아니다.
- 실제 VM Scale-out/in 효과를 측정하지 않았다.
- Philly 공개 자료의 실제 feedback arrival time은 없어, 결과 완료 즉시 전달된다고 가정했다.
- 37·41·51기계 시험 결과의 개선율을 합산하지 않는다.

1-5. Alibaba GPU SM 예측

발표 메시지
“현재 SM 수준과 최근 추세에서 다음 시간 SM 변화량을 예측해 운영 관측 신호를 보강한다.”

데이터·방법
- Alibaba cluster-trace-gpu-v2026, 미래 day116~122를 고정 모델로 평가.

결과
- 엄격 주 집합: 12,097행·30 workloads, persistence MAE1.627406→1.481500, 8.97% 감소.
- 보조 집합: 103,306행·368 workloads, MAE2.073320→1.814805, 12.47% 감소.
- 두 집합 7/7일 개선.
- 완전 새 workload 진단층은 19.71% 악화했으므로 전반 일반화로 표현하지 않는다.

- 실제 사용자 SLO, OOM, VM 증설 효과가 없다.
- priority class는 feature이며 스케줄러 구현이 아니다.
- 실제 데이터셋은 Alibaba GPU v2026이며 Spot GPU 정책 데이터와 다르다.

  CSP·리전·VM 후보 / 가격·가용량 / 실제 VM 제어
            |
            v
[실행된 VM·AI 응용]
  상태·로그·자원 사용량·사용자 요청 결과
            |
            +-------------------- 피드백 -------------------+
                                 |
                                 v
                [경희대 보정·추론 최적화·후속 판단]

PPT 그림에서 경희대 영역은 파란색, INNO는 초록색, ETRI는 주황색으로 구분한다. 실선은 기존 역할·구조, 점선은 협의가 필요한 제안 연결로 표시한다.

2-2. 모듈별 역할

경희대 핵심 모듈
- Requirement Analyzer: 구조화된 앱 조건을 읽고 입력 누락·지원 범위를 확인.
- Shape Predictor/Selector: 성능 모델로 후보를 평가하고 최소 형상 또는 ABSTAIN 반환.
- Demand Predictor: 서비스·단위·준비 지연에 맞는 토큰/호출 q90 반환.
- Risk/Telemetry Predictor: GPU 고사용률 확률과 SM 신호 반환.
- Feedback Calibrator: 완료·가용 시각이 확인된 정답으로 보정.
- Decision Engine: 연구 결과·앱 목표·운영 상태를 이용해 DEPLOY/UPDATE/SCALE_OUT/SCALE_IN/KEEP 후보를 판단하는 연구 계층. 현재 실제 정책 효과는 미검증.
- Evidence/Guard: 모델 버전, 입력 출처, 단위, 예측 기간, 지원 여부, ABSTAIN 이유를 보존.

이노그리드 모듈
- ApplicationProfile과 앱 버전 관리.
- 사용자 요청·응용 운영 정보·모니터링 결과 수집.
- 경희대가 반환한 추상 결과를 플랫폼 Deployment Manifest로 변환.
- 실행·업데이트·상태·로그 관리.
- 경희대 SCALE_OUT/IN 결과를 바탕으로 ETRI VM 요청 흐름 관리.

ETRI 모듈
- 실제 자원 목록·상태 제공.
- 경희대 추상 요구와 INNO 요청을 바탕으로 CSP/리전/VM 세부 선택.
- 가격·가용률·위치·실제 VM 생성/삭제.
- 생성된 자원 ID와 상태 반환.

2-3. 현재 PoC와 연구 계층의 차이

현재 연구 출력은 “연구용 추정/보류”다.
- batch p95는 사용자 E2E p95가 아니다.
- examples/sec÷batch는 실제 서비스 요청률이 아니다.
- process replica는 VM 수가 아니다.
- CPU affinity는 VM vCPU 수가 아니다.
- 관측 reserved VRAM은 최소 VM 메모리가 아니다.
- 수요 토큰/호출 수는 GPU 수로 직접 환산하지 않는다.

실제 실행계획에 필요한 추가 자료
- 사용자 SLO와 비용 한도.
- ETRI 후보의 CPU/RAM/GPU 종류·수·메모리·노드 수·가격·가용량.
- 이미지, 노드 라벨, 배치 제약.
- 모델 dtype·메모리 정의와 실제 앱 처리량.
- action 접수, VM/앱 READY, 트래픽 전환, 후속 사용자 지표.

3. 다른 기관 연동: PPT 내용
======================================================================

3-1. 기관 간 데이터 흐름

1. INNO가 앱 프로필·사용자 목표·모델 실행 조건을 제공.
2. INNO 또는 ETRI가 자원 후보·상태·가용량·가격·계측을 제공.
3. 경희대가 입력 지원 여부를 확인하고 연구 모듈을 선택.
4. 경희대가 추상 Deployment Spec 또는 연구 증거를 반환.
5. INNO가 실제 플랫폼 명세로 변환하고 실행 요청을 관리.
6. ETRI가 실제 CSP/리전/VM을 결정하고 자원을 생성·삭제.
7. INNO가 응용을 배포하고 상태·로그·모니터링을 저장.
8. 실행 결과·READY·라우팅·사용자 지표를 action_id/decision_id로 연결.
9. 경희대는 완료되고 available_at이 판단 시점 이전인 결과만 후속 보정에 사용.

3-2. 경희대가 받아야 할 입력

입력 그룹 | 필수 내용 | 제공 기관
앱 식별 | app_id, app_version, profile_id, workload_id | INNO
응용 조건 | model_id/revision/dtype, 모델 크기, 입력 크기·토큰, batch, 동시성 | INNO/사용자
사용자 목표 | p95, 처리량, 비용 한도, 허용 준비시간 | INNO/사용자
실행 조건 | 이미지, 런타임, 노드 라벨, 배치·anti-affinity 조건 | INNO
자원 후보 | resource_id, CSP, 리전, CPU/RAM/GPU 종류·수·메모리, 노드 수 | ETRI
자원 상태 | 총량, 가용량, 건강 상태, observed_at, available_at | ETRI
가격 | 가격·통화·시간 기준·가격 유효기간 | ETRI
운영 관측 | GPU/CPU/RAM, 요청량, queue, 오류, 응답 지연, 앱 상태 | INNO/ETRI
실행 피드백 | action_id, 접수·READY·FAILED·라우팅 시각, 실제 replica/VM 수 | INNO/ETRI

3-3. 경희대가 반환할 출력

출력 | 단위·의미 | 현재 상태
predicted_batch_latency_p95_ms | 배치 호출 p95, ms | 구현·검증됨
predicted_benchmark_call_rate | examples/sec÷batch, calls/s | 구현·검증됨; E2E 요청률 아님
selected_process_shape | GPU process replicas, CPU affinity cores | 구현·검증됨; VM 형상 아님
next_5min_sample_input_tokens_q90 | 표본 입력 토큰, 5분 q90 | Coding에서 검증됨
peak_5min_sample_input_tokens_q90 | 준비 지연 창의 최대 5분 토큰량 | Coding/LMM별 탐색 검증
peak_5min_recorded_calls_q90 | 5분 기록 호출 수 q90 | Copilot/BurstGPT 조건별 검증
next_30min_gpu_high_util_probability | 30분 내 평균 GPU 사용률≥80% 확률 | Philly에서 검증
next_hour_sm_percent | 다음 시간 SM 사용률 % | Alibaba 조건별 검증
support_status/result_status | SUPPORTED/ABSTAIN, RESEARCH_ESTIMATE | 구현 기반; 기관 API 합의 필요
abstain_reasons | 누락·범위 밖·단위 불일치·피드백 부족 | 구현·계약 기반
provenance | 모델/코드/데이터 해시, 관측·판단 시각 | 증거 스키마 기반

3-4. 기존 Go 구조와의 연결

기존 formal 경로:
ApplicationProfile + ResourceRecommendation
→ 판단·Guard
→ DeploymentPlan
→ DesiredDeploymentSpec / Adapter

연결 원칙
- 연구 결과는 기존 Go의 ResourceRecommendation을 자동으로 대체하지 않는다.
- 연구 증거는 후보 평가의 근거로 전달할 수 있지만, 가격·가용량·CSP·리전이 없으면 최종 후보를 만들지 않는다.
- 연구 결과가 SLO를 만족한다고 예측해도 ResourceCandidate.Feasible=true 또는 실행 승인으로 자동 변환하지 않는다.
- 연구 결과를 DeploymentPlan.Operation으로 바로 변환하지 않는다. 현재 상태·cooldown·READY·정책·Guard가 필요하다.
- 기존 API·스키마는 기관 협의 전 변경하지 않는다.

주요 필드 대응
연구 출력 | 기존 Go 필드 | 주의
application_ref | ApplicationProfile.profile_id/app_id/app_version | INNO 원본과 식별자 일치 확인
앱 SLO | ApplicationRequirements.SLO | batch 목표와 E2E 목표 구분
selected_process_shape | ResourceCandidate.resource_hints | CPU affinity/replica를 VM CPU/노드로 자동 대입 금지
예측 지연·처리량 | ResourceScores/SLO 근거 | 연구 추정치와 Mock 점수 구분
ETRI 후보 정보 | DesiredInfrastructure/ResourceCandidate | 실제 CSP·리전·가격·가용량 필요
판단 결과 | DeploymentPlan.Operation | 예측만으로 DEPLOY/SCALE_OUT 발행 금지
피드백 | metadata/실행 이벤트 | action_id·READY·라우팅·요청 결과 연결 필요

3-5. 회의에서 결정해야 할 연동 항목

1. 경희대 모듈을 INNO가 별도 서비스로 호출할지, INNO 에이전트 내부에 포함할지.
2. INNO가 제공할 앱 조건·SLO·모니터링 데이터의 정확한 필드와 단위.
3. ETRI 자원 조회·생성 API의 후보·가용량·가격·상태 스키마.
4. 경희대가 추상 형상까지만 추천할지, ETRI 후보 점수까지 제공할지.
5. 연구 결과 봉투를 기존 Go 계약의 별도 evidence 객체로 둘지, 별도 API로 둘지.
6. available_at을 어디에서 기록하고 어떻게 지연 도착 관측을 구분할지.
7. 실제 action_id/decision_id/READY/라우팅/request_id의 공통 식별자 규칙.
8. SCALE_OUT/IN 판단의 연차별 구현 범위와 검증 방법.
9. 실제 VM·앱 준비 완료와 사용자 SLO 결과를 누가 수집할지.
10. 공동 개발 항목과 연차보고서 작성 책임.

“경희대 연구는 AI-App의 조건과 운영 관측을 직접 실행 명령으로 바꾸는 플랫폼 개발이 아니라, 요구·형상·수요·위험을 해석하고 판단에 필요한 근거를 만드는 연구 계층이다. 현재 세션에서는 정적 GPU/CPU 후보 선택, GPU 위험 보정, 서비스별 수요·준비 지연 예측, 완료 피드백, Alibaba SM 예측, 판단 계산 최적화를 검증했다. 이 결과를 INNO의 앱·실행 정보와 ETRI의 실제 후보·상태·가격에 연결하려면 공통 식별자, available_at, action/READY/사용자 결과 데이터가 필요하다.”
