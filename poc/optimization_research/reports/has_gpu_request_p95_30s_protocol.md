# HAS-GPU 요청 기록만 사용하는 30초 후 지연 예측 프로토콜 v1

이 문서는 [HAS-GPU 학습 적격성 감사](has_gpu_training_gate.md)를 바탕으로 만든 **후향적 탐색 평가의 고정 규칙**이다. 원본·코드·규칙의 해시를 먼저 고정하고, 건수 게이트를 통과한 뒤에만 모델 점수를 계산한다.

## 자료와 예측 시점

[Zenodo 공식 아티팩트](https://zenodo.org/records/15596511)에 대응하는 [감사 JSON](../artifacts/has_gpu_clock_ranges_v1.json)의 18개 `request_member`·`request_sha256`·실행·모델 계열만 선택한다. 평가 코드는 같은 SHA-256을 가진 [공식 GitHub 고정 커밋](https://github.com/KontonGu/HAS-GPU/tree/31f8ea29ca184193dbc7523736d77c817ddce980)의 해당 요청 CSV만 받는다. 원본이 다른 값을 반환하면 중단한다. GPU 기록의 시각·상태·quota·Pod 수는 특징, 창 선택, 결과 계산에 넣지 않는다. 실험 계열, 실행 번호, stress 표식도 특징으로 사용하지 않고 계열 전체 제외 분할과 실행별 집계에만 사용한다.

`test_batch.py`가 저장한 `timestamp`는 HTTP 요청의 **완료 시각**이며 `duration`은 클라이언트가 본 HTTP 왕복시간(초)이다. 각 요청의 시작은 `timestamp - duration`으로 근사한다. 요청 시각은 시간대가 없는 클라이언트 시각이므로 **각 실행 안의 상대 시각**만 사용한다. 서로 다른 실행의 벽시계가 동기화됐다고 가정하지 않는다. 응답을 받은 때부터 `timestamp`를 적을 때까지의 지연과 기록되지 않은 미완료 요청은 알 수 없다.

원본 SHA-256 확인에 더해 모든 선택 행의 `status_code=200`, `success=True`, BERT의 `mode=bert` 및 다른 세 계열의 `mode=image`, 양의 유한한 `duration≤30초`를 검사한다. 하나라도 위반하면 해당 실행을 조용히 제외하지 않고 전체 평가를 중단한다.

각 실행에서 첫 완료 시각을 `c₀`라 하면 예측 기준 시각은 `tₖ=c₀+30초+k×30초` (`k=0,1,…`)다. 미래 창은 서로 겹치지 않는다. `t+60초 ≤ 마지막 기록 완료 시각`을 만족하는 기준만 후보로 둔다. 입력은 **완료 시각**이 `(t−30초,t]`인 요청만 사용한다. 목표는 **복원한 시작 시각**이 `(t,t+30초]`인 요청의 `duration` p95다. 경계 포함은 코드의 `searchsorted(..., side="right")`로 고정한다. 요청이 `t` 전에 시작했더라도 `t` 뒤에 완료됐다면 입력에 넣지 않는다.

과거 완료 요청과 미래 시작 요청이 각각 **100건 이상**인 창만 1차 평가에 포함한다. `t+60초` 조건은 미래 창 종료 뒤 30초의 기록 여유를 요구해 우측 검열 위험을 낮추지만, 미기록 요청이 없었다는 증거는 아니다. 미래 요청 수로 창을 고르므로 평가 대상은 **나중에 확인된 활성 부하 창**이며, 무부하·저부하 전체 시점의 성능으로 확장하지 않는다.

## 고정 모델과 평가

양의 지연에 대해 `numpy.percentile(..., method="linear")`를 사용한다. 학습 목표는 `y=log(미래 시작 요청 p95 / 과거 완료 요청 p95)`다. 특징은 정확히 다음 4개다.

1. `log(과거 30초 p95)`
2. `log(과거 30초 p50)`
3. `log(과거 30초 완료 요청 수)`
4. `log(최근 10초 완료율 / 앞선 20초 완료율)`. 최근 완료율은 `(최근 10초 건수+1)/10`, 앞선 완료율은 `(앞선 20초 건수+2)/20`이다. 두 구간에 같은 초당 0.1건의 가상 계수를 넣는다.

계열 BERT, ResNet, ConvNeXt, MobileNet을 한 번씩 통째로 제외한다. 각 fold의 다른 세 계열에서만 평균·표준편차(`ddof=0`)를 계산해 특징을 표준화한다. 표준편차 0은 1로 처리한다. Ridge는 고정 `alpha=10`이고 절편을 정규화하지 않는다. 기준선은 예측 비율 1인 **과거 p95 유지**와 훈련 fold의 **평균 `y`**다. 하이퍼파라미터 선택, 계열·실행·stress 식별자 입력, 검증 fold를 이용한 보정은 하지 않는다.

주 지표 MALE은 `mean(abs(log(예측 미래 p95 / 관측 미래 p95)))`다. 진단 지표인 **20% 초과 과소예측률**은 `예측 p95 < 0.8 × 관측 p95`인 창의 비율이다. 각 실행의 창 평균을 먼저 계산하고, 계열 안에서 실행 평균, 마지막으로 4개 계열을 동일 가중치로 평균한다. 창 수로 계열을 가중하지 않는다. 실행별·계열별 수치와 각 fold의 훈련 창 수를 함께 남긴다. 기준선 대비 우위를 보이는지 그대로 보고하며, 점수를 보고 임계값이나 특징을 고치면 새 프로토콜로 분리한다.

## 점수 전 중단 게이트와 재현 순서

1. [`evaluate_has_gpu_request_p95_30s.py`](../scripts/evaluate_has_gpu_request_p95_30s.py)와 이 문서, [합성 테스트](../tests/test_has_gpu_request_p95_30s.py), 감사 JSON의 SHA-256 및 18개 요청 멤버의 경로·SHA-256을 `frozen_manifest.json`에 고정한다. 이후 파일 중 하나라도 바뀌면 평가를 거부한다.
2. `count_gate`는 해시를 검증한 요청 CSV에서 완료·복원 시작 **건수만** 계산한다. 각 계열에 적격 창이 있는 실행이 3개 이상이고 적격 창 총수가 15개 이상이어야 한다. 계열별 후보·적격 창 수와 실행별 적격 창 수를 기록한다. 실패하면 p95·모델 점수를 계산하지 않는다. 기준을 낮추려면 별도의 탐색 프로토콜을 작성한다.
3. 통과한 경우 `score`는 같은 요청 파일의 해시와 게이트 집계를 다시 확인한 뒤 고정한 세 방법을 비교하고 결과 JSON을 새 파일로 작성한다.

실행 순서는 `cd /home/researcher/ai-mcmp/research`에서 `python3 scripts/evaluate_has_gpu_request_p95_30s.py freeze`, `... count_gate`, `... score`다. **건수 게이트 산출물의 별도 검토가 끝나야 `score`를 실행한다.**

자료와 목표는 이미 아티팩트 구조와 요청 성공률을 살펴본 뒤 선택했다. 18개 실행은 4개 모델 계열과 하나의 실험 환경에만 해당하므로 계열 제외 결과도 독립 외부 검증이 아니다. 이 자료에는 발행된 스케일 명령·Pod/VM Ready 시각·대체 조치 결과가 없어 점수가 좋아도 배포·스케일 조치의 효과를 입증하지 않는다.
