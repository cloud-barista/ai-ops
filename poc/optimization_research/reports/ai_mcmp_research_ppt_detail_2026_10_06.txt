용어와 수치 해석
1. 응용 모델: BERT·RoBERTa·Qwen 등 실제 성능 측정 대상인 기존 AI 모델. 이 연구에서 새로 학습한 LLM이 아니다.
2. 예측기: 경희대 자료로 적합한 scikit-learn Extra Trees, 로지스틱 회귀, HGB. 기존 알고리즘 구현을 사용하되 학습된 트리/계수는 연구 자료로 새로 얻었다.
3. 우리 방법: 문제·정답·시간 경계·지원 조건·추천/보정 절차·검증을 구성한 연구 방법. 표준 학습기 자체의 최초 발명을 주장하지 않는다.
4. SLO: 사용자 서비스 목표라는 일반 개념. 정적 연구의 목표는 수집기가 생성한 배치 목표이며 실제 사용자 종단간 SLO와 구분한다.
5. q90: 조건부 90 분위 추정. 관측 피복률이 약 90%라는 평가와 운영 안전 보장은 서로 다르다.
6. 손실 감소율 = 100×(기준선 손실−우리 손실)/기준선 손실. 음수는 악화다. 다른 기간·집합의 개선율을 더하지 않는다.

A1. 정적 GPU/CPU 형상 추천

[1] 담당 항목과 문제
응용 조건을 이해한 인프라 형상 추천의 부분 문제다. 모델·입력·동시성이 주어졌을 때 후보별 배치 지연과 처리량을 미리 추정하고, 두 목표를 함께 만족하는 최소 프로세스 형상을 고른다. CPU affinity를 제어하는 스케줄러나 실제 VM 상품 추천을 구현한 연구는 아니다.

[2] 데이터 출처·사용량·기간·정제·위치
경희대 기존 SQLite 7 개, 2026-09-10~11 실행 기록을 진단했다. 전체 9,591실행, 유효 학습 후보 9,445실행, 671 workload 그룹이다. 136중단·10실패는 성공 성능 정답과 분리했다. 실패 원인을 자원 불가능 정답으로 재명명하지 않았다.
주 학습 자료는 local-exhaustive 4,856실행·575그룹·9응용 모델이며 CUDA 4,600 건, CPU 256 건이다. 같은 host=icns에서 후보 형상을 비교할 수 있어 선택했다. live 2,640 행은 10 작업 그룹에 집중돼 주 학습 자료를 대체하지 않는다. 다른 호스트와 별도 입력 캠페인은 주 학습에 합치지 않았다.
원본: /path/to/aiops/runs/khu-hf-local-exhaustive/executions.sqlite3
정제 스냅샷: R/data/audit_v1/measurements.parquet

[3] 입력 특징·정답·단위·시점
입력: model_id, model_revision, device, batch_size, max_length, request_concurrency, cpu_threads, cpu_core_limit, replica_count, repeats. 실행 후 telemetry·지연·처리량을 특징에 넣지 않는다.
정답: 배치 호출 latency_p95_ms와 examples_per_second. 2replica의 p95는 더 느린 replica, 처리량은 합계다. 후보 판정의 요청/초는 examples/sec÷batch_size이며 실제 온라인 요청 E2E 처리량이라는 의미가 아니다. 형상 선택 전에 모델과 입력 조건을 알아야 한다.

[4] 모델 선정·구성·전처리·설정
범주형 model_id/revision/device를 one-hot, 나머지를 수치로 넣는 scikit-learn Pipeline이다. ExtraTreesRegressor 하나가 두 출력의 로그값을 함께 학습하고 exp로 복원한다. 200trees, min_samples_leaf=2, max_features=1.0, random_state=42, n_jobs=2. 그룹마다 총 학습 가중치가 같다.
비선형 표형 상호작용을 처리하기 위해 RF·Extra Trees를 후보로 두었다. 검증 점수는 두 출력의 그룹 동일가중 평균 절대 로그오차를 평균한 값이다. 중앙값 0.978937, RF 0.192705, Extra Trees 0.192454로 Extra Trees를 선택했다. RF와의 차이는 약 0.000252로 작아 일반적 우월성을 주장하지 않는다. 새 딥러닝 구조·LLM 사전학습 모델을 불러온 연구가 아니다.

[5] 분할·누출 방지
같은 workload의 모든 CPU/GPU 자원 대안을 한 그룹으로 묶었다. 모델별 그룹 분할 결과 train 396그룹/3,348행, validation 89/748, test 90/760이다. 반복과 후보가 학습·시험 양쪽에 흩어지지 않는다. 알려진 모델/revision·호스트·장치·수치 범위 밖은 ABSTAIN하며 모델×장치 세부 지원 범위도 확인한다. 같은 기존 모델 안의 새로운 입력 조건 평가이며 모델 계열 전체 제외 시험은 아니다.

[6] 기준선·우리 방법·수식·흐름
기준선은 학습 분할의 모델ID×장치별 로그 성능 중앙값이다.
우리 흐름: 구조화 앱 조건 → 8후보 생성 → 각 후보 두 성능 예측 → 공동 목표 검사 → 최소 후보 또는 보류.
8후보 = GPU 프로세스 replica {1,2} × affinity cores {2,4,8,16}.
후보 c의 통과 조건: exp(f_latency(x,c))≤L, exp(f_throughput(x,c))/batch_size≥T.
통과 집합에서 (replica_count, cpu_core_limit)의 사전식 최소값을 선택한다. 지원 밖/입력 불일치/모든 후보 실패이면 ABSTAIN한다. 가장 큰 형상을 무조건 추천하지 않는다.

[7] 기존 알고리즘과 경희대 구성
나무 학습과 one-hot은 표준 라이브러리다. 경희대 구성은 두 양의 성능 정답, 그룹 분할·가중치, 공동 목표 선택, 지원 범위·보류, 증거·출처 검증, 고정 기준선 비교다. 실행 성능을 데이터로 학습해 추천 근거로 만든 것이 연구 내용이다.

전체 test 760행 중앙 APE: p95 73.7144→16.9917%, samples/sec 66.0078→10.4123%. 행별 예측 오차와 작업별 추천 성공은 별도 지표다.

A2. GPU 고사용률 위험 확률과 전날 기계·슬롯 보정

[1] 담당 항목과 문제
배포·스케일 판단의 운영 위험 입력 및 운영 피드백 활용 연구다. 최근 사용률로 다음 30 분 고사용률 사건을 예측하고 기계·슬롯별 확률 편향을 줄인다. 사건 확률을 실제 SCALE_OUT 명령의 효과로 해석하지 않는다.

[2] 데이터 출처·사용량·기간·정제·위치

[3] 입력 특징·정답·단위·시점
5 분 평균 사용률 창 중 판단 전 완료된 세 창을 사용한다. 11 특징은 older_util_filled, middle_util_filled, current_util, history_mean, history_max, current_minus_oldest, current_high, any_recent_high, older_valid, middle_valid, past_gap_s다.
정답 y=1은 판단 뒤 30 분의 여섯 5 분 창 중 하나라도 해당 GPU 슬롯 평균≥80%인 경우다. 주 집합은 과거 완전 관측·현재<80%다. 확률 p는 0~1, 사용률은 %다. 미래 30 분 정답이 끝난 뒤에만 보정 피드백으로 사용할 수 있다.

[4] 모델 선정·구성·설정
학습 중앙값으로 결측 대체, 학습 모수로 표준화, L2 LogisticRegression의 통합 확률 p0를 사용한다. C=.1/1/10 중 validation Brier로 선택한 C=10이다. 저장 model_spec.json의 계수·절편·전처리 모수로 재생하는 구조다. 사전학습된 외부 모델을 가져온 것이 아니다.
상태 분리·관측 품질 특징의 독립 이득이 확인되지 않아 후속 보정에는 통합 모델을 고정했다. 간단한 확률 학습기와 강한 확률표 기준선을 비교해 피드백 추가 기여를 분리했다.

[5] 분할·누출 방지
기반 시간 분할은 2017-10-04~11-15 train, 11-16~11-30 validation, 12-01~12-15 test UTC다. 저장 기본 모델의 train은832,496판단(완전 과거832,172), validation은292,580판단(주 평가층207,347)이다. 첫 학습/검증/후속 시험의 기계 해시 집합을 분리한다. 신규 37기계와 후속 51기계는 서로 다른 시험이다.
보정은 전날 완료됐고 당일 00:00 UTC까지 전달된 정답만 사용한다. 기계×GPU 슬롯×시간당 첫 적격 판단만 남겨 과밀 중복을 줄인다. 공개 자료에 실제 전달 시각이 없어 완료 즉시 전달을 가정했다.

[6] 기준선·수식·흐름
기본 기준선은 현재 고사용률 상태와 최근 초과 여부에 대한 Beta(1,1) 평활 확률표다.
보정 흐름: 최근 GPU 계측 → p0 → 전날 기계 절편 δm → 슬롯 잔차 gm,s → p_final.
z=logit(clip(p0,1e-9,1−1e-9)).
δm은 Σ전날[y−sigmoid(z+δm)]−20δm=0을 풀고 ±0.5로 제한한다.
p_machine=sigmoid(z+δm).
gm,s=clip(Σ슬롯[y−p_machine]/(Σ슬롯[p_machine(1−p_machine)]+20),−0.5,0.5).
p_final=sigmoid(z+δm+gm,s).
기계 또는 슬롯 피드백이 없으면 해당 보정은 0이다. 슬롯 추가 비교 기준선은 p0가 아니라 벌점이 있는 정확한 기계별 절편이다.

[7] 기존 알고리즘과 경희대 구성

LMM10분의4.19%는 손실5%개선 기준 아래다. 전체 조건이 채택 기준을 통과했다고 표현하지 않는다. Coding5/10의 보정은 점수를 바꾸지 않았고 Coding30에는 소폭 손실 증가를 동반했다. 목표 정답과 평가 집합이 다르므로 A3의43.6%와 직접 우열 비교하지 않는다.

A5. Copilot·BurstGPT 호출 수요와 완료 피드백

[1] 담당 항목과 문제
토큰이 없는 기록으로 가능한 호출 수요를 연구하고, 서비스별 분포 이동과 희소 호출의 정규화 문제에 대응한다. Copilot과 BurstGPT는 서로 다른 자료·모델이다. 이 절에서 한 범주로 소개하되 점수를 합치지 않는다.

[2] 데이터 출처·사용량·기간·정제·위치
Copilot: Azure GHCP coding agent 2026의 선택된 6월 3~7 일 압축 파티션 5 개,185,011 세션·5,734,290 호출; 해당 시간창 내 5,727,290 호출, 창 밖 7,000. 압축 원본 합계 2,003,061,268바이트를 보존했다. 1,440 개 5 분 구간이다. 세션 시작 파티션 이후 날짜로 이어진 호출도 합산하고 중복 session_id는 거절했다. 제외한 6월 1~2 일 세션의 후속 호출은 누락 가능하다.
R/data/external/ghcp_coding_agent_2026_days03_04/ 및 ghcp_coding_agent_2026_days05_07/
공식 https://github.com/Azure/AzurePublicDataset/releases/tag/ghcp-coding-agent-2026
BurstGPT: R/data/external/burstgpt_v2/BurstGPT_3.csv,전체5,344,021행. 첫 모델의 상대일225~284 60일은3,452,522행·17,280구간. 후속285~314평가까지90일은4,485,656행. 절대 UTC가 아닌 상대초 Timestamp다. ChatGPT/GPT4×API/Conversation4집합. 첫 부분 구간은 결측, 범위 안 미기록 구간은 기록 호출0이며 실제 서비스 무호출을 보장하는 heartbeat는 없다. 원출처는 같은 폴더 SOURCE.md에 보존돼 있다.

[3] 입력 특징·정답·단위·시점
정답 u_t=max(y_t,...,y_t+h), y=5분 기록 호출 수, h1/2/6. 기간은10/15/35분, 값은 그 기간의 최대 5분 호출 수다.
Copilot은11시간/과거 특징과 m=직전1시간 평균을 쓴다. 원시 모델의 정규화 잔차 e_i=(u_i−raw_i)/m_i를 완료 후 보정에 쓴다.
BurstGPT는 s=max(직전1시간 평균,1)로 작은 분모를 안정화한다. 10특징: lag1/2/3/12 비율, hourmax/q90비율, 최근6평균/max(그전6평균,1), log1p평균, 시간창0비율, 마지막양수부터bin거리(상한288). 상대 시각에 절대 요일 특징을 붙이지 않는다.

[4] 모델 선정·구성·설정
Copilot parent는 지연별 HGBq90 3개이며 표준150/lr.05/leaf7/minleaf20/L2=1/seed42다. 새 피드백 연구에서 모델을 다시 학습하지 않고 parent3개를 고정했다.
BurstGPT는4집합×3지연×(상대/절대 HGB) 총24모델이다. 같은 고정 HGB설정, 주 방법은 u/s를 학습하고 s/mean_train(s) 가중치로 절대 호출 pinball에 맞춘다. 절대 HGB는 비교용이다. 희소성 특징의 개별 기여를 독립적으로 입증한 것은 아니다.

[5] 분할·누출 방지
Copilot6월3~5 train851/850/846행,6일validation,7일test287/286/282행. 7일은 이전실험에 노출돼 후향 탐색이다.
BurstGPT225~244 train20일,245~254 validation10일,255~284 test30일. 후속285~314의 추가30일은 원24모델을 고정해 평가했다. 정답 끝나는 i+h+1이 분할 경계 전에 있는 origin만 학습/검증한다.
피드백은 i+h+1+전달 지연≤현재t인 이전 origin만 쓴다. 미래 target배열이 저장돼 있는 재생 함수에서도 이 조건 이후를 접근하지 않도록 검사했다. 실제 운영에서는 전체 미래배열을 넘기는 재생 API를 이력 저장 Adapter로 바꿔야 한다.

[6] 기준선·수식·흐름
최근 288적격 origin 중 최소 96 개 잔차를 모은다. delta=max(0,q90(e_i)), corrected_t=raw_t+scale_t×delta. 보정된 예측의 잔차를 다시 쌓는 재귀 방식이 아니라 원시 예측의 잔차다.
Copilot은 첫 validationorigin864, BurstGPT는train끝5760부터 완료 잔차를 사용한다. 기준선도 같은 보정을 받으며 validation에서 선택한다. Copilot 기준선은 학습 가중peakq90·최근1시간max/q90/mean. BurstGPT는 여기에 절대HGB 등을 비교한다.
Copilot 전달 지연0/5/30분의9조건을 평가했다. BurstGPT는 서비스×유형×지연12조건을 모두 보고한다.

[7] 기존 알고리즘과 경희대 구성
HGB·분위수 잔차는 표준 알고리즘이다. 경희대는 완료 정답만 사용하는 보정, 지연 정렬, 원시 잔차 유지, 기준선에도 동일 보정, 희소분모 1·과거 0비율·마지막호출거리, 조건별 공개 평가를 구성했다. 희소서비스 전반에 이긴 새로운 보편 알고리즘이라는 결론은 없다.

A6. Alibaba GPU SM 계측의 다음 시간 예측

[1] 담당 항목과 문제
운영 관측을 활용하는 판단 입력 연구다. 현재 SM 사용률을 다음 시간에도 그대로 사용하는 persistence를 보완한다. GPU 우선순위 스케줄러, 빈패킹, K8s 개발을 수행한 연구는 아니다.

[2] 데이터 출처·사용량·기간·정제·위치
사용 자료는 Alibaba cluster-trace-gpu-v2026의 시간별 pod 계측이다. Spot GPU 2026 자료와 구분한다.
공식 설명: https://github.com/alibaba/clusterdata/blob/master/cluster-trace-gpu-v2026/docs/schema.md
기존 상대 day109~115: R/data/external/alibaba_gpu_2026_days109_115/
미래 상대 day116~122: R/data/external/alibaba_gpu_2026_days116_122/
미래 원본은 parquet168개, 256,279,382행, 13,595,282,885바이트다. 모델 평가는 이 원본 중 정제 조건을 만족한 하위 집합으로 수행했다. 모호한 pod×시간 중복과 불안정한 workload를 제외했다. GPU 요청이1개이며 과거3시간과 다음 정답 시간의 server가 같은 기록을 구성했다. 주 집합은 네 시간 모두 server의 전체 GPU 수가1개인 엄격한 조건이다. 각 집합의 학습·검증·시험 행 수는 C9 표를 따른다.

[3] 입력 특징·정답·단위·시점
범주형2개: gpu_spec_public, priority_class.
수치11개: sm_current, sm_lag1, sm_lag2, sm_mean3, sm_std3, sm_delta1, sm_delta2, hour_sin, hour_cos, server_gpu_count, cpu_request_cores.
정답은 다음 시간의 SM 계측(%), 잔차 정답은 nextSM−currentSM(percentage point)이다. 현재 시간의 계측이 완료된 뒤 판단한다. 다음 시간의 계측이 끝나야 정답이 완료된다. 원본에는 실제 전달 시각이 없어 완료 즉시 가용하다고 가정한다. priority_class는 입력 범주이며 정책 개선의 정답이 아니다.

[4] 모델 선정·구성·설정
OneHotEncoder(handle_unknown='ignore', dense 출력)와 HGB 회귀를 연결한다. 설정은 loss='absolute_error', max_iter=150, learning_rate=.05, max_leaf_nodes=15, min_samples_leaf=50, l2_regularization=1, early_stopping=False, random_state=42다.
직접 SM 예측과 변화 잔차 예측을 비교했다. 잔차 방법은 clip(sm_current+alpha×HGB(X),0,100)이다. validation에서 alpha={0,.25,.5,1} 중1을 고정했다. 미래 기간의 정답을 읽기 전에 v1의 두 집합별 모델과 persistence 기준선을 고정했다. 후속 v2/v3 모델을 이 확인 시험에 섞지 않는다.

[5] 분할·누출 방지
학습은 workload 해시<70과 day109~112, validation은 해시70~84와 day113, 기존 test는 해시85~99와 day114~115다. 과거·정답이 분할 경계를 넘어가지 않게 구성하고 workload당 총 학습 가중치를 같게 했다.
미래 확인은 사전 고정한 해시85~99의 day116~122다. 첫 시간의 과거 특징에는 기존 day115의22/23시를 사용했다. 학습 workload를 제외한 집합의 새로운7일 결과다. 이 집합에는 이전 validation/test 또는 가공 자료에 등장한 workload가 있을 수 있으므로 '이전에 전혀 관측되지 않은 모든 응용'에 대한 검증과 구분한다. 완전히 새 workload에 대한 진단은 별도 층으로 보고했다.

[6] 기준선·방법·흐름
기준선: nextSM=currentSM.
우리 방법: 과거 계측의 수준·추세·자원 범주에서 다음 시간에 바뀔 잔차를 학습해 현재 SM에 더한다. alpha=0이면 persistence다.
시간별 pod 계측 → 중복·이동·연속성 검사 → 과거3시간 특징 → HGB 잔차 → 현재값에 더하기 → 0~100으로 제한.
실제 추론에서는 미래 server 이동을 미리 알 수 없다. 미래 server 일치 조건은 저장 자료의 평가층 구성 조건이며, 현장 추론 지원 검사로 미래 정보를 읽어서는 안 된다. 자세한 운영 연결은 통합 설계서5-7절에 있다.

[7] 기존 알고리즘과 경희대 구성
HGB와 잔차 회귀는 기존 원리다. 경희대는 단일 GPU 조건, workload·시간 분할, 연속 계측과 server 일치, 고정 모델의 미래 기간 확인, 지원 검사와 집합별 평가를 구성했다. 새 GPU 구조나 스케줄러를 발명했다고 주장하지 않는다.

[8] 지표·수치·사례
미래 주 집합: 12,097행·30workloads.
- MAE: persistence1.627406 → 잔차1.481500, 8.97% 감소.
- workload 동일가중 MAE: .938041 → .719198.
- p95 절대오차: 4.373794 → 4.121206.

- MAE: 2.073320 → 1.814805, 12.47% 감소.

[9] 적용 범위·한계
같은 공개 클러스터의 미래 시간 SM 예측 개선이다. 새 클러스터·GPU 세대·새 응용 전반의 일반화는 입증하지 않았다. 보조 집합은 다중 GPU server를 포함해 물리 슬롯의 SM 해석이 엄격 집합과 다를 수 있다. 실제 사용자 지연, OOM, 요청 부하, 증설 조치 효과는 정답이 아니다.

A7. 판단 추론 계산 최적화

[1] 담당 항목과 문제
배포·제어 판단을 위한 추론 비용 최적화다. 같은 후보의 여러 SLO와 여러 작업의8후보를 반복 예측하면서 생기는 중복 계산·함수 호출 비용을 줄인다.

[2] 데이터 출처·사용량·기간·정제·위치
A1의 저장 Extra Trees와 local-exhaustive 후보를 재사용했다. 새로운 성능 정답이나 학습 자료는 없다.
동일 후보: 9응용 모델에서5작업씩45격자 ×25합성 SLO=1,125질의, 5반복=5,625응답 쌍.
서로 다른 후보: 575고유 격자 ×8행. 최신 v7 확인에서는9짝 반복으로 shared_slo/copied_slo/unique_grids를 비교했다. 온라인 사용자 질의 빈도나 서비스 trace 부하가 아니다.

[3] 입력·출력·단위·시점
A1과 같은 request/response를 사용하고, 예측값·선택·보류를 바꾸지 않는 것이 조건이다. 지표는 준비된 모델의 함수 벽시계(ms), 누적 CPU(ms), peak RSS(MiB), 정규화 JSON 동등성이다. 모델 적재·네트워크·배포·사용자 p95는 포함하지 않는다.

[4] 모델·계산 구성·설정
모델은 A1의200tree Extra Trees이며 새 학습은 없다. 같은 격자의 성능은 한 호출 안에서 재사용하고, 서로 다른 격자는 max_grids=256으로 묶는다.
v7은 지원행1,024개 이상에서 행을 두 연속 chunk로 나누고 workers=2로 계산한다. 각 chunk에서200개 tree의 순서와 float64 누적 순서를 보존한다. 모델의 n_jobs와 caller 설정을 바꾸지 않고 pool은 호출 후 닫는다. 작은 입력은 직렬이며 큰 묶음이 실패하면 원래 격자별 추론으로 재시도한다.
저장 모델 로드는 scikit-learn1.6.1 등 환경과 해시를 확인한다. private forest 검증 API를 쓰므로 다른 버전에 무조건 호환된다고 말하지 않는다.

[5] 분할·동등성 검증
모델 정확도 시험과 다른 문제다. 동일 입력의 기존·새 경로를 짝지어 비교하며 최신9짝은 v6와 row2다. 입력 순서, 동일/복사 리스트, 보류, SLO 경계와 재시도를 검사했다. np.nextafter 목표 경계1,080사례와 관련48테스트의 저장 결과를 확인했다. tree 완료 순서가 바뀌어 생기는 부동소수점 차이를 피하기 위해 행을 분할했다.

[6] 기준선·방법·흐름
단건 반복 → 동일 격자 예측 재사용 → 256격자 묶음 → v7 행 분할.
각 벤치마크의 시점과 비교 경로가 다르므로 속도비를 곱하지 않는다. 원시 지연·처리량 예측은 SLO와 독립이므로 이 예측만 재사용하고 각 SLO 검증·판정은 다시 수행한다. 호출 사이의 영구 캐시는 아니다. 복사한 후보 리스트도 내용·순서·자료형이 안전하게 같은지 확인한 뒤 재사용한다.

[7] 기존 알고리즘과 경희대 구성
새 학습기 없이 재사용 키, 묶음 매핑, 행 분할, 동일 누적 순서, 지원 검사와 실패 재시도를 구현했다. 반환 결과 전체의 동등성을 계산 최적화 채택 조건으로 두었다.

슬라이드 01. 경희대 연구 범위와 기관 역할
화면용 핵심 문장
- 경희대: 응용 요구 해석, 추상 형상 추천, 배포·스케일 판단 메커니즘.
- 이노그리드: AI-App 프레임워크, 모니터링 관리, 명세 변환과 응용 실행.
- ETRI: 실제 CSP·리전·VM 선택과 인프라 생성·삭제.
- 현재 성과는 연구 모듈이며 실제 행동 효과는 다음 검증 과제다.
표·도식: 세 기관을 가로로 놓고 '연구 형상/판단 → 명세·실행 요청 → 실제 인프라'와 결과 반환 화살표를 그린다. 경희대 상자 안에 이번 일곱 연구를 넣는다.
상세 발표자 설명
계획서의 담당 항목을 유지하면서 전체 플랫폼을 중복 개발하지 않는 방향이다. 기존 CPU/GPU VM PoC는 알고리즘 검증을 위한 최소 산출물이다. 앱 등록·버전·라이프사이클·운영 모니터링 플랫폼을 새 연구 성과로 추가하지 않는다. 동일 VM 다중 응용 빈패킹·GPU 공유·로컬 프로세스 스케줄러·K8s도 현재 필수 범위가 아니다. 정적 자료의 CPU affinity는 측정 조건이며 이 제외 범위를 변경한 것이 아니다. 실제 PoC 전체 동작을 이번에 재검증하지 않았다.
근거: R/reports/ai_mcmp_rr_status_2026_10_06.txt; G/AGENTS.md; 통합 설계서 1·2·8절.

슬라이드 02. 풀려는 문제와 현재 해결 수준
화면용 핵심 문장
- 같은 앱도 입력·동시성·자원 조건에 따라 성능이 달라진다.
- 운영 위험과 미래 요청량을 판단 전에 알아야 한다.

- 예측 근거를 실제 실행 판단으로 연결할 데이터가 더 필요하다.
표·도식: 문제 / 연구 출력 / 현재 검증 수준 세 열. 형상 성능, 고사용률 확률, 미래 토큰·호출량, 판단 계산 시간 네 줄.
상세 발표자 설명

 → 연구 증거 결과

운영 결과는 '완료 및 전달 확인' 상자를 거쳐 연구 모듈로 돌아간다. 현재 구현된 개별 함수와 제안 중인 통합 연결선은 선 모양을 다르게 표시한다.
상세 발표자 설명
이 구조는 통합 설계 초안이며 단일 통합 에이전트의 완료 구현을 그린 것이 아니다. 네 종류의 값은 임의로 한 점수에 합산하지 않는다. 특히 토큰/호출량을 GPU 수로 환산하려면 같은 앱·실행 설정에서 실측한 처리 용량이 필요하다. 현재 없는 값을 0이나 높은 추천 점수로 채우지 않는다.
근거: 별도 통합 설계서 3~7절; 기존 함수·계약 대응표.

슬라이드 05. 정적 형상 추천의 방법
화면용 핵심 문장
- 입력: 모델·batch·입력 길이·동시성·프로세스 자원 조건.
- Extra Trees로 후보별 배치 p95와 examples/sec를 함께 예측.
- 지연·요청률 두 목표를 함께 검사해 최소 후보 선택.
- 지원 범위 밖 또는 만족 후보 없음은 ABSTAIN.
표·도식: 1/2replica×2/4/8/16affinity의8칸 격자. 각 칸에 두 예측값·통과 표시. 통과 후보 중 (replica,affinity) 최소에 색을 준다. 요청률=examples/sec÷batch를 각주로 넣는다.
상세 발표자 설명
예측기 하나의 두 출력은 로그 변환된 양의 성능이다. 그룹 가중치와 그룹 분할로 같은 workload의 후보가 학습·시험에 섞이지 않게 했다. RF와 Extra Trees 중 검증 점수가 소폭 더 낮은 Extra Trees를 선택했다. 우리의 방법은 학습 예측을 공동 목표 검사와 최소 형상 선택·보류에 연결한 절차다. replica와 affinity는 프로세스 실험 값이므로 VM 노드 수와 CPU 사양으로 자동 변환하지 않는다.
근거: A1; R/scripts/train_performance.py; R/scripts/assess_gpu_shape.py.

C2. 모델·수식·평가 규칙 요약
성능 Extra Trees: 로그 변환한 두 출력, tree200, minleaf2, seed42, n_jobs2. one-hot3범주형과7수치 특징.
Philly: 학습 중앙값 대체·표준화→L2 로지스틱 C10→전날 기계δ/슬롯g. 기계·슬롯 벌점20, 보정 각각±.5.
토큰/호출 q90 HGB: iter150, lr.05, leaf7, minleaf20, L2=1, early_stopping=False, seed42. 서비스·지연별로 분리한다.
SM 잔차 HGB: absolute_error, iter150, lr.05, leaf15, minleaf50, L2=1, seed42. 현재값+잔차를0~100으로 제한한다.

APE=100×abs(yhat−y)/abs(y), 이번표는행별APE의중앙값이다.
Brier=mean((p−y)^2). 사건 확률의 오차이며 낮을수록 좋다.
Pinball=mean((y−q)×(.9−1[y<q])). 토큰 또는 호출 수 원단위의 분위수 손실이다.
피복률=mean(y≤q). 표본의 경험적 피복률이며 신뢰구간이나 SLO 보장과 다르다.
SM MAE=mean(abs(nextSM−predSM)), 단위는 percentage point다. macro는 workload별 MAE의 동일가중 평균이다.
짝별 속도비 중앙=median(time_base_i/time_new_i). median(base)/median(new)와 다를 수 있다.

준비 지연 정답 경계 예시
결정 t=12:00, 준비 10 분(h=2), y_t=[12:00,12:05), y_t+1=[12:05,12:10), y_t+2=[12:10,12:15).
예측값은 세 구간의 최대5분량이다. 정답은12:15에 끝나고12:17에 전달됐다면12:16의 피드백으로 사용할 수 없다. 가용 시각이 없는 공개 자료는 즉시 가용을 가정하며 이를 근거에 남긴다.

Q. 모델은 직접 만들었나?

Q. 지금오토스케일링이완료됐나?
A. 실제 행동 효과와 통합 정책은 아직 검증하지 않았다. 개별 신호와 가상 정책 연구가 있다.
Q. 왜여러데이터를따로쓰나?
A. 관측하는 정답이 다르기 때문이다. 토큰·호출 수요, GPU 위험, SM, 배치 성능은 같은 라벨이 아니다. 앱 용량과 실제 행동 결과의 연결 없이 하나의 배포 정책을 학습했다고 말할 수 없다.
Q. 다음에가장필요한것은?
A. 앱 요구·후보·available_at·action 접수·READY·라우팅·사용자 결과의 연결 기록과 새 앱/호스트의 미사용 시험이 필요하다.

C12. 추가 재현 안내와 미채택 연구의 코드
아래는 후속 재개 때 사용할 CLI 형식이다. 이번 문서 작성에서는 실행하지 않았다. 기존 산출물을 덮어쓰지 않는 새로운 stage에 코드·tests·프로토콜을 같은 디렉터리 구조로 준비한다. source 자료는 보존된 원본을 읽도록 연결하며 다운로드하지 않는다.

Coding의 현재 CLI는 별도의 --output을 받지 않고 코드 위치의 ROOT 아래에 출력한다. 새 stage에 원본 CSV의 읽기 경로와 scripts/evaluate_azure_code_input_demand.py, tests/test_azure_code_input_demand.py, reports/azure_code_input_demand_protocol.md를 준비한 다음 아래 순서를 따른다.
PYTHONDONTWRITEBYTECODE=1 OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 /usr/bin/python /tmp/ai_mcmp_coding_reproduction_new/scripts/evaluate_azure_code_input_demand.py freeze
PYTHONDONTWRITEBYTECODE=1 OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 /usr/bin/python /tmp/ai_mcmp_coding_reproduction_new/scripts/evaluate_azure_code_input_demand.py evaluate_once
새 stage의 재현 freeze는 새로운 파일이다. 현재 저장된 원래 freeze를 수정하지 않는다.

Philly 기본 학습은 고정 프로토콜과 준비 자료, dry-run 해시가 필요하다. 다음은 자리표시자를 실제 고정값으로 채워야 하는 명령 템플릿이다.
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=/home/researcher/ai-mcmp/research/scripts OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 /usr/bin/python /home/researcher/ai-mcmp/research/scripts/evaluate_philly_gpu_risk.py --expected-dry-run-sha256 <고정 dry-run SHA256> --output /tmp/ai_mcmp_philly_reproduction_new
해시 확인 없이 임의 값을 넣거나 freeze를 변경하지 않는다. 실제 필수 입력과 프로토콜은 원코드의 --frozen-protocol/--draft-protocol/--prepared/--source/--normalization-audit/--source-audit 경로를 따른다.
슬롯 보정은 저장 p0와 전날 피드백을 읽어 policies/philly_slot_day.py의 calibrate_day()를 재생한다. CLI의 collect는 다운로드 단계이므로 이 안내에는 포함하지 않는다. 현재 score_once를 원래 결과 폴더에 재실행하지 않는다.

BurstGPT는 새로운 stage에 scripts/burstgpt_sparse_calls.py, 원검증기 verify_burstgpt_sparse_calls.py, 정정검증기 verify_burstgpt_sparse_calls_precision.py, tests/test_burstgpt_sparse_calls.py, reports/burstgpt_sparse_calls_protocol_v1.json을 준비한다.
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=/tmp/ai_mcmp_burst_reproduction_new/scripts:/home/researcher/ai-mcmp/research/scripts OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 /usr/bin/python /tmp/ai_mcmp_burst_reproduction_new/scripts/burstgpt_sparse_calls.py prepare --stage /tmp/ai_mcmp_burst_reproduction_new
같은 명령의 mode를 train, evaluate로 바꿔 순서대로 실행한다. 마지막에 정정검증기를 사용한다.
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=/tmp/ai_mcmp_burst_reproduction_new/scripts:/home/researcher/ai-mcmp/research/scripts OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 /usr/bin/python /tmp/ai_mcmp_burst_reproduction_new/scripts/verify_burstgpt_sparse_calls_precision.py --stage /tmp/ai_mcmp_burst_reproduction_new
새로운 독립 데이터 검증이 아니라 기존 결과의 재현이다. 원검증기의 최초 정밀도 실패도 역사적 근거로 보존한다.

Copilot 보정의 기존 CLI 형식(새 stage 준비 후):
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=/tmp/ai_mcmp_copilot_feedback_reproduction_new/scripts:/home/researcher/ai-mcmp/research/scripts OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 /usr/bin/python /tmp/ai_mcmp_copilot_feedback_reproduction_new/scripts/evaluate_copilot_call_feedback.py prepare --stage /tmp/ai_mcmp_copilot_feedback_reproduction_new
