# 다른 응용 canary로 GPU 확장 반응을 보정할 수 있는가?

**결론: 현재 자료에서는 효과가 확인되지 않았다.** 처음 보인 큰 지연시간 오차 감소는 수집기 버전 변경과 겹친다. 같은 버전 안에서 검증하면 canary 측정을 추가해도 개선되지 않는다.

## 가설과 자료

새 AI 모델을 GPU 1개에서 한 번 실행한 뒤 GPU 2개의 배치 p95 지연과 요청 처리량을 예측한다. 여기에 별도의 작은 응용인 `bert-tiny-long-burst`를 같은 회차에서 실행해 현재 호스트 상태를 알려주는 canary로 사용하면 예측이 나아질 것이라고 가정했다.

원본은 `khu-hf-live/executions.sqlite3` (`/path/to/aiops/runs/khu-hf-live/executions.sqlite3`)이다. 고정된 24개 조건을 110회 반복해 2,640개 성공 실행을 기록했다. GPU 1→2개 쌍이 있는 5개 대상 AI 모델을 하나씩 통째로 제외하고 나머지 4개 모델로 학습했다. 제외 모델의 현재 GPU 1개 실행과 canary 실행은 모두 예측할 GPU 2개 실행보다 먼저 끝났는지 검사했다. 지연·처리량 결과와 모델 파라미터 크기는 **대상 모델의 GPU 1개 실행**에서만 읽는다. 대상 GPU 2개 결과는 학습 입력에 사용하지 않는다.

회차는 실제 시작 시각 순서다. 첫 63회는 `khu-hf-direct-collector/v1`, 뒤 47회는 `v2`이다. 따라서 다음 네 평가를 분리했다.

| 평가 | 학습 회차 | 시험 회차 | 설명 |
| --- | ---: | ---: | --- |
| 혼합 | 앞 70 | 뒤 40 | 두 수집기 버전 혼합 |
| v1 내부 | v1 앞 43 | v1 뒤 20 | 같은 수집기 |
| v2 내부 | v2 앞 27 | v2 뒤 20 | 같은 수집기 |
| 버전 이동 | v1 전체 63 | v2 전체 47 | 변경 직후 전이 |

각 모델의 시험 회차는 시간상 학습 회차보다 뒤다. 지표는 모델별 평균 절대 로그오차를 다시 5개 모델 평균으로 집계했다. 낮을수록 좋다.

## 검증 결과

| 평가 | GPU 1개 기준 예측 | 기준 + canary | 기준 + 수집기 버전 | 최근 10회 다른 모델 결과로 보정 |
| --- | ---: | ---: | ---: | ---: |
| 혼합, 배치 p95 | 0.945 | 0.418 | **0.182** | 0.365 |
| v1 내부, 배치 p95 | **0.116** | 0.117 | 0.116 | 0.120 |
| v2 내부, 배치 p95 | **0.177** | 0.180 | 0.176 | 0.177 |
| 버전 이동, 배치 p95 | 1.335 | 1.331 | 1.334 | **0.452** |

혼합 평가에서 canary의 개선은 커 보이지만, **추가 측정 없이** 수집기 버전을 입력한 기준선이 더 좋다. v1과 v2 내부에서는 canary가 각각 0.116→0.117, 0.177→0.180으로 오히려 약간 나빠졌다. v1 전체로 학습해 v2로 옮길 때도 1.335→1.331로 효과가 거의 없다. 최근 10회 다른 모델 결과를 이용한 보정은 버전 이동에서 더 강하지만, 이전 회차에 그 결과를 실제로 측정해 두었다는 전제를 갖는다.

요청 처리량도 canary 이익이 없다. 혼합 평가에서 0.107→0.114, v1 내부에서 0.050→0.049, v2 내부에서 0.149→0.151이다. 혼합 결과의 지연시간 개선을 전체 추천 성능 개선으로 해석할 근거가 없다.

수집기 버전 경계 전후 같은 조건의 **GPU 2개 배치 p95 중앙값**은 모델에 따라 v2/v1이 약 0.117~0.290배였다. canary의 중앙값도 약 0.409배였다. 이 큰 동시 변화는 canary가 호스트 부하뿐 아니라 **측정 체계의 차이**를 식별했을 가능성을 뜻한다. 버전 정보만 넣은 기준선이 혼합 평가에서 더 잘 맞았다는 점과 일치한다. 버전 변경 자체가 물리 성능을 바꿨다고 단정할 수는 없으며, 이 자료만으로 측정 코드 변화와 호스트 상태 변화를 분리할 수 없다.

canary는 앱별 독립 판단에 **GPU 실행 1회**를 추가한다. 혼합 평가에서 canary의 평균 GPU 실행 시간은 0.187초, 실제 시작·종료 시각 차이는 0.269초였다. 200개 앱별 시험 판단을 독립적으로 처리하면 canary GPU 실행 시간이 합계 37.3초다. 같은 회차의 5개 앱이 canary를 공유하면 40회 실행, GPU 실행 시간 7.46초다. 어느 경우에도 같은 버전 내부에서 관측한 예측 이익이 없다.

같은 대상 조건의 직전 GPU 2개 결과를 사용할 수 있는 경우, 마지막 관측의 비율을 재사용하는 강한 기준선도 비교했다. 그러나 이는 **신규 응용 첫 배포에는 사용할 수 없는 과거 대상 측정**을 요구하므로 별도 참고 기준선으로 취급했다. 원본의 SLO는 수집 설정에서 생성됐고 반복 110회 중 SLO 합격 여부가 바뀐 조건은 24개 중 1개뿐이다. 이 데이터로 스케일 조정 정책의 이익을 검증할 수 없다.

## 처리 방향

현재 canary 방법을 경희대의 고유 알고리즘으로 주장하지 않는다. 후속 연구를 한다면 수집기 버전을 고정하고, 호스트 부하를 독립적으로 변화시키며, 실행 순서를 무작위화한 반복 데이터를 먼저 확보해야 한다. 그때도 신규 모델 전체 제외·미래 회차 평가, 단순 버전/시간 보정, 과거 측정 활용 기준선, 추가 canary 측정 비용을 함께 비교해야 한다.

재현 코드: [`host_state_canary.py`](../scripts/host_state_canary.py). 원본 예측과 분할·비용·해시는 [`host_state_canary_v1`](../artifacts/host_state_canary_v1/metrics.json)에 있다. 테스트는 [`test_host_state_canary.py`](../tests/test_host_state_canary.py)이며, 대상 GPU 2개 결과를 바꿔도 cold-start 예측이 변하지 않는지 확인한다.
