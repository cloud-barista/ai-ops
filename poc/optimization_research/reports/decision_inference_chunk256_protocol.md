# 64격자→256격자 묶음 예측의 점수 전 비교 규약

2026-09-29. 기존 [64격자 채택](decision_inference_chunk64_findings.md)의 같은 저장 모델·요청·결과 규칙을 유지한 채, 서로 다른 575격자의 예측 호출 수를 9회에서 3회로 줄일 때 이득이 있는지 시험한다. 이 규약은 256 결과의 출력·시간·메모리를 열람하기 전에 썼다.

- 기존 [v4 평가기](../scripts/assess_gpu_shape_microbatch_v4.py)는 `MAX_CACHED_GRIDS=64`로 입력 상한을 둔다. **벤치마크에서만** 이 검증 상수를 호출 동안 256으로 잠시 바꿔 `max_grids=256`을 시험한다. 같은 `_predict_grids`, 예측기, 후보 검증, 선택 코드가 실행된다. 채택되기 전까지 기존 공개 함수의 기본값이나 상한은 바꾸지 않는다.
- 입력은 이전 64격자 시험의 고정 저장 모델·Parquet·분할·세 요청 형태를 재사용한다: 45격자×25 SLO 공유 객체, 그 복사 객체, 서로 다른 575격자. 원본 및 모델 SHA와 요청 생성 코드를 검증한다. 첫 두 입력은 64와 256 모두 예측 1회여야 하므로 회귀·시간 교란 검사이며 속도 이득은 주로 575격자에 기대한다.
- 세 형태에서 초기 출력과 7개 짝의 **정규 JSON 전체**가 64격자와 정확히 같아야 한다. 예측 호출 수는 575격자에서 64→256이 9→3이어야 한다. 큰 호출이 실패할 때 기존 격자별 재시도 결과를 유지한다.
- 모델 적재·첫 완전 호출을 타이머 밖에 두고 요청 블록 순서를 고정 시드로 바꾼 7쌍의 wall/CPU 시간을 잰다. 두 배치 크기 실행 순서는 번갈아 바꾼다. 동일 짝의 `64 wall / 256 wall` 속도비 중앙값을 쓴다. BLAS/OMP/MKL은 1 worker로 고정한다. peak RSS는 입력×배치마다 별도 프로세스에서 측정한다.

**채택 기준:** 모든 출력 동등, 575격자의 9→3 호출, 575격자 중앙 속도비 **≥1.10**, 공유·복사 입력 각각 **≥0.90**, 모든 입력의 peak RSS 증가 **≤20 MiB**. 실패하면 64를 유지한다. 통과해도 결과는 동일 호스트·저장 모델·오프라인 다중 질의의 계산 최적화에만 적용한다. 256을 모든 장비/모델의 최적 배치라고 주장하지 않는다.
