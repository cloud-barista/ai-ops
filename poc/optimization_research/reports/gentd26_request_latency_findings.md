# 공개 AI 서비스 요청 데이터의 실행시간 90백분위 예측

## 담당 항목과 데이터

경희대의 **응용 요구사항 분석**과 **배포·제어 추론 최적화**에 실제 사용자 요청 특성을 추가하려고 [Alibaba GenTD26](https://github.com/alibaba/clusterdata/blob/master/cluster-trace-v2026-GenAI/README.md)의 `lora_request_trace.csv`를 사용했다. [데이터 출처·해시·다른 공개 추적 자료와의 비교](../data/external/gentd26/SOURCE.md)를 별도로 기록했다. 기존 SQLite의 단일 호스트 배치 벤치마크와는 응용·시간·장비가 달라 합쳐 학습하지 않았다.

원본 26,823건에서 성공 요청 26,392건을 분석 대상으로 남겼다. 학습에는 이 가운데 학습 컷오프까지 결과가 가용하다고 가정한 과거 요청만 사용했다. 입력은 요청 시점에 알 수 있는 생성 종류, 익명 모델 ID, 프롬프트 길이, 이미지 수, 추론 단계 수, LoRA 수다. `predict_status`, 요청 완료 후 측정값, 익명 사용자 ID는 입력에 넣지 않았다. 누락된 부정 프롬프트 길이는 0으로 채우고 누락 표시를 별도 특징으로 두었다. 결과 변수 `exec_time_seconds`는 **성공 요청의 실행시간**이며, VM 준비시간·요청 SLO·Scale-out 효과가 아니다. 실패 요청의 실행시간을 같은 결과로 해석할 수 없어 제외했다.

## 학습·검증 방법

날짜를 기준으로 2024-11-29 이전 생성 요청 12,977건을 학습 후보, 11월 29일~12월 3일 7,171건을 검증, 12월 4~8일 6,244건을 시험으로 나눴다. 학습에서도 피드백 가용 시각을 적용해, 기본 1시간 추가 지연에서는 **학습 컷오프까지 결과가 가용하다고 가정한 12,779건만** 사용했다. 198건은 요청이 먼저 생성됐어도 학습 시점까지 라벨을 알 수 없어 제외했다. 시험 시각 이후의 요청 정보는 특징에 넣지 않는다. 기본 예측기는 `HistGradientBoostingRegressor`의 0.9 분위수 손실로 학습했다. 비교 대상으로 모델별 학습 요청 실행시간의 90백분위(해당 모델 <30건이면 전체 학습 90백분위), 모델 ID 없는 동일 회귀기, 가용하다고 가정한 최근 요청의 경험적 90백분위를 사용했다.

운영 중 분포 변화를 흉내 내는 보정기는 과거 요청의 잔차 `실제 실행시간 - 예측시간`의 90백분위를 더한다. **실제 완료 시각은 공개 자료에 없다.** 그래서 관측 가능 시각을 `요청 생성 시각 + 기록된 실행시간 + 추가 1시간`으로 **가정**했다. 검증 기간의 앞 이틀로 시작해 뒤 3일에 대해 최근 잔차 `200/500/1000/2000/전체`건 중 pinball 손실이 가장 작은 창을 골랐다. 이때 **시험 시작 전까지 결과가 도착했다고 가정할 수 있는 5,810건만** 창 선택 점수에 넣었다. 같은 방식으로 단순 기준선도 각자 창 크기를 골랐다. 시험 이전 검증 요청도 가정한 관측 시각에 도달해야 보정에 넣는다. 큐 대기·기록 지연이 알려져 있지 않아 이 방식은 운영상 피드백 누출 방지의 증명이 아니다.

이 실험은 사용 가능한 과거 공개 데이터에 대한 **탐색적 후향 평가**다. 시험 결과를 살피면서 추가 기준선을 보강했으므로 독립적인 사전 등록 검증이라고 주장하지 않는다.

## 시험 결과

낮은 pinball 손실이 좋고, `coverage`는 실제 실행시간이 예측한 90백분위 이내인 비율이다. 수치는 6,244개 시험 성공 요청 전체다.

| 방법 | Pinball 손실 (초) | Coverage | 평균 예측시간 (초) |
| --- | ---: | ---: | ---: |
| 모델별 과거 90백분위 | 3.295 | 83.5% | 43.6 |
| 모델 ID 없는 학습기 | 3.717 | 81.4% | 42.6 |
| 모델·요청 조건 학습기 | 3.104 | 81.4% | 42.0 |
| 학습기 + 고정 검증 잔차 보정 | 2.946 | 87.1% | 44.9 |
| 모델별 90백분위 + 과거 잔차 보정 | 3.142 | 90.7% | 49.7 |
| 과거 요청의 경험적 90백분위 | 5.723 | 89.2% | 64.2 |
| **학습기 + 과거 잔차 보정** | **2.911** | **90.1%** | **47.7** |

추가 1시간 피드백 지연 가정에서 학습기 보정 창은 검증으로 2,000건이 선택됐다. 같은 보정을 적용한 모델별 기준선보다 pinball 손실이 약 7.4% 낮았고 평균 예측시간도 약 2.0초 짧았다. 고정 보정보다는 손실이 약 1.2% 낮지만, 시험 5일 중 3일에만 더 낮았다. 추가 지연을 0/6/24시간으로 바꾸면 학습기+과거 잔차의 시험 손실·coverage는 각각 `2.862/90.2%`, `3.017/91.4%`, `3.238/89.0%`였다. 해당 지연의 학습 컷오프 가용 표본은 각각 12,976/11,903/11,085건으로 달라진다. 따라서 민감도 수치는 피드백 지연과 학습량 변화가 함께 반영된 결과다. **24시간 지연에서는 고정 보정(손실 2.990)보다 나빴다.** 운영 시각 정보가 없으므로 1시간 가정을 성능 보장으로 읽을 수 없다.

전체 coverage가 90%에 가까워도 하위 집단은 불균형하다. `TXT_2_IMG` 5,557건은 91.1%였지만 `IMG_2_IMG` 649건은 80.9%였다. 모델 `M0003` 595건은 74.1%였다. 학습에서 30건 미만인 모델들의 시험 요청 150건은 80.7%였다. 시험 첫날인 12월 4일의 coverage도 84.5%였다. 모델·작업 종류마다 신뢰 가능한 상한으로 쓰려면 별도 보정과 독립 검증이 필요하다.

## 적용 경계와 재현

현 단계의 산출물은 **요청 메타데이터로 실행시간 분포를 추정하는 연구용 모델**이다. 데이터에 노드 수, VM 생성, 배포/스케일 전환 결과, 이미지 생성 서비스의 실제 GPU 형상 비용이 없어 인프라 형상이나 `SCALE_OUT`을 학습할 정답으로 사용할 수 없다. 성공 요청만 사용한 선택 편향과 실제 결과 가용 시각 부재도 남는다. GenTD26의 약 하루짜리 QPS/GPU/대기열 추적 자료는 이 요청 CSV와 익명 시각 범위가 달라 행 단위 결합을 하지 않았다.

```bash
python scripts/fetch_gentd26.py
OPENBLAS_NUM_THREADS=2 OMP_NUM_THREADS=2 python scripts/evaluate_gentd26_request_latency.py
OPENBLAS_NUM_THREADS=2 OMP_NUM_THREADS=2 python -m unittest discover -s tests -p 'test_gentd26_request_latency.py' -v
```
