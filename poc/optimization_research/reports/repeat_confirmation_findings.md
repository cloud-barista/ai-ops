# 한 번 합격한 GPU 형상의 다음 측정 재현성: 시간순 감사

2026-09-29. **판정: 반복 합격 횟수를 늘리는 단순 게이트의 채택 근거 부족.** 앞선 [8후보 순차 확인 재생](sequential_shape_confirmation_findings.md)은 확인한 한 번의 실측을 그 작업의 성공으로 세었다. 같은 형상을 다시 실행하면 결과가 달라질 수 있는지를 기존 SQLite의 `khu-hf-live` 반복 벤치마크로 따로 확인했다. 원래 수집기 생성 목표에서는 평가 기간의 합격 여부가 거의 고정돼 있었지만, 앞부분 자료에서 정한 경계 근처 목표에서는 직전 한 번 합격 후 **다음 실행 실패가 수집기 v1 89/571건(15.6%), v2 79/324건(24.4%)**이었다. 확인을 3회 연속 합격으로 늘려도 v2 실패율은 **50/196건(25.5%)**으로 낮아지지 않았다.

## 자료와 시간 경계

같은 호스트의 GPU 조건 16개를 수집기 `v1`에서 63회, `v2`에서 47회 실행한 **1,760개 성공 기록**을 사용했다. 수집기 버전별로 모든 회차에 같은 16조건이 있는지 검사했다. 회차 이름의 숫자는 시간순이 아니므로, `started_at`으로 정렬하고 **직전 회차 전체 종료가 다음 회차 시작보다 이른지** 확인했다. 두 버전을 섞어 목표를 만들거나 판단하지 않았다.

첫 **20회**만 사용해 형상별 배치 p95 지연의 90백분위와 요청/초의 10백분위를 고정했다. 이후 v1 **43회×16조건=688판단**, v2 **27회×16조건=432판단**에서 해당 목표를 동시에 만족하면 합격으로 정의했다. 이 목표는 변동을 볼 수 있도록 만든 **합성 경계 목표**이며 사용자 SLO가 아니다. 원래 수집기가 만든 목표도 별도로 재생했다. 판단 시점 `t`에는 이미 끝난 직전 `k∈{1,2,3,5}`회의 합격 여부만 읽고 현재 `t`회의 합격 여부로 평가했다.

## 다음 회차 결과

| 목표·버전 | 직전 1회 합격: 승인 / 다음 실패 | 직전 2회: 승인 / 다음 실패 | 직전 3회: 승인 / 다음 실패 | 직전 5회: 승인 / 다음 실패 |
| --- | ---: | ---: | ---: | ---: |
| 원 생성 목표 v1, 688판단 | 387 / **0** | 387 / 0 | 386 / 0 | 384 / 0 |
| 원 생성 목표 v2, 432판단 | 243 / **0** | 243 / 0 | 243 / 0 | 243 / 0 |
| 경계 목표 v1, 688판단 | 571 / **89 (15.6%)** | 483 / 69 (14.3%) | 415 / 54 (13.0%) | 325 / 36 (11.1%) |
| 경계 목표 v2, 432판단 | 324 / **79 (24.4%)** | 250 / 60 (24.0%) | 196 / 50 (**25.5%**) | 112 / 29 (25.9%) |

`승인`은 정책이 직전 회차에 근거해 현재 형상 사용을 허용했을 횟수다. 이 확인 작업은 이미 수집된 벤치마크를 시간순으로 재생했으며 실제 배포 명령을 실행하지 않았다. 원 목표에서 실패가 0건인 것은 **이 16조건에서 목표가 대체로 쉬워 합격 상태가 유지됐기 때문**이다. 강한 안전 보장으로 읽을 수 없다. 경계 목표의 v1에서는 3회 게이트가 실패율을 15.6→13.0%로 낮추면서 승인 156건을 줄였다. v2에서는 승인 128건을 줄였지만 조건부 실패율이 24.4→25.5%로 올랐다. v2에서 1회만 보면 승인하지만 3회 규칙이 버린 128건의 다음 회차 실패율은 **29/128=22.7%**로, 3회 규칙이 유지한 집합의 25.5%보다 낮았다.

따라서 이 자료에서는 “반복 확인을 늘리면 다음 실행 승인 위험이 일관되게 줄어든다”는 단순 규칙이 성립하지 않는다. 특히 [순차 형상 확인의 한 번 실측 합격](sequential_shape_confirmation_findings.md)은 이후 실행의 합격 확률이 100%라는 뜻이 아니다. 그렇다고 위 15.6%·24.4%를 그 8후보 캠페인에 옮길 수도 없다. 두 캠페인의 입력 조건·수집기·목표가 일치하지 않는다.

## 재현·한계

[감사 코드](../scripts/audit_repeat_confirmation.py)는 고정 측정 파일의 SHA-256, 회차 완결성·시간 순서·조건의 목표 일관성을 확인한다. [집계](../artifacts/repeat_confirmation_v1/results.json)와 판단별 행 (`../artifacts/repeat_confirmation_v1/next_run_decisions.csv`)에 네 게이트의 결과를 보존했다. [테스트](../tests/test_audit_repeat_confirmation.py) 2개는 회차 이름과 실제 시간의 불일치, 미래 측정값의 목표·과거 판단 누출, 누락·겹침 회차 거부를 검사한다.

이 결과는 같은 8모델·16조건의 반복으로부터 나온 **상관된 판단**이며, 1,120판단을 독립 사용 요청으로 세면 안 된다. 경계 목표는 이 탐색에서 고른 합성 목표이고, 두 버전의 수치도 결과를 본 뒤 함께 검토한 것이다. 실제 사용자 요청 지연, VM 준비·전환, 여러 호스트, 미래 배포 결과는 없다. 따라서 추가 확인 횟수를 운영용 `DEPLOY`·`SCALE_OUT/IN` 규칙으로 채택하지 않는다. 다음 단계는 동일한 8후보 형상에서 **반복 측정과 실제 사용자 목표를 함께 수집**해 형상 선택과 재현성을 직접 결합하는 것이다.
