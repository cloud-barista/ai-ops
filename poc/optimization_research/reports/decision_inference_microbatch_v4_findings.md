# 복사된 GPU 후보 격자의 검증 재사용 결과

2026-09-29. [사전 동결 규약](decision_inference_microbatch_v4_protocol.md)에 맞춰 [연구용 v4](../scripts/assess_gpu_shape_microbatch_v4.py)를 평가했다. 같은 내용의 후보 리스트를 각 SLO 요청이 **별도 객체로 보유**하는 1,125개 요청에서 v4는 v2보다 쌍별 중앙 **1.3337배**, v3보다 **1.3303배** 빨랐다. 7쌍의 결과 JSON 전체·후보 상태·예측 호출 수는 모두 같았다. 공유 객체 입력에서 v3보다 약 **3.5% 느린** 비용까지 포함하여 사전 시간·메모리 게이트를 모두 통과했다. 따라서 **GO: 복사된 후보 격자의 오프라인 SLO 묶음 채점에 v4를 사용**할 수 있다.

## 변경과 동등성

v4는 각 요청의 상위 필드와 SLO를 매번 검사한다. 이미 검증한 **동일 리스트 객체**에는 v3의 검증·키 재사용을 적용한다. 다른 객체는 첫 후보의 `workload_id`로 비교 대상을 좁히고, 8개 후보의 **내용과 순서 전체가 같은 경우**에만 원래 검증과 정규 키를 재사용한다. 값 동등성 경로는 내장형 `list`/`dict`와 정확한 `str`/`int` 키·값에만 적용한다. `True == 1`, `2.0 == 2`, 사용자 정의 동등성처럼 원래 타입 검증과 다르게 비교될 수 있는 입력은 기존 전체 검증을 따른다. 잘못된 격자는 캐시하지 않는다. 캐시는 한 호출에서만 유지되며, 호출 중 요청·번들을 수정하지 않는 v2/v3의 계약이 필요하다. 모델 예측, 모델별 지원 범위, SLO 선택과 합친 예측 실패 시 격자별 재시도는 기존 함수에 맡긴다.

[결과 JSON](../artifacts/gpu_shape_microbatch_v4/results.json)에서 공유와 복사 입력은 각각 1,125개 결과·6회 예측으로 모두 일치했고, 결과 해시는 둘 다 `87834d2c56f7b1924adecbaaf3bfa40e4a4821cf7e8f0f4a07943abb5fbcc924`였다. 575개 서로 다른 격자는 575개 결과·72회 예측이 같고 해시는 `1054a72560b9c6ba06deece136633e92fb9eeecd3d10a0915edb8812bd141e99`였다. 공유/복사 결과의 상태는 `RESEARCH_ESTIMATE` 720건과 `ABSTAIN` 405건, 고유 격자는 각각 355건과 220건이다. 7번의 각 입력 순서 셔플에서도 v2·v3·v4의 정규 JSON 전체가 일치했다. 오류 이유 순서, 미지원 revision, `bool`/`float`/사용자 정의 값, 독립적인 이유 리스트, 미검증 번들 및 결합 예측 실패 재시도를 [단위 테스트](../tests/test_assess_gpu_shape_microbatch_v4.py)로 확인했다. 전체 GPU 평가기·microbatch 관련 **38개 테스트가 통과**했다.

## 7쌍 시간과 메모리

모델·Parquet 적재와 각 경로의 첫 완전 호출을 타이머 밖에 두고, BLAS/OMP/MKL 각 한 worker 및 `max_grids=8`로 측정했다. 각 쌍의 요청 블록과 세 함수의 실행 순서는 고정 난수로 바꿨다. 속도비는 **각 쌍의 기준 경로/v4 wall time을 구한 뒤 그 7개 값의 중앙값**이다. 아래 각 경로의 wall time 중앙값을 서로 나눈 값과 다를 수 있다. CPU time도 [결과 JSON](../artifacts/gpu_shape_microbatch_v4/results.json)에 보존했다. peak RSS는 입력과 모델 적재를 포함하는 별도 프로세스의 고수위다.

| 입력 | 후보 리스트 객체 | v2 / v3 / v4 wall 중앙 ms | v2/v4 · v3/v4 쌍별 중앙 비 | v2 / v3 / v4 peak RSS MiB |
| --- | ---: | ---: | ---: | ---: |
| 같은 객체 공유, 45격자×25 SLO | 45 | 305.674 / 195.737 / 222.139 | 1.4826× · **0.9659×** | 438.117 / 438.586 / 437.074 |
| 동일 내용을 요청마다 복사, 45격자×25 SLO | 1,125 | 302.854 / 306.647 / **228.133** | **1.3337× · 1.3303×** | 442.965 / 444.004 / 443.316 |
| 서로 다른 격자 575개 | 575 | 2016.483 / 1984.413 / 1973.698 | 1.0168× · 1.0023× | 442.418 / 440.918 / 440.926 |

복사 입력의 쌍별 v2/v4 비율 범위는 `1.0673–1.6307×`로 변동했다. 공유 입력의 v3/v4 중앙 `0.9659×`는 v4가 약 3.5% 느리다는 뜻이지만 사전 10% 악화 한도 안이다. 고유 격자에서는 v2/v3 모두와 거의 같은 시간이다. 세 입력의 v4 peak RSS는 v2/v3보다 최대 0.351 MiB 높고 20 MiB 한도 안이다. 같은 호스트에서 다른 CPU 작업도 실행 중이었으므로, 이 7쌍을 온라인 p95 지연 보증으로 해석하지 않는다.

## 재현성과 연구 범위

[코드·게이트 사전 동결 기록](../artifacts/gpu_shape_microbatch_v4/code_freeze.json) 이후 구현과 규약을 바꾸지 않고 점수를 냈다. 공용 평가기 SHA-256은 `e904a76d9e7940630e8a53f3f0e5d952bb98760fa74697bd7c42bfadb6a1e30e`, 예측기 `46c85961fb4d9388c99bc073522f8cf9c839065a1f4fe67a1b92aa33f3123075`, v2 `20e73cdcf39dbe7252399a3bff8eda9387ff592d046ea6483df15b13710e996d`, v3 `644326f77be68fdd8b4a4050ab3bc0ee031ad8264519ecc54de0b051409e6299`, v4 `191bb2b3fd5d4306078bd4e5d2ebd3d1c8f800023e3eccd8963a1af1fc57dbef`이다. 모델·데이터·manifest와 벤치마크 코드 해시도 결과에 있다.

재현 명령: 연구 루트에서 `OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 /usr/bin/python scripts/benchmark_gpu_shape_microbatch_v4.py`. 관련 테스트는 `/usr/bin/python -m unittest discover -s tests -p 'test_assess_gpu_shape*.py' -v`.

이 결과는 같은 호스트의 알려진 모델·배치에 대한 저장 모델의 **오프라인 CPU 판단 시간**이다. 생성 SLO는 실제 사용자 목표가 아니다. 실제 VM 형상 추천, `DEPLOY`/`SCALE_OUT` 효과, 온라인 서비스 지연 또는 학술적 방법 신규성에 관한 증거로 사용하지 않는다.
