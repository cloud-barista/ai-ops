# 측정 없는 AI 응용 인프라 후보 추천: 직접 분류와 성능 예측 비교

## 결론

기존 SQLite의 완전 측정 후보 표로 **새 모델의 성능 프로브가 전혀 없는 정적 GPU·CPU affinity 추천기**를 학습했다. 지연·요청처리량을 예측하고 SLO를 검사하는 200-tree Extra Trees 회귀와, SLO를 입력으로 받아 후보 합격 확률을 직접 학습하는 HistGradientBoosting 분류를 비교했다. 같은 75% 선택률의 BERT 4종 공동 제외 평가에서 직접 분류는 관측 위반을 **870→667건** 줄였지만, 정확한 최소 자원 선택도 **2856→2633건**으로 줄었다. 이 위반 개선 203건 중 200건이 `bert-base-uncased` 한 모델에서 나왔다. 9종 단일 모델 제외 평가에서는 회귀가 대체로 강했다. 따라서 직접 분류를 기본 추천기로 교체할 근거는 아직 없다.

이 결과는 **모델 맥락과 입력 크기로 정적 인프라 후보를 점수화하는 경희대 담당 항목**에 해당한다. GPU 2개는 같은 호스트의 물리 장치 2개이며 VM 2개 scale-out 결과가 아니다.

## 데이터와 실험 규약

- 원본은 고정 측정 스냅샷 (`../data/audit_v1/measurements.parquet`)의 `khu-hf-local-exhaustive` 성공·적격 GPU 측정 **4600행, 9개 모델, 575개 입력 조건**이다. 각 조건마다 GPU 수 `1/2` × CPU affinity `2/4/8/16`의 8개 후보가 완전히 측정되어 있다.
- **모델 ID 전체 제외 9회**와 `google-bert/bert-base-uncased`, Google BERT tiny/mini/small의 **4종 공동 제외 1회**를 실행했다. 훈련은 본 캠페인의 다른 모델에서만 수행했다. 별도로 수집된 `local-novel-matrix`와 `local-space-filling` 입력 조건의 동일 제외 모델도 평가했다.
- 입력은 등록 시 알 수 있다고 가정한 모델 파라미터 바이트, 배치 크기, 최대 길이, 요청 동시성, 작업 유형, GPU 수, CPU affinity, 반복 횟수다. `model_parameter_bytes`는 역사적 `result_json`에서 **그 키만** 추출했다. 실제 등록 시스템이 이 값을 제공하지 않으면 같은 조건으로 운용할 수 없다. 모델 ID, 대상 모델의 측정 지연·처리량·GPU 사용량, 원본 생성 SLO 성과는 입력하지 않았다.
- 각 분할에서 **학습 모델의 지연·요청/초 측정 분포만** 사용해 축별 10/25/50/75/90% 분위수를 구하고, 25개 SLO 쌍을 만들었다. 이는 실제 사용자 SLO가 아니라 합성 스트레스 조건이다. 요청처리량은 `examples_per_second / batch_size`다.
- 직접 분류는 학습 후보 × 25개 SLO의 합격 여부를 지도 라벨로 학습한다. 회귀는 같은 정적 정보로 로그 지연·로그 요청/초를 예측한 뒤 두 기준을 검사한다. 회귀 점수는 두 로그 여유 중 작은 값인 **원시 로그 마진**과, 학습 모델의 잔차 표준편차로 나눈 **표준화 마진**을 모두 시험했다. 본문 표에는 원시 로그 마진을 쓰고, 전체 집계에는 두 방식을 함께 저장했다. 선택 후보의 우선순위는 **GPU 수, 그다음 CPU affinity core 수**다. 가격이나 실제 VM 용량은 입력에 없다.
- 선택률 비교에서는 각 분할·캠페인·방법의 모든 입력 조건 × SLO 쿼리 중 예측 점수가 가장 높은 25/50/75%를 정확히 선택한다. 동점은 고정 쿼리 순서로 정리한다. **선택률 맞춤에 실제 측정값을 쓰지 않는다.** 선택된 쿼리에서는 점수 경계를 통과한 가장 작은 후보를 고른다. 자연 임계값 0.5(분류 확률)와 0(회귀 로그 마진)도 별도 기록했다.
- 선택률 50/75%는 각 방법의 자연 임계값보다 낮은 점수까지 승인을 강제할 수 있다. 따라서 이는 **동일 처리량의 위험 비교 곡선**이며 그대로 운영할 정책이 아니다.
- `false approval`은 선택한 후보의 실측 배치 지연 또는 요청처리량이 SLO를 못 맞춘 경우다. `exact minimal`은 선택 후보가 실측상 합격하는 후보 중 정의된 자원 순서로 가장 작은 경우다. 실측 합격 후보가 하나도 없는 쿼리도 총 쿼리 분모에 포함된다.

## 주요 결과

아래 표는 **같은 75% 선택률**에서 직접 분류 / 원시 로그 마진 성능 회귀 결과다. `성공`은 선택 후보의 실측 SLO 만족, `최소`는 그중 정확한 최소 자원 선택이다.

| 제외 모델과 평가 조건 | 쿼리 | 선택 | 직접 분류 성공 / 위반 / 최소 | 성능 회귀 성공 / 위반 / 최소 |
| --- | ---: | ---: | ---: | ---: |
| 9개 모델 각각 제외, 본 캠페인 | 14,375 | 10,781 | 4,723 / 6,058 / 4,065 | 4,657 / 6,124 / 4,170 |
| 9개 모델 각각 제외, novel matrix | 450 | 342 | 169 / 173 / 152 | 163 / 179 / 146 |
| 9개 모델 각각 제외, space filling | 1,100 | 827 | 302 / 525 / 274 | 297 / 530 / 265 |
| BERT 4종 공동 제외, 본 캠페인 | 6,400 | 4,800 | 4,133 / 667 / 2,633 | 3,930 / 870 / 2,856 |
| BERT 4종 공동 제외, novel matrix | 200 | 150 | 122 / 28 / 74 | 124 / 26 / 93 |
| BERT 4종 공동 제외, space filling | 500 | 375 | 293 / 82 / 194 | 283 / 92 / 185 |

BERT 공동 제외 본 캠페인의 선택률별 위반 건수는 25%에서 **0/0**, 50%에서 **54/65**, 75%에서 **667/870**이다(직접 분류/원시 로그 마진 회귀). 75%에서 직접 분류의 GPU 2개 선택은 **2462건**, 회귀는 **1826건**이었다. 실제 합격 후보가 있는 4898개 쿼리 중 최소 후보가 GPU 1개·2코어인 것은 **3928개**다. 직접 분류는 높은 선택률에서 자원을 더 많이 요청하는 대신 일부 잘못된 승인을 줄이는 경향을 보였다.

개별 모델 결과를 보면 75% BERT 공동 제외에서 `bert-base-uncased`의 위반은 직접 분류 **567**, 회귀 **767**이었다. 나머지 세 모델 합계는 각각 **100**, **103**이었다. 개선이 모델 계열 전체에 고르게 나타났다고 주장할 수 없다. 또한 `bert-base-uncased`의 직접 분류도 1162개 선택 중 567개가 실패하므로 운영 허용 위험과 거리가 멀다.

단일 모델 제외에서는 25% 선택률에 직접 분류 **404/3594** 위반, 원시 로그 마진 회귀 **371/3594** 위반이다. 50%에서는 **3148/7188** 대 **2973/7188**로 회귀가 낫다. 75%에서는 직접 분류가 위반을 약간 줄이지만 정확 최소 자원 선택은 더 적다. 표준화 마진 회귀도 BERT 공동 제외 본 캠페인의 75%에서 **871**건 위반과 **2867**건 정확 최소 선택을 보였다. 직접 분류의 안전성 이득과 자원 효율 손실은 회귀 점수 정규화에만 의존하지 않는다.

자연 임계값에서는 단일 모델 제외 본 캠페인에서 직접 분류가 **5701건 선택·1486건 위반**, 회귀가 **6100건 선택·1321건 위반**이었다. BERT 공동 제외에서는 직접 분류가 **3172건 선택·50건 위반**, 회귀가 **3458건 선택·95건 위반**이었다. 선택 건수가 다르므로 이 숫자만으로 위험을 비교하지 않는다. 분류 확률 0.5는 별도 모델 단위로 보정한 안전 확률이 아니다.

## 해석과 사용 경계

직접 합격 분류는 SLO와 모델·입력 정보를 함께 받아 **후보 점수화와 보류**에 쓸 수 있는 학습 구조다. 그러나 이 자료에서는 계열 제외의 일부 선택률에서만 안전성 이득이 있었고, 자원 효율과 충돌했다. 따라서 기본 배포 추천에는 기존 성능 회귀 경로를 유지하고, 이 분류기를 **탐색적 대안 및 위험 신호**로만 취급한다. 이 결론은 수집된 한 호스트·두 물리 GPU·배치 처리 조건 안에서만 성립한다.

25개 SLO는 같은 원시 측정에서 만든 상관된 쿼리다. 표의 4800개 선택은 독립적인 실제 사용자 요청 4800건이 아니다. 본 연구는 앞선 관련 실험을 보고 설계한 탐색 결과이고, BERT 공동 제외도 같은 SQLite의 같은 호스트 자료다. 별도 사용자 SLO, 가격, 미지 GPU 종류, 다른 호스트, VM 생성·삭제, 배포 전환, scale-out/in 품질은 검증하지 못한다. 메모리 적합성도 이 정책의 입력이나 제약이 아니다.
