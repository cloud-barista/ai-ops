# Azure 입력 토큰 부하: Coding에서 Conversation으로 이전하는 사전 규약

상태: **Conversation 전체 원본을 읽거나 Coding 입력 부하 모델의 점수를 계산하기 전 작성한 시험 규약**. 주 질문은 Coding 서비스의 기록된 요청으로 학습한 다음 5분 입력 토큰 부하의 상대 90분위 예측기가 별도 Conversation 서비스에서도 강한 온라인 기준선보다 나은지다. 이것은 공개 **표본**의 수요 예측이며 전체 Azure 유입량, GPU 수요, 사용자 SLO 또는 VM 증감 효과의 정답이 아니다.

## 출처와 기존 노출

- 학습 원본은 로컬 Coding CSV, 691,989,454바이트, SHA-256 `71de5c55cbc35f8f1ed0b6b7806b4cd1e9764b0058469725a6aac98023a1448f`다. 별도 [Coding 규약](azure_code_input_demand_protocol.md)에 따라 2024-05-10~12만 학습·기준값 계산에 사용한다. 모델·기준선·특징·결측 규칙은 이 규약 때문에 바꾸지 않는다.
- 시험 원본은 [Azure 공식 릴리스](https://github.com/Azure/AzurePublicDataset/releases/tag/dataset-llm-2024)의 `AzureLLMInferenceTrace_conv_1week.csv`, 1,135,195,393바이트, 공식 SHA-256 `a0cc9b969a9bbf0fd811802cbf4323edd3a209ace791e3799ad4f9207f213941`이다. [공식 설명](https://github.com/Azure/AzurePublicDataset/blob/master/AzureLLMInferenceDataset2024.md)의 열은 `TIMESTAMP,ContextTokens,GeneratedTokens`다. 원본 전체 SHA·헤더·시각 정렬·입력 양수 정수·정확한 2024-05-12~18 UTC 범위를 먼저 확인한다. **첫 5분 구간과 마지막 5분 구간에 각각 요청 행이 있고 일곱 날짜 모두 요청 행이 있는지**도 확인한다. 어느 하나라도 실패하면 점수를 계산하지 않고 결함을 기록한다. 출력 토큰은 열지 않는다.
- 과거 [자료 타당성 조사](azure_llm_2024_feasibility.md)는 Conversation 파일의 **첫·끝 4KiB**를 Range로 확인했다. 그 두 조각의 원시 입력 길이는 이미 노출됐다. Conversation의 일별·5분별 집계나 예측 점수는 이 규약 작성 시점에 열람하지 않았다. 엄밀한 완전 봉인 표본은 아니므로 이를 명시한다.

## 결정 시점과 평가 집합

원본의 UTC 5분 고정 구간마다 기록된 `ContextTokens`를 합해 `y_t`를 만든다. `[t,t+300초)` 시작에 직전 12개 **완료** 구간의 평균 `m_t≥1,000` 입력 토큰인 시점만 예측한다. 이 적격 규칙은 Coding 모델과 같다. 같은 CSV의 2024-05-12~13은 전일·1시간 이력을 마련하는 **점수 없는 준비 기간**이다. 주 시험은 UTC 2024-05-14 00:00부터 05-19 00:00 직전까지의 **5일 1,440개 후보 구간**이다. 이 기간은 Coding 모델 학습 종료와 개발 검증 이후이며, 모든 방법에 동일한 이미 완료된 Conversation 구간 피드백을 준다. 5일의 결과를 보고 날짜를 제외하지 않는다. Coding 후향 점수와 Conversation 기간이 일부 겹치므로 새로운 달력 기간으로의 검증이라고 주장하지 않는다.

공개 요청은 생산 전체의 표본이므로 한 구간의 요청 누락 여부를 알 수 없다. 완전한 CSV를 검증한 뒤 기록 행이 0개인 구간은 `y_t=0`으로 유지한다. 각 날짜의 빈 구간 수와 `m_t<1,000`인 **결정 전 입력 기준 부적격 구간 수**를 점수 계산 전에 보고한다. 시험 날짜 하나라도 부적격 구간이 그날 288개 후보의 **5%를 초과하면** 지원량 실패로 모델 점수를 계산하지 않는다. 통과하면 사전에 정한 적격 구간만 다섯 날짜 동일 가중으로 평가한다. 0인 목표 구간도 결정 당시 `m_t≥1,000`이면 평가에 포함한다. 테스트를 통과시키기 위해 시각이나 문턱을 바꾸지 않는다.

## 고정된 전이와 비교

주 방법은 Coding 학습 분할로만 적합한 상대 목표 `r_t=y_t/m_t`의 90분위 HGB를 **계수·특징·전처리 그대로** 적용하고, `m_t`를 곱해 토큰 총량으로 복원한다. Coding 점수를 본 뒤 모델을 다시 적합하거나 Conversation으로 온도·절편을 보정하지 않는다. 비교기는 Coding 규약의 동일한 네 방법이다: Coding 학습 비율의 고정 90분위, 최근 Conversation 1시간의 경험적 토큰 총량 90분위, 전날 같은 슬롯의 Conversation 상대 비율, 그 비율에 Coding 학습 잔차 90분위를 더한 값. 모두 `t`보다 먼저 완료된 원본만 참조한다. Conversation의 05-12~13 값은 온라인 과거 이력으로만 사용하고 어떤 상수나 하이퍼파라미터도 그 기간의 미래 정답으로 고르지 않는다.

Coding 점수에 관계없이 **이 프로토콜에 고정한 다섯 방법을 전부** Conversation에서 한 번 평가한다. Coding 평가 결과로 후보·게이트·시험 날짜를 변경하지 않는다. Conversation 본문 다운로드 전에 Coding 모델/상수, 평가 코드, 합성 누수 시험, 이 규약과 원본 출처의 SHA-256을 manifest에 적는다. 모델 적합 결과가 없거나 파일 해시가 다르면 다운로드를 시작하지 않는다. 저장 Coding 모델을 읽을 실행환경의 Python·NumPy·pandas·scikit-learn 버전도 Coding freeze에 기록된 값과 일치해야 한다. Conversation 원본은 공식 SHA 확인 전에는 내용 점수화를 하지 않는다.

## 지표와 판정

주 지표는 각 5분 합계의 `q=0.9` pinball 손실을 날짜 안에서 평균한 뒤 **5일 동일 가중** 평균한 값이다. 날짜별 손실·경험적 피복률 `P(y_t≤예측)`, 평균 예측 토큰 수, 과소예측 비율과 전체 합산값을 함께 보고한다. 시간상 연속한 1,440개 구간을 독립 표본으로 간주한 신뢰구간은 계산하지 않는다.

주 후보의 탐색적 이전 통과 조건은 (1) 5일 동일 가중 pinball이 **네 비교기 각각보다 5% 이상 낮고**, (2) 다섯 날짜 중 **최소 네 날짜**에서 그날 최선 비교기보다 낮으며, (3) 각 날짜의 피복률이 **85~95%**인 경우를 모두 만족하는 것이다. 하나라도 실패하면 `NO-GO`로 기록하고 해당 후보를 배포 판단기의 신호로 채택하지 않는다. 통과해도 같은 주 두 Azure 서비스의 공개 표본 안에서 상대 90분위 예측이 이전된 것만 뜻한다. 실제 스케일 정책을 평가하려면 조치 발행·준비 완료·사용자 지연 결과가 같은 실행에 연결된 자료가 별도로 필요하다.
