# 공유 GPU 후보 격자의 검증·키 재사용 결과

2026-09-29. [점수 전 규약](decision_inference_next_optimization_audit.md)에 따라 [연구용 v3 구현](../scripts/assess_gpu_shape_microbatch_v3.py)을 만들고, 같은 저장 모델을 쓰는 v2와 **최종 JSON 전체**를 비교했다. 한 후보 리스트 객체가 25개의 합성 SLO 요청에 쓰이는 경우, 두 경로의 예측 호출 6회와 출력은 같고 7쌍의 중앙 시간비는 **1.6079배**였다. 사전 동등성·시간·메모리 게이트를 모두 통과했다. 후보 리스트를 요청마다 새로 만드는 경우에는 쌍별 중앙 시간비가 `0.9305×`로 v3가 약 **7.5% 느렸으므로**, 개선 효과는 입력을 묶어 공유하는 호출 형태에 한정된다.

## 구현과 동등성

v3는 각 요청의 상위 필드와 두 SLO를 매번 검사한다. 같은 함수 호출에서 유효성이 확인된 **동일 후보 리스트 객체**를 다시 만나면 8후보의 필드·공통 작업 조건·형상 완전성 검사와 격자 JSON 직렬화를 다시 하지 않는다. 처음 본 객체의 전체 검사는 기존 `_request_errors`에 맡긴다. 잘못된 격자는 캐시하지 않고, 내용은 같지만 별도 객체인 격자는 정규 키로 원본 모델 예측만 공유한다. 모델 예측과 SLO별 선택은 기존 코드에 맡긴다. 요청과 모델을 호출 중 수정하지 않는 계약은 v2와 같다. 캐시는 호출이 끝나면 사라진다.

[동결 결과 JSON](../artifacts/gpu_shape_microbatch_v3/results.json)에서 45개 격자×25개 생성 SLO의 1,125개 결과와, 주 CUDA 캠페인의 575개 서로 다른 격자·4,600개 후보 결과가 v2와 정확히 같았다. 모든 실행 순서 셔플 7쌍에서도 차이가 없었다. 1,125개 요청의 결과 해시는 `87834d2c56f7b1924adecbaaf3bfa40e4a4821cf7e8f0f4a07943abb5fbcc924`, 575개 결과 해시는 `1054a72560b9c6ba06deece136633e92fb9eeecd3d10a0915edb8812bd141e99`이다. 예측 호출 수는 각 경로에서 각각 **6회/72회**로 같았다. 유효하지 않은 SLO와 후보 오류가 동시에 있을 때의 이유·순서, 미지원 최상위 가격 제약의 보류, 별도 응답의 `reasons` 독립성, 합친 예측 호출이 실패했을 때의 격자별 재시도도 [테스트](../tests/test_assess_gpu_shape_microbatch_v3.py)로 확인했다. 평가기와 v1/v2를 포함한 관련 테스트 **33개가 통과**했다.

## 계산 시간과 메모리

같은 모델을 예열한 프로세스에서 8격자씩 묶고, 요청 블록 및 v2/v3 실행 순서를 고정 난수로 바꾸어 **7쌍** 측정했다. 모델·Parquet 적재는 시간에서 뺐다. `중앙 시간비`는 각 쌍의 v2 시간/v3 시간 중앙값이다. peak RSS는 입력 적재·모델 적재·예열을 포함한 별도 프로세스의 고수위다.

| 입력 형태 | 후보 리스트 객체 수 | v2/v3 중앙 wall ms | 7쌍 중앙 시간비 | v2/v3 peak RSS MiB | 사전 게이트 |
| --- | ---: | ---: | ---: | ---: | --- |
| 같은 리스트에 25개 SLO, 45격자 | 45 | 318.795 / 212.894 | **1.6079×** | 437.461 / 437.562 | ≥1.20× 통과 |
| 575개 모두 다른 격자 | 575 | 1962.253 / 1951.223 | 0.9985× | 436.371 / 441.324 | 악화 ≤10% 통과 |
| 같은 내용의 리스트를 요청마다 복사 | 1,125 | 294.207 / 309.187 | 0.9305× | 443.879 / 442.773 | 악화 ≤10% 통과 |

공유 입력에서 7개 시간비의 범위는 `1.1559–2.0214`로 변동이 있다. 각 경로의 중앙 wall time을 나눈 값은 쌍별 중앙 시간비와 다를 수 있다. 1,125개 결과의 상태는 `RESEARCH_ESTIMATE` 720건·`ABSTAIN` 405건, 575개 결과는 각각 355건·220건으로 두 경로가 같았다. 최대 peak RSS 증가량은 고유 격자의 **4.953 MiB**로 20 MiB 한도 안이다. 고수위 RSS에는 저장 모델과 입력도 포함되므로 호출 중 임시 메모리의 정밀한 크기는 아니다.

## 적용 판단과 범위

**GO — 동일 후보 객체를 공유하는 오프라인 SLO 묶음 채점의 연구 경로에 v3를 사용한다.** 서로 다른 요청이 각자 후보를 역직렬화하는 환경에는 이 속도 향상이 그대로 적용되지 않는다. 그 경우 v3는 이번 쌍별 측정에서 중앙 약 7.5% 느렸고, 필요하면 기존 v2를 계속 사용할 수 있다. 이 결과는 동일한 저장 ExtraTrees로 같은 호스트의 알려진 모델·배치 벤치마크를 CPU에서 계산한 시간이다. 생성 SLO는 실제 사용자 목표가 아니며, 정확한 VM 크기나 `DEPLOY`/`SCALE_OUT`의 효과, 온라인 서비스 지연 및 학술적 신규성을 검증하지 않는다.

[결과 원본](../artifacts/gpu_shape_microbatch_v3/results.json)에 규약 `2f99ab5c15fe260c5087e63e7778adf0112041f16e69fd465d63296ce62cd035`, 실행 코드·모델·원본 해시 및 모든 쌍의 wall/CPU 시간을 보존했다. 첫 점수 후 예측기의 지원 범위 검사를 강화해 [첫 결과](../artifacts/gpu_shape_microbatch_v3/results_before_device_support_key.json)와 [당시 규약](../artifacts/gpu_shape_microbatch_v3/protocol_before_device_support_key.md)을 별도 보존하고 같은 고정 평가를 재실행했다. 첫 점수의 공유 입력 중앙 시간비 `1.5582×`는 최종 `1.6079×`로 바뀌었지만, 두 조건 모두 사전 게이트를 통과했고 결과 JSON 해시는 같았다.
