# 경희대 담당 연구: 현재 자료로 열 수 있는 학습 과제

2026-09-29 기준. 경희대 SQLite를 우선 사용하고, 부족한 관측량은 Google ClusterData 등 공개 원본에서 별도 도메인 연구로 보완했다. 이 문서는 **지금 관측 가능한 정답과 이미 수행한 학습의 채택 여부**를 담당 항목별로 정리한다. 자료를 섞어 하나의 AI-App 실행 이력처럼 만들지 않는다.

| 담당 항목 | 확보한 입력·정답과 수행 결과 | 현재 결정 |
| --- | --- | --- |
| 응용 요구사항 분석 | 로컬 7개 물리 실행 DB에 9,591회 실행, 그중 학습 적격 9,445회가 있다. 배치 p95·처리량, 관측 GPU 예약 피크·모델 적재시간은 예측할 수 있다. 실제 등록 요청에서 필요 VM CPU·RAM·GPU·노드 수로 이어지는 정답과 사용자 요청 SLO는 없다. [원본 7개 재점검](sqlite_seven_requirement_supervision_audit.md)에서 요청 텍스트와 요구 형상 정답이 없고, 기록된 작업 종류도 모델별로 상수임을 확인했다. | 기존 관측 신호를 출처·지원 범위와 함께 연구용으로 유지한다. 새 최소 VM 형상 지도학습은 시작하지 않는다. |

[저장 성능 모델](../artifacts/performance_v1/experiment_report.md)과 [연구 증거 v0.2](gpu_shape_evidence_v0.2.0_findings.md)를 사용할 수 있다. 모델 전체 제외에서 소수 측정 오차 전이는 [공유 작업 그리드의 탐색 이득](cross_model_covariance_findings.md)이 있었지만 새 작업 조건의 처리량으로 이전되지 않았다. [저장 모델 선택 감사](saved_gpu_shape_decision_audit_findings.md)에서는 원 생성 목표의 시험 54건 선택이 모두 성공했지만 요청/초 목표를 1.25배로 높인 합성 목표에서 잘못 승인한 4건이 나왔다. | 같은 호스트·GPU·작업 지원 범위의 **정적 배치 후보 평가**만 수행한다. GPU 복제본 수를 VM 노드 수로 바꾸거나 최소 안전 형상으로 확정하지 않는다. |
| 배포·Scale-out/in 판단 | 원본 SQLite에는 발행 조치·Ready·같은 앱의 전후 요청 결과 연결이 **0건**이다. Google [2011 자원](google_2011_joint_envelope_findings.md)과 [2019 사건](google_2019_cell_e_selector_findings_v1.md)은 일반 Borg 관측·부하를 학습했지만 AI-App 사용자 결과가 아니다. 2019 ALLOC_SET 두 셀의 유효 제출 108,003건은 전부 제출과 같은 시각에 SCHEDULE되어 [5초 지연 라벨이 상수](google_2019_alloc_set_start_delay_no_go.md)였다. 추가 [공개 AI 추론 자료 검색](public_scale_action_dataset_audit.md)에서도 같은 실행의 조치 발행·Ready·요청별 결과를 모두 가진 학습 원본을 확인하지 못했다. | 실제 조치의 효과 또는 `DEPLOY/UPDATE/SCALE_OUT/SCALE_IN/KEEP` 정답 모델은 열지 않는다. 기존 부하·위험 예측은 의사결정의 관측 신호로만 설명한다. |
| 배포·제어 추론 최적화 | 저장된 정적 성능 모델의 [45개 작업 조건·1,125개 합성 SLO](cross_workload_microbatch_v2_findings.md)를 묶어 채점하자 전체 JSON 동등성을 유지하며 로컬 계산 중앙 시간이 v1 505.251ms에서 v2 303.448ms로 줄었다. [복사된 후보 격자 v4](decision_inference_microbatch_v4_findings.md)는 7쌍 시험에서 v2 대비 1.3337배 빨랐고 출력·예측 호출 수가 같았다. 공개 Qwen 입력 버킷 3,994,435행으로 [전체 접두 60분 재사용](swissai_qwen_full_prefix_support_no_go.md)을 점수 전 규약에 따라 시도했으나 검증 양성 2,204건으로 사전 1만 건 하한을 못 채워 모델 적합 전에 중단했다. [사후 깊이별 검사](swissai_qwen_prefix_depth_support_exploratory.md)에서도 짧은 접두는 거의 모두 재사용되어 음성 지원량이 부족했다. | v3은 공유 후보 객체, v4는 복사된 동등 후보 객체의 오프라인 묶음 채점에 사용한다. 접두 캐시나 실제 GPU KV·TTFT 개선은 주장하지 않는다. |

[Alibaba MaaS SM 관측 상태 후속 연구](maas_sm_observability_findings_v1.md)는 [사전 규약](maas_sm_observability_protocol_v1.md)에 따라 기존 ID 표본의 140–142일로 학습, 143일로 보정, 144일 119,703개 판단에서 검증했다. 미래 고부하 관측(H), 여섯 창 정상 관측(N), 미해결(U)을 함께 예측한 두 단계 모델의 ID 동등가중 3클래스 Brier는 **0.327200**으로 직접 3분류 모델 **0.326560**보다 높았고, 6시간 블록 승리도 **0/4**였다. 개발 채택 기준에 실패해 **미채택**했으며 새 ID 시험 표본은 열지 않았다. 검증의 U는 28,138건으로, 형식적 이진 정답 보충에 따른 사건 비율은 3.50–27.00% 범위다. 이 결과는 5분 평균 SM 계측의 관측 상태에 관한 것이며 실제 VM 증감이나 사용자 SLO 결과가 아니다.

별도 담당 과제로 [Azure Coding의 다음 5분 입력 토큰 부하 상한](azure_code_input_demand_findings.md)을 실제 학습했다. 공개 표본 5분 합계를 직전 1시간 평균으로 정규화해 90분위 HGB를 적합한 뒤 3일을 시간순 평가했다. 후향 평균 pinball은 모델 **418,627**, 최선 단순 기준선 **742,048**이었고 날짜별 승리 3/3·피복률 92.01~93.75%로 사전 탐색 게이트를 통과했다. 그러나 Coding의 해당 기간 입력 집계는 이미 노출돼 독립 시험은 아니다. [별도 Conversation 서비스 전이](azure_input_demand_cross_service_findings_v1_1.md)는 방법과 기준선을 고정한 채 5일을 평가했고 모델 **348,600** 대 최근 1시간 기준선 **335,196**, 날짜별 승리 **0/5**, 모델 피복률 **96.88~98.96%**로 사전 게이트에 실패했다. 따라서 이 학습기를 경희대 배포·스케일 판단 신호로 채택하지 않는다. 두 자료는 실제 서비스 전체 유입량·사용자 지연·GPU/VM 조치 정답이 아니다.

이어 [RAGPulse 별도 AI 요청 표본](ragpulse_input_demand_transfer_support_no_go.md)에 하루 보정 가설과 같은 보정을 받은 단순 기준선을 사전 고정했다. Coding에서 주말·절대 시각 특징을 뺀 모델을 실제 재학습해 동결했지만, RAGPulse 상대일 27–34 각각에서 직전 1시간 표본 평균 1,000토큰 이상인 구간이 **225–250/288**개로 사전 274개 하한에 못 미쳤다. 따라서 **시험 점수 없이 중단**했고 이 자료로 전이 성공·실패를 새로 판정하지 않는다. RAGPulse도 전체 서비스 수요나 VM 효과 정답을 제공하지 않는다.

[저장 형상 모델의 연속 SLO 민감도면 감사](saved_gpu_shape_slo_surface_findings.md)는 이미 사용한 주 시험 90작업에서 생성 목표의 지연·요청/초를 각각 0.75–1.25배로 바꿔 정확한 로그 목표 면적을 계산했다. 저장 모델의 잘못 승인 면적은 전체의 **1.835%**, 저장 훈련 중앙값의 **7.252%**보다 작았다. 일부 후보만 실측 가능했던 면적은 25.747%였으며, 그 안에서 저장 모델의 성공/잘못 승인/보류는 전체 기준 22.561/0.589/2.597%p였다. 기존 2,660개 결정을 새 코드로 재생해 일치시켰다. 이 수치는 이미 열람한 한 호스트의 합성 목표에 대한 후향 진단이며 실제 사용자 SLO, 최소 안전 VM 형상, 스케일 행동 효과를 입증하지 않는다.

FCA 분산 추론의 CPU/GPU 선택도 별도 확인했다. 두 호스트에서 모델·작업 조건별 완전한 쌍은 각각 40개였고 GPU의 p95 지연 우세가 **40/40, 39/40**이었다. 3노드 `PARTITIONED` 실행의 거의 일정한 선택 결과를 현재 단일 VM 가정의 형상 정답으로 재해석하지 않는다. [FCA 원본 감사](local_signal_refresh_2026_09_28.md)

이후 [지연·처리량 공동 잔차 전이](cross_metric_anchor_transfer_findings.md)를 같은 8회 기준 측정으로 모델·계열 전체 제외 평가했다. 공유 encoder 8모델의 미측정 형상에서 지연 MALE는 독립 지표 방식 `0.238524→0.226669`로 낮아졌지만 요청/초 MALE는 `0.120705→0.126337`로 커졌다. 원 생성 SLO의 성공 선택도 `298→295건`, 오승인은 `13→14건`이었다. 두 새 입력 조건의 처리량 오차는 kernel·Ridge 기준선보다 컸다. 고정 채택 기준에 실패해 **미채택**한다. 이는 이미 열람한 같은 호스트의 정적 벤치마크를 다시 쓴 후향 탐색이다.

추가 [로컬 GPU 2개 프로파일 시간 예산 진단](replica_profiling_budget_feasibility_2026_09_29.md)은 2,300개의 GPU 1→2 짝에서 별도 정답을 확인했다. 이 과제로 [90분위 학습기](gpu2_profile_time_budget_findings_v1.md)를 시간순·모델 제외 방식으로 평가한 결과, 후행 encoder 1,004쌍에서 pinball 손실은 최선 기준선 대비 6.77% 줄었지만 피복률 `85.66% < 88%`, 5초 예산 오승인 `5 > 4`로 사전 채택 기준에 실패했다. **학습기는 미채택**하고 단순 donor p90 규칙을 오프라인 기준선으로 유지한다. 이 시간은 로컬 프로파일링 실행 구간이며 VM 배포 준비시간이 아니다. [추가 공개 AI 추론 조치 자료 감사](public_action_ready_slo_strict_followup_2026_09_29.md)에서도 InferScale·Sinan-GCP의 현재 공개 원본은 같은 실행의 조치 발행→Ready→요청별 결과를 연결하지 못했다.

응용별 GPU 형상 비교의 독립 도메인으로 [AgentPerfBench 공식 공개 원본](https://huggingface.co/datasets/agent-perf-bench/AgentPerfBench)을 고정해 [적격성 감사](agentperfbench_feasibility.md)와 [모델 제외 학습 평가](agentperf_shape_transfer_findings.md)를 수행했다. 원본 2,932실행에서 성공·양의 지표·동일 요청 수·유사 토큰량 조건을 지킨 주 분석은 9모델, 485작업 묶음, 1,041개의 앵커 외 대체 형상 후보를 제공했다. 그룹당 한 형상의 실측을 제공한 뒤 형상비 ExtraTrees가 다른 형상을 예측하도록 했지만, p90 E2EL/요청 처리량의 모델 균등 MALE이 `0.660/0.541`로 직접 ExtraTrees `0.452/0.365`보다 컸다. 고정 채택 기준에 실패해 형상비 전이는 **미채택**한다. 직접 회귀는 별도 LLM 서빙 벤치마크의 후속 연구 기준선으로만 남긴다. 원본이 성공한 형상에 편향됐고 실제 사용자 SLO·가격·VM 실행 조치가 없어 운영 추천이나 오토스케일 효과로 해석하지 않는다. [모델 단위 보수적 승인 보정](agentperfbench_uncertainty_design.md)도 독립 모델 수와 형상 쌍별 donor 지원이 부족해 보류했다.

다른 공개 도메인인 [Scherm B200 TP2→TP4 서빙 벤치마크](scherm_b200_tp24_findings.md)에서도 7모델·64짝을 모델 전체 제외로 학습했다. Ridge는 출력 토큰/초 모델 동일 MALE을 동시성별 donor 중앙 비율 `0.07159→0.06526`으로 낮췄지만 TTFT 집계값은 `0.17745→0.17625`로 거의 같았다. 2/7모델만 두 지표가 함께 개선돼 사전 탐색 게이트에 실패했다. `ttft_ms_p95`는 **요청별 p95가 아닌 반복 실행 평균 TTFT의 p95**이고 GPU count 열도 실제 TP 수와 달라, 이를 KHU VM 형상이나 사용자 SLO 정답으로 사용하지 않는다.

같은 B200 TP2의 [저부하 세 점→고부하 곡선 학습](scherm_b200_load_curve_findings.md)도 7모델·42개 고부하 셀에서 모델 전체 제외로 확인했다. Ridge는 출력률 MALE을 donor 동시성 중앙 비율 `0.25188→0.13422`, TTFT 집계 MALE을 `0.29723→0.27010`으로 낮췄다. 그러나 두 지표가 함께 개선된 모델은 3/7뿐이고 최악의 모델별 악화는 2.73배라 사전 탐색 게이트에 따라 **미채택**했다. 같은 파일의 RTX PRO 6000 기존 Qwen AWQ 행은 반복 성공 수와 TTFT 집계 열이 비어 있어 공동 지표의 동일한 외부 검증으로 쓰지 않는다.

[훈련 모델에서만 고른 Ridge·donor 수축](scherm_b200_load_curve_shrinkage_findings.md)도 바깥 모델 결과에서 출력률은 `0.25188→0.20631`로 개선됐지만 TTFT는 `0.29723→0.28940`, 공동 승리 4/7, 최악 악화 1.89배라 **미채택**했다. 전체 결과를 본 뒤 고른 고정 비율 0.25의 더 좋은 점수는 후향 선택 편향이며 독립 검증이 아니다.

[AgentPerfBench 일부 요청 실패의 형상별 정답 적격성](agentperf_partial_failure_shape_feasibility.md)도 따로 확인했다. 공개 2,932실행 중 724개는 일부 요청이 실패했지만, 동일 모델·엔진·프로필·동시성·요청 수에서 형상별 완료 여부가 섞인 그룹은 761개 중 56개뿐이다. 같은 형상 반복과 실패 원인이 없고 성공률 75% 미만 실행이 원본에서 제외돼, 이를 형상별 안전 승인 또는 OOM 정답으로 학습하지 않는다.

공개 LLM 서빙의 [A100 4→8 첫 토큰 지연(TTFT)·토큰당 지연(TPOT) 성분 예측](agentperf_component_pair_findings.md)도 130쌍/5모델로 모델 전체 제외 평가했다. 성분을 결합해 수축하는 후보는 TTFT 모델 균등 MALE `0.2740`으로 최선 기준선 `0.2783`을 1.5%만 앞섰고, TPOT는 `0.3025`로 최선 기준선 `0.1741`보다 악화됐다. 방향 충돌도 36건 중 10건만 찾아 사전 기준을 충족하지 못해 **미채택**한다. 이는 같은 GPU 기종의 텐서 병렬도 비교이며 VM scale 조치 실험은 아니다.

같은 공개 원본의 [GPU 커널 프로필 적격성](agentperf_kernel_shape_feasibility.md)도 감사했다. 실제 모델 prefill 135,341행은 배치 1·길이 128 조건뿐이고, 공개 메타데이터로 맞춘 복수 GPU 논리 연산 660묶음에도 호출 ID와 앱 전체 지연·메모리·사용자 결과가 없다. 이를 AI-App 가속기 종류·수량 추천의 독립 정답으로 학습하지 않는다.

[FreeInference 공개 텔레메트리](freeinference_live_telemetry_feasibility_2026_09_29.md)의 한 시점도 고정해 확인했다. 7일·1시간 집계는 6개 서버의 965표본이며 대기열 양성은 49개다. 최신 요청 120건은 일부 사용자 지연을 담지만, 명령·replica Ready·전후 결과를 잇는 필드가 없어 실제 스케일 행동 모델의 정답으로 쓰지 않는다.

[공개 조치·Ready·요청 원본 추가 점검](public_action_ready_request_refresh_2026_09_29.md)에서는 Zenodo 오토스케일 CSV, ONNX Spring Boot 오케스트레이터, AKS Ready Capacity Autoscaler 캠페인 세 건을 확인했다. ONNX 자료의 반복 `SCALE_UP`은 실행 시작부터 준비된 2개 Pod에 다시 `scale(2)`를 요청하는 코드 경로여서 새 용량 도착의 정답이 아니다. AKS 원본은 일반 HTTP 작업에서 `/scale` 기록·Ready 수·2초 지연 집계를 같은 실행에 담지만 요청별 완료시각·라우팅 ID와 개별 Pod 준비 연결이 없고 AI 추론도 아니다. 출처 저장소의 재사용 라이선스도 확인되지 않아 학습 자료로 들여오지 않았다. 따라서 세 후보 모두 경희대 AI-App의 실제 스케일 효과 학습에는 미채택한다.

[Chutes 공개 요청 추적 자료](chutes_serving_signal_feasibility.md)는 고정 revision의 분리된 두 시간 조각 2,002,944요청을 진단했다. 이어 같은 출처의 연속 구간에서 [모델별 다음 5분 관측 TTFT p90 학습](chutes_ttft_tail_v1_findings.md)을 검증했다. 검증 19모델·908개 창에서 인스턴스 분산·캐시 특징을 더한 후보의 모델 균등 오차는 기본 도착량·토큰 학습기 `0.25416→0.25827`로 악화돼 **미채택**했다. 점수 전 규약에 따라 시험 row group 74–76은 열지 않았다. 검증 스트리밍 요청 중 유효 TTFT가 있는 비율은 60.6%라 이 점수도 관측·완료된 요청의 조건부 결과다. 처리 인스턴스 수는 전체 replica 수가 아니며 조치·Ready·실제 GPU 형상도 없어 실제 `SCALE_OUT/IN` 효과나 최소 VM 형상의 정답으로 쓰지 않는다.

같은 원본에서 TTFT 결측과 별개인 [다음 5분 스트리밍 요청량 p90](chutes_demand_p90_v1_findings.md)도 실제로 학습했다. 35개 학습 등록 모델의 검증 적격 판단 1,514건에서 상대 수요 학습기의 모델 균등 pinball 손실은 절대 건수 학습기 `48.316→45.735`로 5.34% 낮고 피복률은 88.66%였다. 하지만 기준선보다 나은 모델이 **16/35개**로 사전 60% 문턱을 넘지 못해 **미채택**했다. 검증 실패 후 시험 row group 74–76은 계속 봉인했다. 이는 기록된 요청 시작 건수의 수요 신호 탐색이며, 필요 GPU·VM 수나 조치 효과 학습이 아니다.

[최근 오차를 반영한 Chutes 요청량 p90 후속 연구](chutes_demand_p90_v2_findings.md)도 별도 시험 구간을 봉인한 채 학습 구간 내부에서 검증했다. 35개 모델·1,094개 판단에서 모델 균등 pinball 손실은 최선 단일 기준선 `43.665→41.000`으로 낮았지만, 고정 혼합 `41.154` 대비 개선은 0.37%로 사전 2% 문턱에 못 미쳤고 1시간 블록 승리는 2/4였다. 따라서 적응형 후보는 **미채택**했고 시험 row group 77–79도 열지 않았다. 이 결과 역시 관측 요청량의 예측 신호이며 스케일 조치 효과의 정답은 아니다.

[Google 2011 초기 자원 계측 피드백 연구](google_2011_early_feedback_findings_v1.md)에서는 배정 후 5~10분 안에 끝난 사용량 보고로 남은 30분 창의 관측 CPU·RAM 피크를 학습했다. 원본 해시를 검증하고 작업·기계·시각을 연결한 뒤 검증 2,808 task·48 job에서 후보의 job 균등 종합 pinball은 제출 정보만 쓴 기준선 `1.080459→1.096139`로 **1.45% 악화**됐다. CPU·RAM 동시 피복은 94.28%였지만 RAM 손실과 job별 승리 조건도 실패해 **미채택**했다. 사전 게이트에 따라 별도 시험 조각 `00475`는 열지 않았다. 원본에 사용량 보고의 실제 도착시각, AI 응용 정체, 대체 형상 결과가 없으므로 이 연구를 운영용 CPU·RAM 추천기로 바꾸지 않는다.

저장된 로컬 배치 성능 모델의 [모델·장치별 입력 지원 범위](saved_model_condition_support_fix.md)도 수정했다. 기존에는 Qwen에서 측정하지 않은 배치 16이 다른 모델의 전역 범위 때문에 승인됐다. 현재는 고정 원본의 훈련 분할에서 모델·revision·장치별 배치·길이·동시성 범위와 실제 반복 횟수를 재구성해 보류한다. 원본 모델의 예측값은 유지되며, 별도 캠페인의 승인 행은 `local-novel-matrix` 108→56, `local-space-filling` 296→100으로 줄었다. 남은 그룹은 각각 5개·9개라 점수는 제한된 범위의 연구용 결과다. 주변 범위 안의 미측정 조합도 보간 예측으로 남으므로 이것을 실측 승인으로 해석하지 않는다.

[오프라인 추론 v3](decision_inference_microbatch_v3_findings.md)는 동일한 GPU 후보 리스트 객체를 25개의 합성 SLO가 공유하는 경우 후보 검증과 격자 키 생성을 재사용한다. 45격자·1,125질의에서 v2와 전체 JSON과 예측 횟수가 같았고 7쌍 중앙 시간비가 1.608배였다. 후보를 요청마다 복사하면 오히려 7.5% 느려서 공유 객체를 만드는 내부 채점 경로에만 적용한다. 실제 서비스 배포 판단 속도나 성능 개선의 근거로 확대하지 않는다.

[오프라인 추론 v4](decision_inference_microbatch_v4_findings.md)는 SLO 요청마다 별도 객체로 복사한 후보 리스트의 내용이 정확히 같을 때 검증 결과를 재사용한다. 복사 입력 1,125개에서 v2 대비 1.3337배, v3 대비 1.3303배 빨랐고, 공유 객체에서는 v3보다 약 3.5% 느렸다. 따라서 입력의 객체 공유 여부에 따라 해당 경로를 선택한다. 전체 JSON 동등성·예측 호출 수·사전 메모리 게이트를 확인했지만 이는 같은 호스트의 저장 모델을 이용한 오프라인 CPU 시간이다.

[v5 최대 64격자 묶음 예측](decision_inference_chunk64_findings.md)은 v4의 검증·선택 코드를 그대로 쓰면서 예측 호출 묶음만 늘렸다. 같은 1,125개 복사 질의의 7쌍 중앙 시간비는 기본 8격자 대비 **2.007배**, 공유 입력은 **2.354배**, 서로 다른 575격자는 **3.753배**였다. 세 입력 모두 결과 JSON 전체가 같고 peak RSS 증가는 최대 1.024 MiB여서 사전 채택 기준을 통과했다. 이 결과는 저장 모델의 오프라인 CPU 계산이며 온라인 지연·실제 배포 효과의 증거는 아니다.

[v6 최대 256격자 묶음 예측](decision_inference_chunk256_findings.md)은 같은 고정 모델의 575고유 격자에서 64격자 대비 호출을 **9→3회**, 7쌍 중앙 시간을 **1.518배** 줄였다. 1,125개 공유·복사 SLO 질의는 이미 64격자에서 예측 1회이므로 각각 중앙 속도비 **0.995·0.953배**로 거의 같다. 모든 결과 JSON은 정확히 같고 RSS 증가도 사전 한도 안이었다. 이전 연구 버전은 재현을 위해 그대로 보존하고, 이 입력 범위의 오프라인 다중 질의에는 v6를 사용한다.

[64격자에서 ExtraTrees worker 수 1·2·4 비교](decision_inference_workers64_findings.md)는 2·4 worker가 모든 입력에서 최종 JSON의 마지막 자리 수치를 바꾸는 것을 확인했다. 상태·선택 형상은 같은 사전 비교에서 같았지만, 전체 출력 동등성 게이트가 실패해 **1 worker를 유지**하고 속도 채택 점수는 내지 않았다. 입력 수가 커졌다는 이유만으로 이전 1-worker 설정을 바꾸지 않는다.

## 다음 연구의 데이터 조건

현재 자료로 새 지도학습 성과를 억지로 만들기보다 두 관측을 추가하는 편이 우선이다.

1. **새 AI 모델과 형상별 결과:** 학습에 쓰지 않은 모델·호스트에서 등록 시점 메타데이터, 사용자가 제공한 SLO, 동일 응용의 여러 CPU·RAM·GPU·VM 형상별 성공·실패와 요청 지연을 수집한다. 이를 앱/모델 전체 제외로 평가하면 정적 요구 분석과 형상 추천의 일반화를 검증할 수 있다.
2. **실제 조치 연결:** [사건 데이터 계약](scale_effect_data_contract_v1.md)에 따라 `decision_id → action_id → issued_at → ready_at`을 같은 앱·버전·VM 형상과 연결하고, 조치 전후의 요청별 생성·완료시각·오류·SLO와 동시 부하를 남긴다. 새 VM에 별도 배포 ID가 생기는 경우에는 [연구용 0.2.0 계약](scale_action_events_v0_2_0.md)의 안정적인 서비스 ID, 준비 완료 뒤 라우팅 전환, 실제 처리한 배포 ID까지 기록한다. 조치가 없었던 비교 구간도 기록해야 정책의 효과와 자연 부하 변화를 구분할 수 있다.

외부 자료는 계속 사용할 수 있다. Google은 범용 CPU/RAM·도착량 방법의 도메인 내 시험, SwissAI는 LLM 요청·접두의 분포 및 지원량 시험에 적합하다. 이 출처들은 로컬 AI-App의 VM 조치 정답을 추가하지 않는다. 새 공개 자료를 채택할 때는 먼저 원본 권리, 결정 전 입력, 관측 정답, 시간·앱 ID 결합과 단순 기준선의 지원량을 확인한다.

[llm-d 벤치마크 수집기 추가 감사](llmd_benchmark_action_data_audit_2026_09_29.md)에서 replica **시계열**과 Pod 생성·Ready 시각을 수집하고, 요청별 지표 파일을 읽는 코드를 확인했다. 기존 수집 문서의 일회성 스냅샷 설명은 현재 코드의 반복 수집을 완전히 설명하지 않는다. 그러나 해당 고정 저장소·릴리스에서 결합된 실행 산출물을 확인할 수 없었고, 지정 GCS 버킷의 익명 목록 요청은 HTTP 401이었다. 더구나 replica 상태 조회는 명령 발행 사건이 아니므로 지금의 실제 스케일 효과 학습 NO-GO 판정은 유지한다.

[별도 llm-d-autoscaling 저장소의 공개 실행물 감사](llmd_autoscaling_committed_results_audit.md)에서는 고정 커밋의 실행 압축본 3개를 직접 열어 **360요청·177성공·183타임아웃**을 확인했다. 요청별 지연/오류는 있지만, 같은 커밋의 실행물에는 스케일 명령·Pod Ready·replica 시계열이 없고 Grafana 참조는 로컬 주소뿐이다. 이는 앞선 **수집기 기능** 감사와 구별되는 **공개 산출물** 감사이며, 조치 효과 학습은 여전히 NO-GO다.

[저장 GPU 추천의 여유값 보류 감사](saved_gpu_margin_abstention_findings.md)는 주 시험의 엄격한 요청/초 목표 오승인 4개를 10% 문턱으로 모두 보류했지만 성공 승인도 46→40개로 줄었다. 느슨한 목표와 새 입력에서는 10~30% 예측 여유가 있는 오승인도 확인했다. 따라서 예측 여유만으로 운영용 안전 승인 문턱을 정하지 않고, 기존 정적 후보 평가는 연구용으로 유지한다.

[Argonne vLLM 공개 벤치마크](argonne_vllm_shape_transfer_findings.md)의 9모델·169개 같은 작업/다른 가속기 묶음에서는 새 모델의 한 형상 계측 후 다른 관측 형상 지연을 예측했다. 앵커 잔차 보정은 강한 앵커 조건 회귀보다 모델 동일가중 로그오차가 낮았으나 모델별 승리 3/9와 방향 정확도 조건에서 실패해 **미채택**했다. 직접 회귀를 별도 벤치마크 기준선으로만 유지한다. 이 원본에는 실패/OOM·VM 비용·사용자 SLO·실제 스케일 조치가 없으므로 KHU SQLite와 결합하거나 안전한 인프라 형상 추천 정답으로 취급하지 않는다.

[Philly 기계·GPU 슬롯별 전날 위험 보정](philly_slot_day_calibration_holdout_findings.md)은 이미 공개된 세 개발 집합에서 수식을 정한 뒤, **미사용 기계 51대·812,729판단**에서 한 번 확인했다. 강한 정확한 기계별 절편의 행 Brier **`0.085786→0.083532`(상대 2.63% 감소)**, 기계별 개선 **44/51대**, 기계 재표집 차의 95% 구간 **[−0.003105,−0.001443]**이고 사전 여섯 기준을 통과했다. 이는 기존 표의 **배포·Scale-out/in 판단에 제공 가능한 GPU 고사용률 위험 입력**을 개선한 결과다. Philly는 DNN 훈련 클러스터 계측이므로 AI-App VM 수·사용자 SLO·실제 조치 효과의 정답으로 쓰지 않는다.

[전날 GPU 슬롯 보정 계산 모듈](philly_slot_day_core_replay.md)은 같은 방법을 당일 정답 없이 호출할 수 있는 연구 경계로 분리했다. 저장된 새 기계 시험 812,729행에서 기계·슬롯 확률을 전부 재생해 최대 절대 차 0을 확인했다. 실제 피드백 전달 시각은 원본에 없으므로 재생에는 정답 창 종료 즉시 가용 가정을 사용했고, 운영 입력의 관측·가용 시각 검증은 호출 Adapter의 책임으로 남는다.

[같은 새 기계 점수의 사후 피드백 지연 재생](philly_slot_feedback_delay_findings.md)에서는 추가 정답 전달 지연 5분·6시간·12시간을 가정할 때 슬롯 보정의 정확한 기계 절편 대비 행 Brier 감소가 각각 **2.63%·2.11%·1.48%**였다. 24시간 지연은 전날 정답을 사용하지 못해 두 방법이 `p₀`와 같았다. 실제 결과 전달 시각은 원본에 없으므로 지연 허용값이나 운영 정책으로 채택하지 않는다.

[Philly 보정의 Alibaba MaaS 인스턴스 전이 탐색](maas_day_ahead_instance_transfer_findings.md)은 기존 표본의 시험일 145–146에서 현재 정상 53,513행·새 초과 1,899건의 지원량을 통과했다. 전역+인스턴스 전날 보정은 기존 확률표의 행 Brier `0.020702→0.020675`로 **0.13%**만 낮췄다. AP는 올랐으나 사전 5% 개선·양일 승리 조건에 실패해 **미채택**했고 새 ID bucket 1은 열지 않았다. 이미 시험일 결과가 노출된 후향 탐색이며, 온라인 AI-App만의 위험 또는 실제 스케일 효과를 증명하지 않는다.

[같은 MaaS 예측의 사후 경보 순위 진단](maas_alert_ranking_posthoc_diagnostic.md)은 동점을 무작위로 푸는 동일 일자 상위 5% 예산에서 단순 확률표 대비 후보의 신규 초과 기대 포착을 145일 `608.79→656.00`, 146일 `407.13→460.86`건으로 계산했다. 하지만 **이미 저장된 더 강한 MaaS 학습 모델**은 각각 `706·472`건으로 후보보다 높고, 전체 Brier·AP도 더 좋다. 인스턴스·시간 또는 날짜당 첫 판단만 남겨도 후보의 AP는 두 날짜 모두 이 학습 모델보다 낮다. 따라서 사후 선택한 1% 예산의 예외적 이득도 채택 사유로 삼지 않는다. 독립 위험 검증·실제 scale 효과나 원래 Brier NO-GO의 번복이 아니다.

[기존 MaaS 단일 학습 모델의 새 ID 확인](maas_existing_model_new_id_findings.md)은 모델·기준선·지원량·게이트를 bucket 1 원본 접근 전에 동결하고, 원본 21조각을 다시 검증해 새 ID **787개·55,436개 현재 정상 판단**을 한 번 채점했다. 행 Brier는 기존 표 `0.023850→0.022807`(4.38%), 학습 전용 정상 Beta `0.023543→0.022807`(3.13%)로 낮아졌지만 사전 **양쪽 각각 5% 개선** 기준에 못 미쳐 **미채택**했다. ID 동일가중 Brier·AP·양일·재표집은 개선됐어도 GPU 위험 입력에 한정되며 실제 VM scale 효과는 미검증이다.

[MaaS 상태별 전날 확률 보정의 새 ID 시험](maas_state_day_calibration_holdout_findings.md)은 이미 열람한 bucket 0·1에서 수식을 정하고 bucket 2 수집 전에 방법·비교기·문턱을 고정했다. 795개 새 ID·51,577개 현재 정상 판단에서 후보의 행 Brier는 저장 모델 `0.025798→0.025445`(1.37%), 전역 전날 정확한 절편 `0.025710→0.025445`(1.03%)로 낮았으나 각각 2% 감소 조건과 ID 재표집 상한 <0 조건에 실패해 **미채택**했다. 두 날짜의 Brier·ID 동일가중·AP 조건은 통과했고, 독립 검산에서 저장 예측을 전 행 정확히 재생했다. 같은 주간의 관측 GPU 위험일 뿐 조치 효과 정답이 아니다.

[세 MaaS ID 집합의 사후 오차 분해](maas_state_day_no_go_diagnostic.md)에서는 동결 후보의 전체 제곱오차 감소 중 최근 고사용률 상태 2.2–2.7% 행의 기여가 **72–95%**였다. 이미 공개된 bucket 2 정답을 보고 고사용률 상태에서 전날 Beta 표를 반씩 섞자 전체 Brier 이득이 1.37→1.58%로 올랐지만 원래 2% 기준을 여전히 넘지 못했다. 이는 사후 탐색이라 새 방법의 독립 성공이 아니며, 같은 주간 ID를 더 여는 것보다 다른 시기·서비스와 실제 조치 연결 자료 확보가 우선이다.

## 9월 29일 추가 확인: Philly GPU 위험 입력

[미사용 기계 41대·685,940개 판단](philly_day_ahead_calibration_holdout_findings.md)에서 전날 기계별 결과를 이용한 확률 보정은 동결된 GPU 고부하 위험 모델의 Brier를 `0.086988→0.082766`으로 낮추고 사전 탐색 게이트를 모두 통과했다. 이는 배포·스케일 판단에 제공할 수 있는 **위험 확률 입력의 정확도**에 관한 결과다. 위 표의 조치 정답 부재와 실제 Scale-out/in 효과 미검증이라는 결론은 그대로다.
