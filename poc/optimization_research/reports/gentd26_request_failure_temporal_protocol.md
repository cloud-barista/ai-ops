# GenTD26 요청 실패 상태: 후행 기간 민감도 평가 규약

작성일: 2026-09-28. 이 규약은 [검증 결과](gentd26_request_failure_validation_findings.md)를 본 뒤 설계했다. `lora_request_trace.csv`의 2024-12-04~08 요청을 **한 번만** 평가해, 기존 학습 기간(2024-11-29 이전)에서 만든 실패 확률이 같은 서비스의 뒤 기간에도 유지되는지 살핀다. 시험 기간의 실패 총수와 날짜·모델·`groupId` 집중도는 규약 작성 전에 열람됐다. 따라서 이 기간을 블라인드 또는 독립 검증이라고 부르지 않는다. 최종 상태의 확정·전달 시각, 실패 원인, VM 변경 및 사용자 SLO가 없으므로 온라인 판단이나 `DEPLOY/UPDATE/SCALE_OUT/SCALE_IN` 채택 시험도 아니다.

## 고정 입력과 시간 경계

- 원본은 [Alibaba GenTD26 설명](https://github.com/alibaba/clusterdata/blob/8c132fb7717fbd44cf434cf81f2cd865a80072d5/cluster-trace-v2026-GenAI/README.md)의 `lora_request_trace.csv`, SHA-256 `263fb88f1095f62d360cf89ded8cfc24fa2c5d111c1b16e7aaa9ccbfc4b37d78`이다. 원본은 읽기 전용이다.
- 학습에 쓰는 라벨은 `gmt_create < 2024-11-29 00:00:00`의 확정 `SUCCEED/FAILED` 상태뿐이다. 11월 29일~12월 3일 검증 상태는 재학습이나 확률 계산에 쓰지 않는다. 시험은 `2024-12-04 00:00:00 <= gmt_create < 2024-12-09 00:00:00`의 확정 상태만 평가한다. `PENDING/PROCESSING`은 미확정으로 제외하고 수를 기록한다. 날짜는 원본의 익명화된 `gmt_create` 기준이다.
- 시험 특징은 제출 시점 열인 `predict_type`, `checkpoint_model_version_id`, `prompt_length`, `negative_prompt_length`, `num_images_per_prompt`, `num_inference_steps`, `num_lora`만으로 만든다. 숫자는 음수·비유한 값을 거부한다. 비어 있는 부정 프롬프트 길이는 0과 결측 표시로 표현한다. `predict_status`는 별도 라벨 프레임에만 들어가고, `exec_time_seconds`, `groupId`, 날짜 및 다른 상태·모니터링 열은 특징 프레임에 들어가지 않는다. 모델·그룹의 기존/신규 여부는 학습 기간 ID와 비교해 진단에만 쓴다.
- 원본 순서는 `gmt_create` 단조 증가여야 하며, 시험 요청이 지정한 5일 밖에 있으면 중단한다. 원본 바이트, 기존 규약·평가 코드·테스트·freeze manifest, 검증 지표·행별 예측·저장된 로지스틱 모델, 사후 감사 코드·JSON의 SHA-256을 확인한다. 저장된 `model.joblib`을 역직렬화하기 전에 `numpy`, `pandas`, `scikit-learn`, `joblib` 버전도 기존 학습 환경과 정확히 일치시킨다.

## 재학습 없는 세 가지 확률

1. **기존 로지스틱:** [검증 전 코드](../scripts/evaluate_gentd26_request_failure.py)가 학습 기간에 적합해 저장한 `model.joblib`을 그대로 불러온다. 당시와 동일한 2개 범주 one-hot 및 7개 `log1p`/표준화 수치 특징을 사용한다. 재적합·보정·초모수 변경은 하지 않는다.
2. **기존 `model_type` 기준선:** 같은 검증 전 코드의 학습 전용 빈도식 그대로 계산한다. 전역률은 `g=(실패+1)/(요청+2)`; 작업 종류 및 모델별률은 각각 `g`의 100 pseudo-count로 수축하고, 모델×작업 종류률은 두 부모율 평균의 50 pseudo-count로 수축한다. 학습에 없는 범주는 부모율로 돌아간다.
3. **사후 `beta1_model` 기준선:** [검증 사후 감사](gentd26_request_failure_validation_findings.md)에서 제시한 한 pseudo-count 모델별 빈도식 `p_m=(모델 학습 실패+g)/(모델 학습 요청+1)`을 그대로 사용한다. 새 모델은 `g`를 쓴다. 이 방법과 pseudo-count는 **검증 결과를 본 뒤** 정했으므로 뒤 기간 결과가 좋아도 독립 선택 성공이나 고유 학습 알고리즘의 증거가 아니다.

세 확률은 모두 `[1e-6,1−1e-6]`로 제한한다. 원래 로지스틱과 원래 `model_type`의 검증 점수는 본 규약에서 다시 선택하지 않는다. `beta1_model`이 2024-11-29 이전 자료만 썼다는 사실과, 선택 자체가 검증 사후라는 사실을 구분한다.

## 점수 전 지원 게이트와 점수

시험 점수를 계산하기 전에 다음을 모두 검사한다: 확정 요청 **5,000건 이상**, 실패 **50건 이상**, 실패가 있는 날짜 **3일 이상**, 실패 `groupId` **15개 이상**, 최대 한 `groupId`의 실패 비중 **1/3 이하**, 학습에서 요청 10건 이상이 모두 실패한 세 모델을 제외한 실패 **25건 이상**. 12월 4~8일 각각 확정 요청이 있어야 한다. 세 모델 ID는 학습 상태에서 같은 규칙으로 재계산하고, 사후 감사에 기록된 `M0013/M0055/M0061`과 정확히 일치해야 한다. 하나라도 실패하면 확률을 생성·채점하지 않고 `ValueError`의 게이트 상세를 표준 오류로 보고한다. 이 문턱은 시험 전체의 거친 분포가 알려진 뒤 정한 것으로, 사전 독립 시험의 문턱이 아니다.

주 지표는 **5일의 날짜별 Brier 평균**이다. 같은 시험 요청에서 세 방법의 주 지표와 `beta1_model − 로지스틱`, `beta1_model − model_type` 차이를 기록한다. 보조 지표는 전체 요청 가중 Brier, `groupId` 동일 가중 Brier, log loss, average precision(AP), 관측 실패율과 평균 예측 실패율, 각 날짜의 요청·실패·Brier·AP다. 실패가 없는 날짜나 층의 AP는 `null`로 둔다. 학습에서 본/새 모델, 본/새 `groupId`, 세 전량 실패 모델 포함/제외 층을 별도로 기록한다. 빈 층은 요청 수 0과 점수 `null`로 명시한다. 날짜·그룹은 상관된 반복 요청을 포함할 수 있으므로 행 수를 독립 실패 사건 수로 해석하지 않는다.

성능의 GO/NO-GO나 운영 채택 임계값은 두지 않는다. 결과가 어떻든 이 출처만으로 VM 크기·수량 추천, 실패 원인 판단, 스케일 조치 효과를 주장하지 않는다. 후속 채택에는 상태 확정·전달 시각과 다른 서비스·기간의 충분한 실패, 실제 자원·조치·사용자 SLO 기록이 필요하다.

## 실행·동결 순서

새 [평가 코드](../scripts/evaluate_gentd26_request_failure_temporal.py)의 `freeze`는 점수를 읽지 않고 현재 규약·코드·합성 테스트 및 고정 원본·기존 산출물의 해시와 버전을 새 manifest에 기록한다. 결과 경로가 이미 있으면 거부한다. 독립 코드 검토 뒤 `freeze`를 한 번 실행한다. 이후 `score`는 모든 해시·버전·지원 게이트를 다시 확인하고, 한 번만 `score/` 디렉터리에 행별 예측과 지표를 원자적으로 기록한다. 기존 결과는 덮어쓰지 않는다. 코드 검토 전에는 `freeze`와 `score`를 실행하지 않는다.
