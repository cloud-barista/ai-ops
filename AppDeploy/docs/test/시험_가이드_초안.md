# 시험 가이드 초안

## 시험 원칙
- 모든 시험에는 TC ID를 부여한다.
- API 요청/응답, request_id, deployment_id, 로그 파일, VM/GPU readiness 결과를 보존한다.
- 사람 검증자가 실제 VM/GPU/외부 API 통합 시험을 최종 확인한다.

## Inference/Stop 수동 검증

HTTP inference endpoint를 제공하는 앱은 control-plane API로 health와 invoke를 확인한다. Stop 검증은 API 응답의 `status=STOPPED`, deployment log의 `STOPPING`/`STOPPED`, 원격 VM의 app process 제거, app port 연결 실패를 함께 확인한다.

Inference proxy와 stop process 종료 흐름은 테스트 완료했다.

## Evidence Collection

PowerShell 환경에서는 다음 명령으로 테스트와 API smoke 결과를 수집한다.

```powershell
.\scripts\collect-evidence.ps1 -Port 18080
```

외부 제공 인터페이스 예제 검증은 서버 실행 후 다음 명령으로 별도 수행한다.

```powershell
.\scripts\interface-smoke.ps1 -BaseUrl http://localhost:8080
```

Package CLI 계약과 연속 배포는 다음 테스트로 검증한다.

```powershell
go test ./internal/cli ./internal/artifact ./internal/server
$tokens = $null; $errors = $null
[System.Management.Automation.Language.Parser]::ParseFile((Resolve-Path .\scripts\package-deploy.ps1), [ref]$tokens, [ref]$errors) | Out-Null
if ($errors.Count -gt 0) { throw $errors[0] }
bash -n ./scripts/package-deploy.sh
```

실서버 smoke에서는 CPU/GPU와 일치하는 Runtime/Target Profile을 먼저 등록한 뒤 `package-deploy.ps1/.sh`를 실행하고, 최종 JSON의 `package.checksum`, `app.app_version_id`, `resource_check.status`, `deployment.status`와 Deployment 로그를 보존한다. `resource_check.status=unavailable` 시험에서는 Deployment가 생성되지 않는지 확인한다. 연속 호출은 비원자적이므로 실패 시험에서는 오류 또는 `partial_result`에 표시된 archive/App ID도 함께 기록한다.

App 삭제 시험은 별도 미사용 App에 `DELETE /api/v1/apps/{app_id}` 또는 `apps delete <app-id> --yes`를 실행해 목록과 상세 조회에서 사라지는지 확인한다. 이어서 모든 참조 Deployment가 `STOPPED`인 App의 삭제와 Deployment 이력 보존, 같은 name/version 재등록, App Spec의 로컬 artifact 및 VM 파일 유지를 검증한다. `STOPPED` 외 참조 상태를 하나 이상 둔 시험에서는 409 응답과 App 등록 보존을 확인한다.

Profile 삭제 시험은 Runtime과 Target 각각에 대해 미참조, 모든 참조가 STOPPED, STOPPED와 STOPPED 외 상태가 섞인 조건을 분리한다. 앞의 두 조건은 200과 `ProfileDeleteResponse`를 반환하고 STOPPED 외 참조가 하나라도 있으면 Runtime은 `RUNTIME_PROFILE_INVALID`/409, Target은 `TARGET_PROFILE_INVALID`/409이며 등록이 유지되어야 한다. 없는 ID는 `NOT_FOUND`/404를 확인한다. 이름 없는 Profile 삭제도 `name=""` 필드를 포함해야 한다.

Target 삭제 전 Resource Check로 현재 Inventory를 만든 뒤 삭제하여 Inventory 목록에서 해당 snapshot이 제거되고 `inventory_deleted=true`인지 확인한다. Inventory가 없던 Target은 false를 반환해야 하며 Runtime 삭제는 항상 false이다. Profile 삭제 후에도 STOPPED Deployment 조회, Event/로그, Metric 조회가 유지되고 Target이 참조한 Runtime Credential이 목록과 resolver에 남는지 확인한다.

Runtime Credential 시험은 실행 중에 매번 임시 canary 비밀값을 생성하고 요청 fixture나 증적 파일에 저장하지 않는다. private key/password 분기, ID 형식, 필수 `host_key_fingerprint`의 canonical OpenSSH SHA256 형식, 개별 secret 필드 최대 길이 위반, 중복 ID, 전체 JSON 본문 128 KiB 초과, 없는 ID 삭제를 검증한다. 개별 필드 오류는 `TARGET_PROFILE_INVALID`/400, 중복은 같은 코드의 409, 전체 본문 초과는 같은 코드의 413, 미존재 삭제는 `NOT_FOUND`/404가 반환되어야 한다. 등록 응답과 목록에는 공개 메타데이터인 fingerprint가 그대로 포함되고, private key·passphrase·password canary는 응답·목록·로그·store·Web·CLI 출력·증적 어디에서도 검출되지 않아야 한다.

신뢰 가능한 별도 채널에서 얻은 fingerprint와 SSH 서버가 제시한 host key가 일치할 때만 연결되고, 다른 fingerprint이면 인증 정보 사용 전에 연결이 거부되어야 한다. Web/API/CLI `--host-key-fingerprint`와 ENV `_SSH_HOST_KEY_FINGERPRINT` 경로를 각각 확인한다. ENV Credential은 `GET /api/v1/credentials`에 나타나지 않으며, fingerprint가 없는 ENV fallback은 실패해야 한다.

기본 접근 정책은 loopback peer와 loopback `Host`를 모두 요구하고, `Origin`이 있으면 같은 origin만 허용하며, POST의 non-JSON Content-Type을 거부해야 한다. 각 조건의 음성 시험과 `AIAPP_CREDENTIAL_API_ALLOW_REMOTE=true` opt-in 시험을 분리한다. Remote opt-in은 TLS·인증 reverse proxy가 인증 없는 원격 요청을 거부하고 인증된 요청만 성공시키는 행위를 검증하며 proxy 구성과 결과를 함께 증적으로 기록한다.

등록 후 서버를 재시작하면 Runtime Credential 목록이 비어 있어야 한다. Target Profile의 `credential_ref`는 최대 256자의 `cred://namespace/id` 형식만 허용하고 비밀번호·PEM·token canary 직접 입력은 400으로 거부하며 store와 Target 목록에도 남지 않아야 한다. Target이 참조하는 Runtime Credential 삭제는 성공해야 한다. 이후 SSH runner가 실제 연결을 시도하면 Credential 누락으로 실패해야 하지만 dry-run 자원 점검·배포는 Credential을 해석하지 않는다는 차이도 별도 검증한다.

결과는 `deliverables/evidence/results/{timestamp}`에 저장하며, 주요 파일은 다음과 같다.
