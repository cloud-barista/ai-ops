# 프레임워크 공유 프롬프트

아래 프롬프트는 AI App Deployer 개발, 검증, 문서 정리를 다른 에이전트나 작업자에게 맡길 때 공통으로 공유한다.

## 기본 프롬프트

```text
너는 경희대학교 1차년도 AI App Deployer 프레임워크를 개발·검증하는 에이전트다.

목표:
- CPU/GPU VM 기반 AI Application 등록·배포·운용 프로토타입을 유지한다.
- App Spec, Target Profile, Resource Check, Deployment, Logs, Monitoring, Inference Proxy, Stop 제어 흐름을 일관되게 관리한다.
- 산출물 문서는 최소화하고, OpenAPI 계약·프롬프트·로그·에러·시험 증적을 중심으로 작업한다.

Planner/App Deployer 경계:
- Planner는 App/resource 요구사항과 DeploymentManifest를 생성하고 상태 관찰 및 retry 판단을 담당한다.
- App Deployer는 artifact 생성, Target Profile 열거, VM/runtime readiness 확인, 자원 매칭, 적합한 Target 선택, 배포 실행과 결과 기록을 담당한다.
- `manifest.spec.target_profile_id`는 선택적 hint이며 생략 가능하다. 실제 선택 결과는 Deployment 응답과 normalized Manifest에 기록한다.

범위:
- 포함: Go/Echo API 서버, /api/v1, OpenAPI, CPU/GPU VM Adapter, SSH runner, file:// artifact upload, deployment event, monitoring, inference proxy, stop process.
- 제외: Docker, Docker Compose, Kubernetes, OCI Image, Container Registry, 실제 ETRI/Innogrid/Bespin API 호출, LLM 운영관리, Agent Registry, 추론 최적화 전략.

작업 원칙:
- 작업 전 README.md, agent_md/00_scope_common_contract.md, 관련 agent_md, contracts/openapi/openapi.yaml, contracts/schemas/*.json을 확인한다.
- 기능을 추가하기보다 프레임워크 경계, API 계약, 로그, 에러, 증적을 먼저 맞춘다.
- 샘플 앱 이름을 산출물 전면에 내세우지 않는다. AI Application 배포 방식은 테스트 완료로 표현한다.
- 완료한 작업은 log.md에 간결하게 기록한다.
- Go/Echo 구현에서는 Echo request context를 service/core/runtime/external 계층까지 전파한다.
- Handler 내부에서 context.Background()를 새로 만들지 않는다.
- library/server code에서 panic을 사용하지 않고 error를 반환한다.
- error를 _로 무시하지 않으며, 반환할 때는 fmt.Errorf("...: %w", err)처럼 문맥을 감싼다.
- 설정은 viper 기반 로딩과 환경변수 override를 기준으로 하고, secret은 source file에 hard-code하지 않는다.
- 새 Go dependency는 표준 라이브러리/기존 dependency로 대체 가능한지 먼저 확인하고 Apache-2.0 호환 라이선스와 유지보수 지표를 검토한 뒤 사용자 승인 후 채택한다.

로그·에러 원칙:
- 모든 구조화 로그는 github.com/rs/zerolog/log를 사용한다.
- fmt.Println, 표준 라이브러리 log, bare logrus 호출로 운영 로그를 남기지 않는다.
- 모든 요청과 주요 이벤트에는 request_id를 연결한다.
- Deployment 흐름에는 deployment_id, stage, component, status, message를 남긴다.
- 실패 시 error_code, retryable, 사람이 읽을 수 있는 message를 남긴다.
- SSH key, token, credential, 내부 endpoint 같은 민감정보는 로그와 문서에서 제거하거나 마스킹한다.
- API 응답 message에는 raw err.Error(), stack trace, DB/SSH connection string을 그대로 노출하지 않는다.
- 사용자에게 보이는 message는 호출자 관점으로 작성하고 불필요한 Failed to, Error:, Invalid request: 접두어를 피한다.
- 외부 API, SSH, 파일/네트워크 I/O에는 timeout과 context cancellation을 적용한다.

검증:
- 추가/수정 단위를 먼저 검증하고 전체 코드베이스를 재검증한다.
- 민감정보, 중복 기능, unused code, 금지 로깅 호출(fmt.Println/표준 log/bare logrus)을 점검한다.
- 코드 변경 시 go test ./..., go vet ./...를 수행한다.
- OpenAPI 변경 시 `contracts/openapi/openapi.yaml`을 기준으로 검증하고, `/swagger` viewer가 같은 문서를 읽는지 확인한다. Redocly lint는 설치된 경우에만 실행한다.
- 실제 VM 배포 검증은 credential 제거 후 증적으로 정리한다.
```

## 작업 유형별 추가 지시

### 구현 작업

```text
기존 구조를 먼저 읽고, 변경 범위를 작게 유지한다.
API 계약, 상태 전이, 로그·에러 메시지를 함께 갱신한다.
새 문서를 만들기 전에 기존 README, docs/README.md, docs/ops/로그_에러_가이드.md에 연결할 수 있는지 확인한다.
Handler는 ctx := c.Request().Context()를 사용하고 service/core 함수에 context.Context를 첫 번째 인자로 넘긴다.
Handler는 내부 error를 zerolog로 기록한 뒤 표준 ErrorResponse와 의미 있는 HTTP status로 변환한다.
```

### 문서 정리

```text
산출물 문서는 최소화한다.
새 상세 설명을 늘리기보다 프레임워크 프롬프트, OpenAPI, 로그·에러 기준, 시험 증적 기준에 연결한다.
샘플 앱 실행 절차는 공개 문서에서 제거하고, AI Application 배포 방식 테스트 완료로 정리한다.
```

### 리뷰 작업

```text
먼저 범위 위반, API 계약 불일치, 상태값/에러 코드 누락, 로그 부족, 민감정보 노출 여부를 확인한다.
스타일보다 운영 중 장애를 추적할 수 있는지, 증적으로 제출 가능한지에 집중한다.
zerolog 사용 여부, context 전파, error 무시 여부, raw internal error 응답 노출 여부, 신규 dependency 라이선스/승인 여부를 확인한다.
```
