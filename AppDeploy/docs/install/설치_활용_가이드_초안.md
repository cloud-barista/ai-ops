# 설치 활용 가이드 초안

## 개발 환경
- Ubuntu VM
- Go 1.22 이상 권장
- GitHub 저장소 기반 관리
- Echo 기반 Go 서버

후속 개발과 시험 우선순위는 `docs/planning/경희대_1차년도_개발_백로그.md`를 기준으로 관리한다.
제출 직전 점검은 `deliverables/release/1차년도_제출_패키지_체크리스트.md`, 증적 구성은 `deliverables/evidence/증적_패키지_가이드.md`, 외부 API 경계는 `deliverables/interface/external/외부_연동_경계_정리.md`를 따른다.

## 기본 실행
```bash
git clone <repository-url>
cd ai-app-deployer
go mod tidy
go run ./cmd/web
```

웹 콘솔은 `http://localhost:8080/`에서 열리며 App/Target 등록·삭제, 자원 점검, 배포, 로그, 모니터링, 추론, 메트릭, 중지를 제공한다. 별도 프런트엔드 빌드는 필요하지 않고 기본 데이터는 `data/appdeployer-store.json`에 저장된다.
첫 시험은 웹 콘솔의 `사용 가이드`에서 Mock 시나리오를 진행하고, 실제 환경 적용 시 CPU VM 또는 GPU VM 시나리오의 Credential, Profile, readiness, 배포·검증 순서를 따른다.

### Web/CLI/Shell에서 package 생성·배포

App 등록 창의 `패키지 생성 및 입력`은 선택 기능이다. `ai-ops-geon 프리셋`, `Go`, `Python`, `Node.js`, `Linux amd64 바이너리`, `Shell 스크립트`를 선택해 package를 만들 수 있고, Mock App 등은 패키지를 생성하지 않고 아래 App 등록값을 직접 입력할 수 있다. 프리셋은 서버 설정 소스를 사용하고 나머지는 ZIP 또는 단일 파일을 업로드한다. 생성이 끝나면 Artifact URI, checksum, 실행 명령, Runtime, 포트와 health 경로가 App 등록 폼에 자동 입력된다. Go는 `go.mod`가 ZIP 최상위에 있어야 하며 Python/Node.js 의존성은 대상 VM에 준비하거나 ZIP에 포함해야 한다.

업로드는 기본 50 MiB, 압축 해제는 업로드 제한의 5배 이내로 제한한다. ZIP 경로 탈출과 심볼릭 링크는 거부하며 임의 build 명령은 입력받지 않는다. 기본 출력 경로는 `tmp/appdeploy-web/packages`이다.

```powershell
$env:AIAPP_AIOPS_ROOT = "C:\workspace\ai-ops-geon"
$env:AIAPP_PACKAGE_OUTPUT_DIR = "$PWD\tmp\appdeploy-web\packages"
$env:AIAPP_PACKAGE_BUILD_TIMEOUT = "2m"
$env:AIAPP_PACKAGE_MAX_UPLOAD_BYTES = "52428800"
go run ./cmd/web
```

API와 모든 클라이언트는 임의 서버 소스 경로나 build 명령을 받지 않고 프리셋 또는 지원 유형의 고정 규칙만 실행한다. 웹에서는 Package 생성 후 App 등록 값을 확인하고 `앱 등록`을 누른 다음 배포를 요청한다. Target hint를 비워 두면 App Deployer가 VM readiness와 Manifest 자원 요구사항을 검사해 자동 선택한다.

CLI는 같은 Echo API handler를 프로세스 안에서 실행한다. 인자 없이 실행한 대화형 셸에서는 유형과 값을 차례로 선택하고, 인자를 주면 자동화용 단일 명령으로 실행한다.

```bash
go run ./cmd/appdeployer
appdeployer> packages build
appdeployer> packages deploy
```

```powershell
go run ./cmd/appdeployer packages deploy `
  --type script --source .\examples\cpu-smoke-run.sh --name sample-shell-app `
  --version 0.1.0 --entrypoint cpu-smoke-run.sh --runtime cpu `
  --target-id target-cpu-001
```

`packages build`는 Package와 등록 가능한 `app_spec`을 JSON으로 출력한다. `packages deploy`와 별칭 `deploy package`는 `Package 생성 → App 등록 → Deployment 요청` 결과를 한 JSON으로 출력한다. `--target-id`를 생략하면 App Deployer가 후보 Target의 VM readiness와 Manifest 자원 요구사항을 검사해 선택하며, 지정하면 선택적 hint로 사용한다. 지원 유형은 `aiops-geon-service-control`, `go`, `python`, `node`, `binary`, `script`이다.

### App 등록 삭제

웹의 애플리케이션 목록에서 `등록 삭제`를 누르고 확인하면 해당 `app_id`의 Registry record를 삭제한다. CLI 자동화에서는 확인 옵션을 명시한다.

```powershell
go run ./cmd/appdeployer apps delete <app-id> --yes
```

참조가 없거나 해당 App을 참조하는 모든 Deployment가 `STOPPED`이면 등록을 삭제할 수 있으며, 기존 STOPPED Deployment 이력은 그대로 조회할 수 있다. `STOPPED` 외 상태가 하나라도 있으면 `APP_SPEC_INVALID`/409가 반환되고 등록은 유지된다. 삭제 성공 시에도 App Spec이 가리키는 package, git, binary, script 원본과 대상 VM의 배포 파일은 삭제하지 않는다.

### Target Profile 등록 삭제

Target Profile은 `DELETE /api/v1/target-profiles/{target_profile_id}`로 등록 정보를 삭제한다. 웹 콘솔에서는 Target Profile 목록의 `삭제` 버튼을 사용한다. 해당 Profile을 참조하는 Deployment가 없거나 모두 `STOPPED`일 때만 삭제할 수 있으며, STOPPED가 아닌 참조가 있으면 `TARGET_PROFILE_INVALID`/409로 거부된다.

Target Profile을 삭제해도 STOPPED Deployment, Event, Metric 이력은 유지한다. 현재 Resource Inventory snapshot만 함께 제거하며 `inventory_deleted`로 결과를 표시한다. Target의 `credential_ref`가 가리키는 Runtime Credential은 연쇄 삭제하지 않는다.

```text
appdeployer> targets delete target-cpu-001 --yes
```

```powershell
Invoke-RestMethod -Method Delete -Uri http://localhost:8080/api/v1/target-profiles/target-cpu-001
```

실행 중인 웹 서버의 저장 상태를 그대로 사용하려면 HTTP 셸 스크립트를 사용한다. PowerShell 5.1도 multipart 업로드를 지원하며 Bash 3.2 이상 버전은 `curl`, `jq`가 필요하다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\package-deploy.ps1 `
  -PackageType script -Source .\examples\cpu-smoke-run.sh -Entrypoint cpu-smoke-run.sh -AppName sample-shell-app `
  -TargetProfileId target-cpu-001 `
  -BaseUrl http://localhost:8080
```

```bash
bash ./scripts/package-deploy.sh --type script --source ./examples/cpu-smoke-run.sh \
  --entrypoint cpu-smoke-run.sh --name sample-shell-app \
  --target-id target-cpu-001 \
  --base-url http://localhost:8080
```

실행 방식은 Target Profile의 `runtime` 설정에서 파생한다. Package만 만들 때는 PowerShell에 `-Action build`, Bash에 `--build-only`를 사용한다. Go는 ZIP 최상위 `go.mod`, binary는 Linux amd64 ELF가 필요하다. 대상 VM에는 `tar`, `bash`와 유형에 따라 `python3` 또는 `node`가 준비되어 있어야 한다. `file://` artifact는 Package를 만든 AppDeploy 서버와 배포를 처리하는 AppDeploy 서버가 같은 파일시스템을 사용할 때만 유효하다.

`appdeployer` CLI는 실행 중인 웹 서버의 HTTP client가 아니라 독립 프로세스이다. 웹과 CLI를 같은 `AIAPP_STORE_PATH`로 동시에 실행하면 서로 다른 메모리 snapshot이 파일을 덮어쓸 수 있으므로 동시에 실행하지 않거나 저장 경로를 분리한다. 반대로 `package-deploy.ps1/.sh`는 실행 중인 웹 API를 호출하므로 웹과 같은 저장 상태를 사용한다. 연속 흐름은 트랜잭션이 아니므로 후속 점검·배포가 실패해도 이미 생성된 archive와 등록된 App은 남는다. CLI 오류와 셸 스크립트의 `partial_result`에는 정리·재시도에 필요한 archive/App 식별자가 표시된다.

API 서버를 별도로 제공해야 할 때는 다음 진입점을 사용한다.

```bash
go run ./cmd/server
```

서버 실행 후 API 문서는 다음 경로에서 확인한다.

```text
http://localhost:8080/swagger
http://localhost:8080/openapi.yaml
```

## Runtime Credential API

실제 SSH 실행에 필요한 private key 또는 password는 `POST /api/v1/credentials`로 등록할 수 있다. ID는 소문자 영숫자와 단일 하이픈 조합의 2~63자이고, 현재 `credential_type=ssh`, `auth_type=private_key|password`를 지원한다. `host_key_fingerprint`도 필수이며, 대상 VM 운영자나 CSP 콘솔처럼 SSH 접속과 분리된 신뢰 가능한 채널에서 확인한 canonical OpenSSH SHA256 fingerprint(`SHA256:`과 padding 없는 base64 43자)를 사용한다. 이 값은 서버 공개키 식별자이므로 Secret이 아니며 Web 입력, API 필드, CLI `--host-key-fingerprint` 또는 ENV `_SSH_HOST_KEY_FINGERPRINT`로 제공한다. 비밀값이 포함된 정적 요청 예제는 만들지 않는다.

등록된 비밀값은 AppDeploy 프로세스 메모리에만 존재하며 파일 저장소에 기록되지 않는다. 등록 응답과 `GET /api/v1/credentials`는 `host_key_fingerprint`를 포함한 공개 메타데이터와 `persistent=false`만 반환한다. 서버를 재시작하면 Runtime Credential은 소실되므로 다시 등록해야 하며, 환경변수로 주입한 Credential은 이 목록에 포함되지 않는다.

Target Profile의 `credential_ref`에는 등록 응답의 `cred://runtime/{credential_id}`를 사용한다. 이 필드는 최대 256자이며 소문자 영숫자와 단일 하이픈으로 구성된 `cred://namespace/id` 형식만 허용한다. private key, password, token 같은 Secret 원문을 넣으면 Target 등록 단계에서 거부된다. `cred://runtime` 이외의 유효한 ref는 기존 환경변수 resolver로 해석한다. `DELETE /api/v1/credentials/{credential_id}`는 Target이 해당 ref를 사용 중이어도 삭제하고 `deleted=true`, `deleted_at`을 반환한다. 삭제 후 Credential 누락 실패는 SSH runner가 실제 VM 연결을 시도할 때 발생하며, 기본 dry-run은 Credential을 해석하거나 원격 연결하지 않는다.

Credential API는 기본적으로 TCP peer와 HTTP `Host`가 모두 loopback이고, 브라우저가 `Origin`을 보낸 경우 그 값이 요청 `Host`와 같은 요청만 허용한다. POST는 `Content-Type: application/json`만 받는다. 원격 관리를 명시적으로 허용하려면 `AIAPP_CREDENTIAL_API_ALLOW_REMOTE=true`로 설정해야 하며, 운영 환경에서는 TLS와 인증이 적용된 reverse proxy 뒤에서만 사용한다.

CLI에서는 대화형 셸을 열어 Credential 등록부터 배포까지 같은 프로세스에서 이어서 수행한다. private key는 원문을 인자로 넘기지 않고 파일로 읽으며, password와 passphrase는 화면에 표시되지 않는 입력 또는 명시적인 stdin 옵션만 사용한다.

```powershell
go run ./cmd/appdeployer
appdeployer> credentials add --id cpu-vm-001 --user ubuntu --host-key-fingerprint SHA256:<base64> --auth private_key --private-key-file <private-key-file>
appdeployer> credentials list
appdeployer> credentials delete cpu-vm-001 --yes
```

`--host-key-fingerprint`에는 신뢰 가능한 별도 채널에서 확인한 값을 지정한다. 웹 콘솔도 SSH Credential 등록 창의 `Host key fingerprint` 필드에 같은 값을 요구한다. 대상 VM에서 직접 확인할 수 있다면 `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub -E sha256` 결과를 별도 관리 채널로 전달받아 비교하며, 연결하려는 동일 네트워크 경로의 `ssh-keyscan` 결과만 그대로 신뢰하지 않는다.

`credentials add`를 단발 명령으로 실행하면 명령 종료와 함께 해당 프로세스의 Credential도 소실된다. 후속 자원 점검·배포에 사용하려면 대화형 CLI 세션을 유지하거나 실행 중인 Web/API 서버의 Credential 화면/API를 사용한다.

## CPU VM SSH Runner 예시
기본 CPU VM Runner는 dry-run이다. 실제 SSH 실행을 사용할 때만 다음처럼 설정한다.

```bash
export AIAPP_CPUVM_RUNNER=ssh
export AIAPP_CREDENTIAL_CRED_LOCAL_CPU_VM_001_SSH_USER=ubuntu
export AIAPP_CREDENTIAL_CRED_LOCAL_CPU_VM_001_SSH_HOST_KEY_FINGERPRINT='SHA256:<trusted-base64-fingerprint>'
export AIAPP_CREDENTIAL_CRED_LOCAL_CPU_VM_001_SSH_KEY_PATH=/secure/path/cpu-vm-001.pem
export AIAPP_CREDENTIAL_CRED_LOCAL_CPU_VM_001_SSH_TIMEOUT=30s
```

`cred://local/cpu-vm-001`은 환경변수에서 `CRED_LOCAL_CPU_VM_001`로 정규화된다.

`artifact.type=script`이고 `artifact.uri=file://...`이면 로컬 스크립트가 SSH로 대상 VM의
`storage.artifact_dir/{app_name}/{version}` 경로에 업로드된 뒤 해당 경로에서 `entrypoint`가 실행된다.

현재 smoke 예제는 다음 파일이다.

- CPU: `examples/cpu-smoke-run.sh`
- GPU: `examples/gpu-smoke-run.sh`

AI Application 배포 방식은 별도 샘플 앱으로 실제 VM에서 테스트 완료했다. 나중에 실제 AI Application을 배포할 때는 동일한 구조로 모델 서버 실행 스크립트나 실행 바이너리를 `artifact.uri=file://...`로 지정하고, `entrypoint`에 실행 명령을 넣어 배포한다.

## GPU VM SSH Runner 예시
GPU VM은 `nvidia-smi` readiness를 확인한 뒤 배포한다. 실제 SSH 실행을 사용할 때만 다음처럼 설정한다.

```bash
export AIAPP_GPUVM_RUNNER=ssh
export AIAPP_CREDENTIAL_CRED_GPU_VM_001_SSH_USER=ubuntu
export AIAPP_CREDENTIAL_CRED_GPU_VM_001_SSH_HOST_KEY_FINGERPRINT='SHA256:<trusted-base64-fingerprint>'
export AIAPP_CREDENTIAL_CRED_GPU_VM_001_SSH_KEY_PATH=/secure/path/gpu-vm-001.pem
export AIAPP_CREDENTIAL_CRED_GPU_VM_001_SSH_TIMEOUT=30s
```

Target Profile은 `runtime.runtime_type=gpu`, `runtime.accelerator=nvidia`, `gpu.count >= 1`을 포함해야 한다.

## AI Application 배포 방식

실제 SSH runner를 사용할 때는 Target Profile의 `credential_ref`와 Runtime Credential API 또는 환경변수 Credential을 먼저 맞춘다.

| 단계 | 내용 |
| --- | --- |
| 1 | 실행 방식·가속기·접속 정보를 포함한 Target Profile을 등록한다. |
| 2 | 선택적으로 Package API에서 유형과 소스를 지정해 archive 및 App Spec을 생성한다. 직접 App Spec을 준비해도 된다. |
| 3 | 생성된 `app_spec` 또는 직접 작성한 App Spec을 등록하고 Resource Check를 수행한다. |
| 4 | Deployment를 생성해 대상 VM의 `storage.artifact_dir/{app_name}/{version}` 경로에 artifact를 업로드하고 실행한다. |
| 5 | 앱이 HTTP endpoint를 제공하면 inference proxy로 health/invoke를 확인한다. |
| 6 | Stop API로 원격 VM의 배포 프로세스를 종료한다. |

CPU VM 배포, GPU VM 배포, inference proxy, stop process 종료 흐름은 테스트 완료했다.

배포 종료는 다음 API를 사용한다. CPU/GPU VM Adapter는 원격 VM의 배포 작업 디렉터리에서 `.aiapp.pid`를 우선 확인하고, 없으면 작업 디렉터리 기반 프로세스를 찾아 종료한다.

```powershell
Invoke-RestMethod -Method Post `
  -Uri http://localhost:8080/api/v1/deployments/{deployment_id}/stop
```

## AI-Infra 외부 연동 골격
실제 외부 API 연결은 아직 합의 전이므로 기본 서버는 ETRI Mock/Fixture 클라이언트를 사용한다.

- Target Profile runtime: `runtime.runtime_type=aiinfra`, `runtime.operating_mode=remote_api`
- `/api/v1/resources/check`, `/api/v1/deployments`, `/api/v1/deployments/{deployment_id}/logs`, `/api/v1/deployments/{deployment_id}/stop` 흐름은 기존 API를 그대로 사용한다.
- 실제 ETRI/이노그리드/베스핀글로벌 API 명세가 확정되면 `internal/external/*` 클라이언트를 교체한다.

## 주의
- SSH Key와 password는 Runtime Credential API 요청 또는 환경변수/외부 secret store를 통해 주입한다. Runtime Credential API는 비밀값을 프로세스 메모리에만 보관하며 재시작 후 복구하지 않는다. 공개 메타데이터인 host key fingerprint도 신뢰 가능한 별도 채널에서 확인해 반드시 함께 제공한다.
- Credential 값은 정적 문서·예제·응답·로그·증적에 기록하지 않는다.
- Docker/Kubernetes 기반 설치 절차는 1차년도 가이드에 포함하지 않는다.

## Smoke/Evidence Script

PowerShell 환경에서는 다음 스크립트로 기본 API 흐름과 증적 수집을 실행한다.

```powershell
.\scripts\api-smoke.ps1 -BaseUrl http://localhost:8080
.\scripts\interface-smoke.ps1 -BaseUrl http://localhost:8080
.\scripts\collect-evidence.ps1 -Port 18080
```

범용 Package 배포는 `scripts/package-deploy.ps1` 또는 `scripts/package-deploy.sh`를 사용한다. 이 스크립트는 이미 실행 중인 AppDeploy HTTP API를 호출하며, `aiops-deploy-ssh.ps1`는 ai-ops-geon 전용 원격 health/service-operation/tunnel 검증이 필요할 때 계속 사용한다.

`ai-ops-geon` service-control API를 AppDeploy SSH runner로 배포해 확인할 때는 다음 스크립트를 사용한다. 사용자가 조정하는 포트, 경로, SSH alias, AppSpec 이름, service-operation 검증 payload는 `conf/aiops-config-ssh.json`에서 설정한다. 스크립트는 JSON 설정을 읽은 뒤 AppDeploy API 등록/배포, 원격 `/healthz`, `/api/v1/agents`, `/api/v1/service-operations/run` 검증, 로컬 SSH tunnel 생성을 순서대로 수행하고 터미널에 진행 로그를 출력한다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\aiops-deploy-ssh.ps1 -ConfigPath .\conf\aiops-config-ssh.json -Action deploy
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\aiops-deploy-ssh.ps1 -ConfigPath .\conf\aiops-config-ssh.json -Action status
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\aiops-deploy-ssh.ps1 -ConfigPath .\conf\aiops-config-ssh.json -Action stop
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\aiops-deploy-ssh.ps1 -ConfigPath .\conf\aiops-config-ssh.json -Action cleanup
```

상태 파일은 `tmp/aiops-geon-ssh-appdeploy-run/state.json`에 저장되며, 기본 터널 URL은 `http://localhost:18189`이다. `stop`은 기본 설정에서 현재 state deployment와 같은 Target prefix를 가진 RUNNING deployment를 모두 중지하고, 로컬 SSH tunnel도 함께 종료한다. AppDeploy 서버는 스크립트가 직접 시작한 경우에만 종료하며 배포 파일은 삭제하지 않는다. 별도 `cleanup` action은 state에 저장된 원격 artifact 디렉터리가 원격 artifact base 하위 경로인지 검증한 뒤 해당 디렉터리만 삭제하므로, 일반적으로 `stop` 완료 후 실행한다.

- `api-smoke.ps1`는 실행 중인 서버를 대상으로 healthz, readiness, app/target 등록, resource check, deployment, metric, logs, stop, monitoring을 확인한다.
- `interface-smoke.ps1`는 외부 제공 인터페이스 예제인 `deliverables/interface/examples/requests`를 사용해 직접 App Spec 등록, GPU Target, 로그/metric/monitoring 흐름을 확인한다.
- `package-deploy.ps1/.sh`는 유형별 Package 생성 응답의 `app_spec`을 등록하고 Deployment를 요청한다. `-TargetProfileId`/`--target-id`를 생략하면 App Deployer가 Target을 자동 선택한다.
- `collect-evidence.ps1`는 서버를 dry-run으로 임시 실행하고 `go test`, `go vet`, API smoke, readiness, monitoring 결과를 `deliverables/evidence/results/{timestamp}`에 저장한다.
- 요청 body 예제는 `examples/requests`에서 확인한다.
- Metric 확인은 `GET /api/v1/monitoring/metrics` 또는 `GET /api/v1/deployments/{deployment_id}/metrics`를 사용한다.
- 최신 제출 후보 증적은 `deliverables/evidence/results/20260625-173058`를 기준으로 확인할 수 있다.
