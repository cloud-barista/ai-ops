# 로그·에러 가이드

AI App Deployer는 산출물 문서를 늘리는 대신, 실행 로그와 표준 에러 메시지로 동작을 설명한다.

## 목표

- API 요청부터 Runtime Adapter 실행까지 추적 가능해야 한다.
- 실패 원인이 표준 error_code와 사람이 읽을 수 있는 message로 남아야 한다.
- 제출 증적은 긴 설명 문서보다 요청/응답, DeploymentEvent, Runtime Adapter log, ErrorResponse를 우선한다.

## 구현 기준

- Go 코드의 모든 구조화 로그는 `github.com/rs/zerolog/log`를 사용한다.
- 운영 로그에 `fmt.Println`, 표준 라이브러리 `log`, bare `logrus` 호출을 사용하지 않는다.
- 로그 호출은 `log.Info().Str("request_id", requestID).Str("deployment_id", deploymentID).Msg("...")`처럼 필드 기반으로 작성한다.
- 요청에서 전달된 `traceId` 같은 외부 추적값이 있으면 내부 표준인 `request_id`와 함께 별도 필드로 보존할 수 있다.
- Handler는 내부 error를 zerolog로 기록한 뒤 ErrorResponse로 변환한다.
- library/server code에서 `panic`으로 장애를 처리하지 않는다.
- error는 명시적으로 처리하고, 반환할 때는 `fmt.Errorf("...: %w", err)`처럼 문맥을 감싼다.
- 외부 API, SSH, 파일/네트워크 I/O에는 request context와 timeout을 적용한다.
- retry는 idempotent 작업에 한해 exponential backoff와 jitter를 사용한다.
- Credential Handler는 요청 body나 private key, passphrase, password를 로그에 기록하지 않는다. 작업 추적에는 `request_id`, `credential_id`, `auth_type` 같은 비밀값이 아닌 메타데이터만 사용한다. `host_key_fingerprint`는 신뢰 가능한 채널에서 확인하는 공개 서버키 메타데이터이며 Credential 등록 응답과 목록에는 포함한다.
- 비밀값을 포함할 수 있는 검증·SSH 오류는 표준 메시지로 치환하고 raw 오류나 요청값을 ErrorResponse에 넣지 않는다.

## 필수 로그 필드

| 필드 | 설명 |
| --- | --- |
| `timestamp` | 이벤트 발생 시각 |
| `level` | `INFO`, `ERROR` |
| `request_id` | API 요청 추적 ID |
| `deployment_id` | 배포 단위 추적 ID |
| `credential_id` | Runtime Credential 작업 식별자. Credential API에서만 사용하며 비밀값은 기록하지 않음 |
| `component` | `orchestrator`, `validator`, `resource-matcher`, `cpu-vm-adapter`, `gpu-vm-adapter`, `runtime-adapter` 등 |
| `stage` | 표준 Deployment 상태값 |
| `message` | 사람이 읽을 수 있는 작업/실패 설명 |
| `error_code` | 실패 시 표준 에러 코드 |
| `retryable` | 재시도 가능 여부 |

## Deployment 이벤트 기준

| 단계 | 반드시 남길 메시지 |
| --- | --- |
| `REQUESTED` | 배포 요청 생성 |
| `VALIDATING` | App, Runtime Profile, Target Profile 검증 시작 |
| `VALIDATED` | 검증 통과 |
| `SCHEDULING` | 자원 매칭 시작 |
| `DEPLOYING` | Runtime Adapter 배포 요청 |
| `RUNNING` | 앱 healthcheck 또는 실행 확인 |
| `STOPPING` | 중지 요청 수신 |
| `STOPPED` | 원격 프로세스 종료 또는 중지 완료 |
| `*_FAILED` | 실패 원인, error_code, retryable 포함 |

## ErrorResponse 기준

모든 API 에러는 아래 구조를 따른다.

```json
{
  "request_id": "req-...",
  "error": {
    "code": "RUNTIME_FAILED",
    "message": "gpu vm target requires vm.credential_ref",
    "details": {},
    "retryable": false
  }
}
```

## API 메시지 기준

- API caller에게 보이는 `message`는 호출자 관점으로 짧고 조치 가능하게 작성한다.
- raw `err.Error()`, stack trace, DB/SSH connection string, 외부 API 원문 오류는 응답에 그대로 넣지 않는다.
- 불필요한 `Failed to`, `Error:`, `Invalid request:` 접두어를 피한다.
- 장시간 작업 완료 응답에는 가능하면 elapsed time을 포함한다.
- 내부 상세 원인은 로그와 `details`에 남기되 민감정보를 제거하고 표준 error_code로 정규화한다.

## 메시지 작성 원칙

- 어떤 component가 무엇을 하다가 실패했는지 드러나야 한다.
- 사용자가 다음 조치를 알 수 있도록 누락 필드나 실패 조건을 직접 적는다.
- 외부 API 실패는 provider, timeout, auth, gateway failure를 표준 코드로 정규화한다.
- 민감정보는 기록하지 않는다.

## 마스킹 대상

- SSH private key path의 실제 파일명
- API token, password, secret
- SSH private key 원문, private key passphrase, Credential API 요청 body
- 내부 전용 host, endpoint, credential 원문
- 원문 외부 API 응답에 포함된 인증 정보

## 좋은 메시지 예시

| 상황 | 메시지 |
| --- | --- |
| App Spec 오류 | `artifact.type must be one of package, git, binary, script` |
| Target Profile 오류 | `gpu vm target requires vm.credential_ref` |
| GPU readiness 실패 | `nvidia-smi not found` |
| 배포 실패 | `ssh command failed for target target-gpu-001` |
| 중지 완료 | `gpu vm process stop requested: stopped` |
| 이미 종료됨 | `gpu vm process stop requested: no-process` |
| Credential 입력 오류 | `credential fields do not match auth_type` |
| Runtime Credential 없음 | `runtime credential not found` |

## Credential API 에러 매핑

| 상황 | HTTP | error_code |
| --- | --- | --- |
| 형식·인증 분기·host key fingerprint 또는 개별 secret 필드 최대 길이 오류 | 400 | `TARGET_PROFILE_INVALID` |
| 중복 credential_id | 409 | `TARGET_PROFILE_INVALID` |
| 전체 Credential JSON 본문 128 KiB 초과 | 413 | `TARGET_PROFILE_INVALID` |
| 허용되지 않은 peer/Host/Origin 요청 | 403 | `GATEWAY_AUTH_FAILED` |
| 없는 Runtime Credential 삭제 | 404 | `NOT_FOUND` |

Credential API 성공 응답과 목록은 필수 `host_key_fingerprint`를 포함한 공개 메타데이터만 반환한다. ENV resolver로 제공된 Credential은 목록에 포함하지 않으며, 프로세스 재시작으로 Runtime Credential이 소실되는 것은 오류가 아니라 명시된 수명 정책이다. Target의 `credential_ref`는 최대 256자의 제한된 `cred://namespace/id` 형식만 저장하며 Secret 직접 입력을 거부한다.

기본 Credential API 접근은 loopback TCP peer, loopback HTTP `Host`, 요청 `Origin`이 있을 때 same-origin을 모두 요구한다. 원격 opt-in은 TLS와 인증 reverse proxy를 전제로 한다. Credential 삭제 후 누락 오류는 SSH runner가 실제 연결할 때 남기며, dry-run은 Credential을 해석하지 않으므로 누락 오류를 만들지 않는다.

SSH host key fingerprint 불일치는 VM readiness/연결 실패의 표준 메시지와 `CSP_VM_UNREACHABLE`로 정규화한다. 로그나 ErrorResponse에는 private key, password뿐 아니라 공격자가 비교에 이용할 수 있는 요청 원문이나 기대값/실제값 쌍을 넣지 않는다.

## Profile 삭제 에러 매핑

| 상황 | HTTP | error_code |
| --- | --- | --- |
| 없는 Runtime/Target Profile 삭제 | 404 | `NOT_FOUND` |
| STOPPED가 아닌 Deployment가 Runtime Profile을 참조 | 409 | `RUNTIME_PROFILE_INVALID` |
| STOPPED가 아닌 Deployment가 Target Profile을 참조 | 409 | `TARGET_PROFILE_INVALID` |

Profile 삭제 성공 응답은 `request_id`, `profile_type`, `profile_id`, `name`, `deleted`, `inventory_deleted`, `deleted_at`만 반환한다. 성공 로그에는 이 중 추적에 필요한 Profile 메타데이터와 Target Inventory 제거 여부만 기록한다. STOPPED Deployment/Event/Metric 보존 상태를 추적하되 Target의 `credential_ref` 원문이나 Credential Secret은 기록하지 않는다. Target 삭제와 Credential 삭제는 서로 연쇄 실행하지 않는다.

## 제출 증적 우선순위

1. API 요청/응답 JSON
2. `/api/v1/deployments/{deployment_id}/logs`
3. `go test ./...`, `go vet ./...`
4. OpenAPI lint/build 결과
5. VM readiness, inference proxy, stop process 수동 검증 로그
6. 요약 문서

요약 문서는 증적을 대체하지 않는다. 요약 문서는 어떤 로그와 에러를 보면 되는지 안내하는 역할만 한다.
