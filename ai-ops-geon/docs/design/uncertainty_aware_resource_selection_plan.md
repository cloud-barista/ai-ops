# 불확실성 인지 자원 선택 연구·구현 계획

## 목적

자원 추천 결과를 항상 정답으로 가정하지 않고, 후보별 가용성·성능·비용·관측 신뢰도와 과거 실패 이력을 함께 고려해 배포 후보를 선택한다.

연구 대상은 GPU 커널이나 LLM 실행 엔진이 아니라, 불확실한 CPU/GPU VM 환경에서 AI 응용의 배포 행동을 결정하는 추론 최적화기다.

## 연구 질문

> 후보 자원의 불확실성과 배포 이력을 함께 반영하면 정적 자원 선택보다 최초 배포 성공률과 실패 복구율을 높이고, 불필요한 재시도와 배포 시간을 줄일 수 있는가?

## 입력과 판단

입력에는 기존 계약을 재사용하고 다음 정보를 단계적으로 추가한다.

- `ApplicationProfile`: 최소 자원, SLO, 런타임 제약
- `ResourceRecommendation`: 후보 자원, 추천 점수, 실행 가능 여부
- `ResourceSnapshot`: 현재 가용성·사용률·측정 시각·관측 출처
- `DeploymentHistory`: 후보별 성공·실패·오류 이력
- `Policy`: 비용, 재시도, 위험 허용 수준

후보별로 다음을 판단한다.

- 요구사항 충족 가능성
- 자원 상태와 추천 정보의 신뢰도
- 실패 위험과 예상 복구 비용
- SLO·비용·가용성 간의 trade-off

출력은 기존 `DeploymentDecision` 흐름을 확장한다.

- 추천 수용
- 대체 자원 요청
- 재시도
- 신규 VM 요청
- 배포 거절
- 사용자 추가 질의

## 단계별 연구 계획

### 1. 기준선

현재 규칙 기반 후보 선택을 기준선으로 고정한다.

1. 자원 요구사항만 사용
2. 자원 요구사항 + 후보 점수 사용
3. 자원 요구사항 + 후보 점수 + 배포 이력 사용

### 2. 불확실성 모델

초기에는 복잡한 확률 모델을 도입하지 않고, 후보별 신뢰도와 위험 점수를 명시적으로 계산한다.

- 데이터 최신성
- 자원 가용성 변동
- 추천 점수와 실제 결과의 차이
- 동일 후보의 과거 실패율
- 측정되지 않은 성능 정보

후속 단계에서 확률적 성공률 또는 보수적 신뢰구간으로 확장한다.

### 3. 위험 인지 의사결정

단순 최고 점수 선택 대신 다음 정책을 비교한다.

- 평균 점수 최대화
- 실패 위험 최소화
- 비용·SLO·성공 확률의 다목적 선택
- 불확실성이 높을 때 대안 자원 요청 또는 사용자 질의

### 4. 피드백 검증

GPU OOM, CUDA 불일치, 자원 부족, 일시적 배포 실패 시 다음 판단이 동일 오류를 반복하지 않는지 검증한다.

## 평가 방법

다음 구성을 비교한다.

1. 정적 규칙 기반 선택
2. 규칙 기반 선택 + 검증기
3. 검증기 + 배포 이력
4. 검증기 + 배포 이력 + 불확실성 인지 정책
5. 선택적으로 LLM Planner + 동일 검증기

주요 지표:

- 최초 배포 성공률
- 실패 복구율
- 동일 오류 재발률
- 평균 재시도 횟수
- 전체 배포 시간
- 제약조건 위반률
- 후보 선택 정확도와 판단 지연
- 비용 및 불필요한 자원 요청 수

## 성능 검증 계획

성능은 실행 비용과 의사결정 결과를 분리해 측정한다.

- 실행 비용: `go test -bench`로 결정 지연(`ns/op`), 메모리(`B/op`), 할당(`allocs/op`)을 측정한다.
- control-plane E2E: `BenchmarkRuleBasedOptimizationLifecycle`로 응용 문맥 수신부터 피드백·경험 조회까지의 한 사이클을 측정한다.
- 결과 품질: 고정된 배포 시나리오에서 최초 성공률, 복구율, 오류 재발률, 재시도 횟수, 전체 배포 시간, 비용을 측정한다.
- 비교 조건: 동일 입력·시드·하드웨어·서비스 설정으로 기준선과 각 정책을 반복 실행한다.
- 판정 기준: 실행시간만 줄고 성공률이나 복구율이 떨어지면 개선으로 보지 않는다. 최소한 제약조건 위반률을 악화시키지 않으면서 성공률·복구율·재시도 횟수 중 하나 이상이 개선되어야 한다.

현재 기준선 benchmark는 `BenchmarkRuleBasedDecisionFlow`와 `BenchmarkRuleBasedOptimizationLifecycle`이다. 이 E2E benchmark는 실제 CSP·VM 생성 시간은 포함하지 않으며, 해당 측정은 배포 실행기 연동 후 별도 환경에서 수행한다.

## 구현 시점과 범위

불확실성 인지 선택 정책 자체는 현재 구현하지 않는다. P0 규칙 기반 Planner·검증기·피드백 루프가 안정화된 뒤 P1 연구 기능으로 착수한다.

첫 구현은 기존 `agentcontrol`의 `ResourceRecommendation`, `OptimizationFeedback`, `Flow` 저장 구조를 재사용한다. 별도 스케줄러, RL, 다중 응용 빈패킹, VM 내부 스케줄링은 이 연구의 초기 범위에 포함하지 않는다.

## 현재 구현 진행 상태

- P0 계약 필드와 JSON Schema, 호환성 테스트를 완료했다.
- P1 규칙 기반 기준선을 보강하고 추천 상태·후보·정책 요구사항 검증을 완료했다.
- 배포 상태와 피드백을 `QueryExperiences`로 조회할 수 있도록 PoC 경험 조회를 추가했다.
- GPU OOM, CUDA 불일치, 자원 부족, 일시적 배포 실패를 `RepairDecision`으로 분류하는 기반을 추가했다.
- 불확실성 인지 자원 선택 정책은 연구·평가 계획으로 유지하며 아직 구현하지 않는다.

## 완료 조건

- 동일 입력에 대한 기준선 결과가 재현된다.
- 후보별 불확실성 근거와 선택 이유가 `reason_codes`로 남는다.
- 실패 이력이 다음 후보 선택에 반영된다.
- 불확실성이 높은 경우 무리한 배포 대신 대안 요청·질의·거절을 선택한다.
- 기준선 대비 성공률·복구율·재시도 횟수의 개선을 재현 가능한 시나리오로 측정한다.
