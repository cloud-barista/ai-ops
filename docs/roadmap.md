# 경희대 개발 현황과 로드맵

기준일: **2026-10-19**

경희대학교의 개발 범위는 AI 응용 요구사항 분석, 인프라 형상 추천, 배포 및 운영 판단 메커니즘입니다. 이 저장소의 웹 PoC는 해당 알고리즘을 실제 응용 실행과 연결해 시험하는 도구입니다.

## 근거 문서

- **「경희대학교 1차년도 Kick-off 워크샵 발표자료」(2026-05-26)**: 5번 슬라이드의 1차년도 개발 항목, 8번 슬라이드의 2차년도 개발 항목을 기준으로 연구 범위를 정리했습니다.
- **「요구사항 정의서 v0.1」(2026-07-07), 6.5절**: 경희대 담당 SFR-OPS-01~09의 기능과 구현 연도를 확인했습니다.
- **「업무 담당 범위 조율 2026-07-29」**: 경희대, 이노그리드와 ETRI의 책임 경계 및 어댑터 분리 방향을 참고했습니다. 이 문서는 당시의 잠정 조율안입니다.

아래에서는 원문에 명시된 연차별 항목과 현재 저장소의 구현 수준을 구분합니다. 원문 파일과 개인 정보는 공개 저장소에 첨부하지 않습니다. 문서 간 연차 표기가 다른 부분은 별도로 표시하며, 최종 일정과 공동 개발 범위는 기관 간 협의가 필요합니다.

## 현재 구현과 검증

완료 표시는 해당 PoC 기능과 시험 범위에 한합니다. 정식 서비스 수준의 안정성이나 전체 요구사항의 인수 완료를 뜻하지 않습니다.

### 1. 응용 배포 및 운용 구조

- [x] 요구사항 분석, 자원 추천, 배포 판단을 역할별 API로 분리
- [x] `ApplicationProfile`, `ResourceRecommendation`, 실행 계획과 관측 결과의 연결
- [x] 판단, Guard 검증, 계획 기록과 실제 실행 요청의 분리
- [x] Flow별 단계 결과와 실행 이력 추적

관련 코드: [llmop](../llmop/), [resource_ops](../resource_ops/), [deployment_agent](../deployment_agent/), [platform](../platform/)

### 2. CPU/GPU VM 응용 등록 및 배포 PoC

- [x] AppDeploy 연계와 실행 어댑터 구현
- [x] 로컬 CPU의 BERT Tiny 추론과 프로세스 복제본 변경 시험
- [x] AWS CPU VM 배포, 추론, Prometheus 관측과 종료 시험
- [x] AWS GPU VM 추론, 유지 판단과 자원 정리 시험
- [x] 별도 CPU VM 시험에서 명시적 적용 요청에 따른 VM 수 변경 확인

로컬의 복제본 변경은 같은 PC의 프로세스 수 변경입니다. CPU VM 수 변경 시험과 AWS GPU 단일 VM 실행 시험은 각각 다른 검증입니다. TPU 실행, GPU 자동 증감과 운영 중 응용 업데이트의 전체 경로는 완료로 표시하지 않습니다.

시험 환경과 결과: [검증 범위](validation.md)

### 3. LLM 운영 관리와 Agent 프로토타입

- [x] 자연어 및 구조화 입력의 요구사항 분석
- [x] 분석용 LLM 후보 설정, 선택과 비교 경로
- [x] Agent 등록, 활성 여부와 허용 작업 범위 검사
- [x] Agent 호출 전후의 요청 및 결과 검증

현재 Registry와 실행 검사는 프로토타입 범위입니다. 기관 전체의 사용자별 접근 권한, 정책 운영과 외부 Agent 복구까지 완성한 것은 아닙니다. LLM 선택 기능이 있다는 사실과 모든 모델의 실측 품질 우위는 구분합니다.

관련 문서: [Agent 등록 관리](../deployment_agent/docs/deliverables/02_agent_registration_management_prototype.md), [LLM_Op](../llmop/)

### 4. 추천 및 추론 최적화 연구

- [x] 자원 조건 필터링과 가중 점수 기반 후보 추천
- [x] 실측 기록 수집 및 학습 데이터 변환
- [x] 후보별 보상 예측, 자원 제약 검사와 판단 보류 구현
- [x] 예측 재사용, 후보 묶음 처리 및 병렬 처리 비교 실험
- [x] 성능 예측, GPU 구성 평가와 공개 워크로드 분석 코드 및 보고서 정리

학습 정책은 오프라인 평가와 shadow 판단을 포함합니다. 고정 정책 대비 실제 서비스의 SLO 위반이나 클라우드 비용을 줄였다는 결론은 추가 실험이 필요합니다. 개별 연구의 채택 여부와 한계는 각 보고서를 따릅니다.

관련 코드: [Research Policy](../poc/research_policy/), [Optimization Research](../poc/optimization_research/)

## 2차년도 개발 항목

다음 여섯 항목은 Kick-off 발표자료 **8번 슬라이드의 2차년도 계획**에 근거합니다. 현재 코드에서 활용할 부분과 추가 개발할 부분을 함께 적었습니다. 세부 구현 및 검증 방법은 저장소의 후속 개발 방향입니다.

### 1. GPU/TPU VM 응용 배포 자동화와 업데이트

**원문 범위:** GPU/TPU VM 기반 AI 응용 배포 자동화 및 업데이트 기술 개발

현재 CPU/GPU 실행 어댑터와 단일 GPU 실행 결과를 출발점으로 사용합니다. TPU 실행은 확인하지 않았습니다.

- [ ] GPU/TPU 실행 환경과 응용별 호환 조건을 배포 계약에 연결
- [ ] 변경된 응용 또는 실행 구성을 검증하고 업데이트하는 경로 구현
- [ ] 기존 구성, 새 Revision과 실제 적용 상태를 연결해 검증
- [ ] 연계 기관의 실행 API에서 배포와 업데이트 결과 확인

주요 연계: `deployment_agent`, `platform`의 실행 어댑터. 실제 응용 배포와 VM 제어는 기관별 역할에 따라 연계합니다.

### 2. GPU/TPU 응용 요구 분석과 추천

**원문 범위:** GPU/TPU 기반 AI 응용 요구 분석 및 추천 프로토타입 개발

현재 요구사항 구조화와 필수 자원 조건 검사, 후보 점수화를 확장합니다.

- [ ] 모델 특성과 입력 부하를 가속기 종류, 메모리와 수량 조건에 연결
- [ ] GPU/TPU의 호환성, 실측 성능과 현재 자원 상태를 반영한 후보 평가
- [ ] 요구사항 누락, 관측 정보 부족 또는 부적합 후보에 대한 추천 제한
- [ ] 단순 사양 기준과 비교해 추천 적합성과 실패 사례 평가

주요 연계: `llmop`, `resource_ops`, `poc/research_policy`.

### 3. Agent별 프레임워크 접근 권한 관리

**원문 범위:** AI 에이전트별 프레임워크 접근 권한 관리 기술 개발

현재 Agent 역할, capability와 허용 Action 검사를 기반으로 프레임워크 연동 권한을 다룹니다.

- [ ] 호출 주체와 대상 프레임워크에 따른 권한 및 승인 조건 정의
- [ ] 조회, 분석, 배포 요청과 제어 실행의 권한 구분
- [ ] 권한 거부와 허용 범위 초과 요청의 통합 시험

현재 코드의 Action 검사를 기관 전체의 인증 및 인가 체계가 완성된 것으로 해석하지 않습니다.

### 4. Agent 라이프사이클 관리

**원문 범위:** 에이전트 라이프사이클 관리 기술 개발

현재 등록과 활성 여부 관리에서 외부 Agent의 실제 상태를 확인하는 방향으로 확장합니다.

- [ ] 등록, 수정, 활성화, 비활성화와 재등록 상태 전이 정리
- [ ] 실행 상태 및 실패 이력과 Registry 정보의 일관성 확인
- [ ] 재시작과 연계 장애 상황에서 중복 호출 및 오래된 상태 처리 검증

응용의 버전 및 배포 라이프사이클과 Agent 자체의 라이프사이클을 구분합니다.

### 5. 자연어 지원 Agent

**원문 범위:** 자연어 지원 에이전트 프로토타입 개발

현재 자연어 입력은 주로 응용 실행 요구사항을 `ApplicationProfile`로 구조화합니다. 이를 다양한 운영 요청으로 확장합니다.

- [ ] 요청을 상태 조회, 배포, 업데이트 및 제어 등 작업 단위로 분류
- [ ] 필요한 입력 누락과 모호한 요청에 대한 확인 절차 구현
- [ ] 작업별 실행 계획, 허용 범위와 사용자 승인 연결
- [ ] 작업 변환 정확도, 잘못된 실행 요청과 처리 실패 평가

요구사항을 자연어로 입력하는 기능만으로 모든 운영 명령을 처리할 수 있는 것은 아닙니다.

### 6. GPU/TPU 배포와 제어에 특화된 추론 최적화

**원문 범위:** GPU/TPU VM 기반 AI 응용 배포 및 제어에 특화된 추론 최적화 실행

현재 실측 기반 후보 보상 예측과 판단 효율화 실험을 실제 운영 조건에 맞춰 평가합니다.

- [ ] 가속기 및 부하별 실측 자료 확충과 학습 범위 검증
- [ ] 후보 선택의 예측 효용, 신뢰도와 판단 보류 기준 평가
- [ ] 결과 재사용, 묶음 처리와 병렬 처리의 적용 조건 검증
- [ ] 판단 시간과 결과 일치성, 제약 위반 및 실행 후 성능을 함께 비교

판단 알고리즘의 추론 시간 단축과 배포 응용의 추론 성능 향상은 별도 지표로 측정합니다.

## 요구사항 정의서의 연차 구분

「요구사항 정의서 v0.1」 6.5절은 다음과 같이 기재합니다.

- **2026년:** SFR-OPS-01 LLM 및 Agent 등록 관리, SFR-OPS-02 역할·실행 범위·접근 권한·승인 정책 관리, SFR-OPS-03 Agent 라이프사이클 및 실행 상태 관리
- **2027년:** SFR-OPS-04 자연어 운영 요청 분석 및 작업 단위 변환, SFR-OPS-05 응용 운영 요구사항 및 자원 상태 분석, SFR-OPS-06 실행 계획 생성·추천 및 사용자 승인
- **2028년:** SFR-OPS-07 응용 배포 및 업데이트 자동화, SFR-OPS-08 실행 제어 및 추론 최적화, SFR-OPS-09 운영 상태 모니터링·실행 이력·예외 처리

Kick-off 자료는 접근 권한과 라이프사이클 핵심 기술 개발을 2차년도에 두고, 요구사항 정의서는 관련 기능을 2026년으로 기재합니다. 배포 자동화와 업데이트 역시 두 자료의 연차 표기가 다릅니다. 이 문서는 어느 한쪽의 연도를 임의로 바꾸지 않으며, 요구사항 ID의 구현 완료 시기는 최종 합의 시 확인해야 합니다. 현재 일부 기능의 선행 구현도 해당 요구사항 전체의 완료 판정을 대신하지 않습니다.

## 기관 간 연동 과제

업무 담당 범위 조율 문서의 잠정 방향에 따라 다음 경계를 유지합니다.

- **경희대:** 응용 컨텍스트 분석, 인프라 형상 추천, 후보 평가, 배포 및 스케일 조절 판단과 피드백 활용
- **이노그리드:** AI-App 프레임워크, 응용 등록과 버전 관리, 관측 정보 관리, 실제 플랫폼 Manifest 변환과 배포 실행
- **ETRI:** 인프라 정보와 기본 추천, 실제 CSP·리전·VM 결정 및 생성과 삭제

현재 PoC의 실행 어댑터는 알고리즘 검증에 사용한 경로입니다. 정식 시스템 연동을 위해 다음 합의가 필요합니다.

- [ ] 응용 정보, 요구사항과 인프라 형상의 입출력 계약
- [ ] 관측 지표의 단위, 수집 주기, 시각과 유효 기간
- [ ] Agent 호출 방식과 프레임워크별 권한 및 승인 계약
- [ ] 실행 요청, 결과 회신, 실패 및 재요청 처리 방식
- [ ] 기관별 API에 연결한 공동 시나리오와 인수 기준

다중 응용 빈패킹, GPU 공유, 로컬 프로세스 스케줄러나 운영용 포털 전체를 독자 구현하는 것은 현재 조율 문서의 필수 범위가 아닙니다. 3차년도 이후 항목인 NPU와 컨테이너 확장도 2차년도 완료 항목에 포함하지 않습니다.
