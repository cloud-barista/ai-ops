# 구성 요소와 연동 구조

## 역할별 책임

`llmop`은 응용 요구사항을 `ApplicationProfile`로 구조화합니다. 모델 후보 선택은 이 분석을 수행할 LLM을 정하는 기능이며, 실제 배포할 BERT Tiny 등의 응용 모델과 구분합니다.

`resource_ops`는 Profile을 자원 조회 조건으로 투영하고, 소스별 관측을 정규화한 뒤 필수 조건을 통과한 후보를 추천합니다. 결과는 `ResourceRecommendation`입니다.

`deployment_agent`는 두 결과를 함께 받아 실행 가능 여부와 목표 구성을 판단합니다. Guard가 검사한 계획을 Revision으로 기록하고, 별도 적용 요청이 실행 모듈로 전달됩니다. 실행 결과와 목표값을 구분합니다.

`platform`은 이 API들과 외부 AppDeploy 실행 모듈, Prometheus를 하나의 실험 Flow로 연결합니다. 요구사항부터 자원 선택, 배포, 관측과 운영 판단까지 같은 Flow에서 추적합니다.

## 운영 판단과 연구 정책

실행 중 수집한 성능과 자원 사용률을 사용해 허용된 복제본 범위에서 유지·확장·축소를 판단합니다. 변경 검증 후 새 Revision을 만들더라도 실행 상태가 자동으로 바뀌지는 않습니다. 별도 적용과 재관측이 필요합니다.

`poc/research_policy`는 기존 실측 기록에서 후보별 보상을 학습합니다. 자원 제약, 예측 신뢰도, 학습 범위 검사를 포함하며 불확실하면 판단을 보류합니다. 현재 정책 replay는 오프라인 비교이며 실제 클라우드 자원을 변경하지 않습니다.

## 외부 실행 경계

AppDeploy는 별도 실행 컴포넌트입니다. CB-Tumblebug와 AWS는 실제 VM 관리 계층입니다. 이 저장소의 클라우드 어댑터는 승인된 비용·수명, 실행 소유권, 호스트 신원, 종료 후 디스크 정리를 검사합니다.

공개 예시의 관리 서버 주소와 AWS 계정은 문서용 placeholder입니다. 실제 조직의 관리 서버 allowlist와 인증 구성을 검토해 설정해야 하며, 검사 자체를 제거해서 연결해서는 안 됩니다. 정식 이노그리드·ETRI API 연동은 협의된 인터페이스로 별도 진행합니다.
