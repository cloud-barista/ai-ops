# geon external input and AppDeployer integration

## Scope

The geon branch accepts an already analyzed Common JSON input pair, runs its
registered decision Agent and Guards, and produces Revision 1. An explicit
submission operation projects that approved revision into an AppDeployer request.
AppDeployer owns application execution and target selection. This is not branch
merging and does not make geon responsible for cloud VM creation or deletion.

The Jang0826 sender is not implemented here. Its owner must send the two real
outputs to this receiver. The local integration test uses a clearly identified
`integration-fixture`, not a claimed Jang0826 live connection.

## Receive upstream results

POST `/api/v1/agent-control/external-flows` with:

```json
{
  "application_context": { "...": "complete application.context.created envelope" },
  "resource_recommendation": { "...": "complete resource.recommendation.created envelope" },
  "decision_agent": "AIApplicationAutomationAgent"
}
```

The abbreviated example is explanatory, not a valid payload. A complete runnable
CPU example is constructed in `scripts/Test-GeonAppDeployLocal.ps1` and written
to its output directory as `external-input.json`.

Both envelopes must have the same `correlation_id`, `trace_id`, and profile ID.
Both are validated before either is stored. An identical replay returns the
existing Flow. Reusing that Flow ID with changed inputs is rejected. geon does
not regenerate the external recommendation from its Mock catalog in this path.

In the UI, open **고급 프로토콜 검증**, paste both envelopes, then select
**외부 결과로 배포 판단**. Inspect the resulting Flow in **실험 결과**.

## Connect AppDeployer

Register the executable application with AppDeployer first. Its registered
name or app ID, and version, must match the Flow's ApplicationProfile.
Configure a reachable, trusted AppDeployer API before starting geon:

```powershell
$env:AIOPS_APPDEPLOY_BASE_URL = "http://127.0.0.1:18088/api/v1"
$env:AIOPS_APPDEPLOY_SUBMIT_ENABLED = "true"
.\run-agent-control.cmd
```

Keep geon bound to localhost unless authentication and network access are
separately secured. `127.0.0.1` refers to the machine running geon, not a teammate's
machine. Do not point this setting at a billable deployment service merely to
test the UI. Default submission is disabled; the existing Mock experiment path
remains available.

For the selected approved Flow:

1. Enter **등록된 App Version ID** under **AppDeployer 연동**.
2. Click **전송 요청 확인**. This reads the App Registry and prepares JSON without
   creating a deployment.
3. Review the request and limitations, then acknowledge the execution settings.
4. Click **AppDeployer 배포 요청** once.
5. Click **실제 배포 상태 조회** to attach the real status to the same Flow and
   inspect the upstream raw metrics.

API equivalents:

- POST `/api/v1/agent-control/flows/{id}/appdeploy/prepare`
- POST `/api/v1/agent-control/flows/{id}/appdeploy/submit`
- GET `/api/v1/agent-control/flows/{id}/appdeploy`

POST body: `{"app_version_id":"<registered ID>","accept_projection_limits":true}`.
Acceptance is required only for submission. REJECT/RETRY, failed Guards,
already observed deployments, and non-initial revisions cannot submit.

## Contract limitations

- Only one initial node and one replica are supported.
- CPU, memory, GPU count and storage are projected from approved Revision 1.
- The registered AppSpec supplies executable, model and inference settings.
  geon's inference_configuration is NOT applied to the running process.
- AppDeployer selects its target. geon resource_hints and GPU VRAM minima are
  NOT enforced by this projection; the UI requires explicit acknowledgement.
- SLO requirements are forwarded, but this is not proof of SLO compliance.
  A hard hourly-cost cap is rejected because this contract cannot enforce it.
- Raw AppDeployer metrics are displayed, not fabricated into p95 measurements.
  A measured `optimization.feedback.created` message is still required for
  the existing operation Agent. Mock feedback is not prefilled for real status.
- Revision 2 may be generated by the existing operation Agent when an approved
  SCALE_OUT/SCALE_IN decision exists, but is NOT automatically deployed.
- Status polling reports upstream state; detailed failure diagnosis from logs
  and automatic metric aggregation remain separate integration work.

## Retry and persistence

Before sending, geon exclusively creates a journal record at
`runs/appdeploy-deliveries/`, or `AIOPS_APPDEPLOY_DELIVERY_DIR` when configured.
The record binds Flow ID, decision, initial manifest hash, app version and server.
Concurrent calls and restarts do not automatically create another deployment.

`SUBMISSION_UNKNOWN` means the upstream may have accepted the request. Inspect
AppDeployer's deployment list and the receipt before manual reconciliation.
Do not delete the journal and retry blindly. There is no automatic reconciliation
API yet. A new geon process may no longer have the in-memory Flow; the journal
still prevents duplicate delivery, but is not a full persistent Flow store.

## Reproducible local test

Use a checkout of AppDeployer containing `AppDeploy/scripts/local-demo.ps1` and
the `local_process` runtime. The script builds both services, registers a local
CPU worker, sends the external fixture, prepares/submits twice to check duplicate
protection, reads RUNNING, records evidence, and stops its worker and servers.
It never creates a cloud VM and does not use AWS credentials.

```powershell
.\scripts\Test-GeonAppDeployLocal.ps1 -AppDeployModule "C:\path\ai-ops\AppDeploy"
```

Test-only ports are 18089 (geon) and 18088 (AppDeployer); the usual geon UI remains
18080. Occupied ports cause an error rather than stopping another process.
Evidence is written under `tmp/integration-*/evidence.json`. `-KeepRunning` is
for interactive browser QA only; stop the returned local deployment through
AppDeployer before stopping the returned process IDs.
